# 定位短文 — Export-to-Markdown 功能（节点 n2）

> 阶段：定位(positioning) · 节点：n2「build the export-to-markdown feature」
> 产出人：dev-together-kbflow14 · 类型：定位 artifact（单文件）
> 状态：v1 定位草案，供 pm 推进看板使用

---

## 一句话定位

**Export-to-Markdown 让用户把 dev-together 工作区里"活的"协作内容（会话、看板任务线、决策与产物），一键导出为一份干净、可移植、可进版本库的 Markdown 文档。**

---

## 这是什么（What）

一个**导出动作**，不是新的内容系统。它把工作区内已经存在的结构化内容，按可读的层级渲染成标准 Markdown：

- 输入：一个明确的来源对象（一条会话 / 一个看板 / 一个任务节点的讨论线 + 产物）。
- 输出：一份 `.md` 文件（标题、章节、列表、代码块、链接保持语义），可下载、可复制、可写入 Git 仓库或粘进任意 wiki / 文档工具。
- 原则：**所见即所导**——导出的是用户已经看到并参与产生的内容，不做二次加工或"AI 重写"。

它的本质是一座**出口桥**：把平台内的协作产物，搬运到用户自己的文档/代码/知识体系里。

---

## 给谁用（Who）

主要面向**在 dev-together 里产出可沉淀内容的人**：

1. **开发者** — 想把会话里敲定的方案、代码片段、踏坑记录，落进项目仓库的 `docs/` 或 PR 描述里。
2. **PM / 协调者** — 想把一个看板节点上的讨论、决策、交付产物，整理成一份可对外汇报或归档的纪要。
3. **知识沉淀者 / 文档维护者** — 想把零散在多次协作中的结论，导出后并入团队 wiki 或设计文档。

共同画像：他们的"真相源"在平台外（Git / wiki / 文档），但有价值的内容产生在平台内，需要一条低摩擦的搬运通道。

---

## 解决什么痛点（Pain）

| 现状痛点 | 后果 |
|---|---|
| 协作产物锁在平台内，只能截图或手动复制 | 格式丢失、代码块错乱、链接断裂，搬运成本高 |
| 沉淀全靠人工"翻译" | 决策与结论不进版本库，时间一长就丢失、无法追溯 |
| 内容与团队既有文档/代码体系割裂 | 形成信息孤岛，协作成果无法复用 |

一句话：**有价值的东西产生在这里，却带不走、留不下。** Export-to-Markdown 把"带走 + 留下"变成一个动作。

---

## v1 范围边界（Scope）

### v1 做（In）

- 支持导出**单一来源对象**（先锁定一种最高频来源，建议：一条会话线 / 一个看板节点）。
- 渲染**核心 Markdown 语义**：标题层级、有序/无序列表、代码块（保留语言标注）、内联代码、链接、引用、表格。
- 输出为**单个 `.md` 文件**，提供下载与"复制到剪贴板"两种取用方式。
- 保留必要**元信息头**（来源、导出时间、参与者），便于归档溯源。
- 在内容与图片/附件之间，对**附件以链接占位**呈现（不内联二进制）。

### v1 不做（Out — 明确推迟）

- ❌ 多对象**批量/打包导出**（多会话、整板导出 → v2）。
- ❌ 导出到 **PDF / HTML / Word** 等其他格式（v1 只做 Markdown）。
- ❌ **直接推送**到 Git / wiki / 外部系统的集成（v1 只产文件，搬运由用户完成）。
- ❌ 导出模板**自定义 / 主题化**（v1 用一套固定的标准布局）。
- ❌ **增量 / 定时 / 自动**导出（v1 是用户主动触发的一次性动作）。
- ❌ 对原内容的 **AI 摘要 / 重写 / 翻译**（v1 严格"所见即所导"）。

### 边界一句话

**v1 = 一个对象 → 一份标准 Markdown 文件 → 用户自取。** 其余皆为 v2+ 候选。

---

## 关键假设（待 pm / 下游验证）

1. 最高频、最该先支持的**来源对象**是哪一种（会话线 vs 看板节点 vs 产物集合）——决定 v1 的入口位置。
2. 用户更需要**下载文件**还是**复制文本**——决定首要取用方式。
3. 附件/图片以**链接占位**是否足够满足 v1，还是必须内联——影响渲染复杂度。

> 说明：本节点为定位产物，仅界定"是什么/给谁/解痛点/v1 边界"。具体来源对象选型、交互入口与渲染实现，留给后续设计与开发阶段。
