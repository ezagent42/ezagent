## 核心模型（先讲清楚，再往下看）

**一句话**：把"战略 → … → 上线验证"整条链收进**一棵从宏观到微观的树**，每个节点有人认领、有产物、上一层是下一层的 gate；**任何一个 PR 都能往上追到一个痛点、一个战略**——开发因此被产品需求驱动，而不是被"我能做什么技术"驱动。

三条地基决策：

```
D1  树状图 = 呈现形式（单根树，从宏观到微观，最简单直接）
D2  背后真相 = 平面化结构化数据（每个节点 = 一条扁平记录）
    → 导图只是这份数据的一个视图；图错了，以数据为准（堵住"图和现实漂移"）
D3  约定「一个功能的出发点 = 一个痛点」（功能 → 痛点 1:1）
    → 功能分两种：① 新增功能  ② 基于已有功能的迭代
    → 树形不需要 DAG，一对多的问题在源头消解
    → 副作用：每个功能必上溯到一个痛点 = 强约束的判据
```

节点的扁平记录形态（D2 的"形"，一旦定下不常变）：

```
node = { id, parent_id, type, title, body, owner, status, artifact_refs[] }
       type ∈ {战略, 痛点, 模块, 功能, issue, PR, 验证}
       status ∈ {待认领, 进行中, 待验, 通过, drop}
       artifact_refs = [稳定挂载键 → 飞书URL / 文件路径 / issue号 / PR号 / 帖子URL]
```

## 交付物一：端到端产品开发流程

整条链是 **7 层树**，从宏观到微观。每层用**同一个四要素模板**描述：**定义 / 产物 / 认领角色 / 进入下一层的 gate**。

| 层 | 定义（这层在回答什么） | 产物 | 认领 | → 下一层的 gate |
| --- | --- | --- | --- | --- |
| **L1 战略** | 我们是谁、为什么、用 A 换 B 的交易公式是什么 | 一段定版定位文字（A 换 B 讲清楚） | 负责人 | 一句话能讲清"我给你啥、你给我啥"？ |
| **L2 痛点×用户** | 锚定哪部分**零教育成本**用户的**哪一个**痛点 | 痛点卡（谁＋什么痛＋ROI 在哪看） | 产品 | 这痛点的人一说就懂、且知道回报在哪看？ |
| **L3 模块＝价值闭环** | 为治这些痛点，产品需要哪些**价值闭环**（模块 = 一个闭环） | 闭环图（投入→回报怎么闭合） | 产品 | 这模块是不是一个**真闭环**（投入能回到回报）？ |
| **L4 功能** | 完成某闭环的一环；**1 个功能 ← 1 个痛点**（新增/迭代） | 功能 spec（含验收标准） | 产品＋研发 | 功能是否 1:1 指认了一个痛点 + 有验收标准？ |
| **L5 issue** | 功能的开发拆解 | issue | 研发 | issue 是否只属于这一个功能？ |
| **L6 PR** | 当天提交；**只做该功能**、跑通该功能验收用例 | PR + 测试结果 | 研发 | PR 是否只改该功能、跑通验收？**超范围的砍掉** |
| **L7 验证/运营** | 上线引流（小红书/自然流/网页），看指标 | 运营帖/网页 + 指标读数 | 运营 | 指标达标？**达标→进下一闭环；不达标→drop** |

**迭代功能怎么挂（D3 的小尾巴，我先选了一种，待你确认）**：
迭代型功能挂成**那个已有功能节点的子节点**，继承父功能指向的痛点；新增功能直接挂在它所属模块下、并指认一个痛点。这样树保持纯净，且迭代也能上溯痛点。

**走线一句话**：负责人定 L1 → 产品在 L2/L3 把痛点和闭环挂上 → 产品＋研发在 L4 把功能 1:1 钉到痛点 → 研发 L5/L6 开发并过 gate → 运营 L7 引流验证 → **达标反哺下一闭环，不达标 drop**。

## 交付物二：每个阶段的唯一真相源

原则（D2）：**真相永远是节点的扁平记录**，存在 ezagent 自己的库里（符合"真相源在核心库"）；导图/看板/网页都是它的**视图**。外部工具只是"能被 agent 读写的产物容器 + 协作面"，靠**稳定挂载键**挂回节点。

| 层 | 唯一真相源 | 挂载键（外键） |
| --- | --- | --- |
| L1 战略 | 战略节点记录（定位/交易公式文本） | 节点 id |
| L2 痛点 | 痛点节点记录 | 节点 id |
| L3 模块 | 模块节点记录（闭环描述） | 节点 id |
| L4 功能 | 功能节点记录（痛点 ref + 新增/迭代标记 + 验收标准） | 节点 id ↔ issue/PR 号 |
| L5 issue | **GitHub issue** | 节点 id ↔ issue 号 |
| L6 PR | **GitHub PR + CI/测试结果** | 节点 id ↔ PR 号 |
| L7 验证 | **指标数据**（点击/阅读/使用量，从渠道回流） | 指标读数挂回 L4 功能节点 |

> 一句话判据：**"谁是改这条信息的唯一入口，谁就是真相源"**。文档正文在飞书、但"这功能属于哪个痛点/什么状态"只能改节点记录——所以节点记录是真相，飞书是产物容器。

**待你确认的一个点**：L1–L4 的扁平真相，一期是**直接落 ezagent 库（推荐，不漂移）**，还是**先用 Miro 节点承载、保证能导出扁平数据**？前者干净但要先建"节点+认领+挂载"小数据模型；后者起步快但要防 Miro 变成事实真相源。

## 交付物三：工具与数据接入点（给姚的清单）

每个诉求点 → 用什么工具 → 怎么接 ezagent → 真相源还是产物容器。

| 诉求点 | 工具 | 怎么接 | 角色 |
| --- | --- | --- | --- |
| 导图呈现（宏观→微观） | **Miro** | API 建/更新节点 | 视图 |
| 扁平真相数据 | **ezagent 库（SQLite）** | 自研「节点+认领+挂载」小数据模型 | **真相源** |
| L1–L3 文档/图产物 | **飞书文档 / excalidraw** | 文件 URL/路径当挂载键挂回节点 | 产物容器 |
| L4 功能 spec | 飞书 doc 或库内字段 | 节点 ref | 产物容器 |
| L5–L6 开发 | **GitHub（issue/PR）** | 节点 ↔ issue/PR 双向同步（REST 够） | 产物容器 |
| L7 验证/引流 | 小红书发帖 · **网页出口（ezagent socialware public_view）** · 自然流 | 指标回流（webhook/定时拉）挂回 L4 节点 | 产物容器 + 数据回流 |
| 全员协作载体 | **ezagent 第一个 App = 全员群聊 session** | 配 agent 盯节点变化 | 运行载体 |

**验证闭环（L7 的运转语义）**：

```
错位节奏：本周开发的 → 下周验证
不达标   → drop 该功能子树下的 PR/分支，换别的闭环
哨兵指标 → 周价值闭环数 · 挂载覆盖率 · cycle time · 对齐时长
            （从第一天就埋，每周看它们动没动 = 判断这套有没有效的唯一标准）
```
