# 开发流程 · 10 分钟定版

## 一、流程总图（真相源接力）

```
 
 定位稿 → 北极星指标 → 痛点清单 → 认领映射 → 线框/原型 → 功能spec卡 → issue → 测试套件 → PR
 (产品负责人)(运营)    (产品)     (产品负责人) (产品+设计)  (产品+研发)  (研发)  (研发)    (研发)
   └────────── 每个箭头 = 一次"真相源交接" = 一道 gate（上一件不合格不放行）─────────┘
                                  测试用例=spec卡Gherkin（不另写）│ 只做该功能+测试绿才合PR
   ↩ PR上线 → 实测指标回收 → 回②验证/运营对照北极星阈值 → 不达标 drop 砍子树 → 反哺③痛点

注：验证/运营提前到第 2 棒——先定下战略定位对应的北极星指标（"成功长什么样"）；实测数据在末尾随 PR 上线回收，对照阈值验证、不达标 drop。北极星不再是贯穿层，而是 ② 的交付物。
```

## 二、环节明细表（输入 / 产出 / 钦定真相源 / 负责人 / 工具）

> "工具"列：**可直接调 API / 可模仿其形态**；外部工具只贡献能力，真相落 ezagent 库。

| # | 环节 | 输入（真相源） | 产出物 | **钦定下一环节的唯一真相源** | 负责人 | 工具（调用/模仿） |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | **战略/定位** | 团队产品意图 | 价值主张 · PR/FAQ · 交易公式 | **一页定位稿**（价值主张为主，PR/FAQ·交易公式作附件） | 产品负责人 | 飞书 docx；Miro 根节点 |
| 2 | **验证/运营** | 一页定位稿（战略定位） | 北极星指标定义 · drop 阈值 ← *先定度量、末尾才收数据* | **北极星指标**（这个定位对应的"成功度量"）；实测数据随 PR 上线回收后才验证 | 运营 | 飞书 OKR；指标采集见下「验证指标工具」→ 落库；drop 阈值 |
| 3 | **痛点** | 北极星指标（承接战略定位） | 多张痛点卡 · 优先级打分 | **排序后的痛点清单**（机会树，每个痛点都指向北极星指标） | 产品 | 飞书 docx/bitable；Miro / xmind 机会树 |
| 4 | **用户锚定** | 排序后的痛点清单 | 团队画像 · 零教育成本评估 · 岗位↔层映射 | **岗位↔认领层映射表**（决定后面谁认领） | 产品负责人 | 飞书 bitable |
| 5 | **体验主张** | 排序后的痛点清单 | 四条 UX 承诺 · 线框/原型 | **主界面线框/原型** | 产品 + 设计 | excalidraw；**html：Lovable / Zeplin** |
| 6 | **功能/模块** | 主界面线框/原型 | 模块(价值闭环) · 功能 spec · 用户故事 · 验收 · ICE · 价值卡 · 挂钩牌 ← *产出最多* | **功能 spec 卡**（每功能一张，模板 `06·G-r`：用户故事+Gherkin 验收+ICE+价值卡+挂钩牌） | 产品 + 研发 | 飞书 docx；**Zeplin**；markmap 节点 |
| 7 | **issue** | 功能 spec 卡 | issue（含范围/不做/验收用例） | **issue 本身** | 研发 | GitHub（REST/GraphQL） |
| 8 | **测试** | issue（携带 spec 卡 Gherkin） | 测试代码 · 测试结果（绿/红）　*用例=spec卡Gherkin，不另写* | **可跑且对应 Gherkin 的测试套件**（必须变绿才交 PR） | 研发 | dev-loop：test-plan-generator→test-code-writer→test-runner；`mix test` / CI |
| 9 | **PR** | 测试套件（写实现让它变绿） | PR · 测试通过 · 过 gate | **合并后的 PR**（上线后触发实测指标回收 → 回 §2 对照北极星阈值） | 研发 | GitHub + reviewer 过 gate 清单 |

> **§6 为什么要钦定**（回应"不够清晰"）：功能环节天然产出一堆（模块/spec/用户故事/验收/卡），下游研发不可能全盘看。**钦定"功能 spec 卡"为唯一真相源**——研发只认这张卡开 issue，其余都是它的附件/支撑。其它"产出多/产出虚"的环节（§1 定位、§2 验证/运营）同理钦定一件。
>
> **为什么验证/运营提前到 §2**（与 sy 定）：战略定位一旦立住，**马上就要回答"成功长什么样"**——把北极星指标定下来，后面的痛点/功能才有度量靶子（每个痛点都得能撬动它）。实测数据虽然要等末尾随 PR 上线才能回收，但**指标的"定义"必须前置**；回收只是把数填回这个早就钦定好的靶子，对照阈值决定 drop。

## 二·补 · 验证环节指标工具（采集 → 汇总回库 → 对照阈值）

> 注：北极星指标的**定义**在 §2 就钦定好；这里是末尾随 PR 上线的**实测回收**。框架一致：**各渠道用 API/导出把实测指标拉回 → 落 ezagent 库 → 对照 §2 定的北极星阈值（drop 阈值）→ Metabase/飞书出看板**。外部工具只当采集器/视图，不当真相源。

| 要量什么 | 渠道 | 工具（取 API/导出） | 选型说明 |
| --- | --- | --- | --- |
| 网页 使用量/漏斗/留存 | socialware 网页 | **PostHog**（自托管, MIT）/ 或 **ezagent 自身 telemetry** | PostHog=产品分析全家桶(事件/漏斗/留存/录屏)+API；最省则直接数 ezagent 已有 telemetry 事件 |
| 网页 PV/点击/来源 | 网页 / 自然流 | **Umami**（自托管, 轻量, MIT）/ Plausible | 埋一段 JS 就有 PV/UV/来源，看"自然流到了没"；Plausible 营销向更好看 |
| 小红书帖 阅读/互动 | 小红书 | 自己帖→**蒲公英 + 创作者后台导出**；大盘/竞品→**千瓜 / 新红(新榜有数)** | 小红书开放 API 仅对合作品牌开放；爬虫有合规风险不建议，自己帖走官方导出最稳 |
| 汇总成看板/对照阈值 | — | **Metabase**（自托管, 开源, 连库出看板+API）+ 飞书 bitable/OKR | Metabase 直连 ezagent 库出 drop 阈值看板；飞书 OKR 挂北极星（你已选） |

## 三、八道交接 gate（验收 / 打回判据）

> 每条箭头 `i→i+1` 都是一次真相源交接，对应**一道 gate**：上一棒的真相源没过验收，下一棒不放行；不过则按「打回」列退回上一棒。对应 demo 里点箭头看到的 `GATES`。

| 交接 | 真相源棒 | ✓ 验收（放行） | ✗ 不过（打回） |
| --- | --- | --- | --- |
| ①→② | 一页定位稿 | 价值主张明确 + PR/FAQ · 交易公式齐 | 打回重写一页定位稿 |
| ②→③ | 北极星指标 | 北极星指标可量化、对齐战略定位 | 重定北极星指标 |
| ③→④ | 排序后的痛点清单 | 痛点按优先级打分排序 + 每个痛点都能撬动北极星指标 | 回去补打分 / 对齐北极星 |
| ④→⑤ | 岗位↔认领层映射表 | 零教育成本评估通过 + 每个岗位都映射到认领层 | 重做用户锚定 |
| ⑤→⑥ | 主界面线框/原型 | 主界面线框/原型成形 + 四条 UX 承诺落地 | 重做体验主张 |
| ⑥→⑦ | 功能 spec 卡 | 功能 spec 卡的验收用例（Gherkin）写全 | spec 卡没写验收 → 不许开 issue |
| ⑦→⑧ | issue 本身 | issue 范围/不做明确 + 携带 spec 卡 Gherkin | 补全 issue 再开测试 |
| ⑧→⑨ | 对应 Gherkin 的测试套件 | 测试套件可跑且对应 Gherkin、必须全绿 | 测试不绿 → 不许提 PR / 不许合 |

## 五、三条让它转起来的机制

1. **交接即 gate（类似 CI）**：每个箭头都是一次真相源交接；**上一环节的真相源没合格（没过自己的验收），下一环节不放行**。例：功能 spec 卡没写验收用例，不许开 issue。
2. **测试先行、绿才合（§8→§9）**：**测试用例不另写——就是 spec 卡的 Gherkin**；研发先把 Gherkin 写成测试代码（dev-loop `test-code-writer`），再写实现让它变绿（`test-runner`/`mix test`）。**测试不绿，不许提 PR / 不许合**。这把"验收"从一句话变成一道自动闸。
3. **只做该功能（§9 强约束）**：PR 必须只动该功能 spec 卡范围内的东西，**超范围（顺手美化/改无关页面）一律砍**；reviewer 过 gate 清单逐条勾（含"测试是否覆盖 spec 卡每条 Gherkin"），不过打回。这是把"每天 100+PR 收束到产品价值"的那道闸。
4. **不达标就 drop（阈值在 §2 定、末尾随 PR 上线回收）**：北极星指标在 §2 验证/运营就钦定好阈值；PR 上线后实测指标回收，窗口内未达阈值（如小红书帖 7 天阅读 < 500）→ **砍掉该功能子树（§6 功能→§9 PR）的 PR/分支**，反哺回 §3 重选痛点。开发与验证错位（这周开发、下周验证）。

**贯穿纪律——三位一体**：每个开发节点（§7–§9）必带"产品跟进（spec）+ 运营跟进（changelog）"两个兄弟节点，谁缺谁显式"待分配"——杜绝"开发完才补产品运营"。

## 六、一句话收口

**这套流程 = 一条真相源接力链**：定位稿 → 北极星指标 → 痛点清单 → 认领映射 → 线框 → 功能卡 → issue → 测试 → PR，每一棒只接上一棒的一件东西、产出自己的一件交下去；**验证/运营提前到第 2 棒先把北极星指标（成功度量）定下来**，PR 上线后实测回收、不达标 drop 反哺痛点，首尾闭环；**spec 卡的 Gherkin 一物三用**——既是验收、又是测试用例、又是 PR 过 gate 的判据；交接处是 gate、回收即 drop、三位一体贯穿。先在内部跑通（ezagent 第一个产品），适时开放外部。
