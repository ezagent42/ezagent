## ★ G-a · 一句话价值主张（挂 §1.1）

**方法论**：俞军「用户价值 = 新体验 − 旧体验 − 替换成本」`[待原文]`。一句价值主张要同时编码：给谁 + 新体验 + 替代掉的旧痛/旧成本。

**句式（三选一，按场景）**：
```
A 主句式： 让<谁>在<场景>，能<达成新体验>，而不必<旧体验的痛/成本>。
B 差额式： 对<谁>，把<某动作>从<旧体验:花X> 变成 <新体验:花Y>。
C 一句话： <谁> + <达成什么> + <省掉什么旧成本>。
```

**示例（情境 A）**：让 ezagent 团队在开发自己产品时，能一张图看清谁认领了什么、做到哪，而不必每天刷群开会问进度。
**示例【对外·后续】**：让跨境小老板不用学任何工具，就能拿到一套能直接跑的 AI 方案，而不必自己拼一堆插件。

**合格判据**：全队能凭这句话复述、无歧义；句子里能指认出"谁/新体验/被替代的旧成本"三要素。

## ★ G-p · 商业模式 / 交易公式（挂 §1 战略，新增节点）

**方法论**：俞军交易模型 = 利益创造（利从何来）+ 利益分配（利往何去）+ 可持续 `[待原文]`。

**一句话交易公式**：
```
我给<谁><价值A>，<谁>给我<对价B>；
我的成本靠<降本手段:agent/外包/复用>压低，
对方的效用靠<X>放大，
所以更多交易在这个平台上发生。
```

**配套填写骨架（设计/诊断都用）**：
| 板块 | 要回答 |
|---|---|
| 相关方利害（每方当用户核算） | 角色 / 得到 / 付出 / 净值正负 / 哪条边会断 |
| 利从何来 | 创造的"有利可图的用户价值"是什么；效用四分类（底线/够用就好/越多越好/惊喜）各做到什么程度 |
| 利往何去 | 损失厌恶：哪里要用户放弃已有的？补偿到 2.5× 了吗；激励相容：各方自利是否自动推动整体；选择是否增福利 |
| 可持续 | 短期 vs 长期（有无透支信任）；多边是自我强化还是自我稀释；分配是否公平有竞争性 |

**示例【对外·后续，对应录音商业模式】**：学员给我们<钱 / 自己的 knowhow / 分享带来的流量>，我们给学员<可即跑的 skill+课+试验场>；我们的成本靠 <agent 生成 + skill 复用> 压低，学员的效用靠 <即学即跑、玩完即改成下一课> 放大 → 内容与流量自我强化。

**合格判据**：四个板块都填；至少指认出一条"可能会断的边"并说明怎么补。

## ★ G-c · 痛点陈述句式（挂 §2.x）

**方法论**：JTBD + Teresa Torres 机会句——**用用户语言，不用方案语言**（说"我想达成什么受阻于什么"，不说"我们要做个什么功能"）。

**句式**：
```
当<情境>，<谁>想<动机/达成>，以便<结果>；
现状受阻于<障碍>，导致<代价>。
```

**示例（情境 A）**：当团队每天提交 100+ PR 时，负责人想知道哪些 PR 真正推进了产品价值，以便砍掉无效开发；现状受阻于"PR 只有技术描述、不挂产品需求"，导致大量精力浪费在无价值提交上。

**合格判据**：句子里**没有**出现解决方案/功能名；能指认"谁+受阻+代价"。

## G-e · 零教育成本用户评估清单（挂 §3.1）

**方法论**：俞军用户模型（替换成本）+ 录音"锚定一说就懂、知道去哪看 ROI 的用户"。

**五问（全部偏"低/是"才算锚点用户）**：
```
□ 一句话说他就懂吗？（不需要科普背景）
□ 他现在已经在用某种旧方案吗？（旧体验存在=痛是真的）
□ 他知道去哪看自己的 ROI/回报吗？
□ 上手要不要学新心智模型？（要学=教育成本高）
□ 替换成本（迁移+学习+信任）高不高？
```

**合格判据**：目标用户群在五问上的回答能写出来，并据此判定是否锚定。

## ★ G-g · 可测验收（升级 04 的验收为 Gherkin，挂 §5.x / §6.x）

**方法论**：Gherkin Given/When/Then——把"自然语言列点"升级成可断言、可自动化的格式。

**句式**：
```
Given <前置状态>
When  <用户/系统动作>
Then  <可观察、可断言的结果>
```

**示例（功能1 节点认领）**：
- Given 一个状态为"待分配"的节点；When 成员 A 点认领；Then 节点 owner=A、状态变"已认领"、库中可查到这条变更。
- Given 一个无人认领的节点；When 任何人查看导图；Then 它显式显示"待分配"，不存在灰色无状态节点。

**合格判据**：每条验收能直接写成一个测试用例。

## ★ G-r · 功能 spec 卡（§5 钦定唯一真相源 —— 一张整卡）

**为什么**：`07 定版` 把"功能 spec 卡"钦定为 §5 的唯一真相源——研发开 issue **只认这一张卡**，其余（模块图/线框/价值卡散件）都是它的附件。所以要把上面的零件（用户故事 + G-g 验收 + G-q ICE + 价值卡 + 挂钩牌）装进**一张卡**。

**方法论**：04 已有这些散件（每功能都填过），本模板只是把它们**收口成一张可独立交接的卡**。

**模板（一功能一张）**：
```
# 功能卡：<功能名>
- 节点: <node id>        类型: [ 新增 / 迭代(父功能 <id>) ]
- 服务痛点: <痛点 id>（G-c 那句，1:1 上溯）
- 承接定位: <来自 §1 定位稿/价值主张哪一条>

## 用户故事
作为<角色>，我想<功能>，以便<价值>。

## 范围
- 只做: <一句话>
- 不做(out of scope): <列明，防顺手扩张——这条直接喂给 G-i 过 gate>

## 验收（Gherkin，G-g）
- Given… When… Then…
- Given… When… Then…

## 优先级（ICE，G-q）
Impact <> · Confidence <> · Ease <> → 分 <> · 优先级 P<>

## 价值卡（用户价值 = 新−旧−替换，2.5×）
给谁 / 新体验−旧体验 / 替换成本 / 净值判定 / 三位一体(产品+运营跟进)

## 挂钩牌
服务痛点<> / 拨动哪个输入指标<> / 验证假设<> / 闭环判据<>

## 产出去向
→ 开 issue（G-h）时只引这张卡；issue/PR 完成后挂回本节点
```

**合格判据**：研发不看别的、只凭这一张卡就能开出合规 issue（G-h）；卡里每块都不留空（对外阶段专属块除外）。**它就是 §5 交给 §6 的那一棒。**

## ★ G-s · 测试环节（挂 §6.8，issue→测试→PR）

**关键**：**测试用例不另写——就是 spec 卡（G-r）/ G-g 的 Gherkin**。这一环只把 Gherkin 变成可跑的测试代码、跑、绿了才交 PR（TDD：测试先于实现）。

**步骤 + 工具（ezagent dev-loop）**：
```
1. 测试用例   = spec 卡的 Gherkin（直接拿，不重写）
2. 测试计划   → dev-loop: test-plan-generator（从 spec 卡/diff 出计划）
3. 测试代码   → dev-loop: test-code-writer（Gherkin → mix test 用例）
4. 跑 + 绿    → dev-loop: test-runner（mix test / CI）
   （可叠 superpowers:test-driven-development：先写测试再写实现）
```

**钦定真相源**：**可跑且全绿的测试套件**（= PR 环节的输入）。
**合格判据**：spec 卡每条 Gherkin 都有对应测试且全绿；漏一条 → §G-i 过 gate 清单打回。

## ★ G-i · PR 模板 + "只做该功能"过 gate 清单（挂 §6 issue→PR）

**方法论**：录音最强调的强约束（超范围砍掉）+ Stripe API review 式强制门。

PR 描述：
```
关联 issue/节点: <>
改了什么: <>
验收用例结果: <Given/When/Then 跑通截图或说明>
```
**Reviewer 过 gate 清单（任一项不过 → 打回）**：
```
□ 是否只动了该功能需求内的东西？（超范围 → 拆出去或砍）
□ 是否跑通了该功能的验收用例（G-g）？
□ 是否有"顺手美化/改无关页面"？（有 → 砍）
□ 是否挂回了对应节点？
```

## G-q · ICE 判分标尺（补 04 只有公式无标尺，挂 §8.6）

**方法论**：ICE（04 已定：三项各 1–10，相乘/100）。补每维标尺：
| 维度 | 9–10 | 6–8 | 3–5 | 1–2 |
|---|---|---|---|---|
| Impact 影响 | 产品骨架，没它全挂 | 核心闭环一环 | 优化体验 | 可有可无 |
| Confidence 信心 | 现成机制+实测过 | 机制清楚要自研 | 有未验证依赖 | 纯赌 |
| Ease 易实现 | 半天 | 几天 | 一两周 | 最大自研块 |

## ★ 工具可选项总表（每个环节列多个供选 —— 你要的那条）

> 基于 `research/B`（已调研）+ 姚的 Miro + D2（真相源永远在 ezagent 库，外部工具是产物容器/视图）。

| 环节 | 选项（⭐=研究推荐 / 姚=姚已选） | 取舍一句话 | 真相源? |
|---|---|---|---|
| 整体思维导图载体 | **Miro（姚）** / **markmap⭐** / xmind / mermaid / Obsidian Canvas | Miro=可视化协作强、有 REST API，但要把结构镜回库；markmap=纯 Markdown，agent 读写零 API、无冲突；xmind=本地文件无云 API（仅兼容）；mermaid=静态展示；Canvas=本地需客户端 | 都不是；真相源在 ezagent 库 |
| 框架/架构/线框图 | **excalidraw⭐** | JSON 纯文本，agent 能生成、可 mermaid→excalidraw、可嵌网页出口 | 文件当产物挂回节点 |
| 开发 issue/PR/看板 | **GitHub⭐** | 自动化最成熟；issue/PR 有稳定 URL、assignee=认领人；Projects v2 必须 GraphQL | 产物容器 |
| 产品文档/spec | **飞书⭐**（docx+bitable，ezagent 已有插件）/ Obsidian | 飞书=云协作+OpenAPI+变更订阅+现成插件；Obsidian=本地 Markdown 跟 markmap 同源但协作弱 | 产物容器 |
| 节点↔认领↔产物 真相源 | **ezagent 自带 SQLite⭐** | 结构化、单实例、零运维、同库同事务；撞分布式/向量再迁 Postgres | **真相源** |
| 每人一个 agent | **ezagent Entity.Agent + flavor⭐**（MVP 用 curl flavor） | 统一 agent 实体按 flavor 装行为；读"我认领节点"+调外部 API | 运行件 |
| 网页对齐出口 | **socialware public_view⭐**（编排器动态生成 UI） | ezagent 现成把会话公开成网页；注意 world 在建会统一前端 | 视图 |
| 外部进出 | 入站 **Invocation.dispatch**（P14）/ 出站 **external_mirror** | 所有 webhook 入站走 dispatch；出站镜像走 external_mirror | 通道 |

> **Miro 补充**：research B 没评估 Miro。Miro 有官方 REST API（boards/items 有 id），能被 agent 读写、能当"可视化协作面"；但按 D2，**结构真相仍要镜回 ezagent 库**，Miro 当视图。若团队更想要"Markdown 即真相、agent 零成本读写"，markmap 更顺；若更想要"自由画布+多人实时拖拽"，Miro 更顺。两者可并存：Miro 给人看、库给 agent 用。
