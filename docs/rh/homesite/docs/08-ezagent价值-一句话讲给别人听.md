# ezagent 的价值 · 一句话讲给别人听

> 个人备忘，已 gitignore。
> 来源：2026-06-26 我跟 Claude 的一轮对话，基于 `ezagent-biz/docs/discuss/intro/`（00/01/04/05/08/09 篇）梳理。
> 用途：别人问我"ezagent 到底有啥用 / 跟自己搓有啥区别"时，照这份讲。

---

## 0. 一句话定位（先背这句）

> 想给自己的终端用户提供「多渠道接入 + 多 agent 协作 + 可对外公开」的 AI 服务的人，
> 能用 ezagent 这套运行时**把路由、可靠性、鉴权、动态客户界面这些最难且最危险的底座白拿**，
> 自己的工作收敛成"配置会话模板 + 设计编排器怎么编排"——大多数情况下甚至不写代码。

我自己一开始的理解（已被确认是对的，只是要锐化）：
**"想提供多 agent 服务给自己用户的人，能利用这个底层架构更便捷地完成服务搭建。"** ✅

---

## 1. 三个容易想偏的地方（锐化心智模型）

别把它当成普通"多 agent 框架"。三处补精度：

1. **"多 agent 服务" 要补上 "多渠道 → 多 agent" 这半句。**
本质是**消息路由运行时**：各渠道（飞书 / web / CLI / API…）进来的消息，路由给各 agent/会话处理，结果送回。"多 agent"只是一端，另一端是"多入口"。

1. **"给自己的用户" 对应一个专门的产品层叫 socialware。**
不是随便把 agent 暴露出去，而是：一个带 `public_view: true` 的**会话模板** = 一个对外 app。
匿名陌生人凭链接就能进来围观/参与。**这一层就是把"内部多 agent 编排系统"变成"能对外的客户产品"的那道门**——没有它，ezagent 只是内部工具。

1. **"更便捷" 的含金量在于你不用碰的那些东西**（不是泛泛少写代码）：
消息不丢、LLM 越权护栏、客户界面不用手写前端、匿名访问/登录合并/审计/多租户——全是地基现成的。

> ⚠️ 反直觉前提：ezagent 是"消息没人接默认**静默丢失**"的 router，不是"点一下返一下"的网页后端。
> 它的很多价值其实是在**对抗这个默认**（可靠性原语）。

---

## 2. 这套架构到底是给谁的（产品发现 · 别被 solution-shaped 框住）

⚠️ **第 0 节那句"想提供多 agent 服务给自己用户的人"是 solution-shaped——它把结论(要 multi-agent)塞进了主语，不是一个真实的人。**
真实的人不会想"我要 multi-agent"，他们想的是"客服累死了""我有 know-how 但服务不过来""老板要上 AI 但我们没工程"。

**正确问法**：不问"谁想要 multi-agent"，问"谁现有的痛，形状刚好只有我们这套 bundle 能接住"。

### 先剥掉"别人也能做"的，找真正独占的交集
单项能力 Coze / Dify / FastGPT / GPTs 都能做（单 agent、接渠道），所以**痛点不能落在"能做 AI 助手"上**。我们真正不好替代的是这几样的**交集**：
1. **socialware** —— 把会话对**匿名外部用户公开**，客户界面 agent 动态生成、不写前端
2. **人工把关闸门** —— turn 的 `operator_only → customer_visible`：**AI 起草、人工复核后才给客户看**（05 篇）
3. **多租户 + 模板** —— 一套底座复制给很多客户/实例，不用每个重搭

→ **靶心 = 需要「多角色协作 + 必须对客户公开 + 还要人能兜底把关」三者同时成立，且没工程能力自建可靠底座的人。**
单 agent 能搞定的、纯内部用的、有钱养工程团队的——**都不是我们的人**。

### 候选人群 + 我的判断（每个附"淘汰线"防自嗨）

| 候选人群 | 真实痛（他们自己的话） | 为什么需要*多*角色 | ⚠️ 淘汰线（什么情况不是我们的人）|
| --- | --- | --- | --- |
| **数字化服务商 / 代运营 agency**（给餐饮/教培/电商做私域、客服、导购）| "每接一个客户都要重搭一套，养不起这么多人" | 接待→资格判定→出方案→人工接管，天然多角色 | 只交付单 prompt 机器人 → Coze 就够 |
| **领域专家 / 咨询型个体**（法律/财税/留学/健康）| "我一个人服务不了这么多客户，又怕 AI 乱答出事" | AI 答 + **本人复核后才发**（高风险必须人兜底）| 客户能接受纯 AI 无人工 → 单 GPT 即可 |
| **要对客上线 AI、但没工程团队的中小品牌/SaaS** | "老板要上 AI，我们没前端没后端" | 导购+客服+售后合到一个对客面 | 有工程团队 → 自建或走 plugin 路 |
| **培训 / 教育机构** | "答疑、批改、督学，老师忙不过来" | 答疑 + 批改 + 督学 多角色，对学生公开 | 只是 FAQ 答疑 → 单 agent 知识库够 |

### 我赌哪个最锋利
- **第一锐度：数字化服务商 / agency**——我们的"多租户 + 模板复制 + 对客公开 + 不写代码"**正好是他们的生产线**：生意就是"给很多客户快速搭对客 AI 服务"，边际成本越低越赚。**B2B2C，我们卖铲子。**
- **第二锐度（差异化最硬）：高风险领域的"AI 起草 + 人工把关"**——`operator_only→customer_visible` 闸门 Coze/Dify 默认不给。法律/财税/医疗"答错要出事"，**人工兜底是刚需不是 nice-to-have**，这是"为什么不用别的"的那句话。

### 下一步该做的（别再从我们这边猜）
反向验证，用 JTBD 口径问真实的人，验三件事：① 这 job 是否**真需要多角色**（还是单 prompt 就够→证伪）；② 是否**必须对客户公开**（还是内部用→不是我们）；③ 他们**今天怎么凑合做的**、多痛、愿不愿付钱。
👉 **卡在"先接触得到谁"**：产品发现忌讳挑够不着的完美靶子，先打能验证的人群。

## 3. 两条搭建路线（"服务搭建"到底指哪种，决定便捷度）

| <br> | 路 A：写 plugin（加平台能力） | 路 B：做 socialware app（对外产品） |
| --- | --- | --- |
| 加什么 | 新 agent 类型 / 新渠道 / 新行为 | 公开会话 + 客户体验 |
| 形态 | 一个编译进来的 OTP app | 一个带 `public_view` 的会话模板（**数据，不是代码**） |
| 谁做 | 平台开发者 | 产品设计者 / 运营 |
| 便捷度 | 声明式，但要写 OTP 代码 | **纯配置，最便捷** |
| 例子 | 接新 LLM、接新 IM 渠道 | 客服咨询页、电商买家围观页 |

**大多数产品工作走路 B**（组合现有能力，不写底层）。只有需要平台还没有的底层能力时才走路 A。

路 B 三步：① 定义 app = 写 `public_view` 会话模板 → ② 从模板起活会话 → ③ 把链接发出去。
客户界面**不是手写的**，是会话的编排器 agent 一轮轮用工具组合出 JSON 页面树，通用渲染器画成 React。

## 4. 用 vs 不用 ezagent 的对照（讲"省了哪些最难的事"）

| 维度 | 自己手搓 | 用 ezagent |
| --- | --- | --- |
| **消息可靠性** | 消息丢了往往没人知道 | ReadyGate（未就绪先接住）+ PendingDelivery + Idempotency（webhook 去重）+ DLQ（零匹配进死信）——每个投递点强制回答"失败了谁会知道" |
| **崩溃恢复** | 页面已投递但那轮没存住 = 孤儿 bug | `:dispatch_after_commit`：副作用只在持久化后跑；重启自发恢复信号补投 |
| **安全护栏** | LLM 自由发挥易越权改库/改别人会话 | 三层 MCP 桥（认证 socket→零权限传输→会话域逐次鉴权）+ 每次 dispatch 都 CapBAC 5 轴鉴权；身份服务端推导不可伪造；manifest 声明的 caps 不能自我授权 |
| **前端工作量** | 每个客户场景手写页面 | 通用 `JSON→React` 渲染器 + agent 产出页面树；连"能跑的代码片段"都能 Sandpack 实时预览 |
| **审计/合规** | 自己埋点 | 每条 invocation 自动写审计行（caller/target/action/result，密钥脱敏） |
| **架构纪律** | 易写出耦合/绕过路径 | 跨 Kind 唯一通路 = dispatch（P14）；编译期强制声明式注册；三层依赖只能往下 |
| **多租户** | 自己设计隔离 | 内建 workspace = 租户，URI 三段式统一寻址 |

一句对比收尾：
> **不用**：自己搭多 agent 路由、保证消息不丢、给 LLM 装护栏、为每个场景写前端、做匿名访问/合并/审计——还很容易写出"静默失败"的坑。
> **用**：这些最难且最危险的底座现成；自己的活收敛成"配置会话模板 + 设计编排器怎么编排"，多数情况不写代码。

## 5. "客户界面 agent 动态生成" 全链路（被问细节时用，05 篇）

> 编排器 agent 经三层 MCP 桥调 9 个管理工具，**塑造会话的运行形态**（招成员 agent、定路由规则、套提示词模板、存档模板）；
> 每来一轮交互，`Turn` 状态机派活→收齐→`compose` 把 `kind: :page` 的 JSON 页面树登记成 `:surface` 不可变版本→`settle` 提交后才批准+投递；
> `CustomerFeed` 只读、按提交游标把"已提交版本的页面树 + 客户可见消息"投影出来→Phoenix Channel 推到浏览器→`json_render` 查表器渲染成 React。

关键认知：**编排器组合的不是像素，是"会话的运行形态"**（谁在组里、消息怎么流、套哪个提示词）；界面是这套形态每轮跑出来的产物。要改客户面 → 改会话形态，不改前端代码。

## 6. 两个边界提醒（别误用，文档明确标注）

- **world** 目前只接管运营/作者面；**客户面**（`/socialware/chat`、`/socialware/customer`）仍在旧栈 `ezagent_web`，"world 收编客户面"仍是 **future**。
- **loom / autoservice** 只是设计词汇，**没进代码**，别当已有实现引用。
