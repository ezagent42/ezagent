# homesite 产品文档 1：定位 → 北极星（P 层）

> **一句话**：homesite = **让 builder 供给 arc 与 seller 需求 arc 拼成的官网飞轮真转起来**。地基是**供给腿**（builder 搓出 socialware → 发布进 gallery，货架先有货），闭环是**需求腿**（seller fork → 兑现 → 回流，飞轮焊成环）。**目标不是"多一个展示站"，是让两条业务闭环转起来并持续优化。**
>
> **本文在追溯树的位置**：最上游 P 层，全树的根。编号从 P-1.1「飞轮」一路推导：因为要让两条闭环转起来（P-1.1），所以看清靠哪两条 arc 支撑（P-2 两腿），所以每条 arc 得能量出兑现（P-3 北极星，分期）。
>
> **编号规则**：`P-层.序`。§1 根（P-1.1）无上游；往下每层每节点恰一个上游 `↑`。🟦 builder 供给 arc / 🟨 seller 需求 arc 是**颜色属性**，不参与父子结构。

---

## §1 根：飞轮（P-1.1 · 根，无上游）

**homesite 为什么存在？** 因为两条业务闭环**各自能跑、但没焊成环**：builder 搓完一个 socialware 发布就走，seller 用完 / fork 完兑现就走 —— 两条死 funnel，没有网络效应。让它们成为**飞轮**的只有一件事：seller 的产物**回流**成下一个 builder 的供给。而唯一能焊接两条 arc 的点 —— **gallery** —— 今天更像展示墙，不是活货架。

### P-1.1 让两条闭环拼成的官网飞轮真转起来并持续优化

homesite 存在的理由：**让 builder 的"造 + 发布"和 seller 的"试用 + fork + 兑现"在 gallery 这个交换点上焊成一个自我强化的环 —— 供给越多货架越厚、需求越旺回流越多、回流又变新供给。**

- **地基 = 供给腿（先有货）**：builder 从 tech site 进来、建立信任与身份、用 world+hello 搓出自己的 socialware、**发布进 gallery**。没有货架上的货，需求无从谈起。
- **闭环 = 需求腿（焊成环）**：seller 从 Instagram 落在某个 builder 的产品里、试用、**fork** 成自己的、兑现自己的价值、产物**回流** gallery 成为下一个 seller 的落点。回流（S5）是飞轮闭合的证明。

**边界（收进根，不单列节点）**：homesite **只做到"把两条 arc 各段体验做通 + 焊上 gallery 交换点"为止** —— **不做**支付 / 清结算 / 分成（交易模型另议）、**不做**内容审核平台化（质量门沿用 hire 层）、**不做**雇佣关系。homesite 是"让飞轮转起来的官网体验层"，不是交易所、不是审核系统。

> **承重命题（承 `model.md §0`）**：是飞轮不是两条死 funnel，承重假设 = **gallery 必须是"活货架"（可试用 + 可 fork）+ fork 回流真闭合**。这是**结构层**假设，与 hire §0 的**内容层**假设（hire 真承载专家经验）正交：内容再真、货架不活也转不起来。

## §2 两条 arc：builder 供给腿 × seller 需求腿（P-2.x · 各 ↑ P-1.1）

既然根是"两条闭环焊成飞轮"，第一个要拆的就是：**这件事靠哪两条 arc 支撑？** 一条供给腿（灌货进货架）、一条需求腿（从货架取并回灌）。

### P-2.1 ↑ P-1.1 🟦 builder 供给腿（地基）：造出来 → 发布进 gallery

**谁 = 技术创作者（tool-first，判别式 model §1.1）**：vibe coder / 开发者 / 技术型 founder（= hire 的 OPC），因懂 world+hello 而从零造。供给腿是飞轮的**地基**（冷启动供给先行）：

- **建立信任 + 身份**：builder 从 tech site 进来，读理念（intro）、看进度（world.cup）、看团队（team）建立信任 → driver-license 建 builder 身份档案（从"路过的技术人"变"官网上有档案的 builder"）。
- **造**：用 world+hello 搓出自己的 socialware（world 让消息可靠流转、hello 让界面即问即生）。
- **发布**：把产品**发布进 gallery**，成为一个"活的、别人能试用能 fork"的供给。

> **现状（承 README §1.1）**：builder arc **全段无 scenario**（36–39 假设"页面已存在"，从没演示 builder 如何创建+发布）。供给腿是飞轮**最缺 click-level 实现**的半边，Step 1b 新 scenario 40+ 的主战场。

### P-2.2 ↑ P-1.1 🟨 seller 需求腿（闭环）：落地 → fork → 兑现 → 回流

**谁 = 价值优先的业务主（value-first，判别式 model §1.1）**：agency（李复制）/ 高风险专家（周把关）/ 中小品牌 / 教培（08 §2 靶心全在此侧），看到价值才 fork 续 build；**不同行业气质不同 → S0 按渠道分气质变体**（model §1.2）。需求腿是飞轮**焊成环**的那条腿，也是**大半已落地**的那条：

- **落地 + 试用（匿名）**：seller 从 Instagram 直接落进某个 builder 的 gallery 产品，零登录试用拿到价值（hire 树洞 / DealScout 是此段两个趣味化产品实例）。
- **fork**：想要自己的版本 → `save_template_as` 复制这个产品作起点 + `anon→login` 认领 owner。
- **兑现 + 回流**：改成自己的、对自己的客户开放（兑现）；产物回流 gallery，成为下一个 seller 的落点（**回流 = 需求方二次跃迁成供给方**）。

> **现状（承 README §1.1）**：S0–S3（落地→试用→加入/fork）已由 **scenario 36–39** 覆盖，**39 = fork 已经在**；但 **S4 兑现 + S5 回流无 scenario**（飞轮闭合的那一段还没 click-level 实现）。

## §3 北极星（P-3.x · 各 ↑ 对应 arc，分期）

价值靠两条 arc，就得能**量出来**每条有没有兑现。**分期**：供给腿指标是近期主指标（货架先有货，冷启动供给先行）；需求腿的闭环指标是远期愿景、质量加权。为什么分期？把远期的"回流数"当唯一近期指标会误导 —— 回流是飞轮转起来后涌现的果子，急不得；供给是地基，近期该先建起来。

### P-3.1 ↑ P-2.1 🟦 供给北极星（近期·主指标）

- **量什么**：① 发布进 gallery 的 socialware 数（货架有多少货）；② builder 从抵达（B0）到发布（B5）的转化率 & 时间。
- **为什么反映定位**：P-2.1 说供给腿是地基。货架空着，seller 落进来无货可试、无物可 fork，飞轮根本启动不了。
- **目标方向**：发布数 ↑；抵达→发布的转化率 ↑、时间从"想做但没落地"压到"一个下午搓出来发布"。

### P-3.2 ↑ P-2.2 🟨 需求北极星（远期·愿景，质量加权）

- **量什么**：① fork 并**兑现**的 seller 数（fork 了还真做成自己的东西、对自己客户开放，不是 fork 完就弃）；② **回流**产物数（S5，飞轮闭合硬代理 —— 真被下一个 seller 落地试用的回流产物，**不数"存了个模板"**，同 hire 北极星"被接入深用不用 owner 自报"的纪律）。
- **为什么反映定位**：P-2.2 说需求腿是焊成环的腿。回流数直接量的就是"飞轮有没有真转"—— 一个 seller 走完需求腿变成下一轮供给。
- **目标方向**：fork 兑现数 ↑；回流数 ↑（质量加权，不刷存模板量）。
