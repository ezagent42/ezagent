# W · 成果生产工作流（GitHub → 官网内容）

> **轨②**：把 GitHub 上的研发产物，自动拉成官网上的「定位/痛点/成果」内容。轨①前端见 `00` §三 + 01–05。
> **核心判断**：访客看的是**思维导图的上两层（定位 + 痛点，可投票）**（像 `01-demo-定位树-多角色视角.html`）；**具体 issue 是隐藏的实现层**，不直接展示。

---

## 一、上游（接力链：先想清价值，再开发）

> 本工作流是 **公司价值** 向的（不是访客功能）。按 `07-demo` 接力链，先钉死「定位→指标→痛点→角色」再做下面的 spec 卡。

- **战略/定位 (G-a)**：让我们团队，能把 GitHub 上真实的研发产物**零手工**变成官网上可信的成果展示，而不必靠人手写/手工同步内容。〔公司价值〕
- **北极星 / 数据指标**：成果新鲜度（PR 合并 → 上墙时延）↑、导图覆盖率（被覆盖的痛点/PR 占比）↑、**人工维护成本 → 0**。
- **痛点 W-P1 (G-c)**：当团队想持续 build-in-public 展示进展时，想让官网成果始终跟真实 GitHub 进度一致，以便访客看到的是真东西；现状受阻于手写/手工同步成果内容，导致内容滞后失真、维护不起来、最终没人更新。
- **角色**：认领 = **研发**（建工作流）＋ **运营**（审核发布）；间接受益 = 访客 A（看到真实新鲜的成果）。

---

## 二、GitHub ↔ 官网 映射（核心方案）

接力链层级（见 `docs/rh/value-chain-kanban/demo/07-demo-接力链-多角色视角.html`）：`定位 → 痛点 → spec卡/issue → PR → 成果`，层层一对多。

| 接力链层 | GitHub 对应物 | 官网呈现 | 访客可见 | 可投票 |
|---|---|---|---|---|
| 战略/定位 (G-a) | **Milestone**（或 `定位:②` label） | 思维导图顶层节点 | ✅ | ✅ |
| 痛点 (G-c) | **「痛点」追踪 issue**（`type:痛点` + `定位:②`，body = G-c） | 思维导图中层·**主投票单元** | ✅ | ✅✅ |
| spec卡 | **工作 issue**（痛点 issue 的 sub-issue，带 `域/场景` label） | —（隐藏实现层） | ❌ | ❌ |
| 进行中 | 工作 issue 上的 **open PR** | 成果卡「即将上线」态 | ✅ | 评论/点赞 |
| 成果 | **已合并 PR**（close 工作 issue） | 成果卡（可试用） | ✅ | 评论/点赞/分享 |

**为什么不让访客投 issue**：issue 太碎、churn 快、对非技术访客无意义；**痛点才是会共鸣、想投票的稳定单元**。issue 留作隐藏的实现追踪。

**投票存哪**：投票 = 互动层功能，存**官网自己的库**，键 = **痛点 issue 号**（不要求访客有 GitHub 账号）。工作流只拉「定位/痛点/成果」，**不碰投票数据**。

**域/场景标签**：工作 issue / PR 打 `域:跨境`、`场景:客服` label；缺了 **AI 推断 + 人工补**。痛点/成果继承其下 issue 的标签。

**定位/痛点 怎么上 GitHub**：由 brainstorm 文档（`00` / 01–05）**种**进 GitHub（每条定位建一个 Milestone、每个痛点建一个追踪 issue），之后 **GitHub 当活的真相源**（站点从 GitHub 拉）。文档 = 设计依据（上游），GitHub = 已发布状态（下游）。

## 三、工作流 spec 卡

**功能卡 W-1 · GitHub 内容同步**｜服务痛点 W-P1｜认领 研发(建)＋运营(审)
- 用户故事：作为站点，我要从 GitHub 拉 Milestone/痛点 issue/PR，处理成定位·痛点·成果内容，以便官网思维导图与真实研发进度一致。
- 范围：只做 ① 拉取（选定 repo 的 milestone / labeled issue / PR）② 按 §一 表 rollup 成「定位 → 痛点 → 成果/进行中」树 ③ AI 草拟成果卡（标题 / 解决什么 / 域·场景 / 可否试用）④ **人工审核后发布**；不做 投票存储（互动层）/ 自研 git。
- 处理 = **AI 草拟 + 人工过审**（不把内部 PR 噪音裸奔外网）。
- 触发 = 选定 repo 列表 + **PR 合并 / 打标签时拉**（非全自动全量）。
- 验收(G-g)：Given 一个已合并、带 `定位/痛点/域` label 的 PR；When 工作流跑；Then 官网对应痛点下新增一张成果卡（含域/场景标签、试用链接若可部署），且**不出现裸 issue**。
- 优先级：P1（前端可先用 mock 数据并行）
- 挂钩牌：拨动 成果新鲜度 / 导图完整度 / 假设「真实进度自动上墙比手写可信」/ 闭环 成果卡数 vs PR 数
- 产出去向：→ 开 issue 只引本卡

## 四、对前端的接口（轨①只认这个）

工作流输出一份**结构化数据**：`定位 → 痛点（带票数占位）→ 成果/进行中（带域·场景标签、试用链接）` 树。**前端只读这份数据**渲染思维导图 + 成果页，可先 **mock 这份数据并行开发**，不必等工作流。

```
{ 定位: [ { id, title(G-a), 痛点: [ { id=issue号, title(G-c), 域, 场景,
  成果: [ { prId, 标题, 摘要, 域, 场景, 试用链接?, 状态: 已上线|进行中 } ] } ] } ] }
```
