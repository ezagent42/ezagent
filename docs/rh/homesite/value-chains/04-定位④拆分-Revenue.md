> **边界**：本棒接住 ③ 沉淀的关系，负责把「有意向」变成「在官网上自助完成商业动作」。**留资 ≠ 注册**：留资是 ③，注册/下单/预约是本棒。转发分享 = ⑤ Referral，不在本棒。

## §1 定位稿（定位 → 北极星）

母定位（G-a，源自 `00`）：

> **让试用满意的访问者，能在官网上直接完成注册开通或下单，明码看清要花多少、能拿到什么，而不必走一轮来回的销售沟通才搞清价格和交付。**

谁＝试用满意、动了付费/合作念头的访问者 / 新体验＝官网内自助走完商业动作（注册开通/下单/预约），价值与价格透明 / 旧成本＝走长销售漏斗、报价不透明、来回沟通才成交。AARRR 第 4 棒，交棒 = **商业转化量（转化率 · 付费线索量）**。

## §2 北极星 → 输入指标（指标 + 精确定义）

> **关系**：北极星 = 结果（果）；输入指标 = 能动手推高它的杠杆（因），尽量与北极星成**公式分解**；链条 **痛点→角色→卡 拨动输入指标 → 抬北极星**。

**北极星：商业转化量** = 统计窗口内「在官网完成注册开通 / 下单 / 预约」的去重访客数（及其折算的付费线索量）。

**分解：`商业转化量 ≈ 有效试用量 × 决策达成率 × 动作完成率`**

两步：先「敢决策」（看清价格/价值/保障后决定要付或要约），再「完成动作」（发起注册/下单/预约并顺利走完）。价格不透明卡在前一步，流程有坑卡在后一步。

| 输入指标 | 精确定义 |
|---|---|
| 〔承接②/③〕**有效试用量** | 真正跑通 demo、且经 ③ 沉淀的有意向访客 |
| **A 决策达成率** | 看完价格/价值/保障后决定要付或要约的访客数 ÷ 有意向访客数 |
| **B 动作完成率** | 发起注册/下单/预约后成功走完的访客数 ÷ 发起动作的访客数 |

> **实验判读（取代二元 drop）**：每个指标按 `假设 + 窗口 N 天 + 判读{ 达标 T→继续 / 未达→先改方案 / 连续 M 窗口仍未达→drop }`，阈值待运营随上线拍板。

## §3 树主体（输入指标 → 痛点 → 角色 → spec卡 + 原型图）

```
定位④ Revenue
└─ 北极星：商业转化量 (≈ 有效试用量 × 决策达成率 × 动作完成率)
   ├─ 输入指标 A · 决策达成率（价格/价值透明 → 敢决策）
   │   ├─ 痛点 P16 要询价等报价、不透明
   │   │   └─ 角色 全体访客 → 内容卡 ④-A1 明码价格表 · 原型 定价区
   │   ├─ 痛点 P17 花的钱换到什么（钱↔交付物对不上）
   │   │   ├─ 角色 赵全扛 → 内容卡 ④-A2赵 (开箱/最低门槛档对账)
   │   │   ├─ 角色 钱降本 → 内容卡 ④-A2钱 (人力 ROI 对账)
   │   │   └─ 角色 孙集成 → 内容卡 ④-A2孙 (集成/可定制交付对账)
   │   └─ 痛点 P18 临门一脚的顾虑没人答（退款/试用/合规）
   │       └─ 角色 全体访客 → 内容卡 ④-A3 转化FAQ+保障条
   └─ 输入指标 B · 动作完成率（自助完成商业动作）
       ├─ 痛点 P19 注册开通要等销售手动拉群
       │   └─ 角色 全体访客 → 功能卡 ④-B1 自助注册开通(依赖账号后端)
       ├─ 痛点 P20 高意向但要人对接、来回约时间
       │   └─ 角色 全体访客 → 功能卡 ④-B2 预约demo/留高意向线索
       └─ 痛点 P21 要付费却得线下转账对账
           └─ 角色 全体访客 → 功能卡 ④-B3 下单/支付(依赖支付集成)
```

> **卡型两类（模板见 `00` §五）**：内容卡＝不开发、只调内容；功能卡＝需开发。卡模板是 06 `G-r` 的官网精简版（省略 ICE 打分/价值卡/节点 id）。对话框/builder/发布助手 = loom 底座，引用不重建。
> **本棒卡型分布的规律**：**簇 A（决策达成）全是纯前端内容 → 内容卡、无依赖、可先行**；**簇 B（动作完成）都要接后端 → 功能卡、各有依赖**（见附 · 卡速查的依赖盯点）。
> **persona 在本棒的用法**：价值对账按 persona 算账方式不同（赵看开箱门槛、钱算人力 ROI、孙看集成交付）→ 价值对账 ④-A2 按 persona 拆内容卡；价格表/FAQ/注册/支付机制对全体一致，挂「全体访客」。

### 输入指标 A · 决策达成率（价格/价值透明 → 敢决策）

#### 痛点 P16（G-c）
> 当动了付费念头的访问者想知道要花多少钱时，他想一眼看清每档价格、含什么，以便当场判断买不买；现状受阻于旧站只写「联系我们获取报价」，导致他得发询价、等回复，热度一过就算了。 → 压低**决策达成率**

##### 角色：全体访客 · 原型：定价区

**内容卡 ④-A1 · 明码价格表**｜服务痛点 P16｜认领 产品(定价策略)+设计(版式)
- 信息内容：分档价格（每档多少钱 / 含什么 / 不含什么 / 主推标记）
- 数据来源：产品定价策略
- 落位：默认骨架定价区
- 候选形式：分档对比表（默认）/ 滑杆计价（暂缓）
- 验收(G-g)：Given 访客进定价区；When 渲染；Then 各档价格、含/不含、主推档当场可见，无需询价；移动端可横向对比。
- 优先级：P0
- 挂钩牌：拨动 决策达成率 / 验证假设「明码标价比『联系报价』转化更高」/ 闭环判据 定价区曝光→发起动作 转化率
- 产出去向：→ 内容就地维护（改价即改内容），变更记 changelog

#### 痛点 P17（G-c）
> 当访问者在算账时，他想把「花的钱」对上「具体拿到什么」，以便确认值不值；现状受阻于旧站只标价、不列交付物，导致他得猜买了到底给什么、不敢下手。 → 压低**决策达成率**

> 同一痛点对**多个 persona**成立：各 persona 的「值不值」算法不同，各填一套对账内容卡。

##### 角色：赵全扛·单干侠（→ personas）· 原型：赵全扛视角

**内容卡 ④-A2赵 · 单干侠价值对账**｜服务痛点 P17｜认领 产品 + 运营
- 信息内容：最低门槛档「花 X → 开箱即用拿到 Y（省下自己拼工具的时间）」对账
- 数据来源：产品供开箱档交付清单
- 落位：赵全扛视角对账区
- 候选形式：交付清单卡 / 省时对比（暂缓）
- 验收(G-g)：Given 赵视角对账区；When 渲染；Then 钱↔开箱交付物一一对上、突出「省自己拼的时间」。
- 优先级：P1
- 挂钩牌：拨动 决策达成率(赵) / 验证假设「开箱省时对账能让单干型敢付」/ 闭环判据 赵视角发起动作率
- 产出去向：→ 内容就地维护，变更记 changelog

##### 角色：钱降本（→ personas）· 原型：钱降本视角

**内容卡 ④-A2钱 · 降本派价值对账**｜服务痛点 P17｜认领 产品 + 运营
- 信息内容：「花 X/月 → 替下 Y 个客服人力、净省 Z」的人力 ROI 对账
- 数据来源：运营供真实人力成本/ROI 测算（接 ③-A2钱 的报告口径）
- 落位：钱降本视角对账区
- 候选形式：ROI 对比表 / 回本周期图（暂缓）
- 验收(G-g)：Given 钱视角对账区；When 渲染；Then 给出人力 ROI / 回本周期，数字可核实、与 ③ 的测算口径一致。
- 优先级：P1
- 挂钩牌：拨动 决策达成率(钱) / 验证假设「人力 ROI 对账能让降本型敢付」/ 闭环判据 钱视角发起动作率
- 产出去向：→ 内容就地维护，变更记 changelog

##### 角色：孙集成（→ personas）· 原型：孙集成视角

**内容卡 ④-A2孙 · 技术控价值对账**｜服务痛点 P17｜认领 产品 + 研发
- 信息内容：「花 X → 拿到 API 额度/集成支持/SLA」的集成交付对账 +「比自搭省的维护成本」
- 数据来源：研发供集成档交付与 SLA
- 落位：孙集成视角对账区
- 候选形式：交付/SLA 表 / 自搭成本对比（暂缓）
- 验收(G-g)：Given 孙视角对账区；When 渲染；Then 列出集成交付物 + SLA，并对比「比自搭省的维护」；论据可核实。
- 优先级：P2（替换成本高，需强证据）
- 挂钩牌：拨动 决策达成率(孙) / 验证假设「集成交付+省维护对账能让技术型敢付」/ 闭环判据 孙视角发起动作率
- 产出去向：→ 内容就地维护，变更记 changelog

#### 痛点 P18（G-c）
> 当访问者差临门一脚时，他想知道「不满意能不能退、有没有试用期、数据安不安全」，以便打消顾虑下手；现状受阻于旧站没有保障说明，导致他带着疑虑就放弃了。 → 压低**决策达成率**

##### 角色：全体访客 · 原型：FAQ/保障条

**内容卡 ④-A3 · 转化 FAQ + 保障条**｜服务痛点 P18｜认领 产品 + 运营
- 信息内容：临门一脚的高频顾虑答疑（退款/试用期/合规/数据安全/能否换档）
- 数据来源：运营供真实常见顾虑 + 产品供保障政策
- 落位：定价区/动作区附近的 FAQ 与保障条
- 候选形式：手风琴 FAQ + 保障徽标（默认）/ 客服入口（暂缓）
- 验收(G-g)：Given 访客在决策点；When 看 FAQ/保障条；Then 退款/试用/合规等高频顾虑有明确答复；不夸大、不虚标保障。
- 优先级：P1
- 挂钩牌：拨动 决策达成率 / 验证假设「当场答掉顾虑能减少临门流失」/ 闭环判据 看过 FAQ vs 没看的发起动作率
- 产出去向：→ 内容就地维护，变更记 changelog

### 输入指标 B · 动作完成率（自助完成商业动作）

#### 痛点 P19（G-c）
> 当已决定的访问者想开通账号时，他想自助即时开通、马上用，以便不等人；现状受阻于旧流程要销售手动拉群开通，导致他得等、热度一过就黄了。 → 压低**动作完成率**

##### 角色：全体访客 · 原型：注册/开通流

**功能卡 ④-B1 · 自助注册开通**｜服务痛点 P19｜认领 研发
- 用户故事：作为已决定的访问者，我想在官网直接注册开通账号，以便立刻开始用、不用等销售。
- 范围：只做 注册/开通流（前端 + 接注册接口 + 开通后引导）；不做 账号体系本身。
- ⚠ 依赖：依赖后端注册/账号能力——若无，需先备好，否则该卡 > 1 天（同 ② §C1，先备底座再上卡）。开通成功后可回填 ③-B2 的跨设备识别。
- 验收(G-g)：Given 访客点开通；When 走注册流；Then 自助完成注册并即时开通、给开始引导；失败有明确提示。
- 优先级：P0
- 挂钩牌：拨动 动作完成率 / 验证假设「自助开通比销售手动开通转化更高」/ 闭环判据 发起注册→开通完成率
- 产出去向：→ 开 issue 只引本卡（账号后端依赖单列追踪）

#### 痛点 P20（G-c）
> 当暂不自助下单、但高意向的访问者想找人聊聊时，他想一键约个时段，以便不来回约时间；现状受阻于旧流程靠邮件来回敲时间，导致约一次很累、可能就放弃了。 → 压低**动作完成率**（并产出高意向线索）

##### 角色：全体访客 · 原型：预约组件

**功能卡 ④-B2 · 预约 demo / 留高意向线索**｜服务痛点 P20｜认领 研发
- 用户故事：作为高意向但想要人对接的访问者，我想一键选个时段约一对一 demo，以便不用来回约时间。
- 范围：只做 预约组件（选时段 + 留资 + 通知销售；可接日历）；不做 CRM 系统本身。
- 验收(G-g)：Given 高意向访客点预约；When 选时段提交；Then 预约落库、通知销售、给访客确认；可改期/取消。
- 优先级：P1
- 挂钩牌：拨动 动作完成率 + 付费线索量 / 验证假设「一键预约能接住不自助但高意向的人」/ 闭环判据 预约提交率 + 预约→成交率
- 产出去向：→ 开 issue 只引本卡

#### 痛点 P21（G-c）
> 当要付费的访问者准备掏钱时，他想在官网当场付掉，以便干净利落成交；现状受阻于旧流程要线下转账、人工对账，导致他嫌麻烦、拖着拖着就凉了。 → 压低**动作完成率**

##### 角色：全体访客 · 原型：下单/支付

**功能卡 ④-B3 · 下单 / 支付**｜服务痛点 P21｜认领 研发
- 用户故事：作为要付费的访问者，我想在官网完成下单/支付或进入开通，以便不用线下转账对账。
- 范围：只做 下单入口 + 支付跳转（接现成支付）+ 支付回调开通；不做 自研支付。
- ⚠ 依赖：依赖支付集成——若无，需先备好，否则该卡 > 1 天。
- 验收(G-g)：Given 访客点下单；When 走支付；Then 站内完成支付或跳现成支付并回跳、自动开通；失败/超时有兜底。
- 优先级：P1
- 挂钩牌：拨动 动作完成率 / 验证假设「站内支付比线下转账成交率高」/ 闭环判据 下单→支付完成率
- 产出去向：→ 开 issue 只引本卡（支付集成依赖单列追踪）
