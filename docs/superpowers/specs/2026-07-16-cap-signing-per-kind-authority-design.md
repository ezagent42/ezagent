# Cap-signing: per-Kind authority — DESIGN

**Status**: v3 — closes codex adversarial-review round 2 (`NEEDS-REVISION`); model direction confirmed SOUND. **Supersedes** the central-signer line (`2026-07-15-cap-signing-strict-capstore-design.md`, v1–v11) — that design was driven by adversarial review to a sound-but-heavy place (central isolated signer + public keyring + global issuer-authentication); this model is simpler, more aligned with the system's dispatch structure, and distribution-friendly.
**Implementer**: coordinator (Claude) directly (app + ezagent-deploy cutover).

**Revision v2 (2026-07-16)** — closes codex adversarial-review round 1 (`NEEDS-REVISION`). The model direction held (per-Kind self-sign/verify, verify-at-target, issuance-as-cap-gated-action), but three architecture holes were grounded in `origin/main` and are now closed as hard implementation constraints:
1. **Key custody** — a raw key in a Behavior *slice* is NOT isolated: slices are cross-process-readable (`Kind.get_slice/2`/`get_raw_slice/2`, `slice_access.ex`), sibling reads are not cap-gated (`behavior.ex:409-436`), and keys serialize into full snapshots (`snapshot.ex:455-470`) that a system-scope query can list (`ecto/kind_snapshot.ex:44-64`) → any Kind's normal code, or any node sharing the Repo, could exfiltrate the key. **Fix: keys never live in a slice** — see §3.
2. **Presenter authenticity** — `ctx.caller` is caller-supplied and Router-preserved without authentication (`cmd.ex:75-117`, `router.ex:151-170`), so "bound-to-presenter" is forgeable with a stolen cap. **Fix: presenter identity from authenticated provenance** — see §1 item 5.
3. **Genesis + no-bypass** — seeding a K-signed anchor outside `K.grant` contradicts sole-mint (circular otherwise); `entity://admin` is not the canonical admin; and `authz_check` has live bypasses (`cap_exempt_actions`, `cap_issued`, rule-grants, `:vm_internal`). **Fix: one atomic canonical-admin genesis exception + one framework-owned verifier with no X-sensitive bypasses** — see §2, §5.

**Revision v3 (2026-07-16)** — closes codex adversarial-review **round 2** (`NEEDS-REVISION`). The model direction is confirmed SOUND and unchanged; round 2 required that three architectures v2 left as *options* be **pinned to one concrete design each**, and that the §10 gate stop over-claiming static proof of runtime properties. The three picks, each grounded below in `origin/main` file:line:
1. **Key custody = a per-Kind authority SERVICE that authenticates the OPERATION, not the process (§3).** An opaque handle is a copyable Elixir term and `Ezagent.Cap.Signing.sign/verify` are public functions over raw key binaries (`cap/signing.ex:121-132`); handlers run via dynamic `apply/3` (`kind/runtime.ex:816,843`), so process-locality does NOT stop an attached Behavior from signing (round-2 sub-finding b: "runs in K's process" ≠ signing authority). Fix: the key lives in a framework-owned per-instance authority service, never returned by any call; `sign`/`verify` are framework operations reachable from **exactly two** sites — the framework verifier and the post-verifier `K.grant` issuance step — each of which authenticates *the dispatch decision*, not the PID. No handle/key ever enters handler ctx; direct `:crypto`/`Signing` is forbidden to Behavior/domain/plugin tiers.
2. **Presenter authenticity = one framework-minted, unforgeable provenance stamp on the dispatch envelope, terminated below BOTH ingresses (§1 item 5, §2).** Authenticated identities exist at the edges (`api_v1_controller.ex:49,131-151`; `session_principal.ex:79-89`) but never reach the verifier as a non-forgeable value: `ctx.caller` is caller-writable (`cmd.ex:75-117`), Router preserves it (`router.ex:151-170`), Runtime authorizes from it (`kind/runtime.ex:518-545`). There is a SECOND public ingress — adapters build `%Invocation{}` directly and call `Invocation.dispatch/1` (`invocation.ex:118-142`), which `api_v1_controller.ex:54-61` uses — so a Cmd-only scheme misses it (round-2 sub-finding a). Fix: a provenance stamp is a first-class field on the `%Invocation{}` envelope (the single convergence point below both Cmd→Router and direct Invocation), minted ONLY by an enumerated set of framework mint-points, and `Kind.Runtime` REJECTS any envelope lacking a valid stamp **before** capability verification. Presenter identity is read from the stamp, never from `ctx.caller`.
3. **Genesis = a durable create-if-absent authority record (CAS) that is the single commit domain (§5).** `ever_created` (`snapshot.ex:465-490`, `ecto/kind_snapshot.ex:89-119`) is a precedent for a *same-commit atomic marker* but covers only the snapshot row — it cannot hold the key (§3 keeps keys out of snapshots). Fix: a dedicated per-instance authority record whose one winning INSERT-if-absent atomically (a) generates the per-Kind key inside the authority service, (b) emits exactly one K-signed admin anchor naming `User.admin_uri/0`, (c) irreversibly seals genesis; any re-run loses the CAS and is rejected.

**Trust-model narrowing (v3 headline honesty).** All three closures depend on treating **attached Behavior/plugin code as untrusted to mint provenance or call the crypto primitive**. This NARROWS the documented Phase-3 accepted scope ("a malicious in-VM actor is out of scope; the `:vm_internal` trust model already trusts all in-VM code" — `capbac.md §4.5`). It is a real trust-boundary change, not a free closure: the guarantees are enforced by (i) confining the mint/sign surface to an enumerated framework set + (ii) a runtime reject of unstamped/unauthorized envelopes + (iii) arch-gate ratchets — **not** by a second cryptographic system on the envelope (see §10 for the honest static-vs-runtime split).

## 0. The X problem (unchanged)
Capabilities are **forgeable / tamperable / retargetable** under soft verification (dual-read accepts unsigned) → privilege-escalation / credential-theft. **Close it**: every cap signed and strictly verified; unproven authority rejected.

## 1. Core model — each Kind is the authority for caps on itself
1. **The target signs.** A capability authorizes an action on a Kind `K`. **`K` is the sole authority for caps on itself: `K` signs it and `K` verifies it, with `K`'s own key.** The signer of a cap is ALWAYS the target Kind (granter == target == verifier).
2. **Verify at the target, always local.** Verification happens where the action dispatches — at `K`, which holds its key. **No party other than `K` ever verifies a cap-on-`K`.** (This is what makes symmetric per-Kind keys sufficient and the whole model distribution-friendly.)
3. **Issuance is a cap-gated action on `K`.** To make `K` issue a cap to a grantee, the caller invokes the `K.grant` action presenting a valid **authority-cap-on-`K`**; `K` verifies that authority-cap (own key) exactly like any other action, then signs the new cap for the grantee. Issuing is not special-cased — it's an action on `K`, gated by a cap. **This dissolves v11's "authenticate the issuer" problem**: `K` just cap-checks the grant request; nothing global to authenticate.
4. **Authority chain rooted at admin.** The delegation reads `admin → Alice → Bob`, but every cap in the chain is signed by its target Kind. Example: admin causes `W` to sign "Alice manage W" (Alice holds it, W-signed); Alice presents it to invoke `W.grant(Bob, create_session)`; `W` verifies Alice's manage-W cap (W's key) and signs Bob's `create_session` cap. Recursion bottoms out at **admin**, the root every Kind is anchored to trust.
5. **A cap is anchored to `(Kind, Action)`, verified against an AUTHENTICATED presenter carried by an unforgeable provenance stamp (v3 — concrete carrier).** The ActionSet declares "this action requires a cap signed by this Kind, for this action." Verification is a **framework-owned pre-handler gate** in the dispatch pipeline (§2): before running a handler, the presented cap must be (a) signed by the **live target instance's** authority service (§3), (b) for this concrete `(instance, action)`, (c) bound to the **presenter** — and **the presenter identity is read from a framework-minted provenance stamp, never from the caller-writable `ctx.caller`**. A stolen cap does not authorize its thief, because the thief cannot mint a stamp naming the grantee.
   - **Carrier (v3 pick):** the stamp is a **first-class field on the `%Invocation{}` envelope**, not a `ctx` key. `%Invocation{}` is the single convergence point below BOTH ingresses — `Cmd`→`Router.to_invocation/1`→`%Invocation{}` (`router.ex:151-170`) and adapters that build `%Invocation{}` directly and call `Invocation.dispatch/1` (`invocation.ex:118-142`; used by `api_v1_controller.ex:54-61`). Terminating provenance on the envelope (rather than on `Cmd` alone) covers both ingresses and closes round-2 sub-finding (a).
   - **Mint-points (v3 pick — three enumerated categories, nothing else):** (a) **enumerated authenticated edge adapters** stamp the principal they authenticated — `api_v1_controller` from the bearer token (`api_v1_controller.ex:49,131-151`; note it already *rejects* body-supplied identity via `reject_identity_inputs/2`, `:153-163`), the LV/socket path from the signed session principal (`session_principal.ex:79-89`), and the PTY/channel adapters likewise; (b) the **Runtime effect executor** stamps internal Kind→Kind dispatch with the **emitting Kind's URI** (the framework already enriches deferred dispatches with `caller=self_uri`, `server.ex:603-616`) — bound by Runtime, never `ctx.caller`, never `:vm_internal`; (c) **enumerated trusted framework facades** for internal-only cap-storage — `Ezagent.EntityCaps.dispatch_mutation/3` and `Ezagent.Identity.absorb_cap/2` (§5) — stamp an internal-provenance class bound to the target entity, *replacing* today's `caller: :vm_internal` marker (`entity_caps.ex:140-154`).
   - **Check-point:** `Kind.Runtime.handle_dispatch` REJECTS any envelope whose provenance stamp is absent or not minted by an enumerated site, **before** `authz_check` runs (today `authz_check` at `kind/runtime.ex:148-150,340-365` is the first gate; the provenance reject is inserted ahead of it). This is THE single verify chokepoint; `ctx.caller` is retained only as a non-authoritative trace field.

## 2. Retained invariants + the single framework verifier
- **Born signed** — every cap is minted only through the issuance chokepoint (`K.grant`), signed by `K`. The **only** exception is the one-time atomic genesis transition (§5); nothing else mints a cap.
- **One strict predicate, fail-loud** — an unsigned / wrong-signer / wrong-`(instance,action)` / wrong-presenter cap is **rejected, fail-loud**. Shape-matching a cap without verifying its signature is forbidden. No dual-read, no `verify_for`, no default-off `require_signature`.
- **Provenance reject precedes verification (v3).** Before any capability decision, `Kind.Runtime.handle_dispatch` rejects any `%Invocation{}` whose framework-minted provenance stamp is absent or not from an enumerated mint-point (§1 item 5). This runs ahead of `authz_check` (`kind/runtime.ex:148-150`); an envelope with no valid provenance never reaches the cap check. Presenter identity for the verifier is the stamp, not `ctx.caller`.
- **One framework-owned verifier that dominates every entrypoint.** The ActionSet macro declares only *immutable authorization metadata*; a single verifier in `Kind.Runtime` runs before **every** handler invocation and every state-mutating dispatch route — no handler is reachable without it. This is the no-bypass core, and today's dispatch has explicit escape hatches that MUST be closed for any target-cap-gated action:
  - Delete the `cap_issued` grant shortcut and the rule-authorized grant/revoke shortcuts in `authz_check` (`kind/runtime.ex:340-361`); `K.grant` is **unconditionally** target-cap-gated (its authority-cap is verified like any other).
  - No **target-cap-gated** action may carry `cap_exempt_actions` (`behavior.ex` `cap_exempt_actions/0`; live examples `behavior/identity.ex:554`, `behavior/session.ex:326-329`), an `authorization_rule` allow, or ambient `:vm_internal` all-cap authority. The arch-gate (§10 property 2) forbids these FLAGS **only for target-cap-gated actions** — it does not delete them globally.
  - **Internal-only actions are RECLASSIFIED, not deleted (v3 — closes round-2 hole 3).** The load-bearing exemptions stay, re-authenticated by the new provenance (§5): identity persistence (`absorb_cap`/`persist_caps`/`store_cap`/`remove_cap`, `behavior/identity.ex:554`, each `:vm_internal`-gated at `:609,620,640,656`) and session admission (`approve/deny/withdraw_admission`, in-handler `manages?/2`/`requested_by`, `behavior/session.ex:270-329`) are classified **internal-only** and authorized by a framework-minted internal-provenance stamp — NOT by `ctx.caller`, NOT by ambient `:vm_internal`.
  - The signing/verifying primitive is reachable **only** through the framework authority service (§3); direct `:crypto`/`Signing` calls and dynamic `apply/3` invocation cannot reach it.
- **No bypass** — the only paths are mint-via-`K.grant` (or the one genesis exception) and authorize-via-the-single-framework-verifier, over an envelope that carries valid provenance. An arch-gate + runtime invariants (§10) prove no other route mints, stamps, or authorizes.

## 3. Keys & custody — a non-exporting per-Kind authority compartment
- **The key is NEVER a Behavior-slice field.** Codex round 1 falsified the "slice = isolation" premise: slices are cross-process-readable via `Kind.get_slice/2`/`get_raw_slice/2` (`slice_access.ex:54-112`), `Kind.Server` returns any requested slice key without authorization (`server.ex:526-533`), sibling-slice reads are not cap-gated and are injected straight into handler context (`behavior.ex:409-436`, `kind/runtime/context.ex:40-53`), and a durable field serializes into the full snapshot (`snapshot.ex:455-470`) which a system-scope query can enumerate (`ecto/kind_snapshot.ex:44-64`). Any Kind's ordinary code — or any node sharing the Repo — could therefore read a slice-resident key and sign/verify off-`K`.
- **Per-Kind key lives inside a framework-owned per-instance authority SERVICE — no copyable handle (v3 pick — closes round-2 hole 1).** Round 2 falsified two weaker forms: an "opaque handle" is still a **copyable Elixir term** that could be captured and re-used, and `Ezagent.Cap.Signing.sign/2`/`verify/3` are **public functions over raw key binaries** (`cap/signing.ex:121-132`) that any handler — running via dynamic `apply/3` (`kind/runtime.ex:816,843`) — could call. So neither opacity nor process-locality confers authority (sub-finding b: "runs in K's process" ≠ signing authority). Instead:
  - Each Kind `K` has a **per-instance authority service** (framework-owned; concretely a private top-level field of `Kind.Server` state — a *sibling to* `state.state`, which is the slice map that generic reads index into (`server.ex:125-138,526-533`) — or a scoped keystore process). The key material is **never returned by any call** and never enters slice reads, sibling reads, raw reads, snapshots (`snapshot.ex:455-470`), events, logs, or admin listings (`ecto/kind_snapshot.ex:44-64`). **No handle is ever handed to Behavior code** — `build_handler_ctx` (`kind/runtime.ex:801`) never carries key or handle.
  - `sign`/`verify` are **framework operations that authenticate the OPERATION, not the caller PID.** Each is reachable from **exactly two framework sites**: (i) the framework verifier calls `verify` for a dispatch it is about to authorize; (ii) the post-verifier `K.grant` issuance step calls `sign` — but only for a `K.grant` dispatch the verifier has **already authorized** with a valid authority-cap-on-`K`. **A Behavior handler never signs.** Because `K.grant` is itself an ActionSet action whose body runs via `apply/3` like any handler, the handler MUST NOT hold the key: it returns an **issuance intent** (e.g. an `{:issue_cap, grantee, cap_shape}` effect) and the framework issuance path — post-verifier, Runtime-owned, mirroring today's effect executor (`server.ex:603-616`) — performs the `sign` against the authority service. Signing is thus bound to the verifier's *decision*, not to whoever emitted the effect: an attached Behavior emitting a raw `{:issue_cap, …}` gets no signature because no `K.grant` was authorized for it.
  - **Direct `:crypto`/`Ezagent.Cap.Signing` references are forbidden in the Behavior/domain/plugin tiers** and permitted only inside the authority service (arch-gate, §10 property 3).
- **Symmetric is still correct** (sign == verify at `K`, which holds its own key); asymmetric would only help an off-`K` verifier, which does not exist here (see §4 for the distributed case, where the cap is routed to `K`'s owner runtime rather than verified remotely).
- **Admin root = crown jewel.** `admin` is the root of trust. Every Kind, at creation, is anchored to trust the **canonical admin identity** — resolved from the single code authority `Ezagent.Entity.User.admin_uri/0` (`user.ex:30-32`), **not** the literal `entity://admin` (a non-canonical URI lacking the required workspace/type/name components, `uri.ex:420-428`). The anchor names the identity, not a specific admin key.
- **Identity-anchoring + key-versioning** (cheap future rotation): admin's key carries a version; Kinds trust the stable canonical identity. Rotating admin's key = version-bump + re-provision, **not** a fleet-wide re-anchor. Per-Kind keys rotate lazily / on-compromise (blast radius contained to one instance).
- **Residual.** With keys out of slices/snapshots, the residual is privileged BEAM introspection (`:sys.get_state`, tracing) of `K`'s live process — contained to one instance and hardened incrementally (restrict those BIFs in prod). The admin root warrants the strongest custody (owner-scoped storage / KMS). **No global-seed HSM requirement** — each compartment holds only its own key.

## 4. Distribution (friendly by construction — with the key-custody constraint)
- A cap is always verified at its target Kind's **owner runtime**. Today dispatch already requires the local runtime to own the target workspace (`invocation.ex:118-142`, `workspace_owner_gate.ex`, placement local-only `workspace_placement.ex`); remote routing (deferred, §7) must **forward the cap + provenance stamp to the authoritative owner runtime**, where the single local verifier and its authority service run. No cap-on-`K` is ever verified off-`K`; no key or handle crosses the wire.
- **Blast-radius containment depends on §3.** The per-node claim only holds once keys are out of shared plaintext: a slice-resident key serializes into snapshots that a **system-scope query lists across all nodes** (`ecto/kind_snapshot.ex:44-64`) — so a shared-Repo node would NOT be limited to its own Kinds' keys. With §3's authority service (owner-scoped storage / KMS, never in snapshots), **node compromise is contained to that node's live Kinds**. Placement transfer must atomically transfer or rotate the **authority service's key custody** (there is no copyable handle to move).
- Distribution then needs only ① remote transport/routing to the owner runtime and ② bootstrap root-anchoring — **neither is a cap-signing-model change**. This **unblocks** workspace-per-ECS, and is strictly better than v11's seed-on-every-node.

## 5. Bootstrap / genesis — one atomic, one-time, canonical-admin transition
The tension codex flagged: `K.grant` requires a pre-existing authority-cap-on-`K`, but "born signed" says every cap comes from `K.grant` — so seeding an anchor is either a mint *outside* `K.grant` (breaks sole-mint) or circular. Resolution: **one explicit, narrowly-scoped genesis exception, made atomic by a create-if-absent authority record (v3 pick — closes round-2 hole 3).**

- **Atomic genesis = one durable create-if-absent (CAS) commit, one commit domain.** A dedicated **per-instance authority record** (keyed by `K`'s instance URI, with a uniqueness constraint) is the serialization point. Its single winning `INSERT`-if-absent atomically, in **one transaction**: (a) generates `K`'s per-instance key **inside the authority service** (§3), (b) emits **exactly one** `K`-signed authority anchor naming the **canonical admin** (`Ezagent.Entity.User.admin_uri/0` = `entity://system/user/admin`, `user.ex:32`; **not** the literal `entity://admin`, a non-canonical URI, `uri.ex:403-428`), and (c) records the **seal** (the CAS winner) so the transition can never run again for that `K`. Any concurrent or later attempt loses the CAS and is rejected fail-loud.
  - **Why a new record, not `ever_created` (honesty).** `ever_created` (`snapshot.ex:465-490`, `ecto/kind_snapshot.ex:89-119`) is the right *discipline* precedent — a marker set in the SAME upsert as the state it gates, no fire-and-forget window — but it is a boolean on the **snapshot row**, and §3 forbids the key from living in the snapshot. So the seal cannot ride `ever_created`: the authority record IS the key's custody store, and its uniqueness constraint IS the seal. Same atomic-marker principle, different (key-bearing) home.
- **Admin uses the same transition** to create its own self-anchor, after which genesis is permanently disabled system-wide. Root bottoms out at admin trusting itself — non-circular because the CAS is a one-shot durable state change, not a cap-check.
- **Delete + arch-gate** every `{:genesis, arbitrary_uri}` authorization form (`cap.ex:24-27,172,227-229`). No caller may supply a root identity; the canonical admin URI comes from the single code authority `admin_uri/0`, never a passed argument. No key is ever passed as a plain argument.

- **Internal-only actions are authenticated by the NEW provenance, NOT deleted (round-2 hole 3, second half).** Two exemption families are **load-bearing** and cannot vanish globally; v3 re-authenticates them by the framework-minted internal-provenance stamp (§1 item 5 mint category c), replacing their current `:vm_internal`/`ctx.caller` basis:
  - **Identity persistence** (`absorb_cap`/`persist_caps`/`store_cap`/`remove_cap`) is cap-exempt (`cap_exempt_actions/0`, `behavior/identity.ex:554`) and today `:vm_internal`-gated in each handler (`identity.ex:609,620,640,656`), dispatched by `Ezagent.EntityCaps.dispatch_mutation/3` (`entity_caps.ex:140-154`) and `Ezagent.Identity.absorb_cap/2`. These facades become an **enumerated mint-point** stamping internal-provenance bound to the target entity; the handlers gate on **valid internal provenance from that facade**, not on a `caller: :vm_internal` literal any in-VM code could set.
  - **Session admission** (`approve/deny/withdraw_admission`) is cap-exempt and authorized **in-handler** by `Authority.manages?/2`/`requested_by` because the member's owner holds no session cap (`behavior/session.ex:270-329`). This family keeps its in-handler authority check but now runs behind an **edge-authenticated presenter** stamp — the manager's identity in the stamp feeds `manages?/2`, so the in-handler check is over an authenticated principal, not a forgeable `ctx.caller`.
  - The §10 arch-gate therefore forbids the bypass **flags** (`cap_exempt_actions`, `cap_issued`, `authorization_rule`, `:vm_internal`) **only for target-cap-gated actions** — internal-only actions retain cap-exemption but are re-based on provenance.

## 6. Cutover (ezagent-deploy scope)
Self-use, disposable data → **wipe + reseed**: quiesce → wipe cap-bearing data → deploy the new build → seed (admin first, then Kinds each get a fresh key + admin anchor; all caps re-issued signed) → resume. **No app-side migration/backfill code.**

## 7. Non-goals
- **Cap-storage consistency** (a cap in multiple homes, revoke-clears-all) — separate concern.
- **Full distributed transport** — the model SUPPORTS distribution; the routing/bootstrap-anchoring *implementation* is a separate track (deferred). The design must not preclude it (§4).
- Opaque cap representation — not needed here (verify is local at the target with its key, not a global boundary).

## 8. Implementation shape (high-level)
- **Per-instance authority service** (§3): the key is generated at genesis into `K`'s framework-owned authority store (a private top-level `Kind.Server` field, sibling to the slice map `state.state`, or a scoped keystore process); never a slice field, never in snapshots/events/logs/admin-listings; never returned by any call; never placed in `build_handler_ctx`.
- **`sign` / `verify` as framework operations** — reachable from exactly two framework sites (the verifier; the post-verifier `K.grant` issuance step). They authenticate the OPERATION (the verifier's dispatch decision for THIS instance), not the caller PID. Direct `:crypto`/`Ezagent.Cap.Signing` is arch-gated out of Behavior/domain/plugin tiers.
- **The framework verifier** — the ActionSet macro declares immutable metadata; one `Kind.Runtime` verifier dominates every handler/state-mutating route (§2), **first rejecting any `%Invocation{}` without a valid framework-minted provenance stamp**, then consuming the stamped presenter (not `ctx.caller`), and comparing the signed concrete `(instance, action, grantee)` against the live dispatch. Verify or fail-loud.
- **Provenance stamp** — a first-class `%Invocation{}` field (below both Cmd→Router and direct Invocation), minted by three enumerated categories only: edge adapters (`api_v1_controller`, `session_principal`, PTY/channel), the Runtime effect executor (internal Kind→Kind, bound to the emitting Kind URI), and trusted cap-storage facades (`Ezagent.EntityCaps`, `Ezagent.Identity`). Runtime rejects unstamped/unauthorized-mint envelopes before authz.
- **`K.grant` action** — unconditionally cap-gated (requires an authority-cap-on-`K`); the handler returns an **issuance intent** (effect), and the framework post-verifier issuance path performs `sign` via the authority service — the handler never holds the key. Issuance = this one action, uniformly; no `cap_issued`/rule shortcut.
- **Atomic genesis CAS record** (§5) — a per-instance create-if-absent authority record whose one winning INSERT keys-gen + admin-anchor-emit + seal, one transaction, canonical admin (`admin_uri/0`); re-run loses the CAS.
- **Reclassify (not delete) internal-only actions** — identity persistence + session admission re-authenticated by internal/edge provenance (§5); the bypass flags are gated off only for target-cap-gated actions.
- **Delete**: dual-read / `require_signature` default-off (`cap.ex:42-63,200-205`) / `verify_for` / the central-seed `sign_artifact` keypair-from-`granted_by` derivation (`cap.ex:213-220`) + v11's public-keyring machinery / `{:genesis, URI}` (`cap.ex:24-27,172,227-229`) / the `authz_check` `cap_issued`·rule·`:vm_internal` bypasses **for target-cap-gated actions** (`kind/runtime.ex:340-361`).

## 9. Behavioral tests (the X holes, closed — each an INDEPENDENT assertion)
Per representative cap-gated action (session.send, create_session, PTY read, kanban write, world read_unfiltered…), each vector is its own test proving the attempt reached the authorization boundary and was rejected:
- **Forge** — an unsigned cap is rejected fail-loud.
- **Tamper** — a cap whose fields were mutated after signing is rejected.
- **Retarget** — a cap signed for a different instance/Kind is rejected under the live target's own handle; cap-controlled `key_id` cannot select another Kind's key.
- **Stolen-cap + spoofed-presenter** — a valid cap presented by a caller spoofing the grantee's URI via `ctx.caller` is rejected, because presenter identity comes from authenticated provenance (§1.5).
- **Wrong-target-key** — verification uses the live target's authority handle, not one selected by the cap.
- **Issuer-impersonation** — `K.grant` rejects a caller lacking a valid authority-cap-on-`K`; recursion to the canonical admin root is exercised and proven non-circular.
- **Genesis** — the one-time transition anchors each `K` to `admin_uri/0`, then re-invocation is rejected (sealed); strict verify holds end-to-end on a freshly seeded stack.
- **Key egress** — generic slice read, sibling read, raw read, snapshot, event, and admin-listing of `K` never return raw key material (only an opaque handle).
- **Legit** — a properly `K.grant`-minted cap, presented by the authenticated grantee, is accepted.

## 10. Gate plan (this is a first-class deliverable, not just tests)
Two enforcement layers, following the ezagent static-gate discipline (`check_invariants` → `ci.local` full-suite; run pre-push):

**A. Completion / invariant gate — behavioral, fail-when-the-goal-is-unmet.** The §9 vectors as **independent** `/goal`-style assertions on a freshly seeded stack (each proves the attempt reached the authorization boundary, not a shared monolith): forge, tamper, retarget, stolen-cap+spoofed-presenter, wrong-target-key, issuer-impersonation, genesis-seal, key-egress rejected; legit accepted. The forge/tamper/retarget cases **fail on today's `origin/main`** (dispatch authorizes via provenance+structural match without `Cap.verify`, `authorization.ex:6-18`, `kind/runtime.ex:539-545`; `require_signature` default-off, `cap.ex:42-63`) — that red proves each gates a real hole. (The positive `K.grant` path does not exist on `origin/main` yet, so the suite lands with the implementation, not before it.)

**B. Structural arch-gate — HONEST split (v3 — closes round-2 §10 over-claim).** Round 2 was correct that v2 over-claimed: a static grep/AST gate can prove a *syntactic absence* (a flag is not present, a symbol is referenced only in allowed files, a declaration exists) but CANNOT statically prove a *semantic / information-flow / one-shot* property. So each property is classified as **STATIC** (the gate's grep/AST IS the guarantee) or **RATCHET + RUNTIME** (the grep/AST is a shrink-only ratchet, but the security guarantee is owned by a named runtime instrumentation assertion or an independent behavioral test from §9). Only #2 and #4 are genuinely static; the rest are ratchet+runtime.

| # | Property | Class | What the STATIC ratchet checks | Who OWNS the guarantee (runtime invariant / behavioral test) |
|---|----------|-------|--------------------------------|-------------------------------------------------------------|
| 1 | **Verifier dominance** | ratchet + runtime | no dispatch route reaches a handler except through `Kind.Runtime.handle_dispatch`; call-graph has one authz decision site | **Runtime invariant:** a telemetry/instrumentation assertion that every executed handler was preceded by a verifier decision for the same `(instance, action)` (no handler-run event without a matching authz event). Reachability ≠ dominance-in-fact. |
| 2 | **No bypass flags** | **STATIC** | no **target-cap-gated** action carries `cap_exempt_actions`/`cap_issued`/`authorization_rule`/`:vm_internal`; the `cap_issued`+rule shortcuts are deleted from `authz_check` (`kind/runtime.ex:340-361`) | (self-enforcing: syntactic absence IS the property) |
| 3 | **Sign/verify confinement** | ratchet + runtime | `:crypto`/`Ezagent.Cap.Signing` referenced ONLY inside the authority service module; zero refs in Behavior/domain/plugin tiers | **Behavioral test:** the §9 *retarget* + *wrong-target-key* + *key-egress* vectors — an attached Behavior attempting to sign/verify off-`K` is rejected. Static can't prove `apply/3` never reaches it; the test proves the operation is refused. |
| 4 | **Declaration parity** | **STATIC** | every cap-gated action declares its cap requirement — leverages the existing required-cap coverage check (`behavior.ex` `required_caps/0` vs actions; `keys(required_caps) ∪ cap_exempt_actions == actions`) | (self-enforcing: declaration coverage IS the property) |
| 5 | **Key egress absence** | ratchet + runtime | the key field name appears in no slice schema, snapshot serializer, event, log, or admin-listing path | **Behavioral test:** the §9 *key-egress* vector — generic slice read / sibling read / raw read / snapshot / event / admin-listing of `K` returns no key material. Information-flow (does *some* value alias the key?) is not statically decidable; the test exercises the actual egress boundaries (`server.ex:526-533`, `snapshot.ex:455-470`, `ecto/kind_snapshot.ex:44-64`). |
| 6 | **Presenter authenticity** | ratchet + runtime | no path lets `ctx.caller` stand in for the verifier's presenter; provenance stamp is minted only at the enumerated sites | **Runtime invariant + behavioral test:** Runtime asserts every `%Invocation{}` reaching authz carries a stamp from an enumerated mint-point (else reject); the §9 *stolen-cap + spoofed-presenter* vector proves a forged `ctx.caller` cannot authorize. "Unforgeable" here = mint-confined + runtime-reject, **not cryptographic** — so not a static proof. |
| 7 | **Unique target-key binding** | ratchet + runtime | no cap-controlled `key_id` selects the verifying key (`cap/signing.ex` `key_id`); verify always uses the live target's authority service | **Behavioral test:** the §9 *retarget* + *wrong-target-key* vectors — a cap signed for another instance/Kind, or carrying a chosen `key_id`, is rejected under the live target's own service. |
| 8 | **Genesis one-shot** | ratchet + runtime | every `{:genesis, URI}` authorization form removed (`cap.ex:24-27,172,227-229`); admin URI sourced from `admin_uri/0`, never an argument | **Behavioral test:** the §9 *genesis* vector — the CAS commits exactly once, re-invocation loses the CAS and is rejected. One-shot-ness is a runtime state property (the uniqueness constraint), not statically provable. |

**Honest enforceability limit (v3).** Only properties **2 and 4** are statically proven; **1, 3, 5, 6, 7, 8** are static *ratchets* whose security guarantee is a named runtime invariant or a §9 behavioral test — this spec does **not** claim static proof of any semantic (verifier-dominance-in-fact), information-flow (key non-egress), authenticity (provenance unforgeability), or one-shot (genesis) property. Caps remain public Elixir structs, so discovering arbitrary semantic field reads stays best-effort AST. Collapsing verification to ONE framework verifier, minting to ONE `K.grant`, and provenance to THREE enumerated mint-points keeps both the scan surface and the runtime-assertion surface minimal — but the guarantee lives at runtime, and §10 now says so plainly.

## 11. Open (residual sub-mechanism only — the three architectures are CHOSEN in v3)
The v3 picks are settled: authority service (§3), envelope provenance stamp with three enumerated mint-points (§1 item 5), atomic genesis CAS record (§5). What remains is sub-mechanism inside those choices, not the choices themselves:
- **Authority service host** — private top-level `Kind.Server` field vs a scoped keystore process; the symmetric primitive (HMAC vs a symmetric AEAD/MAC). (The *choice to use a non-exporting service* is closed; only its internal form is open.)
- **Provenance stamp representation** — the exact term/encoding on `%Invocation{}` and the precise reject hook offset in `handle_dispatch` (relative to `authz_check`, `kind/runtime.ex:148-150`). (The *carrier, mint-points, and reject-before-verify ordering* are closed.)
- **Genesis-CAS transaction shape** — the authority record's schema + uniqueness constraint and the exact seal column, reusing the `ever_created` same-commit discipline. (The *create-if-absent-one-commit* choice is closed.)
- **admin-root key custody** (owner-scoped storage / KMS) + version scheme; bootstrap sequencing (admin genesis before any Kind anchors).
- **Migration bookkeeping** — enumerating today's `{:genesis, URI}` and bypass-flag call-sites to delete, and the exact `EntityCaps`/`Identity` facade edits that swap `caller: :vm_internal` for internal-provenance stamping.
