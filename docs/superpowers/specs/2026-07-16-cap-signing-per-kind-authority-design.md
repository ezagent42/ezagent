# Cap-signing: per-Kind authority — DESIGN

**Status**: v4 — adopts **PATH A** (first-party / reviewed-code threat model; lead decision 2026-07-16). Model direction confirmed SOUND across codex rounds 1–3, unchanged. **Supersedes** the central-signer line (`2026-07-15-cap-signing-strict-capstore-design.md`, v1–v11) — that design was driven by adversarial review to a sound-but-heavy place (central isolated signer + public keyring + global issuer-authentication); this model is simpler, more aligned with the system's dispatch structure, and distribution-friendly.
**Implementer**: coordinator (Claude) directly (app + ezagent-deploy cutover).

**Revision v4 (2026-07-16) — adopt PATH A (first-party / reviewed-code threat model).** codex round 3 proved v3's "trust-model narrowing" (treat attached in-VM Behavior/plugin code as an *untrusted, malicious* actor that must be cryptographically contained) is NOT achievable in one unsandboxed BEAM: `:sys.get_state`/tracing reach any live process's state and `apply/3`-dispatched handlers share the VM with the framework (`kind/runtime.ex:816,843`) — no in-process construct is a cryptographic boundary against code already running in the VM. The lead's actual model, stated plainly: **all loaded code — framework, domain, community plugins, socialware — is REVIEWED before load.** v4 reframes to that model (Path A) and keeps only the closures that are real *under* it.

> **Load-bearing precondition (stated LOUDLY):** the reviewed-code assumption. Cap-signing under Path A is **not** a boundary against unreviewed code running in-BEAM — see the threat model below and §3's honesty note. When/if unreviewed third-party code must run in-BEAM, the roadmapped upgrade is **Path B** — a separate protected signing runtime, the revival of the v11 isolated-signer design (`docs/superpowers/specs/2026-07-15-cap-signing-strict-capstore-design.md`), which is **NOT retired**; it is the Path B design of record.

The 5 changes v4 makes on top of the SOUND, unchanged model (per-Kind self-sign/verify, verify-at-target, issuance = cap-gated `K.grant`, admin-rooted delegation, born-signed + strict-verify):
1. **Threat model → Path A** (below): defends ① accidental forgery, ② architecture-violating code review missed, ③ external-ingress caller spoofing; OUT of scope = a malicious actor running unreviewed code in-BEAM.
2. **Key custody simplified** (§3): key stays in private non-slice `Kind.Server` state (never slice/snapshot/event/log/admin-listing, `server.ex:125-138,526-533,603-616`; `snapshot.ex:455-470`); DROP v3's authority-service/KMS; ADD a static arch-gate banning the introspection primitives + direct `:crypto`/`Ezagent.Cap.Signing` (`cap/signing.ex:121-132`) in Behavior/domain/plugin tiers — a **ratchet + review**, not a cryptographic boundary.
3. **Presenter at the external EDGE** (§1.5, §2): authenticated principal stamped at ingress adapters (`api_v1_controller.ex:45-59,131-163`; `session_principal.ex:63-89`) into the envelope; Runtime reads presenter from the stamp for externally-originated requests, never from caller-writable `ctx.caller` (`cmd.ex:75-117`, `router.ex:151-170`); internal reviewed code is TRUSTED to pass a correct caller. Non-edge ingress paths inventoried (DeliveryOutbox replay, ExternalMirror, SessionTemplate, CLI, EntityCaps facade) so strict-verify does not break them.
4. **Genesis CAS correctness fix** (§5): a durable **append-only, non-deletable-by-runtime/plugin** authority record holds {committed key, the one signed canonical-admin anchor, key version, seal}; anchor read FROM the row; bootstrap admin's immutable self-row FIRST. (v3's "anchor emitted as an effect atomic with the CAS insert" is impossible — effects fire AFTER the slice commit, `server.ex:605-650` — and a bare uniqueness constraint is reversible by row deletion.)
5. **Intent binding** (§1.5, §8): signing binds to the verifier-approved `(target, action, grantee, bounds)` reconstructed from the authenticated invocation — NEVER a handler-supplied `cap_shape`, because `post_handle/4` can replace the effect list (`kind/runtime.ex:901-909`).

v4 **supersedes** the v3 picks in §3 (authority service → private state) and §1.5/§2 (stamp-all-internal → edge-only + trusted internal reviewed code); the SOUND model and §5's atomic-genesis *direction* stand. The v2/v3 notes below are retained as the codex-round history.

**Revision v2 (2026-07-16)** — closes codex adversarial-review round 1 (`NEEDS-REVISION`). The model direction held (per-Kind self-sign/verify, verify-at-target, issuance-as-cap-gated-action), but three architecture holes were grounded in `origin/main` and are now closed as hard implementation constraints:
1. **Key custody** — a raw key in a Behavior *slice* is NOT isolated: slices are cross-process-readable (`Kind.get_slice/2`/`get_raw_slice/2`, `slice_access.ex`), sibling reads are not cap-gated (`behavior.ex:409-436`), and keys serialize into full snapshots (`snapshot.ex:455-470`) that a system-scope query can list (`ecto/kind_snapshot.ex:44-64`) → any Kind's normal code, or any node sharing the Repo, could exfiltrate the key. **Fix: keys never live in a slice** — see §3.
2. **Presenter authenticity** — `ctx.caller` is caller-supplied and Router-preserved without authentication (`cmd.ex:75-117`, `router.ex:151-170`), so "bound-to-presenter" is forgeable with a stolen cap. **Fix: presenter identity from authenticated provenance** — see §1 item 5.
3. **Genesis + no-bypass** — seeding a K-signed anchor outside `K.grant` contradicts sole-mint (circular otherwise); `entity://admin` is not the canonical admin; and `authz_check` has live bypasses (`cap_exempt_actions`, `cap_issued`, rule-grants, `:vm_internal`). **Fix: one atomic canonical-admin genesis exception + one framework-owned verifier with no X-sensitive bypasses** — see §2, §5.

**Revision v3 (2026-07-16)** — closes codex adversarial-review **round 2** (`NEEDS-REVISION`). The model direction is confirmed SOUND and unchanged; round 2 required that three architectures v2 left as *options* be **pinned to one concrete design each**, and that the §10 gate stop over-claiming static proof of runtime properties. The three picks, each grounded below in `origin/main` file:line:
1. **Key custody = a per-Kind authority SERVICE that authenticates the OPERATION, not the process (§3).** An opaque handle is a copyable Elixir term and `Ezagent.Cap.Signing.sign/verify` are public functions over raw key binaries (`cap/signing.ex:121-132`); handlers run via dynamic `apply/3` (`kind/runtime.ex:816,843`), so process-locality does NOT stop an attached Behavior from signing (round-2 sub-finding b: "runs in K's process" ≠ signing authority). Fix: the key lives in a framework-owned per-instance authority service, never returned by any call; `sign`/`verify` are framework operations reachable from **exactly two** sites — the framework verifier and the post-verifier `K.grant` issuance step — each of which authenticates *the dispatch decision*, not the PID. No handle/key ever enters handler ctx; direct `:crypto`/`Signing` is forbidden to Behavior/domain/plugin tiers.
2. **Presenter authenticity = one framework-minted, unforgeable provenance stamp on the dispatch envelope, terminated below BOTH ingresses (§1 item 5, §2).** Authenticated identities exist at the edges (`api_v1_controller.ex:49,131-151`; `session_principal.ex:79-89`) but never reach the verifier as a non-forgeable value: `ctx.caller` is caller-writable (`cmd.ex:75-117`), Router preserves it (`router.ex:151-170`), Runtime authorizes from it (`kind/runtime.ex:518-545`). There is a SECOND public ingress — adapters build `%Invocation{}` directly and call `Invocation.dispatch/1` (`invocation.ex:118-142`), which `api_v1_controller.ex:54-61` uses — so a Cmd-only scheme misses it (round-2 sub-finding a). Fix: a provenance stamp is a first-class field on the `%Invocation{}` envelope (the single convergence point below both Cmd→Router and direct Invocation), minted ONLY by an enumerated set of framework mint-points, and `Kind.Runtime` REJECTS any envelope lacking a valid stamp **before** capability verification. Presenter identity is read from the stamp, never from `ctx.caller`.
3. **Genesis = a durable create-if-absent authority record (CAS) that is the single commit domain (§5).** `ever_created` (`snapshot.ex:465-490`, `ecto/kind_snapshot.ex:89-119`) is a precedent for a *same-commit atomic marker* but covers only the snapshot row — it cannot hold the key (§3 keeps keys out of snapshots). Fix: a dedicated per-instance authority record whose one winning INSERT-if-absent atomically (a) generates the per-Kind key inside the authority service, (b) emits exactly one K-signed admin anchor naming `User.admin_uri/0`, (c) irreversibly seals genesis; any re-run loses the CAS and is rejected.

## Threat model (Path A — first-party / reviewed-code) — v4 headline
**Precondition (load-bearing).** Every module loaded into the BEAM — core framework, domain, and third-party plugins/socialware — passes review before load. There is no sandbox: one unsandboxed BEAM shares process memory, `:sys`/tracing, ETS, and the code server across all loaded code, so we do **not** claim a cryptographic boundary against code already running in the VM. Cap-signing here hardens the *first-party* system against bugs and review escapes, not against a determined in-VM adversary.

**Cap-signing under Path A defends against:**
- ① **Accidental forgery** — a bug that mis-signs, mis-targets, or emits an unsigned cap; a soft-verify path that accepts unsigned/unverified caps (`require_signature` default-off, `cap.ex:42-63`). Strict verify + born-signed make these fail loud instead of silently escalating.
- ② **Architecture-violating code that review missed** — a Behavior/plugin that, through a bug or an oversight review didn't catch, reaches a signing or authorization path it shouldn't. The single framework verifier + confined sign surface + the arch-gate ratchets (§10) catch the syntactically-detectable classes and fail loud at runtime for the rest.
- ③ **External-ingress caller spoofing** — an external caller presenting a stolen cap while claiming to be the grantee via caller-writable `ctx.caller` (`cmd.ex:75-117`, `router.ex:151-170`). The edge-stamped authenticated presenter (§1 item 5) defeats this.

**Explicitly OUT of scope (honest limit).** A **malicious untrusted actor running unreviewed code inside the BEAM.** Such code can read any live process's key via `:sys.get_state`/tracing, call `:crypto`/`Ezagent.Cap.Signing` directly (`cap/signing.ex:121-132`), or reach the signing path through `apply/3` (`kind/runtime.ex:816,843`) — none of which any in-process construct can prevent in one unsandboxed VM. This aligns with the documented Phase-3 stance: *"a malicious in-VM actor is out of scope; the `:vm_internal` trust model already trusts all in-VM code"* (`capbac.md §4.5`, lines 261-262). v4 makes the reviewed-code ASSUMPTION explicit as the precondition that makes that stance sound.

**Path B (roadmapped upgrade).** If/when unreviewed third-party code must run in-BEAM, the reviewed-code precondition breaks and Path A's custody provides no boundary. The upgrade is a **separate protected signing runtime** — the revival of the v11 isolated-signer design (`2026-07-15-cap-signing-strict-capstore-design.md`: central isolated signer + public keyring + global issuer-authentication). That spec is **not retired**; it is the Path B design of record. v4 is deliberately scoped to Path A so it stays light and aligned with the dispatch structure while the reviewed-code precondition holds.

## 0. The X problem (unchanged)
Capabilities are **forgeable / tamperable / retargetable** under soft verification (dual-read accepts unsigned) → privilege-escalation / credential-theft. **Close it**: every cap signed and strictly verified; unproven authority rejected.

## 1. Core model — each Kind is the authority for caps on itself
1. **The target signs.** A capability authorizes an action on a Kind `K`. **`K` is the sole authority for caps on itself: `K` signs it and `K` verifies it, with `K`'s own key.** The signer of a cap is ALWAYS the target Kind (granter == target == verifier).
2. **Verify at the target, always local.** Verification happens where the action dispatches — at `K`, which holds its key. **No party other than `K` ever verifies a cap-on-`K`.** (This is what makes symmetric per-Kind keys sufficient and the whole model distribution-friendly.)
3. **Issuance is a cap-gated action on `K`.** To make `K` issue a cap to a grantee, the caller invokes the `K.grant` action presenting a valid **authority-cap-on-`K`**; `K` verifies that authority-cap (own key) exactly like any other action, then signs the new cap for the grantee. Issuing is not special-cased — it's an action on `K`, gated by a cap. **This dissolves v11's "authenticate the issuer" problem**: `K` just cap-checks the grant request; nothing global to authenticate.
4. **Authority chain rooted at admin.** The delegation reads `admin → Alice → Bob`, but every cap in the chain is signed by its target Kind. Example: admin causes `W` to sign "Alice manage W" (Alice holds it, W-signed); Alice presents it to invoke `W.grant(Bob, create_session)`; `W` verifies Alice's manage-W cap (W's key) and signs Bob's `create_session` cap. Recursion bottoms out at **admin**, the root every Kind is anchored to trust.
5. **A cap is anchored to `(Kind, Action)`, verified against an AUTHENTICATED presenter for externally-originated requests, and bound to the verifier-approved intent (v4 — Path A).** The ActionSet declares "this action requires a cap signed by this Kind, for this action." Verification is a **framework-owned pre-handler gate** in the dispatch pipeline (§2): before running a handler, the presented cap must be (a) signed by the **live target instance's** key (§3), (b) for this concrete `(instance, action)`, (c) bound to the **presenter**.
   - **Presenter authenticity at the external EDGE (v4 — lighter than v3's stamp-everything).** The authenticated principal is stamped at the ingress adapters — bearer-token auth in `api_v1_controller.ex:45-59,131-163` (which already *rejects* body-supplied identity via `reject_identity_inputs/2`, `:131-163`), the signed browser/session principal in `session_principal.ex:63-89`, and the PTY/channel adapters — into the dispatch envelope (a first-class field on `%Invocation{}`, the single convergence point below both `Cmd`→`Router` (`router.ex:151-170`) and direct `Invocation.dispatch/1`, `invocation.ex:118-142`). For an **externally-originated** request, `Kind.Runtime` reads the presenter **from that stamp, never from the caller-writable `ctx.caller`** (`cmd.ex:75-117`, `router.ex:151-170`). A stolen cap does not authorize its thief because the thief cannot forge the edge stamp naming the grantee. **Internal reviewed code is TRUSTED to pass a correct `ctx.caller`** (Path A): internal Kind→Kind dispatch and the framework facades do NOT carry a per-call framework-minted stamp — v3's "stamp all internal dispatch + reject any unstamped envelope" machinery is dropped as incoherent under a model that trusts internal code.
   - **Discriminator (external vs internal).** The edge stamp is the mark of external origin: an envelope bearing an edge-provenance stamp is externally-originated → Runtime MUST use the stamp for the presenter; an envelope with no edge stamp is internal → `ctx.caller` is trusted. The load-bearing obligation is therefore **completeness of the edge**: every external-influenced request must acquire the stamp at ingress, and every non-edge path that re-introduces an external-derived request into dispatch must re-mint the stamp locally from its own authenticated record. `ctx.caller` is retained only as a non-authoritative trace field on the trusted branch.
   - **Non-edge ingress inventory (v4 — each enumerated as a trusted-internal minter or routed through the edge), so strict-verify does not break them:**
     - **DeliveryOutbox replay** reconstructs an unstamped `%Invocation{}` on restart from a durable envelope (`cap/delivery_outbox/envelope.ex:68-100` `to_invocation` sets `ctx.caller: envelope.caller`; `cap/delivery_outbox.ex:258-265` `invocation_for_claim`). It MUST **re-mint provenance locally from its own durable, authenticated outbox record** — the row is the authority for the original presenter; it is a trusted framework minter, not an external edge.
     - **ExternalMirror worker** dispatches `Router.dispatch` from a Lifecycle hook carrying its **own** URI + inline caps (`external_mirror_worker.ex:861-915`: `caller: self_uri, caps: worker_subscribe_caps()`) — internal, trusted, self-URI caller.
     - **SessionTemplate in-handler write** (`behavior/template.ex:655-665` `dispatch_template_write` forwards `ctx`) — internal, trusted; `ctx` already carries the authenticated presenter from the originating dispatch.
     - **CLI direct-dispatch** builds `%Invocation{}` with a caller-supplied `caller` and calls `Invocation.dispatch/1` (`ezagent_cli/dispatch.ex:82-94,300-318`). The CLI is a first-party operator surface (reviewed, Path A) → trusted internal minter; if a CLI ever fronts an untrusted caller, it must route through an authenticating edge.
     - **`EntityCaps`/`Identity.absorb_cap` internal persistence** (`entity_caps.ex:140-154`, `caller: :vm_internal`) is a **trusted framework facade** under Path A — it keeps its internal-persistence classification (§5); no per-call stamp is required.
   - **Intent binding (v4 — closes the handler-supplied-shape hole).** When `K.grant` issues, signing binds to the `(target, action, grantee, bounds)` the **verifier approved** from the authenticated invocation — NEVER a handler-supplied arbitrary `cap_shape`. This matters because `post_handle/4` can replace the effect list AFTER the handler runs (`kind/runtime.ex:901-909`), so an issuance effect's payload is not trustworthy: the framework issuance path reconstructs the intent from the verified grant request, not from whatever `{:issue_cap, …}` payload survived post-handle (§8).

## 2. Retained invariants + the single framework verifier
- **Born signed** — every cap is minted only through the issuance chokepoint (`K.grant`), signed by `K`. The **only** exception is the one-time genesis transition (§5); nothing else mints a cap.
- **One strict predicate, fail-loud** — an unsigned / wrong-signer / wrong-`(instance,action)` / wrong-presenter cap is **rejected, fail-loud**. Shape-matching a cap without verifying its signature is forbidden. No dual-read, no `verify_for`, no default-off `require_signature` (`cap.ex:42-63,200-205`).
- **Presenter from the edge stamp for external requests (v4).** For an externally-originated `%Invocation{}` (bearing an edge-provenance stamp, §1 item 5), the verifier reads the presenter from the stamp, never from `ctx.caller`. Internal reviewed dispatch is trusted to carry a correct `ctx.caller`. The edge adapters are the authenticity boundary; the non-edge inventory (§1 item 5) guarantees no external-derived request reaches the verifier on the trusted branch unstamped. (v4 drops v3's "reject any unstamped envelope" — under Path A internal dispatch is legitimately unstamped and trusted.)
- **One framework-owned verifier that dominates every entrypoint.** The ActionSet macro declares only *immutable authorization metadata*; a single verifier in `Kind.Runtime` runs before **every** handler invocation and every state-mutating dispatch route (`kind/runtime.ex:148-150,340-365`) — no handler is reachable without it. This is the no-bypass core, and today's dispatch has explicit escape hatches that MUST be closed for any target-cap-gated action:
  - Delete the `cap_issued` grant shortcut and the rule-authorized grant/revoke shortcuts in `authz_check` (`kind/runtime.ex:340-361`); `K.grant` is **unconditionally** target-cap-gated (its authority-cap is verified like any other).
  - No **target-cap-gated** action may carry `cap_exempt_actions` (`behavior.ex` `cap_exempt_actions/0`; live examples `behavior/identity.ex:554`, `behavior/session.ex:326-329`), an `authorization_rule` allow, or ambient `:vm_internal` all-cap authority. The arch-gate (§10 property 2) forbids these FLAGS **only for target-cap-gated actions** — it does not delete them globally.
  - **Internal-only actions are RECLASSIFIED, not deleted, under a CLOSED static allowlist (v4).** The load-bearing exemptions stay: identity persistence (`absorb_cap`/`persist_caps`/`store_cap`/`remove_cap`, `behavior/identity.ex:554,609,620,640,656`) and session admission (`approve/deny/withdraw_admission`, in-handler `manages?/2`/`requested_by`, `behavior/session.ex:270-329`). The set of `internal-only` actions is a **closed static allowlist** (§10 property 2) so a cap-gated action cannot be relabeled `internal-only` to escape the flag rule. Under Path A they stay authorized by their trusted-internal facade (identity persistence) or by the in-handler authority check over the **edge-authenticated presenter** (session admission) — not by a forgeable `ctx.caller`, and needing no per-call framework stamp.
  - The signing/verifying primitive (`cap/signing.ex:121-132`) is reachable **only** from the framework signer path (§3); direct `:crypto`/`Signing` calls are arch-gated out of the Behavior/domain/plugin tiers (a ratchet, §10 property 3) — an accidental/review-missed call is caught, but this is not a runtime barrier against reviewed-admitted code (§ threat model).
- **No bypass** — the only paths are mint-via-`K.grant` (or the one genesis exception) and authorize-via-the-single-framework-verifier. An arch-gate + named runtime invariants (§10) — **not** a second cryptographic system — keep the mint/sign/authorize surface minimal; under Path A they are review aids that fail loud, sufficient given the reviewed-code precondition.

## 3. Keys & custody — private framework state + a ratchet, under Path A
- **The key is NEVER a Behavior-slice field.** codex round 1 falsified the "slice = isolation" premise: slices are cross-process-readable via `Kind.get_slice/2`/`get_raw_slice/2` (`slice_access.ex:54-112`), `Kind.Server` returns any requested slice key without authorization (`server.ex:526-533`), sibling-slice reads are injected straight into handler context (`behavior.ex:409-436`, `kind/runtime/context.ex:40-53`), and a durable field serializes into the full snapshot (`snapshot.ex:455-470`) which a system-scope query can enumerate (`ecto/kind_snapshot.ex:44-64`). A slice-resident key is readable by ordinary code and by any node sharing the Repo.
- **The key lives in private, non-slice `Kind.Server` state (v4 — simplified from v3's authority service).** codex confirmed `state.state` (the slice map generic reads index into, `server.ex:125-138,526-533`) is separable from a private top-level `Kind.Server` field: generic slice/sibling/raw reads only reach `state.state`, the snapshot serializer only serializes the slice map (`snapshot.ex:455-470`), and effect enrichment (`server.ex:603-616`) carries no key. So the key sits in a private top-level field that is **never** in a slice, snapshot, event, log, or admin listing (`ecto/kind_snapshot.ex:44-64`), and is **never** placed in `build_handler_ctx` (`kind/runtime.ex:801`). **DROP v3's separate authority-service / KMS requirement** — that is Path B; under Path A a private in-process field is the custody. There is **no handle** — the key never leaves framework state, so nothing (opaque or otherwise) is handed to Behavior code.
- **Signing stays a framework-internal op reached from exactly two sites.** `sign`/`verify` (`cap/signing.ex:121-132`) are reached only from (i) the framework verifier (`verify` for a dispatch it is about to authorize) and (ii) the post-verifier `K.grant` issuance step (`sign` for a grant the verifier already authorized with a valid authority-cap-on-`K`). **A Behavior handler never signs.** `K.grant`'s handler returns an **issuance intent** effect; the framework post-verifier path performs the `sign`, binding to the verifier's approved intent (§1 item 5 / §8) — so an attached Behavior emitting a raw `{:issue_cap, …}` gets no signature.
- **Arch-gate ratchet (v4 — the honest custody mechanism).** A static gate BANS, in the Behavior/domain/plugin tiers: the introspection primitives (`:sys.get_state`, `:sys.replace_state`, `:erlang.process_info` on framework PIDs, `:dbg`/tracing, direct ETS reads of key tables) AND direct `:crypto`/`Ezagent.Cap.Signing` calls (`cap/signing.ex:121-132`). **Stated honestly: this is a ratchet + review, not a cryptographic boundary.** It catches accidental and review-missed use (threats ① and ②); it does NOT stop code that review admitted from calling these primitives at runtime — nothing in one unsandboxed BEAM can. It is sufficient ONLY under the Path A reviewed-code precondition (§ threat model).
- **Symmetric is still correct** (sign == verify at `K`, which holds its own key); asymmetric would only help an off-`K` verifier, which does not exist here (§4).
- **Admin root = crown jewel.** `admin` is the root of trust. Every Kind, at creation, is anchored to trust the **canonical admin identity** — resolved from the single code authority `Ezagent.Entity.User.admin_uri/0` (`user.ex:30-32`) = `entity://system/user/admin`, **not** the literal `entity://admin` (a non-canonical URI lacking workspace/type/name, `uri.ex:420-428`). The anchor names the identity, not a specific admin key.
- **Identity-anchoring + key-versioning** (cheap future rotation): admin's key carries a version; Kinds trust the stable canonical identity. Rotating admin's key = version-bump + re-provision, **not** a fleet-wide re-anchor. Per-Kind keys rotate lazily / on-compromise (blast radius contained to one instance).
- **Residual (Path A).** The custody provides no boundary against unreviewed in-BEAM code (threat-model OUT-of-scope). Under the reviewed-code precondition the residual is bounded to review escapes + privileged BEAM introspection (`:sys.get_state`, tracing) of `K`'s live process — contained to one instance, ratcheted by the arch-gate, and hardened incrementally (restrict those BIFs in prod). The durable upgrade for unreviewed code is **Path B** (§ threat model). **No global-seed HSM requirement** — each Kind holds only its own key.

## 4. Distribution (friendly by construction — with the key-custody constraint)
- A cap is always verified at its target Kind's **owner runtime**. Today dispatch already requires the local runtime to own the target workspace (`invocation.ex:118-142`, `workspace_owner_gate.ex`, placement local-only `workspace_placement.ex`); remote routing (deferred, §7) must **forward the cap + the edge stamp to the authoritative owner runtime**, where the single local verifier runs. No cap-on-`K` is ever verified off-`K`; no key crosses the wire.
- **Blast-radius containment depends on §3.** The per-node claim only holds once keys are out of shared plaintext: a slice-resident key serializes into snapshots that a **system-scope query lists across all nodes** (`ecto/kind_snapshot.ex:44-64`) — so a shared-Repo node would NOT be limited to its own Kinds' keys. With §3's key in **private non-slice `Kind.Server` state** (never in snapshots), **node compromise is contained to that node's live Kinds**. Placement transfer must atomically transfer or rotate the key custody (it is private in-process state, not a copyable handle to move).
- Distribution then needs only ① remote transport/routing to the owner runtime and ② bootstrap root-anchoring — **neither is a cap-signing-model change**. This **unblocks** workspace-per-ECS, and is strictly better than v11's seed-on-every-node.

## 5. Bootstrap / genesis — one durable, append-only authority record (v4 correctness fix)
The tension codex flagged: `K.grant` requires a pre-existing authority-cap-on-`K`, but "born signed" says every cap comes from `K.grant` — so seeding an anchor is either a mint *outside* `K.grant` (breaks sole-mint) or circular. Resolution: **one explicit genesis exception, made durable and one-shot by an append-only authority record.**

- **codex round-3 correction (why v3's shape was wrong).** v3 said "emit the admin anchor as an effect, atomic with the CAS insert." That is NOT achievable: effects (deferred dispatches) run AFTER the slice durably commits, not in the same transaction (`server.ex:605-650` — `commit_and_notify` first, then `DeferredDispatch.enqueue(deferred)` "AFTER the parent slice durably committed"). And a bare uniqueness constraint is not irreversible — a row deletion permits a re-insert, so it does not seal.
- **The fix: a durable, append-only, non-deletable-by-runtime/plugin authority record.** A dedicated per-instance record (keyed by `K`'s instance URI) whose ONE winning `INSERT` holds, in one row committed in one transaction: **{the committed per-Kind key, the ONE `K`-signed canonical-admin anchor naming `Ezagent.Entity.User.admin_uri/0` (= `entity://system/user/admin`, `user.ex:32`; not the literal `entity://admin`, `uri.ex:420-428`), the key version, the seal flag}**. The anchor is not emitted as a fire-and-forget effect — it is **produced and stored inside the same INSERT**, so genesis is not "sealed" until the usable anchor is durably committed in that row. Runtime/plugin code has **no delete path** to the record (revoke/GC operate on caps, not this table); only an explicit admin-scoped operation can touch it. Any concurrent or later genesis attempt loses the insert and is rejected fail-loud.
  - **Why a new record, not `ever_created` (honesty).** `ever_created` (`snapshot.ex:465-490`, `ecto/kind_snapshot.ex:89-119`) is the right *same-commit atomic-marker discipline*, but it is a boolean on the **snapshot row**, and §3 forbids the key from living in the snapshot. The authority record IS the key's custody store, its winning INSERT + append-only/non-deletable property IS the seal (a reversible uniqueness constraint alone is not).
- **How admin loads the anchor.** The admin anchor is **retrieved FROM that row**, not from a slice or a cap store: at boot / on demand the framework reads `K`'s authority record and presents the stored `K`-signed anchor as admin's authority-cap-on-`K`. There is no separate "seed the anchor into a slice" step; the row IS the anchor's home and the read path.
- **Bootstrap admin FIRST (chicken-egg).** Admin's own **immutable self-row** is written FIRST, with **no verifier** (admin is the root; there is no prior authority to check). Only then do other Kind rows genesis, each anchoring to the already-committed canonical admin identity. This avoids the circular "K needs admin, admin needs a verifier" dependency; root bottoms out at admin trusting itself, non-circular because the record is a one-shot durable state change, not a cap-check.
- **URI reincarnation (Kind delete/recreate).** Because the record is append-only and non-deletable-by-runtime, a Kind deleted then recreated at the same instance URI would collide with the sealed row. Semantics: a recreated Kind at a reused URI is a **new incarnation** carrying an incarnation/generation component (so its authority record is distinct), OR the recreate is an **explicit admin re-genesis operation** that supersedes the prior row under audit. A plugin/runtime path can **never** silently re-genesis a URI; re-genesis is admin-scoped and recorded, so a reused URI cannot resurrect an old key or silently re-anchor.
- **Delete + arch-gate** every `{:genesis, arbitrary_uri}` authorization form (`cap.ex:24-27,172,227-229`). No caller may supply a root identity; the canonical admin URI comes from the single code authority `admin_uri/0`, never a passed argument. No key is ever passed as a plain argument.
- **Internal-only actions authenticated under Path A (not deleted).** Two exemption families are load-bearing and stay under the **closed internal-only allowlist** (§10 property 2):
  - **Identity persistence** (`absorb_cap`/`persist_caps`/`store_cap`/`remove_cap`) is cap-exempt (`cap_exempt_actions/0`, `behavior/identity.ex:554`) and today `:vm_internal`-gated per handler (`identity.ex:609,620,640,656`), dispatched by `Ezagent.EntityCaps.dispatch_mutation/3` (`entity_caps.ex:140-154`) and `Ezagent.Identity.absorb_cap/2`. Under Path A these facades are **trusted framework minters**; the classification stays and no per-call framework stamp is required.
  - **Session admission** (`approve/deny/withdraw_admission`) is cap-exempt and authorized **in-handler** by `Authority.manages?/2`/`requested_by` because the member's owner holds no session cap (`behavior/session.ex:270-329`). It keeps its in-handler authority check, now over the **edge-authenticated presenter** — the manager's identity comes from the edge stamp, not a forgeable `ctx.caller`.
  - The §10 arch-gate therefore forbids the bypass **flags** (`cap_exempt_actions`, `cap_issued`, `authorization_rule`, `:vm_internal`) **only for target-cap-gated actions**; the internal-only set is a closed allowlist so nothing new can hide behind it.

## 6. Cutover (ezagent-deploy scope)
Self-use, disposable data → **wipe + reseed**: quiesce → wipe cap-bearing data → deploy the new build → seed (admin first, then Kinds each get a fresh key + admin anchor; all caps re-issued signed) → resume. **No app-side migration/backfill code.**

## 7. Non-goals
- **Cap-storage consistency** (a cap in multiple homes, revoke-clears-all) — separate concern.
- **Full distributed transport** — the model SUPPORTS distribution; the routing/bootstrap-anchoring *implementation* is a separate track (deferred). The design must not preclude it (§4).
- Opaque cap representation — not needed here (verify is local at the target with its key, not a global boundary).

## 8. Implementation shape (high-level)
- **Per-instance key in private `Kind.Server` state** (§3): key generated at genesis into a **private top-level `Kind.Server` field** (sibling to the slice map `state.state`, `server.ex:125-138`); never a slice field, never in snapshots/events/logs/admin-listings (`snapshot.ex:455-470`, `ecto/kind_snapshot.ex:44-64`), never placed in `build_handler_ctx` (`kind/runtime.ex:801`). **No authority service / KMS — that is Path B.** No handle exists.
- **`sign` / `verify` as framework operations** (`cap/signing.ex:121-132`) — reached from exactly two framework sites (the verifier; the post-verifier `K.grant` issuance step). Direct `:crypto`/`Ezagent.Cap.Signing` + the introspection primitives are arch-gated out of Behavior/domain/plugin tiers (a ratchet + review, §10 property 3 — not a runtime barrier).
- **The framework verifier** — the ActionSet macro declares immutable metadata; one `Kind.Runtime` verifier dominates every handler/state-mutating route (§2, `kind/runtime.ex:148-150,340-365`). For an **externally-originated** envelope it reads the presenter from the edge stamp (not `ctx.caller`); internal reviewed dispatch is trusted to carry a correct `ctx.caller`. It then compares the signed concrete `(instance, action, grantee)` against the live dispatch. Verify or fail-loud.
- **Presenter stamp at the external edge only** — a first-class `%Invocation{}` field stamped by the enumerated ingress adapters (`api_v1_controller.ex:45-59,131-163`; `session_principal.ex:63-89`; PTY/channel). Internal reviewed dispatch carries no per-call stamp (Path A); the **non-edge inventory** (§1 item 5) enumerates each trusted-internal minter: DeliveryOutbox re-mint from its durable record (`cap/delivery_outbox/envelope.ex:68-100`, `cap/delivery_outbox.ex:258-265`), ExternalMirror self-URI (`external_mirror_worker.ex:861-915`), SessionTemplate ctx-forward (`behavior/template.ex:655-665`), CLI (`ezagent_cli/dispatch.ex:82-94,300-318`), and the EntityCaps/Identity facades (`entity_caps.ex:140-154`).
- **`K.grant` action** — unconditionally cap-gated (requires an authority-cap-on-`K`); the handler returns an **issuance intent** effect, and the framework post-verifier issuance path performs `sign`, **binding to the verifier-approved `(target, action, grantee, bounds)`** reconstructed from the authenticated invocation — NEVER a handler-supplied `cap_shape`, because `post_handle/4` can replace the effect list after the handler runs (`kind/runtime.ex:901-909`). The handler never holds the key. Issuance = this one action, uniformly; no `cap_issued`/rule shortcut.
- **Genesis authority record** (§5) — a durable, **append-only, non-deletable-by-runtime** per-instance record; one winning INSERT stores {key, one `admin_uri/0`-signed anchor, key version, seal} in one transaction; **admin self-row first**; anchor read FROM the row; re-genesis is admin-scoped (URI reincarnation).
- **Reclassify (not delete) internal-only actions under a closed allowlist** (§10 property 2) — identity persistence + session admission stay exempt as trusted facades / in-handler checks over the authenticated presenter; the bypass flags are gated off only for target-cap-gated actions.
- **Delete**: dual-read / `require_signature` default-off (`cap.ex:42-63,200-205`) / `verify_for` / the central-seed `sign_artifact` keypair-from-`granted_by` derivation (`cap.ex:213-220`) + v11's public-keyring machinery / `{:genesis, URI}` (`cap.ex:24-27,172,227-229`) / the `authz_check` `cap_issued`·rule·`:vm_internal` bypasses **for target-cap-gated actions** (`kind/runtime.ex:340-361`).

## 9. Behavioral tests (the X holes, closed — each an INDEPENDENT assertion)
Per representative cap-gated action (session.send, create_session, PTY read, kanban write, world read_unfiltered…), each vector is its own test proving the attempt reached the authorization boundary and was rejected:
- **Forge** — an unsigned cap is rejected fail-loud.
- **Tamper** — a cap whose fields were mutated after signing is rejected.
- **Retarget** — a cap signed for a different instance/Kind is rejected under the live target's own key; cap-controlled `key_id` cannot select another Kind's key.
- **Stolen-cap + spoofed-presenter (external)** — a valid cap presented through an external ingress by a caller spoofing the grantee's URI via `ctx.caller` is rejected, because for externally-originated requests presenter identity comes from the edge stamp, not `ctx.caller` (§1 item 5).
- **Wrong-target-key** — verification uses the live target's own key (from private `Kind.Server` state), not one selected by the cap.
- **Issuer-impersonation** — `K.grant` rejects a caller lacking a valid authority-cap-on-`K`; recursion to the canonical admin root is exercised and proven non-circular.
- **Intent-binding** — a handler/`post_handle` that replaces the issuance effect's shape (`kind/runtime.ex:901-909`) cannot cause a cap outside the verifier-approved `(target, action, grantee, bounds)` to be signed.
- **Genesis** — the one-time transition anchors each `K` to `admin_uri/0` and stores the usable anchor in the durable record; re-genesis collides/loses and is rejected (sealed); strict verify holds end-to-end on a freshly seeded stack; a reused URI does not resurrect an old key.
- **Key egress** — generic slice read, sibling read, raw read, snapshot, event, and admin-listing of `K` return **no key material at all** — the key lives in private framework state and never leaves; there is **no handle** (v4 corrects v3's "opaque handle" wording).
- **Legit** — a properly `K.grant`-minted cap, presented by the authenticated grantee, is accepted.

## 10. Gate plan (this is a first-class deliverable, not just tests)
Two enforcement layers, following the ezagent static-gate discipline (`check_invariants` → `ci.local` full-suite; run pre-push):

**A. Completion / invariant gate — behavioral, fail-when-the-goal-is-unmet.** The §9 vectors as **independent** `/goal`-style assertions on a freshly seeded stack (each proves the attempt reached the authorization boundary, not a shared monolith): forge, tamper, retarget, stolen-cap+spoofed-presenter, wrong-target-key, issuer-impersonation, intent-binding, genesis-seal, key-egress rejected; legit accepted. The forge/tamper/retarget cases **fail on today's `origin/main`** (dispatch authorizes via structural match without `Cap.verify`, `authorization.ex:6-18`, `kind/runtime.ex:539-545`; `require_signature` default-off, `cap.ex:42-63`) — that red proves each gates a real hole. (The positive `K.grant` path does not exist on `origin/main` yet, so the suite lands with the implementation, not before it.)

**B. Structural arch-gate — HONEST split.** A static grep/AST gate can prove a *syntactic absence* (a flag is not present, a symbol is referenced only in allowed files, a declaration exists) but CANNOT statically prove a *semantic / information-flow / one-shot* property. So each property is classified as **STATIC** (the gate's grep/AST IS the guarantee) or **RATCHET + RUNTIME** (the grep/AST is a shrink-only ratchet, but the security guarantee is owned by a named runtime instrumentation assertion or an independent behavioral test from §9). Only #2 and #4 are genuinely static; the rest are ratchet+runtime. **Under Path A, even the STATIC gates are review aids** — they catch accidental and review-missed violations (threats ① and ②), not a determined actor running unreviewed code in-BEAM (§ threat model, out of scope).

| # | Property | Class | What the STATIC ratchet checks | Who OWNS the guarantee (runtime invariant / behavioral test) |
|---|----------|-------|--------------------------------|-------------------------------------------------------------|
| 1 | **Verifier dominance** | ratchet + runtime | no dispatch route reaches a handler except through `Kind.Runtime.handle_dispatch`; call-graph has one authz decision site | **Runtime invariant:** a telemetry/instrumentation assertion that every executed handler was preceded by a verifier decision for the same `(instance, action)` (no handler-run event without a matching authz event). Reachability ≠ dominance-in-fact. |
| 2 | **No bypass flags + closed internal-only allowlist** | **STATIC** | no **target-cap-gated** action carries `cap_exempt_actions`/`cap_issued`/`authorization_rule`/`:vm_internal`; the `cap_issued`+rule shortcuts are deleted from `authz_check` (`kind/runtime.ex:340-361`); the set of actions classified **internal-only** is a **closed static allowlist** (identity persistence + session admission only, §5) — so a cap-gated action cannot be relabeled `internal-only` to escape the flag rule | (self-enforcing: syntactic absence + fixed allowlist IS the property) |
| 3 | **Sign/verify + introspection confinement (named grep-ratchet)** | ratchet + runtime | `:crypto`/`Ezagent.Cap.Signing` AND the introspection primitives (`:sys.get_state`/`:sys.replace_state`/`:erlang.process_info` on framework PIDs/`:dbg`/tracing/direct key-table ETS reads) referenced ONLY in the framework signer path; **zero refs in the Behavior/domain/plugin tiers** | **Behavioral test + review:** the §9 *retarget* + *wrong-target-key* + *key-egress* vectors — an attached Behavior attempting to sign/verify off-`K` is rejected. Static can't prove `apply/3` never reaches it and CANNOT stop reviewed-admitted code; the grep is a ratchet + review aid under Path A, the test proves the operation is refused at runtime. |
| 4 | **Declaration parity** | **STATIC** | every cap-gated action declares its cap requirement — leverages the existing required-cap coverage check (`behavior.ex` `required_caps/0` vs actions; `keys(required_caps) ∪ cap_exempt_actions == actions`) | (self-enforcing: declaration coverage IS the property) |
| 5 | **Key egress absence** | ratchet + runtime | the key field name appears in no slice schema, snapshot serializer, event, log, or admin-listing path | **Behavioral test:** the §9 *key-egress* vector — generic slice read / sibling read / raw read / snapshot / event / admin-listing of `K` returns **no key material** (private framework state; no handle). Information-flow (does *some* value alias the key?) is not statically decidable; the test exercises the actual egress boundaries (`server.ex:526-533`, `snapshot.ex:455-470`, `ecto/kind_snapshot.ex:44-64`). |
| 6 | **Presenter authenticity (external edge)** | ratchet + runtime | no path lets `ctx.caller` stand in for the presenter of an **externally-originated** request; the edge stamp is minted only at the enumerated ingress adapters | **Runtime invariant + behavioral test:** Runtime asserts every externally-originated `%Invocation{}` reaching authz carries an edge stamp (else reject) and reads the presenter from it; the §9 *stolen-cap + spoofed-presenter* vector proves a forged `ctx.caller` cannot authorize an external request. Internal dispatch is trusted (Path A), so this is edge-completeness + runtime-reject, **not cryptographic** — not a static proof. |
| 7 | **Unique target-key binding** | ratchet + runtime | no cap-controlled `key_id` selects the verifying key (`cap/signing.ex` `key_id`); verify always uses the live target's own key from private `Kind.Server` state | **Behavioral test:** the §9 *retarget* + *wrong-target-key* vectors — a cap signed for another instance/Kind, or carrying a chosen `key_id`, is rejected under the live target's own key. |
| 8 | **Genesis one-shot** | ratchet + runtime | every `{:genesis, URI}` authorization form removed (`cap.ex:24-27,172,227-229`); admin URI sourced from `admin_uri/0`, never an argument | **Behavioral test:** the §9 *genesis* vector — the authority record commits exactly once (append-only, non-deletable-by-runtime), re-genesis collides/loses and is rejected. One-shot-ness is a runtime state property, not statically provable. |

**Honest enforceability limit (v4 / Path A).** Only properties **2 and 4** are statically proven; **1, 3, 5, 6, 7, 8** are static *ratchets* whose security guarantee is a named runtime invariant or a §9 behavioral test — this spec does **not** claim static proof of any semantic (verifier-dominance-in-fact), information-flow (key non-egress), authenticity (presenter/edge), or one-shot (genesis) property. **And under Path A even the static ratchets are review aids**: they catch accidental and review-missed violations (threats ① and ②), not a determined actor running unreviewed code in-BEAM, which is out of scope (§ threat model). Caps remain public Elixir structs, so discovering arbitrary semantic field reads stays best-effort AST. Collapsing verification to ONE framework verifier, minting to ONE `K.grant`, presenter to the external edge, and custody to private framework state keeps both the scan surface and the runtime-assertion surface minimal — but the guarantee lives at runtime and at review, and §10 says so plainly. The cryptographic boundary against unreviewed in-BEAM code is **Path B** (§ threat model), not this spec.

## 11. Open (residual sub-mechanism only — the architecture is Path A)
The v4 architecture is settled: private-state key custody + grep-ratchet (§3), edge-only presenter stamp with the non-edge inventory (§1 item 5), append-only genesis authority record (§5), intent-binding at issuance (§1 item 5 / §8). What remains is sub-mechanism inside those choices:
- **Key-custody field form** — the exact private top-level `Kind.Server` field vs a scoped keystore process co-owned by the framework (both are private in-process state, NOT the Path B authority service); the symmetric primitive (HMAC vs a symmetric AEAD/MAC).
- **Edge-stamp representation** — the exact term/encoding of the provenance field on `%Invocation{}` and the precise point in `handle_dispatch` where Runtime reads it for external requests (relative to `authz_check`, `kind/runtime.ex:148-150`). (The *carrier, edge mint-points, and internal-trusted branch* are closed.)
- **Genesis-record shape** — the append-only authority record's schema, the non-deletable-by-runtime guarantee (table permissions / no runtime delete path), the seal + key-version columns, the anchor-read path, and the incarnation/generation component for URI reuse.
- **admin-root key custody + version scheme; bootstrap sequencing** — admin self-row before any Kind anchors (§5).
- **Migration bookkeeping** — enumerating today's `{:genesis, URI}` (`cap.ex:24-27,172,227-229`) and bypass-flag call-sites to delete, and the exact edge-adapter stamp-write + DeliveryOutbox re-mint edits (§1 item 5 inventory).
- **Path B trigger** — the criterion (unreviewed third-party code admitted in-BEAM) that promotes the roadmapped Path B isolated-signer design (§ threat model) from deferred to active; not needed while the reviewed-code precondition holds.
