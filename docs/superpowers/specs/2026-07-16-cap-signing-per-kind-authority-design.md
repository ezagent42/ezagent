## Threat model (Path A — first-party / reviewed-code) — SETTLED (rounds 1–4)
**Precondition (load-bearing).** Every module loaded into the BEAM — core framework, domain, and third-party plugins/socialware — passes review before load. There is no sandbox: one unsandboxed BEAM shares process memory, `:sys`/tracing, ETS, and the code server across all loaded code, so we do **not** claim a cryptographic boundary against code already running in the VM. Cap-signing here hardens the *first-party* system against bugs and review escapes, not against a determined in-VM adversary.

**Cap-signing under Path A defends against:**
- ① **Accidental forgery** — a bug that mis-signs, mis-targets, or emits an unsigned cap; a soft-verify path that accepts unsigned/unverified caps (`require_signature` default-off, `cap.ex:42-63`). Strict verify + born-signed make these fail loud instead of silently escalating.
- ② **Architecture-violating code that review missed** — a Behavior/plugin/adapter that, through a bug or an oversight review didn't catch, reaches a signing or authorization path it shouldn't, OR **a review-missed external ingress that fails to stamp provenance**. The single framework verifier + confined sign surface + the arch-gate ratchets (§10) catch the syntactically-detectable classes; the **fail-closed provenance reject (v5 §1 item 5)** turns a review-missed unstamped ingress into an OUTAGE, not a silent promotion to trusted-internal.
- ③ **External-ingress caller spoofing** — an external caller presenting a stolen cap while claiming to be the grantee via caller-writable `ctx.caller` (`cmd.ex:49-66,84-116`, `router.ex:151-170`). Standard session/bearer auth at the edge defeats this (§1 item 5): the presenter is the ingress-authenticated identity, never `ctx.caller` — the thief cannot make the edge authenticate as the grantee.

**Explicitly OUT of scope (honest limit).** A **malicious untrusted actor running unreviewed code inside the BEAM.** Such code can read any live process's key via `:sys.get_state`/tracing, call `:crypto`/`Ezagent.Cap.Signing` directly (`cap/signing.ex:121-132`), or reach the signing path through `apply/3` (`kind/runtime.ex:816,843`) — none of which any in-process construct can prevent in one unsandboxed VM. This aligns with the documented Phase-3 stance: *"a malicious in-VM actor is out of scope; the `:vm_internal` trust model already trusts all in-VM code"* (`capbac.md §4.5`, lines 261-262). v4 made the reviewed-code ASSUMPTION explicit as the precondition that makes that stance sound; v5 keeps it unchanged.

**Path B (roadmapped upgrade).** If/when unreviewed third-party code must run in-BEAM, the reviewed-code precondition breaks and Path A's custody provides no boundary. The upgrade is a **separate protected signing runtime** — the revival of the v11 isolated-signer design (`2026-07-15-cap-signing-strict-capstore-design.md`: central isolated signer + public keyring + global issuer-authentication). That spec is **not retired**; it is the Path B design of record.

## 0. The X problem (unchanged)
Capabilities are **forgeable / tamperable / retargetable** under soft verification (dual-read accepts unsigned) → privilege-escalation / credential-theft. **Close it**: every cap signed and strictly verified; unproven authority rejected.

## 1. Core model — each Kind is the authority for caps on itself
1. **The target signs.** A capability authorizes an action on a Kind `K`. **`K` is the sole authority for caps on itself: `K` signs it and `K` verifies it, with `K`'s own key.** The signer of a cap is ALWAYS the target Kind (granter == target == verifier).
2. **Verify at the target, always local.** Verification happens where the action dispatches — at `K`, which holds its key. **No party other than `K` ever verifies a cap-on-`K`.** (This is what makes symmetric per-Kind keys sufficient and the whole model distribution-friendly.)
3. **Issuance is a cap-gated action on `K`.** To make `K` issue a cap to a grantee, the caller invokes the `K.grant` action presenting a valid **authority-cap-on-`K`**; `K` verifies that authority-cap (own key) exactly like any other action, then signs the new cap for the grantee. Issuing is not special-cased — it's an action on `K`, gated by a cap. **This dissolves v11's "authenticate the issuer" problem**: `K` just cap-checks the grant request; nothing global to authenticate.
4. **Authority chain rooted at admin.** The delegation reads `admin → Alice → Bob`, but every cap in the chain is signed by its target Kind. Example: admin causes `W` to sign "Alice manage W" (Alice holds it, W-signed); Alice presents it to invoke `W.grant(Bob, create_session)`; `W` verifies Alice's manage-W cap (W's key) and signs Bob's `create_session` cap. Recursion bottoms out at **admin**, the root every Kind is anchored to trust.
5. **A cap is anchored to `(Kind, Action)`, verified against an AUTHENTICATED presenter carried in EXPLICIT envelope provenance, and bound to the verifier-approved intent (v5 — fail-closed).** The ActionSet declares "this action requires a cap signed by this Kind, for this action." Verification is a **framework-owned pre-handler gate** in the dispatch pipeline (§2): before running a handler, the presented cap must be (a) signed by the **live target instance's** key (§3), (b) for this concrete `(instance, action)`, (c) bound to the **presenter**.
   - **Standard-web-auth identity + a LIGHT provenance guard, fail-closed (v5, reverses v4's fail-open default).** The identity itself is derived the standard Phoenix way — from the **authenticated session/bearer** (`conn.assigns`/socket assigns), NEVER from client params. The provenance field is NOT a cryptographic/sealed ticket; it is a **light boolean/enum `origin`** on **both** `%Cmd{}` (`cmd.ex:49-66` defstruct + ctx type; `cmd.ex:84-116` `new/4`, which already raises if `ctx.caller` is absent — #154 "no implicit caller default") **and** `%Invocation{}` (`invocation.ex:81-89` defstruct + type; the single dispatch convergence point `invocation.ex:121-142`). It takes exactly three states (two positive values + unstamped):
     - **`authenticated-external`** — set at an ingress adapter whose caller is **already derived from the authenticated session/bearer** (not client-supplied). The complete edge (v5 completes the inventory), each of which ALREADY authenticates correctly today and now must ALSO set this flag: bearer-token API v1 (`api_v1_controller.ex:131-163` — authenticates via `Ezagent.Authentication.authenticate/1`, *rejects* body/header-supplied identity via `reject_identity_inputs/2`), the signed browser/session principal (`session_principal.ex:80-89`, `put/3` minting `:current_entity_uri`), the PTY/channel adapters, **and the two doors v4 missed** — `POST /v1/chat/completions` (`chat_completions_plug.ex:51-61` authenticates via `ApiKeyStore.verify/1`, then dispatches cap-gated actions building `%Ezagent.Cmd{}` at `:185-196` and `%Invocation{}` at `:253-263`) and `POST /world/uploads` (`world_uploads_controller.ex:55-65` derives caller from `conn.assigns[:current_entity_uri]`, then dispatches `:session :attach` via `%Invocation{}` at `:119-134`). Both currently authenticate but do NOT set the flag; under v5 they MUST. **v6 completes the inventory** with three more external doors codex round 5 found reaching a direct `%Invocation{}`: `/api/session-config` (bearer-authenticated `session_config_controller.ex:19-45` → `session_config/executor.ex:100-119`) and **inbound email** (`email/inbound/authority.ex:29-37` authenticates the record → `email/inbound.ex:164-185`) — both authenticate today and now MUST set `authenticated-external`; and **⚠ the Feishu webhook, which is network-UNAUTHENTICATED today** (`plugin_feishu/webhook_plug.ex:20-25` accepts payload sender data `:53-55,69-89`; `sender_resolver.ex:39-73` resolves the supplied `open_id` to a bound user and loads THAT user's caps; `inbound_dispatcher.ex:280-300` dispatches `session.send` AS that user) — i.e. a **live caller-impersonation vector on `origin/main`**. Feishu MUST authenticate its transport (Feishu signature/secret verification) BEFORE it may set `authenticated-external`; until it does, its envelopes stay unstamped → **rejected**. It may NEVER be `trusted-internal`. *(This is also a standalone production security fix, tracked separately from the cap-signing cutover.)* **v7 refinement — the two Feishu ingresses are distinct and must be classified SEPARATELY** even though both funnel through the same `InboundDispatcher` (`inbound_dispatcher.ex:280-300`): (a) the **HTTP webhook** (`webhook_plug.ex`) is network-unauthenticated → stays **unstamped/rejected** until it verifies the Feishu signature; (b) the **WSS ingress** (`ws_client.ex` + `priv/ws_sidecar/main.js` — an SDK long-connection opened with the Feishu app id/secret) IS transport-authenticated and may set `authenticated-external`. Therefore the transport provenance must be passed **into** `InboundDispatcher` (per-ingress), NOT stamped unconditionally inside it — otherwise the shared constructor would either bless the unauthenticated webhook or wrongly reject the authenticated WSS path.

- **Ingress-completeness is a BUILD-GATE obligation, not a prose enumeration (v7).** Each codex round found one more external `%Cmd{}`/`%Invocation{}` constructor (chat_completions, world/uploads → session-config, email, Feishu-HTTP → Feishu-WSS) — proving prose cannot exhaustively enumerate ingresses. So completeness is enforced at build time: the §10 arch-gate **enumerates every `Router.dispatch/1`/`Invocation.dispatch/1` call site and every `%Cmd{}`/`%Invocation{}` constructor, and fails the build if any does not set a positive `origin`** (external adapters → `authenticated-external` only after authenticating; internal minters → `trusted-internal`). The spec's inventory below is the *current known* set (seed for the gate + the migration checklist); the gate — not this list — is what guarantees no ingress is missed. This dissolves the round-over-round "one more edge" whack-a-mole: a newly-added ingress that forgets to classify `origin` fails the gate (build red), the fail-closed reject catches any that slip to runtime as an outage.
     - **`trusted-internal`** — set **ONLY by the internal constructors/minters** in the non-edge inventory below (structurally a closed set). A *positive* value, NOT the absence of a flag.
     - **UNSTAMPED (no `origin`)** — **REJECTED, fail-loud, BEFORE capability verification.** Under Path A this reject is a **review/architecture ratchet**: a *future* edge that forgets to authenticate, or a minter that forgets to set `origin`, becomes an **OUTAGE** (caught in test/integration), NOT a privilege escalation. It is not malicious-BEAM resistance (§ threat model).
   - **How external `%Cmd{}` provenance reaches the verifier.** An external adapter sets `origin: :authenticated-external` on its `%Cmd{}`; `Router.to_invocation/1` preserves it into the `%Invocation{}` alongside its existing `ctx` preservation (`router.ex:151-170` `Map.put_new`, which never overwrites caller/caps); adapters that build `%Invocation{}` directly (`invocation.ex:121-142`) set it directly.
   - **Presenter carrier (v6 — pinned to resolve the round-5 contradiction).** There is NO separate presenter field; the carrier is `ctx.caller`, and its *authority* derives from WHO wrote it, gated by `origin`: at an `authenticated-external` edge the adapter **OVERWRITES `ctx.caller` from the authenticated session/bearer principal** (server-written, never the client's claimed value — `api_v1_controller.ex` `reject_identity_inputs/2` already discards client-supplied identity), so once the verifier confirms `origin = authenticated-external` that server-written `ctx.caller` **IS the authoritative presenter**. A stolen cap does not authorize its thief because the thief cannot make the edge authenticate *as* the grantee. For a `trusted-internal` envelope `ctx.caller` is likewise trusted (Path A: internal reviewed code passes a correct caller). For an **unstamped** envelope `ctx.caller` is never consulted — the envelope is rejected first (§1 item 5). (No cryptographic ticket; the guarantee is "the edge wrote it from an authenticated source," enforced by the standard web auth the edges already do.)
   - **Discriminator (v5 — positive `origin`, not flag-absence).** The load-bearing obligation is **completeness of authentication**: every external edge authenticates + sets `authenticated-external`; every internal constructor sets `trusted-internal`; anything else is unstamped and rejected. This is v3's reject-unstamped, refined to a light both-envelope boolean rather than inferring internal-ness from the absence of an edge stamp (v4's fail-open hole) — and it leans on the standard web-auth the edges already do, not a new crypto protocol.
   - **Non-edge ingress inventory (v5 — each a `trusted-internal` MINTER in the closed allowlist, or routed through the edge), so strict-verify does not break them:**
     - **DeliveryOutbox replay.** On restart it reconstructs an `%Invocation{}` from a durable envelope (`cap/delivery_outbox/envelope.ex:35-49` `encode/1` serializes `caller`; `:68-100` `to_invocation/2` reconstructs `ctx.caller = envelope.caller`; `cap/delivery_outbox.ex:202-220` `dispatch_claimed/2` → `:258-265` `invocation_for_claim/2`, which on cold replay `nil` calls `Envelope.decode` + `to_invocation`). **v5 change:** the durable record persists the **authenticated presenter** (the original authenticated principal) as its authoritative field — NOT a bare `ctx.caller` — and replay **re-mints `trusted-internal` provenance locally from that durable, authenticated record**. The row is the authority for the original presenter; it is a trusted framework minter, not an external edge.
     - **ExternalMirror worker** dispatches `Router.dispatch` from a Lifecycle hook carrying its **own** URI + inline caps (`external_mirror_worker.ex:861-915`: `caller: self_uri, caps: worker_subscribe_caps()`) — `trusted-internal` minter, self-URI caller.
     - **SessionTemplate in-handler write** (`behavior/template.ex:655-665` `dispatch_template_write` forwards `ctx`) — inherits the originating envelope's provenance (the `ctx` already carries the authenticated presenter from the originating dispatch).
     - **CLI direct-dispatch** builds `%Invocation{}` with a caller-supplied `caller` and calls `Invocation.dispatch/1` (`ezagent_cli/dispatch.ex:82-94,300-318`). The CLI is a first-party operator surface (reviewed, Path A) → `trusted-internal` minter; if a CLI ever fronts an untrusted caller, it must route through an authenticating edge.
     - **`EntityCaps`/`Identity.absorb_cap` internal persistence** (`entity_caps.ex:140-154`, `caller: :vm_internal`) is a **trusted framework facade** → `trusted-internal` minter; it keeps its internal-persistence classification (§5).
   - **Intent binding — freeze BEFORE hooks (v5 fix 4).** When `K.grant` issues, signing binds to the `(target, action, grantee, bounds)` **frozen at framework validation time, BEFORE any handler hook runs** — NOT `effective_args` (which `pre_handle` can rewrite, `runtime.ex:801-848`) and NOT a returned effect (which `post_handle` can replace, `runtime.ex:901-909`). Authorization and validation precede the handler (`runtime.ex:142-153`); the frozen validated grant intent captured there is the sole signing input (§8).

## 2. Retained invariants + the single framework verifier
- **Born signed** — every cap is minted only through the issuance chokepoint (`K.grant`), signed by `K`. The **only** exception is the one-time genesis transition (§5); nothing else mints a cap.
- **One strict predicate, fail-loud** — an unsigned / wrong-signer / wrong-`(instance,action)` / wrong-presenter cap is **rejected, fail-loud**. Shape-matching a cap without verifying its signature is forbidden. No dual-read, no `verify_for`, no default-off `require_signature` (`cap.ex:42-63,200-205`).
- **Presenter from the session-authenticated identity + a light `origin` guard, fail-closed (v5).** Every dispatch envelope carries a light `origin` boolean/enum (§1 item 5). `authenticated-external` → the verifier reads the presenter from the **server-written `ctx.caller`** (the edge overwrote it from the ingress-authenticated session/bearer identity, discarding any client-supplied value — §1 item 5); never a *client-supplied* caller. `trusted-internal` → `ctx.caller` is trusted. **Unstamped → REJECT before capability verification** (v5 restores v3's reject-unstamped, reversing v4's "trust unstamped as internal" default). Identity-spoofing prevention is standard web auth the edges already do; the `origin` guard's only job is to make a *future* un-authenticated edge fail loud. The non-edge inventory (§1 item 5) guarantees every internal path sets a positive `origin`.
- **One framework-owned verifier that dominates every entrypoint.** The ActionSet macro declares only *immutable authorization metadata*; a single verifier in `Kind.Runtime` runs before **every** handler invocation and every state-mutating dispatch route (`kind/runtime.ex:142-153` — `authz_check` precedes the handler in the `with` chain) — no handler is reachable without it. This is the no-bypass core, and today's dispatch has explicit escape hatches that MUST be closed for any target-cap-gated action:
  - Delete the `cap_issued` grant shortcut and the rule-authorized grant/revoke shortcuts in `authz_check` (`kind/runtime.ex:340-361`); `K.grant` is **unconditionally** target-cap-gated (its authority-cap is verified like any other).
  - No **target-cap-gated** action may carry `cap_exempt_actions` (`behavior.ex` `cap_exempt_actions/0`; live examples `behavior/identity.ex:119,554`, `behavior/session.ex:328-329`), an `authorization_rule` allow, or ambient `:vm_internal` all-cap authority (the `:vm_internal` short-circuit is NOT in the `authz_check` head at `340-361` — it lives deeper in `default_holds_cap?(:vm_internal, …)` ~`kind/runtime.ex:530` and `workspace_of_caller(:vm_internal), do: :any` `kind/runtime.ex:678`; the gate must reach all three sites). The arch-gate (§10 property 2) forbids these FLAGS **only for target-cap-gated actions** — it does not delete them globally.
  - **Non-cap actions become a STRUCTURAL class, not a flag on cap-gated actions (v5 — preferred end state; §10 property 2).** Today the `cap_exempt_actions/0` flag (`behavior.ex:341-356`) sits on the same declaration as the cap-required actions (`required_caps/0` `behavior.ex:307-318`). The preferred v5 target splits them into two declaration classes so a cap-gated-AND-exempt action is **unrepresentable by construction**: cap-gated actions (verifier ALWAYS applies, no exempt flag) vs non-cap actions carrying their OWN first-class authorization predicate. The **INTERIM** (if the macro refactor is out of scope) is a closed static allowlist enumerating every current non-cap class member. Either way the members are load-bearing and stay: identity persistence, identity `cascade_notify_managers`, agent & user `receive`, socialware publisher `snapshot/history`, and session admission + `composition_consent` — each authorized by its own predicate (trusted-internal facade, or an in-handler authority check over the **session-authenticated presenter**), never by a forgeable `ctx.caller`, and none relabelable to escape the verifier.
  - **The signing/verifying primitive** (`cap/signing.ex:121-132`) is reachable **only** from the framework signer path (§3). **v5 gates the signing operation + key access specifically** — NOT all `:crypto` — so legitimate domain crypto (PAT HMAC `:crypto.mac`/`:crypto.strong_rand_bytes`, `token.ex:232-235`) is untouched. An accidental/review-missed direct call to `Ezagent.Cap.Signing`/key-access is caught by the arch-gate (§10 property 3); this is a ratchet + review, not a runtime barrier against reviewed-admitted code (§ threat model).
- **No bypass** — the only paths are mint-via-`K.grant` (or the one genesis exception) and authorize-via-the-single-framework-verifier. An arch-gate + named runtime invariants (§10) — **not** a second cryptographic system — keep the mint/sign/authorize surface minimal; under Path A they are review aids that fail loud, sufficient given the reviewed-code precondition.

## 3. Keys & custody — private framework state + a signing-specific ratchet, under Path A
- **The key is NEVER a Behavior-slice field.** codex round 1 falsified the "slice = isolation" premise: slices are cross-process-readable via `Kind.get_slice/2`/`get_raw_slice/2` (`slice_access.ex:54-112`), `Kind.Server` returns any requested slice key without authorization (`server.ex:526-533`), sibling-slice reads are injected straight into handler context (`behavior.ex:409-436`, `kind/runtime/context.ex:40-53`), and a durable field serializes into the full snapshot (`snapshot.ex:455-470`) which a system-scope query can enumerate (`ecto/kind_snapshot.ex:44-64`). A slice-resident key is readable by ordinary code and by any node sharing the Repo.
- **The key lives in private, non-slice `Kind.Server` state.** codex confirmed `state.state` (the slice map generic reads index into, `server.ex:125-138,526-533`) is separable from a private top-level `Kind.Server` field: generic slice/sibling/raw reads only reach `state.state`, the snapshot serializer only serializes the slice map (`snapshot.ex:455-470`), and effect enrichment (`server.ex:603-616`) carries no key. So the key sits in a private top-level field that is **never** in a slice, snapshot, event, log, or admin listing (`ecto/kind_snapshot.ex:44-64`), and is **never** placed in `build_handler_ctx` (`kind/runtime.ex:801`). There is **no handle** — the key never leaves framework state, so nothing (opaque or otherwise) is handed to Behavior code. **DROP v3's separate authority-service / KMS requirement** — that is Path B; under Path A a private in-process field is the custody.
- **Signing stays a framework-internal op reached from exactly three framework sites (v6).** `sign`/`verify` (`cap/signing.ex:121-132`, EdDSA `:crypto.sign`/`:crypto.verify` over raw key binaries) + private-key custody are reached only from (i) the framework verifier (`verify` for a dispatch it is about to authorize), (ii) the post-verifier `K.grant` issuance step (`sign` for a grant the verifier already authorized), and (iii) **the authority genesis / authority-row custody path** (`sign` for the one K-signed admin anchor at genesis, plus per-Kind key generation and load into the authority record — §5). *(Codex round 5: genesis necessarily creates and stores a K-signed anchor and initializes/loads the key, so it is a third legitimate signer/custody site — the earlier "exactly two sites" was internally impossible.)* **A Behavior handler never signs.** `K.grant`'s handler returns an **issuance intent** effect; the framework post-verifier path performs the `sign`, binding to the frozen validated intent (§1 item 5 / §8) — so an attached Behavior emitting a raw `{:issue_cap, …}` gets no signature.
- **Arch-gate ratchet — SIGNING-SPECIFIC (v5 fix 2, the honest custody mechanism).** A static gate BANS, in the Behavior/domain/plugin tiers, exactly two families:
  1. **The capability-signing operation + key access** — direct `Ezagent.Cap.Signing.sign/verify` (`cap/signing.ex:121-132`) and any read of the private key field. It does **NOT** ban `:crypto` wholesale: legitimate domain crypto stays legal (e.g. PAT HMAC `:crypto.mac(:hmac, :sha256, …)` and `:crypto.strong_rand_bytes/1` in `token.ex:232-235`). The allowlist of framework sites permitted to call `sign`/`verify`/key-access is exactly {the authority genesis/authority-row custody path, the central verifier, the `K.grant` issuance step} (v6 — three sites).
  2. **The privileged introspection primitives** — `:sys.get_state`, `:sys.replace_state`, **`:sys.get_status`** (alias), `:erlang.process_info` / **`Process.info`** (alias) on framework PIDs, `:dbg`/tracing, and direct ETS reads of key tables. (`:sys.get_status`/`Process.info` do not appear in `apps/` today — the alias entries are a **preventive completeness** ratchet so a future introduction is caught, not a fix to an existing call.)
  **Stated honestly: this is a ratchet + review, not a cryptographic boundary.** It catches accidental and review-missed use (threats ① and ②); it does NOT stop code that review admitted from calling these primitives at runtime — nothing in one unsandboxed BEAM can. Sufficient ONLY under the Path A reviewed-code precondition (§ threat model).
- **Symmetric-at-`K` is still correct** (sign == verify at `K`, which holds its own key; the EdDSA keypair is `K`'s own, never off-`K`); an off-`K` verifier does not exist here (§4).
- **Admin root = crown jewel.** `admin` is the root of trust. Every Kind, at creation, is anchored to trust the **canonical admin identity** — resolved from the single code authority `Ezagent.Entity.User.admin_uri/0` (`user.ex:32`, which constructs the canonical system/admin URI via `Ezagent.URI.user(:system, :admin)`), **not** the literal `entity://admin` (a non-canonical URI lacking workspace/type/name, `uri.ex:420-428`). The anchor names the identity, not a specific admin key.
- **Identity-anchoring + key-versioning** (cheap future rotation): admin's key carries a version; Kinds trust the stable canonical identity. Rotating admin's key = version-bump + re-provision, **not** a fleet-wide re-anchor. Per-Kind keys rotate lazily / on-compromise (blast radius contained to one instance).
- **Residual (Path A).** The custody provides no boundary against unreviewed in-BEAM code (threat-model OUT-of-scope). Under the reviewed-code precondition the residual is bounded to review escapes + privileged BEAM introspection (`:sys.get_state`, tracing) of `K`'s live process — contained to one instance, ratcheted by the arch-gate, and hardened incrementally (restrict those BIFs in prod). The durable upgrade for unreviewed code is **Path B** (§ threat model). **No global-seed HSM requirement** — each Kind holds only its own key.

## 4. Distribution (friendly by construction — with the key-custody constraint)
- A cap is always verified at its target Kind's **owner runtime**. Today dispatch already requires the local runtime to own the target workspace (`invocation.ex:118-142`, `workspace_owner_gate.ex`, placement local-only `workspace_placement.ex`); remote routing (deferred, §7) must **forward the cap + the envelope provenance to the authoritative owner runtime**, where the single local verifier runs. No cap-on-`K` is ever verified off-`K`; no key crosses the wire.
- **Blast-radius containment depends on §3.** The per-node claim only holds once keys are out of shared plaintext: a slice-resident key serializes into snapshots that a **system-scope query lists across all nodes** (`ecto/kind_snapshot.ex:44-64`) — so a shared-Repo node would NOT be limited to its own Kinds' keys. With §3's key in **private non-slice `Kind.Server` state** (never in snapshots), **node compromise is contained to that node's live Kinds**. Placement transfer must atomically transfer or rotate the key custody (it is private in-process state, not a copyable handle to move).
- Distribution then needs only ① remote transport/routing to the owner runtime and ② bootstrap root-anchoring — **neither is a cap-signing-model change**. This **unblocks** workspace-per-ECS, and is strictly better than v11's seed-on-every-node.

## 5. Bootstrap / genesis — one durable, append-only authority record (with the pinned reincarnation protocol)
The tension codex flagged: `K.grant` requires a pre-existing authority-cap-on-`K`, but "born signed" says every cap comes from `K.grant` — so seeding an anchor is either a mint *outside* `K.grant` (breaks sole-mint) or circular. Resolution: **one explicit genesis exception, made durable and one-shot by an append-only authority record.**

- **codex round-3 correction (why v3's shape was wrong).** v3 said "emit the admin anchor as an effect, atomic with the CAS insert." That is NOT achievable: effects (deferred dispatches) run AFTER the slice durably commits, not in the same transaction (`server.ex:605-650` — `commit_and_notify` first, then `DeferredDispatch.enqueue(deferred)` "AFTER the parent slice durably committed"). And a bare uniqueness constraint is not irreversible — a row deletion permits a re-insert, so it does not seal.
- **The fix: a durable, append-only, non-deletable-by-runtime/plugin authority record.** A dedicated per-instance record (keyed by `K`'s instance URI **and generation**, see reincarnation below) whose ONE winning `INSERT` holds, in one row committed in one transaction: **{the committed per-Kind key, the ONE `K`-signed canonical-admin anchor naming `Ezagent.Entity.User.admin_uri/0` (`user.ex:32`; not the literal `entity://admin`, `uri.ex:420-428`), the key version, the active generation, the seal flag}**. The anchor is not emitted as a fire-and-forget effect — it is **produced and stored inside the same INSERT**, so genesis is not "sealed" until the usable anchor is durably committed in that row. Runtime/plugin code has **no delete path** to the record (revoke/GC operate on caps, not this table); only an explicit admin-scoped operation can touch it. Any concurrent or later genesis attempt for the same `(URI, generation)` loses the insert and is rejected fail-loud.
  - **Why a new record, not `ever_created` (honesty).** `ever_created` (`snapshot.ex:465-490`, `ecto/kind_snapshot.ex:89-119`) is the right *same-commit atomic-marker discipline*, but it is a boolean on the **snapshot row**, and §3 forbids the key from living in the snapshot. The authority record IS the key's custody store; its winning INSERT + append-only/non-deletable property IS the seal.
- **How admin loads the anchor.** The admin anchor is **retrieved FROM that row** (for the active generation), not from a slice or a cap store: at boot / on demand the framework reads `K`'s authority record and presents the stored `K`-signed anchor as admin's authority-cap-on-`K`. The row IS the anchor's home and the read path.
- **Bootstrap admin FIRST (chicken-egg).** Admin's own **immutable self-row** is written FIRST, with **no verifier** (admin is the root; there is no prior authority to check). Only then do other Kind rows genesis, each anchoring to the already-committed canonical admin identity. Root bottoms out at admin trusting itself, non-circular because the record is a one-shot durable state change, not a cap-check.
- **URI reincarnation — PINNED PROTOCOL (v5 fix 3, Option B, fail-closed).** Runtime "incarnation" today is only the PID (`invocation.ex:537-541` `current_incarnation/1` returns the registry `pid`), which is **not durable** and cannot distinguish a cold restart from a delete/recreate. So v5 does NOT rely on any runtime incarnation marker. Instead:
  - The append-only authority row **survives the Kind's deletion** (non-deletable-by-runtime, above). The two paths are distinct in the Lifecycle contract: **cold restart rehydrates via `activate/2`** (reads the existing sealed row for the active generation; attempts NO genesis INSERT — normal, allowed), whereas **delete/recreate re-runs the `create` / genesis path** (the one-shot INSERT).
  - **A recreate collides fail-closed.** When the genesis/`create` path runs at a URI that already has a sealed authority row for the current active generation, the INSERT collides and is **REJECTED, fail-loud** — the URI cannot be silently reincarnated, and an existing authority row is **NEVER** silently adopted as ordinary rehydration after deletion.
  - **Load-bearing invariant (Option B depends on it): `destroy` MUST clear the Kind's rehydration/snapshot state so a subsequent same-URI spawn runs `create`, not `activate`.** The pin rests entirely on the create-vs-activate path split (the PID incarnation, `invocation.ex:537-541`, is non-durable and cannot be the discriminator). The two durable stores are deliberately asymmetric on delete: the **snapshot/rehydration state IS cleared** by destroy (so recreate is a fresh `create` — cf. the same-commit `ever_created` marker on the snapshot row, `snapshot.ex:474-490`, which governs the create-vs-rehydrate decision), while the **append-only authority row is NOT** (§5, non-deletable-by-runtime). That asymmetry is what makes a recreate run `create` → collide with the surviving authority row. If a destroy path left rehydratable snapshot state, recreate would silently `activate` and adopt the old row — the exact failure this forbids; the gate/tests (§9 genesis+reincarnation) must assert destroy clears rehydration state.
  - **Reincarnation requires an explicit, append-only admin re-genesis record** that **activates a NEW generation** for that URI. Authority-row selection thereafter keys on `(instance URI, active generation)`, so the new incarnation gets a fresh key + fresh admin anchor and the old row can never be silently selected. A plugin/runtime path can **never** re-genesis a URI; re-genesis is admin-scoped and recorded, so a reused URI cannot resurrect an old key or silently re-anchor.
- **Delete + arch-gate** every `{:genesis, arbitrary_uri}` authorization form (`cap.ex:24-27,172,227-229`). No caller may supply a root identity; the canonical admin URI comes from the single code authority `admin_uri/0`, never a passed argument. No key is ever passed as a plain argument.
- **Non-cap actions authorized by their own predicate under Path A (not deleted) — structural class / interim allowlist in §10 property 2.** The non-cap families are load-bearing and stay; each keeps its own handler-owned predicate over the **session-authenticated presenter** (session admission via `Authority.manages?`/`requested_by`) or its trusted-internal facade (identity persistence). Preferred end state: cap-gated and non-cap are separate declaration classes so exempt-on-a-cap-gated-action is unrepresentable; interim: the §10 arch-gate forbids the bypass **flags** (`cap_exempt_actions`, `cap_issued`, `authorization_rule`, `:vm_internal`) **only for target-cap-gated actions** and locks the non-cap set to a closed enumerated allowlist so nothing new can hide behind it.

## 6. Cutover (ezagent-deploy scope)
Self-use, disposable data → **wipe + reseed**: quiesce → wipe cap-bearing data → deploy the new build → seed (admin first, then Kinds each get a fresh key + admin anchor; all caps re-issued signed) → resume. **No app-side migration/backfill code.**

## 7. Non-goals
- **Cap-storage consistency** (a cap in multiple homes, revoke-clears-all) — separate concern.
- **Full distributed transport** — the model SUPPORTS distribution; the routing/bootstrap-anchoring *implementation* is a separate track (deferred). The design must not preclude it (§4).
- Opaque cap representation — not needed here (verify is local at the target with its key, not a global boundary).

## 8. Implementation shape (high-level)
- **Per-instance key in private `Kind.Server` state** (§3): key generated at genesis into a **private top-level `Kind.Server` field** (sibling to the slice map `state.state`, `server.ex:125-138`); never a slice field, never in snapshots/events/logs/admin-listings (`snapshot.ex:455-470`, `ecto/kind_snapshot.ex:44-64`), never placed in `build_handler_ctx` (`kind/runtime.ex:801`). No authority service / KMS — that is Path B. No handle exists.
- **`sign` / `verify` as framework operations** (`cap/signing.ex:121-132`) — reached from exactly three framework sites (the authority genesis/authority-row custody path; the verifier; the post-verifier `K.grant` issuance step). **The signing operation + key access (NOT all `:crypto`) and the introspection primitives (incl. the `Process.info`/`:sys.get_status` aliases) are arch-gated out of Behavior/domain/plugin tiers** (a ratchet + review, §10 property 3 — not a runtime barrier); legitimate domain crypto (`token.ex:232-235`) is untouched.
- **The framework verifier** — the ActionSet macro declares immutable metadata; one `Kind.Runtime` verifier dominates every handler/state-mutating route (§2, `kind/runtime.ex:142-153`, and the escape-hatch sites `340-361` + `:vm_internal` ~`530`/`678`). It reads the presenter per the envelope's light `origin`: `authenticated-external` → the **server-written `ctx.caller`** (edge-overwritten from the ingress-authenticated session/bearer identity, never a client-supplied value); `trusted-internal` → trusted `ctx.caller`; **unstamped → reject before verification** (v5 fail-closed). It then compares the signed concrete `(instance, action, grantee)` against the live dispatch. Verify or fail-loud.
- **Light `origin` provenance on BOTH envelopes** — a boolean/enum (NOT a signed ticket) on `%Cmd{}` (`cmd.ex:49-66,84-116`) and `%Invocation{}` (`invocation.ex:81-89,121-142`), preserved Cmd→Invocation by `Router.to_invocation/1` (`router.ex:151-170`). Set `authenticated-external` at the enumerated ingress adapters — each already derives identity from the authenticated session/bearer the standard Phoenix way (`api_v1_controller.ex:131-163`; `session_principal.ex:80-89`; `chat_completions_plug.ex:51-61,185-196,253-263`; `world_uploads_controller.ex:55-65,119-134`; PTY/channel). Set `trusted-internal` by the internal constructors: DeliveryOutbox **persists the authenticated presenter and re-mints on replay** (`cap/delivery_outbox/envelope.ex:35-49,68-100`, `cap/delivery_outbox.ex:202-220,258-265`), ExternalMirror self-URI (`external_mirror_worker.ex:861-915`), SessionTemplate ctx-forward (`behavior/template.ex:655-665`), CLI (`ezagent_cli/dispatch.ex:82-94,300-318`), EntityCaps/Identity facades (`entity_caps.ex:140-154`). Anything unstamped is rejected.
- **`K.grant` action** — unconditionally cap-gated (requires an authority-cap-on-`K`); the handler returns an **issuance intent** effect, and the framework post-verifier issuance path performs `sign`, **binding to the `(target, action, grantee, bounds)` frozen at framework validation time — BEFORE `pre_handle`/`post_handle`** (`runtime.ex:142-153` authz/validation precede the handler; `pre_handle` can rewrite `effective_args` `runtime.ex:801-848`; `post_handle` can replace effects `runtime.ex:901-909`). NEVER `effective_args` and NEVER a returned effect. The handler never holds the key. No `cap_issued`/rule shortcut.
- **Genesis authority record** (§5) — a durable, **append-only, non-deletable-by-runtime** per-instance record keyed by `(URI, generation)`; one winning INSERT stores {key, one `admin_uri/0`-signed anchor, key version, active generation, seal} in one transaction; **admin self-row first**; anchor read FROM the row; **recreate at a reused URI collides fail-closed**, reincarnation only via an append-only admin re-genesis record that activates a new generation.
- **Split cap-gated vs non-cap into structural declaration classes (preferred); enumerate-and-lock as interim** (§10 property 2) — identity persistence, `cascade_notify_managers`, agent/user `receive`, socialware `snapshot/history`, session admission + `composition_consent` stay as non-cap members authorized by their own predicate (trusted facades / in-handler checks over the session-authenticated presenter). Preferred end state makes exempt-on-a-cap-gated-action unrepresentable via the macro layer (`behavior.ex:307-318,341-356`); interim gates the bypass flags off only for target-cap-gated actions and locks the non-cap set.
- **Delete**: dual-read / `require_signature` default-off (`cap.ex:42-63,200-205`) / `verify_for` / the central-seed `sign_artifact` keypair-from-`granted_by` derivation (`cap.ex:213-220`) + v11's public-keyring machinery / `{:genesis, URI}` (`cap.ex:24-27,172,227-229`) / the `authz_check` `cap_issued`·rule bypasses at `kind/runtime.ex:340-361` and the `:vm_internal` all-cap authority (~`530`/`678`) **for target-cap-gated actions**.

## 9. Behavioral tests (the X holes, closed — each an INDEPENDENT assertion)
Per representative cap-gated action (session.send, create_session, PTY read, kanban write, world read_unfiltered…), each vector is its own test proving the attempt reached the authorization boundary and was rejected:
- **Forge** — an unsigned cap is rejected fail-loud.
- **Tamper** — a cap whose fields were mutated after signing is rejected.
- **Retarget** — a cap signed for a different instance/Kind is rejected under the live target's own key; cap-controlled `key_id` cannot select another Kind's key.
- **Stolen-cap + spoofed-presenter (external)** — a valid cap presented through an external ingress by a caller spoofing the grantee's URI via client-writable `ctx.caller` is rejected, because for an `authenticated-external` envelope the presenter comes from the ingress session-authenticated identity, not `ctx.caller` (§1 item 5).
- **Unstamped-envelope reject (fail-closed — v5's blocking-fix assertion)** — an envelope carrying NO `origin` (neither `authenticated-external` nor `trusted-internal`) is **rejected BEFORE capability verification**. A `%Cmd{}`/`%Invocation{}` from a hypothetically un-authenticated ingress does not fall through to a trusted-internal default (this is the fail-open regression fix 1 closes).
- **Wrong-target-key** — verification uses the live target's own key (from private `Kind.Server` state), not one selected by the cap.
- **Issuer-impersonation** — `K.grant` rejects a caller lacking a valid authority-cap-on-`K`; recursion to the canonical admin root is exercised and proven non-circular.
- **Intent-binding (freeze before hooks)** — a `pre_handle` that rewrites `effective_args` (`runtime.ex:801-848`) or a `post_handle` that replaces the issuance effect (`runtime.ex:901-909`) cannot cause a cap outside the **validation-time-frozen** `(target, action, grantee, bounds)` to be signed.
- **Genesis + reincarnation** — the one-time transition anchors each `K` to `admin_uri/0` and stores the usable anchor in the durable record; re-genesis for the same `(URI, generation)` collides/loses and is rejected (sealed); a **reused URI after delete is rejected on the `create`/genesis path until an admin re-genesis activates a new generation**, and an existing authority row is never silently rehydrated after deletion; strict verify holds end-to-end on a freshly seeded stack; a reused URI does not resurrect an old key.
- **Key egress** — generic slice read, sibling read, raw read, snapshot, event, and admin-listing of `K` return **no key material at all** — the key lives in private framework state and never leaves; there is **no handle**.
- **Legit** — a properly `K.grant`-minted cap, presented by the authenticated grantee, is accepted.

## 10. Gate plan (this is a first-class deliverable, not just tests)
Two enforcement layers, following the ezagent static-gate discipline (`check_invariants` → `ci.local` full-suite; run pre-push):

**A. Completion / invariant gate — behavioral, fail-when-the-goal-is-unmet.** The §9 vectors as **independent** `/goal`-style assertions on a freshly seeded stack (each proves the attempt reached the authorization boundary, not a shared monolith): forge, tamper, retarget, stolen-cap+spoofed-presenter, unstamped-envelope-reject, wrong-target-key, issuer-impersonation, intent-binding, genesis+reincarnation, key-egress rejected; legit accepted. The forge/tamper/retarget cases **fail on today's `origin/main`** (dispatch authorizes via structural match without `Cap.verify`, `authorization.ex:6-18`, `kind/runtime.ex:539-545`; `require_signature` default-off, `cap.ex:42-63`) — that red proves each gates a real hole. (The positive `K.grant` path does not exist on `origin/main` yet, so the suite lands with the implementation.)

**B. Structural arch-gate — HONEST split.** A static grep/AST gate can prove a *syntactic absence* (a flag is not present, a symbol is referenced only in allowed files, a declaration exists) but CANNOT statically prove a *semantic / information-flow / one-shot* property. So each property is classified as **STATIC** (the grep/AST IS the guarantee) or **RATCHET + RUNTIME** (the grep/AST is a shrink-only ratchet; the guarantee is owned by a named runtime invariant or an independent §9 behavioral test). Only #2 and #4 are genuinely static; the rest are ratchet+runtime. **Under Path A, even the STATIC gates are review aids** — they catch accidental and review-missed violations (threats ① and ②), not a determined actor running unreviewed code in-BEAM (§ threat model, out of scope).

A NEW action cannot escape the verifier by adopting an exemption class: in the preferred end state a non-cap action must join the separate declaration class and carry its own predicate (there is no exempt flag on the cap-gated class to abuse); in the interim the allowlist is closed and fixed, and each entry names the exact handler-owned predicate that must hold.

**Honest enforceability limit (v5 / Path A).** Only properties **2 and 4** are statically proven; **1, 3, 5, 6, 7, 8** are static *ratchets* whose security guarantee is a named runtime invariant or a §9 behavioral test — this spec does **not** claim static proof of any semantic (verifier-dominance-in-fact), information-flow (key non-egress), authenticity (presenter/provenance), or one-shot (genesis/reincarnation) property. **And under Path A even the static ratchets are review aids**: they catch accidental and review-missed violations (threats ① and ②), not a determined actor running unreviewed code in-BEAM, which is out of scope (§ threat model). Caps remain public Elixir structs, so discovering arbitrary semantic field reads stays best-effort AST. Collapsing verification to ONE framework verifier, minting to ONE `K.grant`, presenter to **standard session auth + a light fail-closed `origin` guard**, and custody to private framework state keeps both the scan surface and the runtime-assertion surface minimal — but the guarantee lives at runtime and at review, and §10 says so plainly. The cryptographic boundary against unreviewed in-BEAM code is **Path B** (§ threat model), not this spec.

## 11. Open (residual sub-mechanism only — the architecture is Path A, v5-settled)
The v5 architecture is settled: private-state key custody + signing-specific grep-ratchet (§3), **standard session auth + a light fail-closed `origin` guard on both envelopes with the completed ingress inventory** (§1 item 5), the **structural cap/non-cap class split (preferred) / enumerate-and-lock (interim)** for exemptions (§10 property 2), append-only genesis authority record with the **pinned reincarnation protocol** (§5), **intent freeze before hooks** at issuance (§1 item 5 / §8). What remains is sub-mechanism inside those choices:
- **Authentication + `origin`-completeness is the new load-bearing obligation (name it).** With fail-closed `origin`, a **future edge that forgets to authenticate, or an internal constructor that forgets to set `origin`, now becomes an OUTAGE, by design, not a privilege escalation** — the operational cost of fix 1. The mitigations are standard-web-auth at every edge (which today's edges already do) + the enumerated internal constructors (§1 item 5) + the §10 property-6 runtime reject + the §9 unstamped-reject vector. This mirrors v4's "edge completeness" obligation but is now fail-closed on both envelopes and rests on standard auth rather than a new protocol.
- **Key-custody field form** — the exact private top-level `Kind.Server` field vs a scoped keystore process co-owned by the framework (both are private in-process state, NOT the Path B authority service); the symmetric primitive (the EdDSA keypair used today, `cap/signing.ex:121-132`, vs an HMAC/AEAD MAC).
- **`origin` carrier representation** — the exact atom/enum for the light `origin` field on `%Cmd{}`/`%Invocation{}` and the precise point in `handle_dispatch` where the verifier reads it (relative to `authz_check`, `kind/runtime.ex:142-153`). (The *light-boolean shape on both envelopes, the edge set, the two positive values + the fail-closed reject* are closed.)
- **Exemption structural-split scope** — whether this pass does the ActionSet/Behavior macro refactor (`behavior.ex:307-318,341-356`) that makes cap-gated-AND-exempt unrepresentable, or lands the enumerate-and-lock interim first and does the class split as a follow-up. The *end state* (two declaration classes) is decided; the *sequencing* is the open sub-mechanism.
- **Genesis-record shape** — the append-only authority record's schema, the non-deletable-by-runtime guarantee (table permissions / no runtime delete path), the seal + key-version + active-generation columns, the anchor-read path, and the admin re-genesis operation that activates a new generation for URI reuse.
- **admin-root key custody + version scheme; bootstrap sequencing** — admin self-row before any Kind anchors (§5).
- **Migration bookkeeping** — enumerating today's `{:genesis, URI}` (`cap.ex:24-27,172,227-229`) and bypass-flag call-sites to delete, the exact edge-adapter provenance-mint edits (incl. the two newly-inventoried doors), and the DeliveryOutbox authenticated-presenter persistence + re-mint edits (§1 item 5 inventory).
- **Path B trigger** — the criterion (unreviewed third-party code admitted in-BEAM) that promotes the roadmapped Path B isolated-signer design (§ threat model) from deferred to active; not needed while the reviewed-code precondition holds.
