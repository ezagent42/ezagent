## 1. ① gate 状态怎么算：复用 status 4 态，`:done` 钉成「本棒已过 gate」

### 1.1 决策：不新增字段，复用现有 `status`

产品 spec §2.2（`df-prd-mindmap-product-spec.md:58-70`）已钦定：`status` 映射「待认领→认领→进行→交接合格」，**`:done` 的语义 = 本棒真相源已过 §2.1 gate**。

**本 spec 钉死**：
- `status` 不扩字段、不加第 5 态。`:done` 就是「人宣布本棒交接合格（过 gate）」。
- gate **判据是一个独立只读计算**（`check_gate`），**不写回节点、不改 status**。即「这个节点现在符不符合 gate 判据」是**算出来的派生态**，不是存储态。
- 因为 D2=全软提示：`set_status(done)` **保持现状自由置**（`behavior/mindmap.ex:340` 不加 gate 拦截），人想标 done 随时能标。`check_gate` 只告诉你「按自动判据这棒到底齐没齐」，齐不齐都不挡手动操作。

> **为什么不存 gate 态**：gate 判据依赖节点的 artifacts/metrics/子树，这些会变；存一个 `gate_passed: bool` 会立刻 stale（artifact 删了但 flag 还是 true）。派生计算永远跟 artifacts 一致，零陈旧。**这是钉死的设计，不留 D**。

### 1.2 三个正交维度（前端要分开显示，别混成一个词）

| 维度 | 来源 | 取值 | 谁改 |
|---|---|---|---|
| **认领/进度** | 存储 `node.status` | unassigned / claimed / doing / done | 人手动（claim / set_status）|
| **gate 评价** | 派生 `check_gate` | `:pass` / `:warn` / `:n/a` | 算出来的（artifacts/metrics/子树）|
| **owner** | 存储 `node.owner` | uri \| nil | claim/unclaim |

「done」（人说做完了）和「gate pass」（自动判据齐了）是**两件事**：人可以标 done 但 gate 还 warn（spec 卡没写 Gherkin 就硬推 done）——前端要把这种「done 但 gate 没齐」高亮成提醒（软提示的本体）。

## 2. ② 哪些 gate 能自动判 / 哪些人工

逐棒抄 `df-prd-mindmap-product-spec.md:48-56`（§2.1 表），按「本节点交付物是否结构化可查」分自动 / 人工：

| gate（stage） | 自动判据（`check_gate` 算）| 判定函数 | 类型 |
|---|---|---|---|
| `:positioning` | 有 ≥1 个 `kind∈{positioning_doc, prfaq}` 的 artifact | `has_artifact_kind?` | **半自动**（存在性自动，「明确」人工）|
| `:metric` | 有 ≥1 个 metric 且其 `name` 与 `target` 非空 | `has_metric_with_target?` | **半自动** |
| `:pain` | 每个 pain 节点有 metric 或 artifact（ICE/挂钩）| `has_any_attachment?` | **半自动** |
| `:anchor` | 有 `kind: :role_map` artifact | `has_artifact_kind?` | 人工为主 |
| `:ux` | 有 `kind: :wireframe` artifact | `has_artifact_kind?` | **半自动**（存在性）|
| `:feature` | 有 `kind: :spec_card` artifact 且其 `content` 含 ≥1 条 Gherkin（grep `Given/When/Then`，大小写不敏感）| `gherkin_nonempty?` | **可自动**（核心）|
| `:issue` | 有 `kind: :issue` artifact 且有 `url`（github 链接）| `has_issue_ref?` | **可自动** |
| `:test` | 有 `kind: :test_suite` artifact 且其 `ref`/`content` 标 `status=green`（约定 artifact 带 `%{kind: :test_suite, ref: "green"}` 或 content 含 `"green"`）| `test_green?` | **可自动** |
| `:pr` | 有 `kind: :pr` artifact 且 `url` 存在 + **回溯祖先链** test/issue/feature 都 pass | `pr_ready?`（递归祖先）| **可自动** |

**钉死的 gate 判定基元**（都在 behavior 内，纯函数，读 node + 子树）：
- `gherkin_nonempty?(node)`：在 node.artifacts 里找 `kind == :spec_card` 的，取 `content`，`String.match?(c, ~r/\b(given|when|then)\b/i)`。这是**最关键、唯一靠 inline content 的判据**——印证「CI 内容 inline 存」决策。
- `has_artifact_kind?(node, kind)` / `has_metric_with_target?(node)` / `has_issue_ref?(node)` / `test_green?(node)`：都是 node 字段查，无外部调用。
- `pr_ready?`：沿 `parent_id` 回溯（复用 `ancestors/2` `behavior/mindmap.ex:537`）或按 stage 找子树里的 issue/test/feature 节点，逐个跑各自判据。

**人工 gate 怎么办**：半自动/人工的棒，`check_gate` 返回的不是「fail」而是 `:warn`（带 reason），意思是「自动判据没齐，请人确认」。**永不返回阻塞**——这就是软提示。pass/warn/n/a 三态，没有 fail/block。

> **待定 D-gate-1（小，建议自定）**：`:test` 的「绿」怎么编码到 artifact？建议约定 `attach_artifact(%{kind: :test_suite, ref: "green"|"red", url: ci_url})`，`test_green?` 查 `a.ref == "green"`。CI 轮询（`GithubSync`，纯出站）拿到 CI 结果后 dispatch 这个 attach。格式 trivial，开工时定即可，不阻塞片4主体。

## 3. ④ 新动作 `check_gate`（只读），**不复用 set_status**

### 3.1 为什么独立动作不内嵌 set_status

D2=软提示已排除「`set_status(done)` 内嵌 gate 校验」（那是硬闸=方案B，已否决）。所以：
- `set_status` **一行不改**（`behavior/mindmap.ex:340`），保持自由置 done。
- 新增**只读** `check_gate`，给前端徽章 / CI 轮询 / agent 调，**纯算，零 effect、零 `{:set}`**。

### 3.2 确切动作签名（加到 `behavior/mindmap.ex`）

```elixir
action(:check_gate,
  args: %{id: :string},
  returns: %{verdict: :string, reasons: :list, stage: :string},
  caps: [:check_gate],
  modes: [:call],
  description: "只读：算某节点 gate 评价(pass/warn/n_a)+不齐原因，不改任何状态(软提示)"
)

def handle_check_gate(%{id: id}, ctx) do
  t = tree(ctx)
  case Map.fetch(t.nodes, id) do
    :error -> {:error, :node_not_found}
    {:ok, node} ->
      {verdict, reasons} = gate_eval(node, t.nodes)   # 纯函数
      {:ok, %{verdict: to_string(verdict),
              reasons: reasons,
              stage: to_string(node.stage)}, []}       # ← 空 effect 列表，只读
  end
end
```

`gate_eval/2` = 按 node.stage 派发到 §2 的判定基元，返回 `{:pass | :warn | :n_a, [reason_atom]}`。

### 3.3 改动清单（behavior）

| 文件 | 改动 | 行 |
|---|---|---|
| `apps/ezagent_plugin_mindmap/lib/ezagent/behavior/mindmap.ex` | 加 `action(:check_gate, ...)` 宏 | `:146` 后（最后一个 action 之后）|
| 同上 | `required_caps/0` 列表加 `:check_gate` | `:149-168` 那个 for 列表里加一项 |
| 同上 | 加 `handle_check_gate/2` + 私有 `gate_eval/2` + §2 的判定基元（`gherkin_nonempty?` / `has_artifact_kind?` / `has_metric_with_target?` / `has_issue_ref?` / `test_green?` / `pr_ready?`）| helpers 区（`:424` 之后）|

**关键不变式守住**：`handle_check_gate` 返回 `{:ok, result, []}`——**空 effect**，不能出现 `{:set, ...}`。这保证它是真只读（grep `commit(` 在 check_gate 路径上零命中），不污染快照、不触 snapshot-on-change。

## 4. ③ 前端怎么显示 gate 状态：节点徽章 + 侧边栏

gate 评价是派生态——**前端可以本地算（不必每次 dispatch check_gate）**，因为 node.artifacts/metrics 已经在前端 tree 里（`Mindmap.tsx:9-18` Node 类型已含 artifacts/metrics）。两条路：

- **路 A（推荐 MVP，零后端往返）**：前端 `gateVerdict(node)` 纯函数，镜像 §2 判据（feature 查 spec_card content 有没有 given/when/then 等），直接画徽章。**优点**：实时、无 dispatch；**代价**：判据逻辑前后端各一份（要对齐）。
- **路 B（权威）**：前端调 `onAction("mindmap.check_gate", {id})` → 后端算 → 推回。**优点**：单一判据源；**代价**：每次选节点一次往返。

**MVP 用路 A 画徽章 + 路 B 兜底**（CI/agent 用 check_gate 拿权威值；前端徽章用本地算法即时反馈，二者判据同一张表）。

### 4.1 节点卡片徽章（`MindmapCanvas.tsx`）

`MmNode`（`:51`）已显示 `STATUS_ICON` + stage 标签。加一个 **gate 徽章**：
- `gate == "warn"` → 黄点/⚠（「本棒交付物没齐，软提示」）；尤其当 `status=="done" && gate=="warn"` → 红边高亮（人标了 done 但判据没齐，最需要看见）。
- `gate == "pass"` → 绿勾 ✓（判据齐）。
- `gate == "n_a"` → 不画（人工棒未提供自动判据时不打扰）。

改动：`MindmapCanvas.tsx:51-76` `MmNode` 加一个 `gateVerdict(node)` 调用 + 一个 `<span>` 徽章；新增导出 `gateVerdict(node): "pass"|"warn"|"n_a"`（§2 判据的 TS 镜像，约 30 行）。

### 4.2 侧边栏 NodePanel（`Mindmap.tsx`）

`NodePanel`（`:187`）当前显示 status/stage/owner（`:200-204`）。加一行 **gate 评价 + 不齐原因列表**：
- 顶部状态行加 gate 徽章（同卡片）。
- 若 `gate=="warn"`，列出 `reasons`（如「缺 spec_card」「Gherkin 为空」「测试未标绿」），每条一句中文，告诉 owner 差什么才算过 gate。
- **纯提示，不禁用任何按钮**（set_status done 仍可点——软提示本体）。

改动：`Mindmap.tsx:198-217` 区域加 gate 徽章 + reason 列表（约 20 行 JSX + 共享 `gateVerdict`/reason 文案表）。

### 4.3 data 层（`mindmap_data.ex`）：无须改

`check_gate` 走标准 dispatch（`Invocation.dispatch`，与 `read_tree:114` 同路径），world 层只要在 `MindmapActions` 加一个 `mindmap.check_gate` 路由子句即可（若走路 B）。路 A 则 data 层完全不动（前端本地算）。

**改动（仅路 B 需要）**：`apps/ezagent_plugin_world/lib/ezagent/world/mindmap_actions.ex` 加一个 `handle_dispatch(socket, "mindmap.check_gate", %{"mindmap_uri"=>u, "id"=>id})` 子句（`:89` 那个 catch-all 之前），dispatch check_gate（`:call`），把 `{verdict, reasons}` push 回前端。约 8 行，对称现有 `act/4`（`:94`）。

## 9. 对抗审查（2026-06-23，逐条对真实代码核）

主干三条（软提示 / 独立只读 / 复用 `:done`）**可行、贴合代码、不破不变式**。但有 3 个落地缺口必须开工前钉死，否则 feature gate 永远判不到、doc.scan 可能红、路 B 不可用。

### 必改 1 —— artifact `kind` 是 string，且现有 UI 挂的是 `"spec"` 不是 `:spec_card`（核心 bug）
- `normalize_artifact`（`mindmap.ex:505-513`）用 `sget` **原样存** kind，dispatch 边界传进来是 **string**（`"spec"`/`"link"`）。spec §2 判定基元写 `kind == :spec_card`（atom）→ **永远 false**，feature gate 全军覆没。
- 更糟：现有「加内容」按钮（`Mindmap.tsx:261`）挂的是 `kind: "spec"`，**根本不是 `spec_card`**。「加链接」是 `kind: "link"`（`:249`），issue/test/pr 的 kind 在 UI 里**根本没有产出路径**。
- 修：判定基元一律按 **string** 比（`a.kind == "spec_card"` 之类），**且**统一 UI 与判据的 kind 词表（要么 UI 改挂 `"spec_card"`，要么判据认 `"spec"`）。e2e/单测里 attach 的 kind 也必须跟这张表一致，否则测试自欺（绿了但线上判不到）。这是片4 头号风险。

### 必改 2 —— 路 B `act/4` 丢弃 dispatch payload，check_gate 拿不到 verdict
- spec §4.3 说「对称现有 `act/4`，约 8 行」——但 `act/4`（`mindmap_actions.ex:94-112`）走 `push_tree` + `status_of`，**只回 `"ok"/"error:*"`，把 dispatch 的 result payload 整个丢了**。check_gate 要回 `{verdict, reasons}`，`act/4` 结构上不可复用。
- 修：路 B 需**新写**一个不走 `push_tree` 的子句，取 `Invocation.dispatch` 的 `{:ok, %{verdict, reasons, stage}}` 推回前端（约 15-20 行，不是 8 行）。或干脆 **MVP 只走路 A**（前端本地算，零后端往返），路 B 延后——这更省且不阻塞。建议把 D-gate-2 直接钉成「MVP 路 A，路 B 不做」。

### 必改 3 —— `handle_check_gate/2` 必须带 `@doc false`，否则 doc.scan 红
- doc.scan（`ezagent.doc.scan.ex:20-28`）数「无 `@doc` 的 public def」，`@impl` 豁免。Lifecycle 的 `handle_*` **不是 `@impl`**（现有全部显式标 `@doc false`，如 `:148`/`:312`/`:339`）。spec §3.2 的代码块**漏了 `@doc false`** → 新增一个 undocumented public def → ratchet 红。私有 `gate_eval`/判定基元是 `defp`，不计，OK。

### 过 gate / 不变式 / 单一真相源（通过项）
- **只读不变式**：`handle_check_gate` 返 `{:ok, _, []}` 空 effect、不调 `commit/1`（`:447` 唯一 `{:set` 字面），不触 snapshot-on-change。§5 测试点1 已断言 `effects == []`。**守住**。
- **arch.scan oversized**：是 baseline ratchet 且只数 `@def_count_files` 白名单文件（`arch.scan.ex:24-29`），mindmap.ex 不在内，新增不触 oversized。set_effect_sites 计数也因零 `{:set` 不增。**过**。
- **uri_query raw URI**：check_gate 不带 URI query、不拼 raw URI，与 `uri_query.scan` 无交集。**过**。
- **单一真相源**：判据全读 node.artifacts/metrics/子树（已落 ezagent 快照），Gherkin inline `content` 是真相源本体；不在外部建真相、不靠死链 ref。**守住**。CI 绿/红经 `GithubSync` 纯出站轮询回填 attach（D-gate-1），仍是「ezagent 全赢」投影，不开 inbound——**不违 GitHub 纯出站 / CI 非阻塞决策**。
- **per-node CapBAC / R1**：check_gate 只读不写，不碰 owner/stage/`stage_fits?`（`:293`）/`set_status`（`:340`）。`set_status` 一行不改 → 软提示成立、R1 不破。**守住**。

### 埋坑提醒
- **快照膨胀**：判据不新增存储字段（gate 是派生态），content 已有 8KB cap（`:503/:515`）。无新膨胀。但 D-gate-1 若让 CI 把整段 test 日志塞进 artifact content，会吃 8KB cap——约定只塞 `ref: "green"|"red"` + url，别塞日志。
- **两份判据漂移（路 A）**：前端 `gateVerdict`（TS）与后端 `gate_eval`（Elixir）是两份镜像，kind 词表、Gherkin 正则（`~r/\b(given|when|then)\b/i` vs JS `/\b(given|when|then)\b/i`）必须逐字对齐，否则徽章与权威值不符。这是路 A 的固有税；选「MVP 仅路 A」可暂免后端那份，但 CI/agent 拿权威值时仍要补 `gate_eval`——两份迟早都要写。
- **formatter / 两 BEAM**：纯函数 + 现有桩，无 formatter 陷阱、无跨 BEAM 状态。`String.to_existing_atom` 那类坑不涉及（check_gate 不解析 enum）。无新坑。

**结论：主干可行，开工先钉必改1（kind 词表）+ 必改3（@doc false），把路 B 降级为「MVP 仅路 A」绕开必改2。** 三者都不动架构、不破不变式，属实现细节就地定。
