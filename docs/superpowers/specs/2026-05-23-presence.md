# SPEC — `Ezagent.Presence` (core primitive)

**Status:** rev 3 · 2026-05-23 (built on top of `Ezagent.CapabilityRegistry` PR #264)
**Tier:** `apps/ezagent_core/`
**Predecessors:** ARCHITECTURE.md §16 (Phoenix.Presence priority-1 ecosystem dep), Decision Log #10 ("Phoenix as transport — Endpoint/Socket/Channel/PubSub/**Presence**/Plug"), Decision Log #93 (online-offline events on `esr:session:<uri>:events`), `docs/superpowers/specs/2026-05-23-capability-registry.md` (cap-only Behavior pattern)
**Companion SPEC (separate PR):** `2026-05-23-read-receipts.md` (chat domain — uses but does not co-own Presence)

## Rev 3 changelog (vs rev 2)

PR #264 (CapabilityRegistry) landed first, eliminating the entire "cap-only Behavior anti-pattern" concern that drove rev-2's macro design. Rev 3 is much smaller because:

- `Ezagent.Behavior.Presence` becomes a **regular Behavior** with `dispatchable?/0 → false` (the new optional callback). `CapabilityRegistry.register/3` handles "cap subject without dispatch" natively — no `BehaviorRegistry` write, no raising `invoke/4` workaround.
- `Ezagent.Presence.subscribe/2` now takes an explicit `ctx` argument (codex Q2A — matches existing dispatch pattern, no invented ambient state). Cap shape comes from `CapabilityRegistry.needed_for(User, :online, uri)` — same path the registry already exposes.
- Plugin-isolation invariant is dropped per Allen Q3C ("对 core 单向依赖就够了"). Existing `layer_purity_test.exs` already enforces plugin→core single-direction; plugin-to-plugin coupling is allowed.
- `:phoenix` added to `ezagent_core/mix.exs` (Allen Q1A — confirmed not a layer violation; only the umbrella-dep rule is enforced).
- `recently_present?/2` DROPPED for V1 (codex round-2 HIGH-4 — `meta.since` semantics didn't work for long-lived connections without a heartbeat layer). Future heartbeat-based freshness check is a separate SPEC.
- `handle_metas/4` bridge unchanged from rev 2.
- Stale-window SLA unchanged (rev 2 §9.3).

## 1. Problem

Today there is no truth-of-record for "is this entity currently connected somewhere". Symptoms:

- LiveView session lists cannot render online dots
- Chat domain cannot make routing/notification decisions based on online state (e.g. "if user is offline, escalate to Feishu push")
- Operators cannot answer "is principal X currently connected via any transport" from `/admin/users`
- Crash recovery: when a LV socket dies, nothing fans out a `:left` event to interested consumers

The architectural decision was made — `Phoenix.Presence` is the chosen primitive. PR #264 (CapabilityRegistry) just landed the cap-discovery layer Presence needs. This SPEC ships the Presence primitive on top.

## 2. Goal

Land `Ezagent.Presence` in `apps/ezagent_core/` that:

- Lets ANY transport (LV / Feishu / CC / future Slack) `track(uri, transport_id, meta)` on connect and auto-untracks on calling-process exit
- Lets ANY consumer (chat domain fanout, LV views, admin UI, future routing rules) `list/1`, `present?/1`, `subscribe/2` to liveness state of an entity URI
- Emits **`{:ezagent_presence_diff, topic, %{joins, leaves, current}}`** tuple events (normalized from Phoenix.Presence's `%Phoenix.Socket.Broadcast{}` — no consumer dependency on Phoenix.Channel internals)
- Cap-gates `subscribe/2` via `Ezagent.CapabilityRegistry.needed_for(kind_module, :online, uri)` + `Capability.matches?/2` against the caller's `ctx.caps`
- Replicates across cluster (free from Phoenix.Presence + DNSCluster)
- Has explicit stale-window SLA (`permdown_on_shutdown: true` for graceful shutdown; up to ~30s stale for non-graceful node loss)

Non-goals:
- Read receipts → companion SPEC, chat domain
- "Last seen at" historical timestamp → User Profile attribute, identity domain
- Per-message delivery acknowledgment → explicitly deferred (codex round-1 reasoning kept; SPEC §6)

## 3. API surface

### 3.1 `Ezagent.Behavior.Presence`

Regular Ezagent.Behavior, cap-only (`dispatchable?: false`). Registered against `Ezagent.Entity.User` and `Ezagent.Entity.Agent` via CapabilityRegistry's standard path.

```elixir
defmodule Ezagent.Behavior.Presence do
  @moduledoc """
  Cap-only Behavior for entity presence subscription.

  `:online` is a subscription gate, not a dispatch target — it exists
  to give `Ezagent.Presence.subscribe/2` a cap shape coherent with
  the rest of CapBAC (`%Capability{kind, behavior: Ezagent.Behavior.Presence,
  instance, workspace_uri}`).

  `dispatchable?/0` returns `false`, so `CapabilityRegistry.register/3`
  records the subject but does NOT write to `BehaviorRegistry` —
  `Invocation.dispatch/1` can never accidentally invoke `:online`.
  `invoke/4` raises with a clear error if someone tries.

  Registered against User + Agent in `EzagentCore.Application.start/2`.
  """

  @behaviour Ezagent.Behavior

  @impl Ezagent.Behavior
  def actions, do: [:online]

  @impl Ezagent.Behavior
  def cap_subjects do
    [{:online, "observe an entity's online/offline status across all transports"}]
  end

  @impl Ezagent.Behavior
  def dispatchable?, do: false

  @impl Ezagent.Behavior
  def state_slice, do: :presence

  @impl Ezagent.Behavior
  def init_slice(_args), do: %{}

  @impl Ezagent.Behavior
  def invoke(:online, _slice, _args, _ctx) do
    raise "Ezagent.Behavior.Presence.:online is cap-only — subscribe via Ezagent.Presence.subscribe/2"
  end

  @impl Ezagent.Behavior
  def interface, do: %{}
end
```

### 3.2 `Ezagent.Presence` (the public API)

```elixir
defmodule Ezagent.Presence do
  @moduledoc """
  Cross-node liveness tracking for entity URIs. Thin URI-shaped wrapper
  over `Ezagent.Presence.Tracker` (Phoenix.Presence). Transport-agnostic;
  plugins write via `track/3`, anyone reads via `list/1` / `present?/1`
  / `subscribe/2`.

  ## Subscribe events

  Subscribers receive tuple messages:

      {:ezagent_presence_diff, topic, %{
        joins:   %{transport_id => [meta]},
        leaves:  %{transport_id => [meta]},
        current: %{transport_id => [meta]}
      }}

  This is broadcast by `Ezagent.Presence.Tracker.handle_metas/4` via
  `Phoenix.PubSub.local_broadcast` after Phoenix.Presence has updated
  its CRDT. Documented translation of the raw `%Phoenix.Socket.Broadcast{}`
  the default dispatcher emits — pattern-matchable from a plain GenServer
  without depending on Phoenix.Channel.

  ## Stale-window SLA (§9)

  After non-graceful node loss (SIGKILL, BEAM panic, hardware crash),
  remote views show this node's entries as ONLINE for up to ~30s
  (Phoenix.Tracker's default `down_period`) before they expire. Graceful
  shutdown is immediate (`permdown_on_shutdown: true`).
  """

  alias Ezagent.{Capability, CapabilityRegistry}
  alias Ezagent.Presence.Tracker

  @type entity_uri :: URI.t() | String.t()
  @type transport_id :: String.t()
  @type meta :: %{required(:transport) => atom(), optional(atom()) => any()}

  @doc "PubSub topic for `uri`'s presence diffs."
  @spec topic(entity_uri()) :: String.t()
  def topic(uri), do: "esr:presence:#{to_uri_string(uri)}"

  @doc """
  Mark `uri` as present via `transport_id`. The calling process is
  monitored — exit auto-removes. `meta` MUST include `:transport`.

  Raises if the SAME pid tries to track the SAME `(uri, transport_id)`
  twice on the same topic (Phoenix.Presence's underlying behavior;
  caller bug — P2 let-it-crash).
  """
  @spec track(entity_uri(), transport_id(), meta()) ::
          {:ok, ref :: binary()} | {:error, term()}
  def track(uri, transport_id, meta) when is_map(meta) do
    track(self(), uri, transport_id, meta)
  end

  @doc """
  Same as `track/3` but lets a long-lived caller (e.g. a supervisor)
  track on behalf of a short-lived child process.
  """
  @spec track(pid(), entity_uri(), transport_id(), meta()) ::
          {:ok, ref :: binary()} | {:error, term()}
  def track(pid, uri, transport_id, meta)
      when is_pid(pid) and is_binary(transport_id) and is_map(meta) do
    Tracker.track(pid, topic(uri), transport_id, meta)
  end

  @doc "Remove a `(uri, transport_id)` entry. Idempotent."
  @spec untrack(entity_uri(), transport_id()) :: :ok
  def untrack(uri, transport_id) when is_binary(transport_id) do
    Tracker.untrack(self(), topic(uri), transport_id)
  end

  @doc """
  All `(transport_id → [meta])` tracked for `uri`. List value handles
  CRDT same-key-multiple-nodes case.
  """
  @spec list(entity_uri()) :: %{transport_id() => [meta()]}
  def list(uri) do
    Tracker.list(topic(uri))
    |> Enum.into(%{}, fn {tid, %{metas: metas}} -> {tid, metas} end)
  end

  @doc "True if any transport currently tracks `uri`."
  @spec present?(entity_uri()) :: boolean()
  def present?(uri), do: list(uri) != %{}

  @doc """
  Subscribe the calling process to presence diffs for `uri`.

  Caller MUST pass `ctx` containing `:caps` (a `MapSet.t(Capability.t())`).
  The required cap shape comes from `CapabilityRegistry.needed_for(kind,
  :online, uri)` — `kind` is resolved from the URI scheme + first segment
  (`entity://user/...` → `Ezagent.Entity.User`, etc.). Raises
  `Ezagent.Capability.Unauthorized` on cap miss.

  Internal callers (chat domain's PresenceFanout, system admin LV)
  pass `%{caps: :system}` — the system bypass mirrors the
  `Ezagent.Audit.Writer` pattern.

  Subscribers receive `{:ezagent_presence_diff, topic, %{...}}` (see
  module @doc).
  """
  @spec subscribe(entity_uri(), ctx :: map()) :: :ok
  def subscribe(uri, ctx)

  @doc "Unsubscribe the calling process from `uri`'s presence diffs."
  @spec unsubscribe(entity_uri()) :: :ok
  def unsubscribe(uri) do
    Phoenix.PubSub.unsubscribe(EzagentCore.PubSub, topic(uri))
  end

  defp to_uri_string(%URI{} = uri), do: URI.to_string(uri)
  defp to_uri_string(s) when is_binary(s), do: s
end
```

### 3.3 `Ezagent.Presence.Tracker`

```elixir
defmodule Ezagent.Presence.Tracker do
  @moduledoc false

  use Phoenix.Presence,
    otp_app: :ezagent_core,
    pubsub_server: EzagentCore.PubSub

  alias Phoenix.PubSub

  @impl true
  def init(_opts), do: {:ok, %{}}

  @impl true
  def handle_metas(topic, %{joins: joins, leaves: leaves}, presences, state) do
    # Bridge Phoenix.Presence's CRDT diff into a plain tuple message that
    # subscribers added via `Ezagent.Presence.subscribe/2` can pattern-match
    # without depending on `Phoenix.Socket.Broadcast`. We `local_broadcast`
    # (single-node) — Phoenix.Presence already handles cross-node CRDT
    # convergence; each node's local handle_metas fires on its own state.
    msg =
      {:ezagent_presence_diff, topic,
       %{
         joins: normalize_metas(joins),
         leaves: normalize_metas(leaves),
         current: normalize_metas(presences)
       }}

    PubSub.local_broadcast(EzagentCore.PubSub, topic, msg)
    {:ok, state}
  end

  # Phoenix.Presence stores values as `%{transport_id => %{metas: [meta]}}`.
  # Normalize to `%{transport_id => [meta]}` for the SPEC contract.
  defp normalize_metas(presences) do
    Enum.into(presences, %{}, fn {tid, %{metas: metas}} -> {tid, metas} end)
  end
end
```

## 6. Failure modes & semantics

### 6.1 Process crashes mid-track
Phoenix.Presence's `Process.monitor` fires `:DOWN` → entry removed locally → CRDT diff replicates → `:leaves` event fires on all nodes' topics. **No stale window for local DOWN.**

### 6.2 Graceful node shutdown (deploy / restart)
`permdown_on_shutdown: true` → Tracker permdowns its own presences to all replicas before exit. Remote view sees `:leaves` near-immediately (sub-100ms intra-cluster PubSub propagation).

### 6.3 Non-graceful node loss (SIGKILL, OOM, BEAM panic, hardware crash)
The tracker did not get to broadcast permdown. Remote nodes show this node's presences as ONLINE until `:down_period` (default 30s) elapses without heartbeat — then emit `:leaves` and remove from `list/1` / `present?/1`.

**SLA: up to ~30s of stale "online" view after non-graceful node loss.** Native Phoenix.Presence behavior; consumers needing tighter accept the trade-off OR layer their own heartbeat (future SPEC).

### 6.4 Network partition
Each partition keeps local view. On heal both sets merge (`list/1` union). Brief flicker on heal is expected.

### 6.5 Meta size discipline
Phoenix.Presence replicates meta on every change. Keep small. Guidance via @spec: `%{transport: atom, since: DateTime, optional small attrs}`.

### 6.6 Subscriber missing intermediate events
Phoenix.Presence doesn't replay history. Late subscriber must `list/1` once at subscribe time, then merge in future diffs.

### 6.7 Why no `recently_present?/2` in V1
(Codex round-2 HIGH-4.) A `meta.since` (connection-start) timestamp doesn't capture liveness for long-lived connections — a healthy 1-hour connection would look "not recent" past `max_age_ms`. Real freshness requires a heartbeat layer that updates `meta` periodically. Out of scope for V1; future SPEC if needed.

## 10. Open questions for Allen

- **System-bypass shape** — rev 3 §3.2 uses `ctx.caps == :system` for internal-trusted bypass (chat domain's PresenceFanout). Acceptable, or want a separate explicit marker (e.g. `:system_actor` atom field on ctx)? Matches the `Ezagent.Audit.Writer` pattern; keeping it.
- **Workspace-scoped `:online` cap grant** — User.default_caps grants `Capability{kind: :session, behavior: :any, instance: :any, workspace_uri: ws}`. Should we add a similar `Capability{kind: :user, behavior: Ezagent.Behavior.Presence, instance: :any, workspace_uri: ws}` so users in the same workspace can see each other's presence by default? Going YES (matches existing chat-cap precedent). Easy to narrow later.
- **Agent presence visibility** — registering `:online` on Agent Kind means operators can see "is the cc agent currently online", BUT a User in the same workspace would inherit visibility under the workspace-default-grant policy. If this is undesirable (Agent presence should be admin-only), Agent registration moves to a separate "admin-only" cap with `instance: :any` + workspace_uri default narrower. Going with workspace-visible for V1; flagging.
