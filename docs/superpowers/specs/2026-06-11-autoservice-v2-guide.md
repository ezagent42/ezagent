# AutoService v2 架构引导

> 状态: **v3** | 日期: 2026-06-12
> 给团队成员的快速入门 — 了解 AutoService v2 是什么、怎么工作、有哪些关键设计。
> 不需要懂代码，只需要理解概念和流程。
> 详细设计见 [`2026-06-10-autoservice-v2-design.md`](2026-06-10-autoservice-v2-design.md) (v3)
>
> **v3 变更**: 编排模型 = Session + CsOrchestrator Behavior (vs 旧 CsOrchestrator Kind)

---

## 1. 一句话概括

**一个插件体系，让任何企业都能拥有自己的 AI 客服助手。**

平台管理员创建"租户"（一个企业），租户管理员配置 AI 客服的身份、话术、知识库，客户通过聊天界面与 AI 客服对话，人工客服可以随时接管。

---

## 2. 概念映射 — AutoService 在 ezagent 中的位置

> 如果你已经了解 ezagent 的核心概念（Workspace、Session、Routing、CapBAC），这节帮你快速理解 autoservice 是怎么"复用"这些能力的。

```
AutoService 概念          ezagent 实现              说明
─────────────────────────────────────────────────────────────────
租户 (Tenant)      →     Workspace                 每个企业 = 一个 Workspace
                                                   "workspace://cinnox"

客户会话            →     Session                   客户聊天 = 一个 Session
                                                   "session://cs/<ws>/<name>"

AI 客服 (Agent)     →     Agent + AgentTemplate     fast agent = curl.agent (调用 DeepSeek HTTP)
                                                   slow agent = cc agent (Claude Code)

路由 (Routing)      →     RoutingRegistry           "客户消息 → 发给 session (cs_orchestrator.receive)"
                         + CsOrchestrator Behavior 编排 fast+slow (cancel+reopen 接管)

人工接管 (Turn)     →     Behavior.Turn             open → compose → claim → settle
                         (socialware domain)        cancel+reopen (CsOrchestrator Behavior 内)

消息门控 (Feed)     →     CustomerFeed              只投递已发布的回复（不是草稿）
                         (socialware domain)        接管期间客户看不到客服编辑中内容

内容存储            →     ConfigStore               租户配置（品牌名、渠道等）
                         (socialware domain)        不走文件系统，走数据库

权限控制            →     CapBAC                    5 维权限: kind/behavior/action/
                         (ezagent_core)             instance/workspace_uri

外部 AI 服务调用    →     ExternalAdapter            DeepSeek HTTP API（curl agent）
                         + cc bridge                Claude Code SDK bridge（cc agent）
```

### 关键架构原则

```
core (ezagent_core)         — 完全不动（dispatch, routing, CapBAC, Kind）
domain (ezagent_domain_*)   — 完全不动，纯复用（Turn, CustomerFeed, SocialwareSession Kind）
plugin (ezagent_plugin_*)   — 所有 autoservice 新功能都在这里
编排 (CsOrchestrator)       — Behavior 注册在 SocialwareSession Kind 上
                              - Session 进程内执行 (同进程 Turn 操作)
                              - fan-out via dispatch_after_commit effects
                              - 状态在 Session slice 的 cs_orchestrator namespace
```

**autoservice 不发明新机制，只组合现有能力。** 就像搭积木——Turn 是 socialware 提供的"回合管理积木"，CustomerFeed 是"消息门控积木"，Session 是"会话管理积木"，CsOrchestrator Behavior 是"编排积木"（注册在 Session 上），autoservice 把它们拼成客服场景。

                              │

## 4. AI 客服的"大脑"是怎么构成的

AI 客服需要知道三件事：**我是谁**、**我会什么**、**我查什么**。

我们用三层内容来定义：

```
┌──────────────────────────────────────────────────┐
│                   Soul（灵魂）                     │
│            "我是谁，我该怎么做"                     │
│                                                  │
│  始终在 AI 的"记忆"里（每次对话都带着）              │
│  · 身份：我是 XX 公司的客服助手                      │
│  · 安全：不能说我是 AI，不能承诺做不到的事            │
│  · 风格：简洁、友好、用中文回复                      │
│  · 规则：遇到投诉必须转人工                         │
│                                                  │
│  大小：约 30KB 文本                                │
└──────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────┐
│                  Skill（技能）                      │
│            "我会处理哪些场景"                        │
│                                                  │
│  AI 需要时才查阅的"手册"（不是每次都看）              │
│  · 新客户引导流程："先问姓名→问需求→推荐产品"         │
│  · 故障排查流程："先确认型号→检查网络→尝试重启"       │
│  · 投诉处理流程："先道歉→记录详情→升级人工"           │
│                                                  │
│  按需加载，不读不花钱                               │
└──────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────┐
│                    KB（知识库）                     │
│              "我知道哪些事实"                        │
│                                                  │
│  结构化的"百科"（AI 主动搜索查询）                    │
│  · 产品信息：规格、价格、功能对比                     │
│  · 术语表：DID=直拨号码、IVR=语音导航               │
│  · 触发词：客户说"退款"、"投诉" → 升级人工           │
│                                                  │
│  存储在数据库里，AI 通过搜索工具查询                   │
└──────────────────────────────────────────────────┘
```

## 5. Soul 的四层继承

Soul 不是一份文件，而是**四层叠加**（后一层覆盖前一层）：

```
第 0 层：框架层（Framework）
  "所有 AI 客服都必须遵守的基本规则"
  例：不能说自己是 Claude/Anthropic，不能承诺无法做到的事

第 1 层：平台层（Platform）
  "我们平台上所有 AI 客服的通用规范"
  例：支持多语言、回复长度限制

第 2 层：行业层（Industry）
  "云通讯行业 AI 客服的特定要求"
  例：涉及号码、线路、合规要求

第 3 层：租户层（Tenant）
  "CINNOX 这家公司的 AI 客服专属设置"
  例：品牌名 CINNOX、母公司 M800、产品线
```

**租户管理员只需要填第 3 层的"填空"**：
- 模板里写 `{{bot_full_name}}`，租户填 `"CINNOX AI Bot"`
- 模板里写 `{{escalation_triggers}}`，租户填 `"转人工, 投诉, 退款"`
- 不需要懂 Markdown，填表即可

## 6. Skill 的四层加载

和 Soul 类似，Skill 也有四层，**租户的 Skill 优先级最高**：

```
租户 Skill（最高优先）
  "CINNOX 专属的客户分类流程"
    ↓ 如果没有，用
行业 Skill
  "云通讯行业通用的合规检查流程"
    ↓ 如果没有，用
平台 Skill
  "平台通用的故障排查流程"
    ↓ 如果没有，用
框架 Skill
  "所有 AI 客服共用的基本对话规则"
```

## 7. 内容发布流 — 编辑→预览→发布

租户管理员修改 AI 客服的内容时，不会直接生效。需要经过发布流程：

```
┌──────────┐     ┌──────────┐     ┌──────────┐
│ 编辑      │ ──→ │ 预览测试   │ ──→ │ 发布      │
│ (草稿区)  │     │ (沙盒)    │     │ (生产区)  │
└──────────┘     └──────────┘     └──────────┘
  "改一改"         "试试看"          "正式上线"
```

### 为什么要有预览？

```
错误做法：
  租户改了 Soul → 直接生效 → 客户看到错误内容 → 事故

正确做法：
  租户改了 Soul → 进入草稿区（沙盒）
  → 管理员用预览功能测试（模拟客户对话，只有管理员能看到）
  → 确认没问题 → 发布 → 正式客户才能看到新内容
```

### 选择性发布

一次可能修改了很多内容，但不想全部发布：
```
本次改动：
  ☑ 修改了 AI 客服的自我介绍     ← 要发布
  ☑ 修改了投诉处理流程            ← 要发布
  ☐ 修改了产品价格（还没确认）     ← 取消勾选，不发布
  ☐ 修改了知识库（还在测试）       ← 取消勾选，下次再发
```

## 8. 客户对话流程

客户发一条消息，背后发生了什么：

```
客户："CINNOX 支持哪些渠道？"
  │
  ▼
┌──────────────────────────────────────────────┐
│ 第 1 步：即时安抚（快速 AI，~1 秒）              │
│   "让我帮您看看..."                            │
│   客户马上看到回复，知道有人在处理               │
└──────────────────────────────────────────────┘
  │
  ▼
┌──────────────────────────────────────────────┐
│ 第 2 步：正式回复（主 AI，~30 秒）               │
│   AI 用自己的 Soul（身份+规则）                  │
│   + 查阅 Skill（相关流程手册）                   │
│   + 查询 KB（产品知识库）                        │
│   → 生成正式回复："CINNOX 支持 Web、移动端、API…" │
└──────────────────────────────────────────────┘
  │
  ▼
┌──────────────────────────────────────────────┐
│ 第 3 步：门控投递                              │
│   回复先经过"可见性检查"                        │
│   正常情况 → 客户看到                           │
│   人工接管中 → 客户看不到（人工在编辑）           │
└──────────────────────────────────────────────┘
```

## 9. 人工客服接管流程

当 AI 判断需要人工介入，或客户主动要求转人工时：

```
AI 判断需要转人工
  │
  ▼
┌──────────────────────────────────────────────┐
│ 1. AI 暂停回复                                │
│    客户的消息不再发给 AI，而是发给人工客服        │
└──────────────────────────────────────────────┘
  │
  ▼
┌──────────────────────────────────────────────┐
│ 2. 人工客服接管                               │
│    客服在工作台看到会话，点击"接管"              │
│    此时客户看不到客服正在编辑的内容（草稿保护）    │
└──────────────────────────────────────────────┘
  │
  ▼
┌──────────────────────────────────────────────┐
│ 3. 客服编辑回复并提交                          │
│    客服写完回复，点击"发送"                     │
│    客户现在看到回复                            │
│    AI 恢复服务（可选）                         │
└──────────────────────────────────────────────┘
```

## 10. 数据分区 — 版本隔离

```
每个租户有两套数据区：

┌──────────────────┐     ┌──────────────────┐
│   沙盒 (Sandbox) │     │  生产 (Release)   │
│   草稿区          │     │  已发布区          │
│                  │     │                  │
│   管理员编辑       │     │   客户看到的       │
│   预览测试         │     │   正式 AI 使用      │
│   随时可改         │     │   不可直接修改      │
│                  │     │                  │
│   修改 → CR → 发布 → → → → → → → 进入生产     │
└──────────────────┘     └──────────────────┘

CR = Change Request（变更请求）
     "我要把这些改动发布到生产"
```

## 11. 租户隔离

每个租户（企业）的数据完全隔离：

```
平台
 ├─ 租户 CINNOX
 │   ├─ AI 客服配置 (Soul cinnox 版)
 │   ├─ 技能 (Skill cinnox 版)
 │   ├─ 知识库 (KB cinnox 产品数据)
 │   ├─ 客服会话
 │   └─ 人工客服账号
 │
 ├─ 租户 Acme
 │   ├─ AI 客服配置 (Soul acme 版)
 │   ├─ 技能 (Skill acme 版)
 │   ├─ 知识库 (KB acme 产品数据)
 │   ├─ 客服会话
 │   └─ 人工客服账号
 │
 └─ 租户 Demo
     └─ ...
```

**CINNOX 的管理员看不到 Acme 的数据，Acme 的客户不会得到 CINNOX 的 AI 回复。**

## 12. 关键术语速查

| AutoService 术语 | ezagent 对应 | 含义 |
|---|---|---|
| **租户 (Tenant)** | Workspace | 一个使用平台的企业（如 CINNOX → workspace://cinnox） |
| **Soul** | — (内容层) | AI 客服的身份、规则、风格（始终加载，存文件系统） |
| **Skill** | — (内容层) | AI 客服处理特定场景的流程手册（按需查阅，cc agent Read tool） |
| **KB** | — (内容层) | 知识库，产品数据、术语、触发词（SQLite + MCP server） |
| **Slot** | — (内容层) | 模板中的填空位，如 `{{bot_full_name}}` → "CINNOX AI Bot" |
| **沙盒 (Sandbox)** | — (文件系统) | 草稿区，管理员编辑和预览的地方 |
| **生产 (Release)** | — (文件系统) | 已发布区，客户实际看到的内容，`_current` 符号链接指向当前版本 |
| **CR** | ConfigStore | 变更请求，从沙盒到生产的发布单 |
| **AI Agent** | Agent + AgentTemplate | fast=curl.agent(DeepSeek), slow=cc agent(Claude Code) |
| **路由** | RoutingRegistry + RuleStore | 客户消息→agent 的规则，接管时 disable/enable |
| **Turn** | Behavior.Turn (socialware) | 回合管理: open→compose→claim→settle |
| **CustomerFeed** | CustomerFeed (socialware) | 消息门控，只投递 settled 消息，visibility 控制 |
| **接管** | Turn.claim | 人工客服介入 AI 对话 |
| **权限** | CapBAC | 5 维权限: kind/behavior/action/instance/workspace |
