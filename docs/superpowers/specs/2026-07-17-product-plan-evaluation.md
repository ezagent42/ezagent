# 产品方案评审 ·《俞军产品方法论》

## 〇、评审对象类型

**主类型：A（内部 spec / PRD / 功能设计）。** 文档目标是让研发团队照着构建 beta 版本。

纳入 **E 类视角（改版/迭代）** 的「替换成本 = 老用户习惯被打断」必查项——因为产品建立在已有 Ezagent 平台上，beta 用户是被 admin 邀请加入存量系统的，他们的第一个体验是从「无 Ezagent 使用习惯」到「建立 Ezagent 使用习惯」的切换。

## 一、方案翻译（交易本质还原）

- **用户（情境 + 需求集合）：** 被 admin 邀请加入 Ezagent workspace 的企业成员。情境：打开浏览器 → 进入 workspace → 和 agent 对话 → 期望得到有用的 AI 回复来完成工作任务。需求强度：中等偏高——有真实的工作场景需要 AI 辅助，但还没到「没这个活干不了」的程度。
- **交易结构：** 平台提供：零配置的 AI agent（托管 agent 模型，用户不需自己搞 API key）+ 团队协作空间 + 失败时的可行动错误提示。用户支付：时间（学习 world 界面）、注意力、认知负担（理解 workspace/agent 概念）。企业层面支付：未在文档中讨论（这是文档的一个缺口，见维度二）。
- **旧的利益平衡：** (a) 直接用 ChatGPT/Claude 网页版 → 有 AI 回复，但无团队协作、无 workspace 上下文；(b) 无 AI 助手 → 旧体验 ≈ 0，但也没有被满足的需求。
- **翻译判断：** 文档可以翻译成「谁、什么情境、支付什么、换取什么效用」——**这是一份产品方案，不是功能清单。** 但「企业支付什么」这笔交易没写，是缺口。

## 二、五维评审

### 1. 用户价值核算 [4/5]

**新体验：** 三个核心增量——(a) 零配置：managed agent 模型意味着用户打开 workspace 就能用 agent，不需要搞 API key（对比直接使用 ChatGPT/Claude 需要自行注册获取 key）；(b) 团队空间：多人在同一 workspace 协作，agent 是共享资源；(c) 失败可行动：G5 的三层错误处理（知道缺什么 → 找谁修 → 兜底自动登记），对比现状的通用道歉是质的提升。

**旧体验：** 旧体验因用户类型差异大——「完美新用户」（从没用过 AI 助手的企业团队）旧体验 ≈ 0，净值最高；已有 ChatGPT 使用习惯的用户，旧体验中等（ChatGPT 的回复质量好但无团队协作），替换成本偏高。

**替换成本：** (a) 认知成本：理解什么是 workspace、agent、session——这是 Ezagent 概念模型的门槛，G7（onboarding 向导）被推到 post-beta 意味着 beta 用户要靠 admin 当面引导，增加了认知摩擦；(b) 使用成本：world 界面学习——G6（UI 可读性）推到 post-beta，意味着 beta 界面还有裸 UUID/atom 等问题，早期用户的体验会很粗糙；(c) 迁移成本（E 类视角）：从直接使用 ChatGPT → 切到 Ezagent workspace 的习惯打断。**但有个亮点：** 托管 agent 模型巧妙地消灭了一个替换成本——用户不需要自己搞 API key。v1 的 BYOK 假设下「获取 key」就是一道替换成本，v3 砍掉了。

**净值判定：** 「完美新用户」（旧体验≈0 的企业）净值明显为正。现有 ChatGPT 用户净值取决于 beta 体验的粗糙程度——G6/G7 推到 post-beta 意味着早期替换成本偏高，对这个人群的净值可能只是微正。

**红线检查：** 不触发——净值对主要目标人群（完美新用户）明显 > 0。但 beta 的极度精简（G4+G5 两条，不含 UI 可读性和 onboarding）是一把双刃剑：快速验证核心闭环的同时，早期用户体验的粗糙会压低净值。

> `★ 洞察：` 这条产品计划的真正巧妙之处在「砍」——不是砍功能（v1 10 条 → v3 2 条），而是砍掉了用户的一项支付成本（不需要自己搞 key）。在俞军框架里，降低支付成本 = 提升净值的合法路径。很多产品计划拼命加功能做「新体验」，但忽略了「降低替换成本/支付成本」这条同样有效的路。

**改进建议：** beta 上线时至少把 G6 的 5 个痛点中挑 1-2 个低成本快赢做了（如错误消息去 atom 化、会话名校验修复），否则 beta 用户面对裸 `:unauthorized` 会直接怀疑产品坏了——不用等 G5 完整体制，先做局部止血。

### 2. 好产品三属性 [3/5]

**有效用 — 成立。** 企业用户获得一个「打开就能用」的团队 AI 助手。但效用的**主观感知**受制于 beta 界面的粗糙度——agent 回复了但界面显示裸 UUID 和 `:unauthorized`，用户能感知到的效用会大打折扣（俞军：用户感知不到的效用 = 没有）。

**有利润 — 文档未讨论，需补。** 整份产品计划（v3 + SOP）对商业模式保持沉默。作为 beta spec 这可以接受——beta 的目标是验证用户价值而非赚钱。但产品计划应至少**标注此缺口**：「beta 阶段不涉及商业化；盈利模型将在 beta 闭环验证通过后单独设计」。否则读文档的人不知道这是「刻意不做」还是「忘了」。

**可持续 — 有好的信号，但未展开论证。** 三个好信号：(a) 托管 agent 模型 vs BYOK——平台集中管理凭证比散落在各企业 founder 手里更可持续（不会出现「founder 离职、key 失效、整个 workspace 的 agent 停摆」）；(b) G5 通用错误机制——运作层面的可持续基础设施（降低每次新增功能的错误处理成本）；(c) 决策 ③ 的 agent 分身架构（单独立项）——在架构层面考虑了「一 agent 服务多企业」的扩展性。**但：** 可持续性需要验证指标（如「beta 上线后 N 周内用户留存率」「agent 失败率」「admin 修复响应时间」），文档没有给。

**判定：** 有效用成立；有利润待补；可持续有好的设计意图但缺乏验证指标。整体不触发「可持续 1-2 分 → 最高有条件合格」的红线——因为这是一个 beta spec，不要求完整的商业论证，但要求它承认缺口的存在。

**改进建议：** 在文档中加一段 §1.5——「beta 不涉及的维度」：明确标注盈利模型和留存指标不在 beta 范围，将在 beta 闭环验证后单独设计。这不是写方案，是让读方案的人知道边界在哪。

### 3. 用户模型 [4/5]

| 属性 | 评审发现 |
|------|---------|
| **异质性** | **好。** G5 明确区分了「有权限修复的用户（Layer 1）」和「无权限修复的用户（Layer 2）」——两群人对同一错误的体验和行动路径完全不同。G6 区分了 admin（认识 UUID）和普通用户（不认识）。没有假设单一画像 |
| **情境性** | **好。** 用户旅程锚定具体场景：「用户发消息 → agent 失败 → 看到错误消息」。不是空谈「用户需要更好的错误提示」 |
| **可塑性** | **未深挖，beta 可接受。** 托管 agent 模型在培养用户习惯：「你不需要自己搞 key，直接用就行」——这是在养成一个不关心底层凭证的心智模型。长期看是对的（降低认知负担），但 beta 期间如果 admin 修错了、agent 还是不能用，用户会困惑「为什么我什么都不用做但还是不行」 |
| **自利性** | **好。** Layer 2 用户行为（点击「发送提醒给 admin」）是自利的——用户想让 agent 能用，所以愿意通知 admin。没有指望用户「为平台好」而做额外的事 |
| **有限理性** | **好。** G5 结构化错误消息顺应系统 1——用户不需要分析 `:unauthorized` 是什么意思、不需要知道 `credential_status` 在哪看，直接看到「Agent 未配置凭证 → 请联系 founder 陈瑞华 → 点击发送提醒」。每一步都是识别而非推理 |

**扣分项：** 文档没有明确说出「完美新用户」是谁——虽然在 §1 用户画像里写了「被 admin 邀请加入 workspace 的企业用户」，但没有进一步刻画：这些人是第一次用 AI 助手、还是从 ChatGPT 迁过来的、他们的技术能力如何。对于一份 beta spec 这不致命，但如果能加一段「beta 期最该优先服务的两类用户」，用户模型的分数可以到 5。

### 4. 交易模型与利益相关方 [3/5]

**利益相关方分析 — 做得好的部分：**

| 角色 | 得 | 失 | 文档是否核算 |
|------|----|----|:--:|
| 企业用户（workspace member） | 零配置 AI 助手 + 失败可行动 | 学习 world 界面 + 认知门槛 | ✅ G4/G5 用户旅程 |
| Admin / Founder | 统一管理 agent 凭证 + 收到修复提醒 | 增加了运维负担（用户会 @ 你修东西） | ✅ G5 Admin 行为总览 |
| 平台（Ezagent） | 验证核心闭环 → 积累 beta 数据 → 为规模化打地基 | 托管 agent 的 API 调用成本（谁付？） | ❌ 未讨论 |
| 功能负责人（研发） | 标准化错误注册流程 → 减少每次新功能的错误处理成本 | SOP 学习成本 + 迁移现有 `error_message/1` 的成本 | ⚠️ SOP §3 覆盖，但迁移成本未量化 |

**利益创造与利益分配 — 最大的缺口。** 「利从何来」说清楚了（agent 回复 → 用户价值）；「利往何去」完全没说——平台怎么回收托管 agent 的 API 成本？企业付不付钱？付多少？这笔交易在 beta 期间能不能至少打平平台成本？

**多边平衡 — 有好设计但缺验证。** G5 Layer 2 的「用户发提醒 → admin 修 → 用户收到回执」是一个良性闭环：双方都受益（用户得到修复的 agent，admin 知道出了问题）。但如果 admin 被提醒频率过高（beta 早期 bug 多），这个闭环会从「互助」退化为「骚扰」——admin 的支付成本（注意力被打断）超过收益。文档没有给缓解措施。

**改进建议：** (a) 在 §1 加一段标注：「beta 不涉及商业化——平台 API 成本由 Ezagent 自行承担，不计入 beta 验证范围」；这块明确说「不做」比沉默好。(b) G5 加一条 admin 侧的 AC：「admin 在 beta 期间每周收到的修复提醒 ≤ N 条」——给 admin 的注意力成本设个上限，超过说明系统稳定性有问题而非错误机制的问题。

### 5. 决策质量 [4/5]

**决策依据类型 — 诚实。** 文档明确标注了 §0 的 7 条裁定来自 lead，v1→v3 的变化逻辑（为什么 G1-G3 降 backlog、为什么取消 stub_grant、为什么 G5 升级）有迹可循。不是「我觉得这样更好」，而是「lead 裁定了 X，所以改成了 Y」。

**理性三要素：**
- **理性的信念（有自我怀疑吗？）：** 有。§0 的存在本身就是自我怀疑的结果——v1 被 lead 打回，而不是坚持「我的产品判断是对的」。Return 里记录了 method friction，说明在复盘「哪想错了」。
- **理性的目标（被偷换成虚荣指标了吗？）：** 基本干净。beta 的成功定义是「admin 开通 workspace → agent 回复」，不是「完成 10 条缺口的 UI」「用户量达到 X」。但 G5 的验收标准第 AC11 条（「冷启动实测：普通成员在 agent 失败时能理解发生了什么」）稍软——「能理解」怎么验证？是问卷还是观察？建议改成一个可观测的行为指标，如「用户在看到错误消息后的下一步操作：点击修复链接 or 点击发送提醒 or 放弃（关闭页面）」。
- **理性的行动（当前约束下最优吗？）：** 在当前约束（cap-signing 排期中、agent 分身架构未定、beta 范围 = admin 手动开通）下，v3 的选择是合理的。把 10 条缺口砍到 2 条 beta P0 是克制——知道什么不做。

**致命假设与证伪 — 有，但不完整：**

文档暴露了至少 3 条致命假设，但没有主动标注和给验证路径：
1. **「agent 分身架构能及时就绪」**——G4 的凭证就绪依赖两个东西：cap-signing + agent 分身架构。如果分身架构排期远超 cap-signing，G4 会被双杀。文档没有问「如果分身架构比 cap-signing 晚很多怎么办」。
2. **「admin 愿意承担修复负担」**——G5 Layer 2 假设 admin 会响应提醒并修复。如果 admin 不理（或不会修），整个 Layer 2 链路断裂——用户发了提醒 → 石沉大海 → 挫败感比没有提醒机制更糟。
3. **「beta 界面粗糙度不致命」**——G6/G7 推到了 post-beta，假设 admin 当面引导能弥补。但如果 admin 也不熟悉界面、或者用户是远程加入的，裸 UUID 和 404 会直接造成用户流失。

**权衡取舍 — 好。** v3 最明确的选择是「只做 G4+G5，其余全推到 backlog/post-beta」——这是一个真实的取舍（放弃了 UI 可读性、放弃了 onboarding、放弃了 KB 导入…），而不是「全都要」。§2 总览表和 backlog 触发条件是取舍的体现。

**改进建议：** 把上面 3 条致命假设写进文档（加一段 §1.6「beta 的致命假设与证伪路径」），每条给一个最小验证方式。例如假设 2：「beta 上线第一周，人工观察 admin 对 Layer 2 提醒的响应率，若 < 80% 且不是因为不会修而是因为不想修，则重新评估 Layer 2 的设计」。

## 三、最终判定

### **有条件合格。**

这份产品计划**能让「对用户有效用、有利润、可持续」的交易更多发生吗？**——前半段（对用户有效用）成立；后半段（有利润、可持续）还没有，但作为 beta spec 不要求它现在就有，只要求它诚实标注边界。它在这一点上做到了 70%：利益相关方分析清楚、取舍明确、决策链路可追溯，但盈利模型和致命假设没有显性化。

### 最致命的 3 个问题

1. **盈利模型缺口（维度二）。** 整份文档对「平台怎么回收成本」保持沉默。beta 可以不做商业化，但不能不标注这是刻意不做——否则读文档的人（研发、lead、未来的产品负责人）不知道这是边界还是疏忽。

2. **致命假设未标证伪路径（维度五）。** 「agent 分身架构及时就绪」「admin 愿意承担修复负担」「beta 界面粗糙度不致命」——三条假设如果有一条错了，整条 beta 链路会断。文档没有主动暴露它们并给验证方式。这是产品计划从「好」到「经得起拷问」的最后一公里。

3. **beta 用户价值的感知度取决于被推迟的缺口（维度一/三）。** beta 只交付 G4+G5——agent 能回复、失败了有提示。但如果用户面对裸 UUID、404、`:unauthorized` atom，他们能感知到的效用会被界面粗糙度稀释。建议 beta 至少从 G6 里挑 1-2 个低成本快赢（错误提示去 atom 化、会话名校验修复）作为 beta 的「最低体验基线」。

### 达到合格线优先改的几点

1. 在 §1 加「beta 不涉及的维度」小节（盈利模型、留存指标），标注这些都是「刻意不做，非遗漏」
2. 加 §1.6「beta 致命假设与证伪路径」，3 条假设各给一个最小验证方式
3. 从 G6 挑 1-2 个快赢，标注为「beta 最低体验基线」（不改优先级，但标为 beta 上线前建议完成）
4. G5 AC11 的「用户能理解」改为可观测的行为指标
