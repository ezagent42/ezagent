§4 流程沉淀（Act）

  1. 强化——SPEC → codex 对抗审查 → 修订，先于构建。 no-tail spec 走了两轮审查，每轮都抓出真实架构缺陷（分类器语义、ABA-unsafe CAS、quarantine 生命周期、required-sweeper、flip fence）。在 spec 阶段抓住这些省下了一个坏掉的构建。循环跑到 SOUND 为止。
  2. 纠正失手——handoff = 自驱整段到目标分支，而非逐 phase PR 合并。 第一次 no-tail handoff 错误地把每个 phase 卡在 coordinator review 上；已修（#1414）为既定约定（feedback_phased_handoff_target_branch_no_wait / feedback_codex_handoff_self_merge_target）：codex 自驱 P0→P3 到一条目标分支，coordinator 一次性验收+合并。规则本在记忆里；失手在于应用。
  3. 强化——裸 mix test ≠ 本 umbrella 的验收信号。 entity-caps 复验显示 76/78「失败」是 harness 产物（未加载 sibling app 的 UndefinedFunctionError + SQL-Sandbox ownership）；CI gate 才是权威信号。红色复跑先对 ci.local 对账，再怪代码。
  4. 确认有效——诚实的分段验证胜过伪造的绿。 gaga 的 #1416 在不走任何 raw-RPC / live-DB / 提权捷径的前提下推进了 demo 并钉出真实缺口。这就是标准。
