## #1117 — World UI Surface Substrate

#1117 establishes a World-owned convention for plugin-contributed UI surfaces:

- `nav_surfaces/0`: optional left-rail entries.
- `session_tabs/0`: optional per-session tabs.
- `Ezagent.World.UiSurfaceProvider`: duck-typed read + fail-closed shape
  filtering.

This is a good split because the data is World UI data. It should not be added
to the core `Ezagent.Plugin` contract. For T7, this is the canonical home for
the **UI/surface declaration** carrier: a socialware package or plugin may
declare that a surface exists, but World owns the shell convention and rendering
adapter.

T7 implication:

- AutoService and kanban can both map "surface declaration" to this carrier.
- T7 does not need to invent a second UI-surface mechanism.
- Any socialware package checklist should distinguish "surface declaration" from
  "surface runtime/rendering".

## #1116 — Generic Role-Agent Materialization

#1116 extracts the generic mechanism for creating a per-session role-agent:

- Resolve role recipe by name through `RecipeRegistry`.
- Build a `cc x <role>` AgentTemplate via `DefaultAgentSeed`.
- Spawn a session/workspace-scoped agent through supported agent primitives.
- Land requested caps through the `GrantRecipeCaps` chokepoint.
- Support concrete `instance_overrides`, e.g. board-scoped kanban caps.

This is directly relevant to T7's installer/deployment boundary. A socialware
installer should be able to materialize package-declared agents/roles without
hand-stitching private runtime state.

T7 implication:

- Treat #1116 as the expected substrate for package role materialization.
- Do not duplicate this logic in AutoService seed code or kanban plugin code.
- Any remaining call to private stitching such as direct MCP registry mutation,
  hand-written working-copy binding, or ad hoc session manager startup should be
  treated as a supported-path gap, not product definition data.

## Key Boundary Concern

The largest T7-relevant concern is the #1110 `DefaultRecipes` direction.

In #1110, `pm-coordinator` and `dev-together` recipes were placed in
`ezagent_domain_agent` as default role data. #1116 intentionally drops
`DefaultRecipes` / `DefaultRecipeSeed` and keeps only the generic by-role
materialization path.

That drop is correct for the current boundary. PM/dev-together are product or
socialware-package definitions, not obviously platform domain defaults. They
should live in a package/default-pack layer unless there is an explicit product
decision that they are global ezagent defaults.

For T7, this is the exact distinction to preserve:

- **Substrate**: "materialize role X for session Y and grant declared caps".
- **Definition data**: "role X is pm-coordinator with these skills, prompts,
  caps, and board workflow assumptions".
