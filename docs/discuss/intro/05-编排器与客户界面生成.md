# 05 · 编排器 agent 怎么"长出"客户界面（动态 UI 生成全链路）

> 这一篇把产品工作流里最关键的一块拼图讲透：**客户最终在网页上看到的那块界面，不是程序员手写死的，而是会话里那个"编排器 agent"一轮一轮、用工具组合出来的。**
> 全程大白话，所有机制都带 `file:line`。读完你应该能回答：编排器经哪些工具改会话、客户那块 React 界面的 JSON 从哪来、turn 怎么把"准备好的页面"推到客户屏幕上。
> 配套阅读：本系列 [08 socialware 深入](./08-socialware深入.md)（公开会话的门）、[02 领域层全览](./02-领域层全览.md)。

---

## 0. 先建立一个总图（30 秒版）

把一个 socialware 会话想成一个"舞台"，台上有三类角色：

1. **编排器 agent（orchestrator）**——一个跑在沙箱里的 `claude` 进程，它是"导演"。它不直接写页面，而是**通过一组管理工具（MCP tools）改造会话本身**：往会话里加成员 agent、定路由规则、存模板……
2. **turn（一轮）**——会话里的状态机，把"一次交互"从"开工 → 派活 → 收活 → 合成 → 结算"走完。**结算（settle）那一步会把一个"页面树（page tree）"定格成一个不可变版本。**
3. **CustomerFeed（客户投影）**——一个**只读、带门禁**的投影层，专门算"客户此刻该看到什么"，把定格的页面树 + 客户可见的聊天消息打包，推到客户浏览器里的 React SPA 去渲染。

一句话串起来：**编排器用工具搭好"会话的形状" → 每来一轮交互，turn 收集各成员的产出、把其中的"页面"定格成一个版本 → CustomerFeed 把"已提交的那个版本"投影给客户 → 浏览器把这棵 JSON 页面树用 React 渲染出来。**

下面分四段拆。

---

## 1. 编排器 agent 怎么"够到"它的工具：MCP 传输三层

编排器是一个真的 `claude` 进程，它怎么调到 ESR（Elixir 这边）的能力？走的是一条**纯传输、零权限**的 MCP 桥。三层，每层只干一件事：

### 第一层：WebSocket 接入 + 身份认证

`Ezagent.Orchestrator.McpSocket`（`apps/ezagent_plugin_cc/lib/ezagent/orchestrator/mcp_socket.ex`）。

- 一个编排器 `claude` 进程 = 一条 WS 连接，连接参数必须带 `token` + `agent_uri`（`mcp_socket.ex:52-55`）。
- **身份是服务端推导的，不能伪造**：`verify_token/2` 检查 token 解析出来的 URI 必须等于声称的 `agent_uri`（`mcp_socket.ex:86-98`），验过后把它盖进 `socket.assigns.agent_uri`。后面"用哪套权限、改哪个会话"全部从这个**认证过的值**派生，绝不从 `tools/call` 的载荷里取（`mcp_socket.ex:32-39`）。这意味着一个 `claude` 进程没法把编排器界面指向别人的身份/权限/会话。
- 连接还把验证过的 token 暂存成 `:bridge_token`（`mcp_socket.ex:62-63`），后面要转发给会话域去验。

### 第二层：工具清单 + tools/call 转发

`Ezagent.Orchestrator.McpServer`（`apps/ezagent_plugin_cc/lib/ezagent/orchestrator/mcp_server.ex`）。这是 cc 插件的 **MCP 传输，本身不持有任何权限**（`mcp_server.ex:6-24`）。它只做三件事：

1. **报菜单**：`tool_schemas/0` 返回 MCP `tools/list` 形状的描述符，告诉编排器的 `claude` "你有这 9 个工具能用"（`mcp_server.ex:303-309`，菜单本体在 `tool_catalog.ex`）。
2. **转发 tools/call**：`handle_tool_call/3` 把线上传来的 `{工具名, 参数}` 解码，**按编排器 URI 在会话域的 Registry 里查到对应的 `SessionManager` 进程**，`GenServer.call` 一个裸元组 `{:run_tool, tool, arguments, bridge_token}` 过去（`mcp_server.ex:329-362`）。注意它**故意不 import 会话域**（`mcp_server.ex:26-34`），只靠 URI 字符串 + Registry 名字够到对方——这是运行时的边，不是编译期依赖。
3. **编码结果**：把 SessionManager 返回的裸结果映射成 MCP 的成功/错误形状（`mcp_server.ex:370-408`）。

> **冷启动自愈**：BEAM 重启后编排器进程和它的 SessionManager 都没了。`rebuild_from_durable/1`（`mcp_server.ex:146-197`）从持久化的会话快照里把会话 URI 反查出来，重新登记，并把会话 Kind + 编排器 Agent 都强制重新拉起，让重连后的第一个 tools/call 能找到活进程。这就是 [CLAUDE.md](../../../CLAUDE.md) 反复强调的"这条消息没人接会怎样"——这里的答案是"它会响亮地失败并自愈"，不是静默丢。

### 第三层：会话域真正执行工具（权限在这一层验）

`Ezagent.Orchestrator.Tools`（`apps/ezagent_domain_session/lib/ezagent/orchestrator/tools.ex`）。前两层都不持权限；**真正的权限校验（CapBAC）在每一次 dispatch 上发生**（`tools.ex:31-56`）。SessionManager 收到 `{:run_tool, ...}` 后，用 bridge token 验明编排器身份、重建它被委派的权限（caps），再调到这里。每个工具的 `ctx` 都带 `caller: 编排器URI` + `caps: 编排器被委派的权限`（`tools.ex:838-844`），LLM **永远不自己填** caller/caps/会话上下文（`tools.ex:73-79`）。

**为什么这样分层重要（对产品）**：编排器是个会"自由发挥"的 LLM，但它能对会话做的每一件事都被这三层卡死成"声明式工具调用 + 逐次鉴权"。它没法绕过去直接改数据库、改别的会话。这是"让 AI 导演安全地改造产品形态"的护栏。

## 2. 编排器手里的 9 个工具：它"组合界面"其实是在组合会话

菜单全文在 `tool_catalog.ex`（`apps/ezagent_plugin_cc/lib/ezagent/orchestrator/mcp_server/tool_catalog.ex:8-216`），语义在 `Ezagent.Orchestrator.Tools` 的模块文档表里（`tools.ex:19-29`）。分三组：

**A. 搭团队（往会话里加/换/删成员 agent）**
- `add_managed_member`（`tools.ex:132-179`）——从一个 AgentTemplate 起一个 worker agent，用一个稳定的 `role_name` 加进会话当成员。**这是编排器"招人进组"的动作。**
- `update_member_template`（`tools.ex:359-362`）——换某成员的底板模板并原地重建它（杀旧的、按新模板在同一 `role_name` 上起新的、重新接线）。
- `remove_member`（`tools.ex:393-406`）——按 `role_name` 移除成员，连带清理指向它的路由规则。

**B. 定流程（成员之间怎么传话）**
- `define_rule_set_rule`（`tools.ex:540-580`）——往一个具名"规则集"里加一条**单接收者路由规则**：消息匹配上某个 matcher，就投递给某个 `role_name` 的成员，可选地套一个提示词模板渲染。多 agent 流程就是一组这样的静态 `{from: X} → Y` 规则，**没有模型现算的"接力棒"**（`tools.ex:526-530`）。
- `define_prompt_template`（`tools.ex:646-672`）——装一个具名提示词模板，规则用 `prompt_template_ref` 引用它，投递时渲染。
- `define_legend`（`tools.ex:691-718`）——给一个规则集起一个面向用户的 `@传话游戏` 这样的把手，一喊它就触发整组流程。

**C. 存档（把当前会话形态固化成可复用的模板）**
- `update_template`（`tools.ex:808-809`）——把当前会话快照成"它来源的那个 SessionTemplate"的新版本。
- `save_template_as`（`tools.ex:812-813`）——快照成一个**全新**模板家族的第一版。
- `list_templates`（`tools.ex:816-819`）——列出（按权限过滤的）可见模板。

**这跟"生成客户界面"什么关系？** 关键认知：**编排器组合的不是像素，是"会话的运行形态"**——谁在组里、消息怎么流、套哪个提示词。客户看到的界面内容（聊天消息 + 页面树），是这套形态在每一轮交互里跑出来的**产物**。编排器调 `add_managed_member` 招了个"出图 agent"、定了条规则让用户的话路由给它，那么之后这个 agent 产出的页面树就会经 turn 定格、经 CustomerFeed 投给客户。**编排器是在"设计这台机器"，机器再"吐出界面"。**

> 注意：当前 main 的这 9 个工具里**没有**一个叫"写一个页面"的工具。页面树（`page` 节点）是成员 agent 在干活时**作为 turn 的产出物 ref 交回来的**（见下一段 `page_tree_from_ref`）。编排器塑造"谁来产出页面、什么时候产出"，页面内容本身由被招进来的成员 agent 生成。这正是 SKILL 里说"客户 UI 是 agent 动态生成的"的精确含义。

## 3. turn 怎么把一次交互"跑成"一个定格的页面版本

`Ezagent.Behavior.Turn`（`apps/ezagent_domain_session/lib/ezagent/behavior/turn.ex`）是 socialware 的**编排状态机**，拥有 `:turns` slice。一轮交互的生命周期（`turn.ex:17-71` 声明了这些 action）：

```
open（开一轮）→ dispatch（派子任务给各成员）→ deliver（收某成员的交付）
            → compose（把收齐的交付合成一个 turn 结果）→ [claim 进人工复核]
            → settle（结算：定格页面 + 提交客户投递）
```

**界面是怎么"冒出来"的，关键在 compose 和 settle 两步：**

### compose：从成员产出里挑出"页面树"，登记成一个不可变版本

`handle_compose/2 → compose_result_and_effects/3`（`turn.ex:299-312`、`420-459`）：

- 把各成员交回来的 `result_refs` 里**找出第一个 `kind: :page` 且带 `tree` 的 ref**（`page_tree_for/2` + `page_tree_from_ref/1`，`turn.ex:554-570`）。这棵 `tree` 就是**客户界面的 JSON 描述**。
- 找到了就分配一个新版本号，并发一个 `:put_version` dispatch，把这棵页面树**作为不可变版本追加进 `:surface` slice**（`turn.ex:424-442`）。
- 同时 `write_chat_messages/3`（`turn.ex:585-613`）把 `kind: :chat` 的 ref 写成聊天消息——`mode: :auto` 的轮自动设成 `:customer_visible`（`turn.ex:615-616`），`copilot`/人工复核的设成 `:operator_only`，先扣住不给客户看。

页面版本由 `Ezagent.Behavior.Surface`（`apps/ezagent_domain_session/lib/ezagent/behavior/surface.ex`）管，它拥有 `:surface` slice：`handle_put_version/2` 把每棵树存成一个带版本号的不可变条目（`surface.ex:50-66`），`handle_approve/2` 推进"已批准"指针（`surface.ex:68-77`）。**运营看最新版本，客户只看被批准的那个版本**（`surface.ex:99-106`）。

### settle：结算，把"批准 + 提交"作为提交后的副作用发出去

`handle_settle/2`（`turn.ex:329-358`）：

- 先 `prepare_settlement` 起一条结算记录、把目标消息可见性翻成客户可见（`turn.ex:536-546`）。
- 然后发出 `:approve`（推进批准指针到这一版）+ `:commit_settlement`（提交结算）——**但用的是 `:dispatch_after_commit`**（`turn.ex:344-348`、`507-521`）：这两个面向客户的副作用，只有在父 `:turns` slice **真的持久化提交之后**才会跑。这堵住了"页面已投递、但那一轮其实没存住"的孤儿投递 bug。
- 还有**崩溃恢复**：万一在"`:turns` 已标记 settled、但投递副作用还没跑"之间崩了，`activated/2` 每次启动自发一个恢复信号（`turn.ex:91-95`），`handle_signal/2` 扫所有 settled 但副作用还欠着的轮，重发 approve + commit（`turn.ex:110-166`）。再次呼应 CLAUDE.md 的"失败了谁会知道"——这里答案是"重启时会自己补上"。

**小结**：一轮交互结束时，会话里多了一个"已批准、已提交"的页面版本，和一批客户可见的消息。turn 是把"AI 们干的活"沉淀成"客户能看的定格内容"的那台沉淀机。

## 4. CustomerFeed 怎么把定格内容投给客户 + 浏览器怎么渲染

到这一步，内容已经在会话里定格了。**客户界面 = 一个只读、带门禁的投影 + 一套通用 JSON→React 渲染器。**

### CustomerFeed：只读、带门禁、按游标可回放的投影

`Ezagent.Socialware.CustomerFeed`（`apps/ezagent_domain_socialware/lib/ezagent/socialware/customer_feed.ex`）。客户路由**只能走这个模块**，绝不直接碰原始 MessageStore（`customer_feed.ex:1-16`）。它给客户算两样东西：

- **消息**：`MessageStore.committed_customer_visible/2`——只取已提交、客户可见的消息（`customer_feed.ex:29-40`）。
- **页面**：`customer_page/1`（`customer_feed.ex:367-372`）——**关键**：它渲染的是**"已提交的那个结算所记的版本"**，而不是 `surface.approved` 这个活指针（`customer_feed.ex:359-366` 讲了为什么：approve 先于 commit 翻状态，读活指针会漏出"已批准但没提交"的页面）。具体版本由 `committed_surface_version/1`（`customer_feed.ex:383-395`）按提交顺序（`committed_seq`）取最近一个带页面的提交，再 `Surface.tree_for_version/2` 取出那棵树（`surface.ex:114-124`）。

**投递是游标驱动的，丢通知也不丢数据**：客户投递记在 `CustomerOutbox`，每条提交时按提交顺序分配一个 `committed_seq` 游标（`customer_feed.ex:52-84`）。客户连上来时 `join/3`（`customer_feed.ex:113-140`）走"下界游标"协议：先订阅通知、再读快照、再从游标回放整段已提交积压，保证**那个窗口里来的提交即使通知丢了也会被回放补上**，靠 `committed_seq` 幂等去重（`customer_feed.ex:86-140`）。

> 这里再次体现 ezagent 的 router 心智：客户那条 `{:customer_delivery}` PubSub 事件只是**"敲门提醒"**，真正的数据源是持久的 outbox + 游标。丢一条提醒不会丢一条投递。

### 传输：Phoenix Channel 把快照推到浏览器

`EzagentWeb.Socialware.CustomerChannel`（`apps/ezagent_web/lib/ezagent_web/socialware/customer_channel.ex`）。join 时鉴权 + 拿初始快照 + 存游标（`customer_channel.ex:41-55`）；之后**每来一条投递提醒就 `CustomerFeed.replay/3` 从存的游标回放，把刷新的快照 `push("snapshot", ...)` 推给浏览器**（`customer_channel.ex:69-84`）。撤权时服务端推 `unauthorized` 再关闭通道——客户端也跟着 fail closed。

### 浏览器：通用 JSON→React 渲染器把页面树画出来

客户那块 SPA 是 `customer_app.js`（`apps/ezagent_domain_socialware/assets/js/customer_app.js`）：

- 连上 socket、join 那个 `socialware:customer:<session_uri>` 频道，把收到的 `snapshot` 存进 React state（`customer_app.js:34-73`）。
- 渲染时分两块：`ChatPane` 画客户可见的聊天气泡（`customer_app.js:121`、`126-159`），然后 **`renderJsonNode(snapshot.page, registry)` 把那棵页面树画出来**（`customer_app.js:122`）。

渲染器本体在 `json_render.mjs`（`apps/ezagent_domain_socialware/assets/js/json_render.mjs`）。它是个**节点类型 → React 组件**的注册表查表器（`json_render.mjs:1-29`）：每个 JSON 节点形如 `{type, props, children}`，按 `type` 在 registry 里找对应组件递归渲染。基础注册表支持四种节点（`json_render.mjs:21-29`）：

- `container`——容器，`layout: "grid" | "stack"` 决定网格还是堆叠（`json_render.mjs:31-56`）。
- `text`——文本段（`json_render.mjs:58-66`）。
- `table`——表格，吃 `columns` + `rows`（`json_render.mjs:68-116`）。
- `code`——**用 Sandpack 把代码跑成可交互的实时预览**（`json_render.mjs:118-137`），所以编排器/成员 agent 产出的页面里可以塞"能跑的 React/HTML 片段"。
- 不认识的类型走 `__unknown` 兜底，画一个"不支持的节点"占位（`json_render.mjs:139-151`），**不静默吞掉**。

所以"客户界面"在数据上就是**一棵 `{type, props, children}` 的 JSON 树**，由成员 agent 产出、turn 定格、CustomerFeed 投影、这个查表器渲染成 React。要扩展能渲染的 UI 种类，就往这个 registry 加节点类型。

## 5. 把全链路连成一句话（给产品工作流用）

> **编排器 agent** 经三层 MCP 桥（认证 socket → 零权限传输 → 会话域逐次鉴权执行）调用 9 个管理工具，**塑造会话的运行形态**（招成员 agent、定路由规则、套提示词模板、存档成可复用模板）；**每来一轮用户交互，`Turn` 状态机**派活给成员、收齐产出、在 `compose` 里把其中 `kind: :page` 的那棵 JSON 页面树**登记成 `:surface` 的不可变版本**、在 `settle` 里**提交后才**批准+投递；**`CustomerFeed` 只读地、按提交游标**把"已提交版本的页面树 + 客户可见消息"投影出来，经 Phoenix Channel 推到浏览器；浏览器里的 **`json_render` 查表器**把页面树渲染成 React 界面。

### 这对"团队产品开发 workspace"意味着什么

- **思维导图节点的"网页出口"**：一个对外展示状态的客户面，就是一个 `public_view` 会话的 CustomerFeed 投影。编排器决定"展示什么、谁来产出"，页面树就是那块出口的内容。
- **"产物挂载到节点"**：成员 agent 把产物（文本/表格/可跑代码片段）作为 turn 的 `kind: :page` ref 交回来，turn 定格成版本——这天然就是"把某岗位在某工具里的产出，沉淀到一个可投影的位置"。
- **动态而非写死**：要改客户面的样子/内容，不改前端代码，而是让编排器调工具改会话形态、或让成员 agent 产出不同的页面树。**这正是"编排器 agent 动态生成客户界面"在 ezagent 上的落地方式。**

### 配套与边界
- 公开会话的门（`public_view`、匿名生命周期、两个对外面）见 [08 socialware 深入](./08-socialware深入.md)。
- **产品化方向（还没进 main，别当已有）**：`world`（统一前端，最终吃掉客户面）+ `agent-schema`（编排契约规范）。今天 `/socialware/chat` 这套 React+json-render 是过渡形态。权威说明见 `.claude/skills/ezagent-socialware/SKILL.md` §Future。
