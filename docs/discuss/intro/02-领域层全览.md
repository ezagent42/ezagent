# 领域层全览

> 这篇讲 ezagent 里所有 `ezagent_domain_*` 这一层的 app（共 10 个）各自干嘛、关键模块在哪。
> 看完你应该知道：一条消息进来后，是哪些"域"在干活；产品最值钱的"公开会话给陌生人看"这件事落在哪里。
>
> 上游 main：`e2abc02f`。下面所有行号都是真实文件位置，可以直接点进去。

领域层是 ezagent 的"业务肉"。底下 `ezagent_core` 是引擎（消息怎么路由、怎么持久化、怎么保证不丢），但引擎本身不知道"会话""客服""租户"是什么——这些概念全在领域层。领域层往上是插件层（接微信、接 Telegram、接 Web），往下只调引擎。

下面按"它对用户意味着什么"分成五块来讲。

---

## 一、会话域（session）—— 一切的中心

**app**：`apps/ezagent_domain_session`

这是最大、最核心的一个域。所有"人和 agent 在一个房间里聊天"的逻辑都在这里。

### 一个会话是什么

会话（Session）就是一个"房间"：有成员（人 + agent）、有消息流、有时候还配一个编排器（orchestrator，统一从这个域跟 cc 域协作）来调度多个 agent 协作。

值得注意的一件事：**以前有两种会话 Kind**（普通聊天的、客服 socialware 的），现在**合并成了同一个可参数化的 Kind**。同一个 `Ezagent.Entity.Session`，靠模板挑选要装哪些行为，就能既当普通聊天房，又当客服会话房。

- 统一 Session Kind：`apps/ezagent_domain_session/lib/ezagent/entity/session.ex:1`（`@behaviour Ezagent.Kind` 在 `:21`）
  - `behaviors/0`（会话默认装的全部行为，是 chat + socialware 两套的并集）：`session.ex:56`
  - `chat_behaviors/0`（纯聊天子集）：`session.ex:72`
  - `socialware_behaviors/0`（客服/顾问会话子集，多了 Turn 回合状态机 + Surface 投影）：`session.ex:87`
  - 模板在 spawn 时通过 `:kind_base` 机制把上面某一套"穿"到具体实例上——这就是"可参数化"的意思。

### 会话怎么造出来

造一个会话不是一句话的事：要建房间、绑租户、可能还要拉起编排器、给编排器发权限、把房主和编排器拉进群——任何一步失败都得整体回滚（要么全成，要么当没发生过）。这套"原子建房"逻辑收口在一个地方：

- 单一建房入口（原子序列 + 失败回滚）：`apps/ezagent_domain_session/lib/ezagent_domain_instance_message/session_creator.ex:1`
  - 配套拆出来的几个小模块：`materializer.ex`（物化）、`rollback.ex`（回滚）、`template_resolver.ex`（解析模板）、`template_team.ex`（拉团队成员），都在同目录下。

### 模板——一个团队长什么样

会话模板（SessionTemplate）描述"一个多 agent 团队的配方"：哪些 agent 槽位、用哪个 agent 模板实例化、路由规则怎么连、配哪个编排器、落到哪个租户。它是 git 风格内容寻址版本化的（同样配置算出同样的哈希）。

- 模板 Kind + slice 结构：`apps/ezagent_domain_session/lib/ezagent/entity/session_template.ex:1`
- **要注意的内容键 `public_view`**：模板上有个 `public_view` 标志位，决定"这个会话允不允许陌生人公开看"。它从 JSON 边界（字符串键 `"public_view"`）被吸进持久化内容，再由客户面域的 `PublicView.public_view?/1` 读回来。定义在 `session_template.ex:719`，白名单字段登记在 `session_template.ex:726`。这是后面客服域那条"公开会话"链路的源头开关。

### ⚠️ 一个会让人困惑的命名

这个 app 里有一堆模块还顶着旧名字 `EzagentDomainInstanceMessage.*`（比如上面的 `SessionCreator` 全名是 `EzagentDomainInstanceMessage.SessionCreator`）。这是**故意不改的**——历史包袱，改名要动太多引用，没收益。看到 `instance_message` / `EzagentDomainInstanceMessage` 就当它是 session 域，别以为是另一个独立 app。

## 二、agent 物化域（agent）—— 造一个干活的 worker

**app**：`apps/ezagent_domain_agent`

会话域负责"房间和团队"，这个域负责"造出团队里的每一个 agent worker"。

一个 Agent Kind 代表"会话里的一个外部参与者"——通常是一个 Claude CLI（cc）子进程，通过桥接接进来，在房间里既能发消息也能收消息，地位跟人类房主平等。

- Agent 实体 Kind：`apps/ezagent_domain_agent/lib/ezagent/entity/agent.ex:1`
  - 它装的行为集（base + 按 flavor 加 CurlAgent 等）：`agent.ex:86`
- 从模板内容造单个 worker（**不自己读 slice，内容当参数传进来，避免自己 call 自己死锁**）：`apps/ezagent_domain_agent/lib/ezagent/entity/agent/template_spawn.ex:1`
- agent 模板：`apps/ezagent_domain_agent/lib/ezagent/entity/agent_template.ex`

这个域是个**无环叶子**：它只管"把一个 agent 造出来并接好线"，不反过来编排别人。谁来调度多个 agent 协作？是**编排器**，而编排器住在 session 域（配合 cc 域），不在这里。这样切是为了避免"造 worker"和"调度 worker"互相纠缠成环。

## 三、客户面域（socialware）—— 产品最值钱的一块

**app**：`apps/ezagent_domain_socialware`

> 这一节只点到为止，详细的回合状态机 / 结算交割 / 三层链路见同目录 `08-socialware深入.md`。

这是整个产品**最关键的差异化能力**：把一个内部会话，安全地"开个公开窗口"给**陌生匿名用户**看和聊。想象一个客服场景——你的客户不需要注册账号，点开一个链接就能跟 agent 对话；agent 背后是你配好的团队。这个"陌生人能进来"的整条链路就在这个域。

它解决三个问题：

**1. 这个会话允许公开吗？** —— 看模板上的 `public_view` 开关，fail-closed（默认不公开）。

- `Ezagent.Socialware.PublicView.public_view?/1`：`apps/ezagent_domain_socialware/lib/ezagent/socialware/public_view.ex:38`

**2. 陌生人是谁？怎么管他的生命周期？** —— 这一版的核心新东西是**匿名用户（anon-user）的完整生命周期**。陌生人第一次打开公开页，系统给他临时铸一个**只读匿名身份**（一个 `entity://<ws>/user/anon-<随机>` 用户，只有"看这一个会话"的窄权限），并记一条绑定。48 小时不活动就被后台清理掉。整套是 crash 安全的（清理半截宕机也不会留垃圾）。

- 铸匿名用户（`mint/1` / `mint_for_public_session/1`）：`apps/ezagent_domain_socialware/lib/ezagent/socialware/anon_user.ex:64`
- 匿名绑定表（anon-User ↔ session ↔ 最后活跃时间，兼当 GC 索引和 claim 令牌）：`apps/ezagent_domain_socialware/lib/ezagent/socialware/anon_binding.ex:120`
- 48h 过期清理逻辑：`apps/ezagent_domain_socialware/lib/ezagent/socialware/anon_user/gc.ex:26`
- 定时驱动清理的调度器（GenServer，小时级扫描）：`apps/ezagent_domain_socialware/lib/ezagent/socialware/anon_user/sweeper.ex`

**3. 陌生人看到的内容是什么？** —— 不是把内部会话原样暴露，而是过滤出一个"客户可见"的投影（feed）。

- `ChatFeed`（聊天 SPA 读模型，快照-重读，无光标）：`apps/ezagent_domain_socialware/lib/ezagent/socialware/chat_feed.ex:119`
- `CustomerFeed`（客户投影，有 delta 光标 + 可重放 + 结算凭证，更重）：`apps/ezagent_domain_socialware/lib/ezagent/socialware/customer_feed.ex:29`
- 两套签名 token 授权（客户纯匿名 token / 成员身份 token）：`customer_auth.ex:12`、`chat_feed_auth.ex:23`

一句话记住：**会话域决定"能不能公开"，客户面域决定"陌生人是谁、看到什么、待多久"**。

## 四、身份域（identity）+ 租户域（workspace）—— 谁是谁、归谁管

### 身份域

**app**：`apps/ezagent_domain_identity`

管"用户是谁、有什么凭证、有哪些权限"。

这里有个常被问的点：身份、凭证、能力**是不是有干净的分离**？答案是**有**——User 实体装了三套行为，对应三个分离的 slice：

| 这一层 | 存哪 | 持久化后端 |
|---|---|---|
| 身份 / 能力（caps） | `:identity` slice（一个权能集合） | 快照（snapshot-on-change） |
| 凭证（密码） | `:user_credentials` slice 只放计数器 | 真正的 password_hash 在 `users` 表 |
| 令牌 | `:user_tokens` slice 只放计数器 | 令牌在 `entity_tokens` 表 |

- User 实体（声明三套行为）：`apps/ezagent_domain_identity/lib/ezagent/entity/user.ex`（三行为声明在 `user.ex:207` 一带）
- 身份/能力行为（持有 caps，只读那部分）：`apps/ezagent_domain_identity/lib/ezagent/behavior/identity.ex:1`；写操作（grant/revoke）拆到同文件的 IdentityAdmin（`identity.ex:291`），故意分开，免得用户给自己授权。
- 凭证授权 / 用户密码：`apps/ezagent_domain_identity/lib/ezagent/behavior/credential_grant.ex:1`、`user_credentials.ex:1`
- admin 判定：`apps/ezagent_domain_identity/lib/ezagent/identity/admin_authority.ex:107`

**CapBAC 授权的唯一收口**：所有"给谁发权限"的动作都必须走 `Grant`，"谁授的（granted_by）"**永远从授权标签派生、绝不能由调用方传参伪造**。

- 唯一收口：`apps/ezagent_domain_identity/lib/ezagent/identity/grant.ex:1`，核心校验在 `grant.ex:175`。

**anon 这版的新东西**：匿名身份的"判定来源"从旧的"`anon-` URI 前缀"升级成了一个干净的 `confirmed` 布尔字段——`confirmed: false`（或这行根本不存在）才是"匿名/未确认"的**真实来源**；URI 前缀只是防护（防正常用户冒充 `anon-`）。匿名用户只有"看自己这个会话"的结构性窄权能，没有后门。相关逻辑在 `apps/ezagent_domain_identity/lib/ezagent/users.ex` 的 `confirmed` 字段（`users.ex:42`，说明在 `:38` 一带）、保留前缀校验（`users.ex:68` 的 `reserved_anon_name?`）、anon GC 说明（`users.ex:174`）。注意是上下文模块 `users.ex`，不是 Kind 声明模块 `entity/user.ex`。

### 租户域

**app**：`apps/ezagent_domain_workspace`

Workspace 就是"租户/团队空间"，是隔离边界。`workspace://<name>` 这个 URI 是一等公民，参与权限检查和 Kind 查找；一个租户里的成员 URI 必须带本租户的前缀（防跨租户混入）。

- Workspace 实体（隔离边界）：`apps/ezagent_domain_workspace/lib/ezagent/entity/workspace.ex:1`
- 租户域门面（`create/2` 建租户、`create_session/3` 建会话、`add_member` 加成员，统一"先 dispatch 校验、成功再落库"）：`apps/ezagent_domain_workspace/lib/ezagent/workspace.ex:54`
- 租户行为 + 成员前缀校验器（唯一的成员合法性闸门）：`apps/ezagent_domain_workspace/lib/ezagent/behavior/workspace.ex:1`、`workspace/members.ex:1`
- 魔法链接规则（per-租户的邀请/登录规则，取代旧的全局白名单，支持 domain / 用户名单 / 仅邀请三种）：`apps/ezagent_domain_workspace/lib/ezagent/workspace/magic_link_rule.ex:1`

## 五、基础设施域 —— 把外部世界接进来的零件

这几个域不承载"业务概念"，而是提供能力零件，给上面四个域和插件层复用。

- **pty 域**（`apps/ezagent_domain_pty`）：管 PTY 伪终端子进程的生命周期——分配真 tty 跑命令（cc 插件用它跑 `claude` TUI），带自动应答扫描、登录失效观察、输出快照回放。入口：`apps/ezagent_domain_pty/lib/ezagent_domain_pty/server.ex:1`（`start_link/1` 在 `server.ex:131`）。

- **python 域**（`apps/ezagent_domain_python`）：管 uv 启动的 Python 子进程（不带 pty），用 JSON-RPC 跟它通信，做同步 RPC、异步通知、超时即重启。入口：`apps/ezagent_domain_python/lib/ezagent/domain/python/server.ex:1`（`start_link/1` 在 `server.ex:90`）。

- **ui 域**（`apps/ezagent_domain_ui`）：**无状态**组件库——一堆 shadcn 风格的 HEEx 组件（button / card / badge / page_header 等），统一 admin 和插件 UI 的样子，纯 `Phoenix.Component`，没有任何 GenServer 或状态。入口：`apps/ezagent_domain_ui/lib/ezagent_domain_ui/components.ex:1`。

- **external_mirror 域**（`apps/ezagent_domain_external_mirror`）：统一出站镜像——把消息"镜"到外部去。adapter pattern 把协议细节关在 adapter 里，域只给无协议感知的门面。两种 KIND：`:push`（域起 Worker 主动推）和 `:pull`（按需被外部 Phoenix Channel 拉，无常驻 Worker）。绑定时跑三重权限门禁 + 验证码握手防伪。入口：`apps/ezagent_domain_external_mirror/lib/ezagent/external_mirror.ex:1`，push/pull 切分在 `external_mirror/adapter.ex:1`。

- **agent_bridge 域**（`apps/ezagent_domain_agent_bridge`）：sidecar 桥接内核——把外部 agent worker（cc / python 子进程）接进 ezagent。transport-neutral，按 flavor 选 adapter：`:subprocess_ws`（cc/codex 走 Phoenix.Channel WebSocket 异步投递）vs `:in_process_sync`（curl 风格，无子进程、同步执行返回）。带就绪门禁 + per-binding 缓冲。入口：`apps/ezagent_domain_agent_bridge/lib/ezagent/agent_bridge.ex:1`，transport 切分在 `agent_bridge/adapter.ex:1`。
