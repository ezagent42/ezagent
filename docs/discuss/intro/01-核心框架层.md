# 01 · 核心框架层（ezagent_core）

> 上游最新 main（`e2abc02f`）。core 是地基，所有消息都从它过。路径相对 worktree 根。

## 一句话：core 只管"消息怎么进、谁接、有没有权限、改了什么"的统一机制

它不含任何业务概念。业务（会话、agent、客户面）都在上层的 domain/plugin。core 提供：统一寻址（URI）、运行时活实体（Kind）、动作处理者（Behavior）、唯一的消息分发通路（dispatch）、权限（CapBAC）、和几个"别让消息悄悄丢"的可靠性原语。

## 核心概念（用日常话讲）

- **Kind（运行时活实体）**：一个有身份（URI）的活进程，比如一个会话、一个 agent、一个 workspace 都是一个 Kind 实例。`Ezagent.Kind`（`apps/ezagent_core/lib/ezagent/kind.ex`），唯一 spawn 入口 `Kind.spawn/2`。
- **Behavior（动作处理者）**：定义"某个 Kind 能做哪些动作、每个动作怎么处理"。写法 `use Ezagent.Behavior` + `action :foo, ...` 宏 + `def handle_foo(args, ctx) → {:ok, result, [effect]}`（`behavior.ex`）。处理函数**不直接改状态**，而是返回一串 **effect**，由框架去执行。
- **dispatch（消息分发）**：跨 Kind 之间传消息的**唯一合法通路**——`Ezagent.Invocation.dispatch/1`（`invocation.ex:88`）。这是 P14 铁律：不许用 `PubSub.broadcast` 往入站 topic 发消息绕过它。
- **CapBAC（5 轴权限）**：每次分发都做权限检查，5 个轴 = kind / behavior / action / instance / workspace。`Ezagent.Capability.Match.matches?/2`（`capability/match.ex`）。
- **URI（统一寻址）**：所有东西的"门牌号"，三段式 `<scheme>://<workspace>/<type>/<name>`（如 `entity://system/user/admin`、`session://team-alpha/default/main`）。`Ezagent.URI`（`uri.ex`）有硬化的 canonical 守卫（拒绝非规范网址）。
- **可靠性原语**：因为"消息没人接收默认会静默丢"，core 提供几个兜底——
  - **ReadyGate**：actor 还没就绪时收到分发，先接住（不是丢掉）。
  - **PendingDelivery**：缓冲未就绪的投递。
  - **Idempotency**：重复入站（webhook 重试）去重，"收到即记"。
  - **DLQ（死信队列）**：零匹配的消息进死信，不静默消失。
  - 每写一个投递点都要能回答"这里失败了谁会知道"。

## 一条消息怎么走（分发链路，带 file:line）

```
外部入口(webhook/CLI/API/world 前端)
  → Router.dispatch/1 (router.ex:79，收 %Cmd{} 信封，薄封装翻译成 Invocation)
  → Invocation.dispatch/1 (invocation.ex:88，真正的分发收口点)
      → 幂等检查 → ReadyGate 门控 → 必要时从快照冷启动 lazy-spawn
  → Kind.Server (server.ex，目标 Kind 的 GenServer，唯一 def init/1)
  → Kind.Runtime.handle_dispatch/4 (runtime.ex，做权限/隔离检查 → 调对应 handle_<action> → 应用 effects)
```
> ⚠️ 双入口现状：`Router.dispatch` 目前是 `Invocation.dispatch` 的薄封装，真逻辑在 Invocation。

## effect 机制（重要纠偏）

动作处理函数返回 `{:ok, result, [effect]}`，框架按固定顺序执行这些 effect。
- ⚠️ **effect 实际有 12 个**（`behavior/effects.ex` 的 `@type effect`）：`:set` `:set_transient` `:emit` `:dispatch` `:dispatch_after_commit` `:dispatch_returning` `:notify` `:effect` `:effect_returning` `:terminate` `:saga` `:halt`。**CLAUDE.md / 旧文档写"9 个"是文档漂移**，以代码为准。
- 执行序大致：先改状态（State）→ 检查 Halt → Saga → 各种 Dispatch → Notify → Events → Termination。
- **插件作者永远不直接碰 slice/snapshot**：读靠框架注入的 `ctx[:read]`，写靠 `{:set, key, value}` effect。

## 给读者的注意点
- **跨 Kind 只能 dispatch**，不能直接调对方进程/广播绕过（P14）。
- **手写 `def init/1` 跳过 Kind 宏 = bug**（唯一合法的 init 在 `kind/server.ex`）。
- **不要静默成功**（返回 `:ok` 但啥也没干）——要么有效果，要么显式报错。
- **权限不可伪造**：`granted_by` 这类不能由调用方传参（见 identity 域）。

## agent manifest（agent-contract 这版新进 core）

core 新增了 **agent manifest**——用一份声明文件描述"一个 agent 装哪些工具、声明哪些权能"，是 agent-contract / agent-schema 落地的地基（已进 main，不再是"在建"）。两个关键点：

- **声明 vs 执行分离**：manifest 上的 caps **只是声明**，不直接授权。工具真正被调用时（`Ezagent.AgentManifest.Tools.dispatch_action/4`，`agent_manifest/tools.ex`）走的还是 core 唯一通路——`Invocation.dispatch/1`，且 **`ctx.caps` 强制清空**，让授权落回 agent 自己 Identity slice 的 `holds_cap?/2`。也就是说 manifest 不能绕过 CapBAC 给自己加权。
- **加载入口**：`Ezagent.AgentManifest.load/1`（`agent_manifest.ex:42`）解析 YAML/map 成 manifest；CLI 侧门面 `EzagentCli.AgentManifestFacade`（`apps/ezagent_cli/lib/ezagent_cli/agent_manifest_facade.ex`）从 manifest 走既有模板 spawn 路径造出 Agent Kind。配套的 versioned artifact pin、ledger 记账的 migrate_session 在 CLI / agent 域上层。
