# 插件层 + 传输层

> 面向读者的模块介绍。基于上游最新 main（worktree HEAD `b6818123`）只读分析，文中所有 file:line 都按当前代码核实过。

ezagent 是一个消息路由运行时：外面各种渠道（飞书、网页、命令行……）的消息进来，里面各种 agent（Claude Code、Codex、HTTP 接口的大模型……）来处理。这一篇讲两件事：**怎么往里加能力（插件层）**，以及**消息怎么进出这个系统（传输层）**。

---

## 一、声明式插件机制：加能力的标准方式

### 它解决什么问题

一个能长期演进的平台，最怕的就是"每加一个新功能都要去改核心代码"。改核心意味着每个新功能都可能碰坏老功能，核心越改越乱，最后没人敢动。

ezagent 的做法是反过来的：**新功能写成一个独立的"插件"，插件只负责"声明"自己带来了什么，至于怎么把这些东西登记进系统、让系统认识它们，全由框架代劳。插件作者从头到尾不碰任何登记表（代码里叫 registry）。**

打个比方：你入职一家公司，不需要自己跑去人事系统、门禁系统、工资系统挨个建账号；你只要填一张入职表，写清楚"我叫什么、归哪个部门、需要哪些权限"，后台自动把各个系统的账号给你开好。插件就是这张入职表，框架就是后台。

### 具体长什么样

每个插件就是一个标准的 Elixir/OTP 应用（一个独立可启停的程序单元），它的入口模块同时做两件事：

```elixir
use Application       # OTP 的标准启动外壳
use Ezagent.Plugin    # ezagent 的"声明式契约"

def start(_type, _args), do: Ezagent.Plugin.boot(__MODULE__)
```

注意第三行——插件的启动逻辑被压缩成了一句话：把自己交给 `Ezagent.Plugin.boot/1` 去引导。插件**不写**任何"我要登记一个 agent 类型""我要登记一条路由"这样的命令式代码。

它要做的，是按需实现一组**声明回调**，每个回调就是"我带来了什么"的一份清单（定义在 `apps/ezagent_core/lib/ezagent/plugin.ex`，回调声明集中在 `plugin.ex:186-234`）：

- `plugin_info/0`——插件的名片（名称、版本、描述），**唯一必填项**；
- `kinds/0` / `behaviors/0`——带来了哪些"实体类型"和"动作处理器"；
- `template_classes/0`——带来了哪些"模板"（按模板能批量造出运行时实例）；
- `agent_flavors/0`——带来了哪种 agent 口味（比如"cc 口味""curl 口味"）；
- `adapters/0`——带来了哪些"对外镜像适配器"（往外发消息的通道）；
- `config_surface/0`——在 `/plugins` 管理页上，这个插件的配置入口点开后跳到哪；
- `children/0`——插件自己要启动的常驻进程；
- `after_boot/0`——全部登记完成后要补做的一次性收尾。

除 `plugin_info/0` 外其余全部有默认值（默认返回空清单或"什么都不做"，见 `plugin.ex:259-268`），插件只声明用得上的那几项。

框架的 `Ezagent.Plugin.boot/1`（`plugin.ex:386`）分三步引导：先把插件自己的常驻进程拉起来，再把每一份声明清单翻译成对应的内部登记动作（`plugin.ex:410` 的 `publish/1`），最后跑 `after_boot/0` 收尾。**翻译这一步是关键：插件写的是清单，框架替它去敲每一张登记表。**

### 为什么这套设计好

- **加能力不动核心**：新插件只是新增一个目录，核心代码一行不改，老功能不受牵连。
- **作者碰不到登记表，就出不了那类错**：插件没法直接往系统里塞一个会顶掉别人的登记项。代码里有个硬规矩——任何插件都不允许声明"接管某一类 URI 的生成权"（`spawns/0` 必须返回空，否则启动直接报错，见 `plugin.ex:475`），因为那等于劫持了全系统某一类资源的入口。
- **编译期强制，逃不掉**：有一个叫 `:ezagent_plugin_check` 的编译器插件（`apps/ezagent_core/lib/mix/tasks/compile/ezagent_plugin_check.ex`），在每个插件应用编译时就检查声明是否合规——声明了不存在的模块、写错适配器配对等等，**编译就过不去**，根本到不了运行时。这是一道绕不过的关卡。

一句话：**"声明而不是改核心"是这个项目往平台上加能力的标准姿势。** 下面每个插件都遵守同一套。

## 二、各插件一览

每个插件都用上面那套声明机制接入。下表"入口"指的是 `start/2`（即 `Ezagent.Plugin.boot(__MODULE__)` 那一行）所在位置。

### cc —— Claude Code agent + 编排器传输

接的是 Claude Code 这个命令行 agent：把它当成一个子进程（通过伪终端 PTY）拉起来对话。它还内置了**编排器的 MCP 传输**——一个活着的 Claude 编排器通过这套传输拿到一组管理工具去调度别的 agent。
入口：`apps/ezagent_plugin_cc/lib/ezagent/plugin_cc/application.ex:70`。它声明了 `cc` 口味（复用统一的 `Ezagent.Entity.Agent` 实体类型，口味体现在 URI 名字前缀里）和 `cc.agent` 模板。

### codex —— Codex agent

接的是 Codex agent：起一个共享的 Codex 应用服务进程、一个用户能看到的终端界面、再加一个把消息桥接进去的 Python 边车进程。
入口：`apps/ezagent_plugin_codex/lib/ezagent/plugin_codex/application.ex:15`。声明 `codex` 口味 + `codex.agent` 模板，并在 `children/0` 里启动自己那几个常驻进程。

### curl_agent —— HTTP 接口的大模型（如 DeepSeek）

接的是"用 HTTP 接口调用的大模型"，比如 DeepSeek、OpenAI 这类——本质上就是发一个 HTTP 请求过去、把回答取回来。它是统一 agent 实体的一种 **curl 口味**（curl 是常见的发 HTTP 请求的工具，这里借指"走 HTTP 往返"这条路）。
入口：`apps/ezagent_plugin_curl_agent/lib/ezagent_plugin_curl_agent/application.ex:70`。声明 `curl` 口味（同样落在统一的 `Ezagent.Entity.Agent` 上）、`curl.agent` 模板，以及一组 curl 专属动作处理器（重置对话、配置、同步取结果）。

### np —— Python 计算 agent

接的是一个真正的 Python 子进程，加载 numpy、sympy 这些科学计算库，把用户在对话里发来的公式算出来。它存在的意义是端到端验证"ezagent 能托管 Python 子进程"这条能力。
入口：`apps/ezagent_plugin_np/lib/ezagent_plugin_np/application.ex:77`。声明 `np` 口味（用专属的 `Ezagent.Entity.NpAgent` 实体类型）+ `np.agent` 模板，每个 np agent 独占一个 Python 子进程。

### echo —— 测试桩 agent

接的是"什么都不接"——它只是把收到的消息原样回弹，作为测试用的最简 agent，用来验证消息能不能正常走通一圈。
入口：`apps/ezagent_plugin_echo/lib/ezagent_plugin_echo/application.ex:73`。声明 `echo` 口味 + `echo.agent` 模板，并在收尾阶段播一个默认 echo 实例好让冒烟测试有现成对象可用。

### advisor —— 第一个 socialware 垂直场景

socialware 是"面向客户的对话场景"这条产品线（详见 `docs/discuss/intro/08-socialware深入.md`）。advisor 是它的第一个垂直模板，贡献了一个"顾问会话"模板，运行时仍然落在统一的会话实体上，只是带上 socialware 那套行为子集。
入口：`apps/ezagent_plugin_advisor/lib/ezagent_plugin_advisor/application.ex:16`。它最特别的是只声明了模板和**两个"拉取式"对外适配器**（客户 feed 和聊天 feed，`application.ex:43-45`）——拉取式适配器没有专属常驻通道，所以登记时不会起额外进程。

### feishu —— 飞书出入站

接的是飞书（Lark）。**入站**：飞书的 webhook 或长连接收到群消息，统一汇到一个入站分发器，解析出发件人、找到对应会话、再分发进系统（`apps/ezagent_plugin_feishu/lib/ezagent/plugin_feishu/inbound_dispatcher.ex:58`，HTTP webhook 和 WS 长连两条入站路都走这里，行为一致）。**出站**：通过统一的"对外镜像"机制，声明一对适配器+绑定（`{FeishuAdapter, FeishuChatBinding}`），系统把会话里要外发的消息经由它推回飞书群。
入口：`apps/ezagent_plugin_feishu/lib/ezagent/plugin_feishu/application.ex:70`。

### world —— 统一前端 / 管理面

它本身**就是那套网页管理界面**——会话列表、会话对话页、工作区、身份与权限、插件目录、管理后台等等都是它提供的页面。技术形态变了：可见 UI 是 **React + shadcn/ui（Vite 构建）**，跑在一层**只做 SSR/通信壳的 Phoenix LiveView 页面**（`WorldLive`）上——LiveView 负责鉴权、路由、把入站事件桥进来、把出站动作走 `Invocation.dispatch/1`，真正渲染交给注水进来的 React 组件（通过 `phx-hook="WorldRenderer"` 挂载 TSX 组件）。生产链路里没有 Node 运行时。

它**复刻并完整取代了原来的 liveview 插件**（那套 25 个 HEEx LiveView 管理面已物理删除，world 顶替了它的位置，app 总数仍是 21）。
入口：`apps/ezagent_plugin_world/lib/ezagent_plugin_world/application.ex:13`（`start/2` 即 `Ezagent.Plugin.boot/1` 那一行）。跟旧 liveview "不带任何实体/行为" 不同，world **声明了一个 behavior**——`{Ezagent.Entity.Workspace, :manage, Ezagent.World.Behavior.Layout}`（`application.ex:27-31`，管"改布局"这件事，布局是 runtime 数据、组件是 build-time 代码）——并有一个 `after_boot/0`（`application.ex:34-36`，`LayoutBootstrap.ensure_system_admin_manage_cap` 把改布局的 cap 授给工作区 admin）。它挂在独立子域 `host: "world."` 上（`apps/ezagent_web/lib/ezagent_web/router.ex:32`）。

## 三、传输层：消息怎么进出

插件层管"接什么、怎么处理"，传输层管"消息从哪进、从哪出"。这里有一条贯穿全项目的硬规矩：**传输只做传输，不做全栈**——传输层负责把外部协议翻译成系统内部的统一动作，业务逻辑一律交回内部去做。

### ezagent_web —— Phoenix 传输

这是基于 Phoenix（Elixir 的 Web 框架）的网页与 HTTP 入口，但它**刻意只当传输用，不写业务**。所有路由集中声明在 `apps/ezagent_web/lib/ezagent_web/router.ex`。

关键约束：网页/接口收到一个"要改变系统状态"的请求时，**不直接动数据**，而是统一封装成一次 `Ezagent.Invocation.dispatch/1`（消息分发）交给内部去执行——这样权限校验、审计、可靠性兜底全都在分发这条主干上统一发生。代码里能看到这条纪律被一致遵守，比如聊天页发消息走的就是分发（`apps/ezagent_web/lib/ezagent_web/controllers/socialware/chat_feed_controller.ex:171`），首页、对外 API 控制器同理。

socialware 那条产品线的**客户面控制器**单独放在 `apps/ezagent_web/lib/ezagent_web/controllers/socialware/` 目录下，两个文件：

- `customer_controller.ex`——客户单页应用入口（`router.ex:60`）+ 附件下载（`router.ex:67`）；
- `chat_feed_controller.ex`——对外聊天单页应用入口（`router.ex:78`）。

这两个控制器面向的是**外部访客**（可能没登录），所以它们不走后台管理那套登录门禁，而是靠"令牌 + 能力"做按需授权，每次访问都重新校验权限。

### ezagent_cli —— 命令行入口

命令行不是另起一个独立程序去连数据库，而是通过分布式 Erlang 的远程调用（RPC）**直接进到正在运行的同一个 BEAM 虚拟机里执行**（`apps/ezagent_cli/lib/ezagent_cli/exec.ex`）。也就是说命令行和网页共享同一套登记表、同一套内存状态、同一套数据库连接，没有 HTTP 中转、没有第二个虚拟机。命令行里的每条真实操作同样要带令牌鉴权——没令牌就拒绝，不会偷偷以管理员身份运行。
