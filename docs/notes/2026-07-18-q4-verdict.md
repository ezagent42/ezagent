## Q1 分享模型是不是 socialware_mounts 那张「发钥匙」表？——是

- **表**：`socialware_mounts`，schema `Ezagent.Socialware.MountRow`（domain_session mount_row.ex:41-53）。runtime mount 的 durable SoT（moduledoc :3-11）。
- **行结构**：自然键 `(session_uri, target_uri, grantee_uri, behavior)`（含 session，:9 + `mount_id/4` :165-180 把 session 哈进主键）+ `actions_json`（发的动作集）/ `access`（read|operate）/ `granted_by` / `workspace_uri` / `mounted_at`。
- **现网行样例**（dev DB `ezagent_pg_compat_dev`，10 行）：grantee 三类都有——
  1. **人类 user**：`entity://owner-c9f54a/user/owner`、`entity://owner-c9f54a/user/editor`（operate 全 20 动作，来自 create_board 给建板人/成员的行）；
  2. **kanban-assistant agent**：`entity://owner-c9f54a/agent/assistant-test-kanban`（operate 或 read）；
  3. **uuid 匿名 agent**（receive 路挑出来的落点 assistant）。
  `granted_by` 全部 = `entity://owner-c9f54a/user/owner`（板 data_owner）。
- **结论**：「agent(板) 给人发钥匙」的行**现网已存在**（owner/editor 的人类 grantee 行就是），表和机制都在用。

## Q2 Cap.issue 支不支持「板→人」发钥匙？——支持，机制方向没错

- **grantee 约束**：`Ezagent.Cap.issue(authorization, grantee_uri, cap)`（core cap.ex:33）对 grantee 只要求 `%URI{}`——**无 kind/scheme 限制**，人类 user URI 完全合法。#1386 per-grantee 签名把 grantee 签进 artifact（`prepare_provenance/3` cap.ex:163-167 + `sign_artifact` :204-211），`verify_for/2`（:94-100）serve 侧按确切 grantee URI 匹配。
- **granter 语义**：约束在发方——`granted_by` 必须 `entity://` scheme（cap.ex:153-157 `:granter_not_entity`）。mount 链里 granter **不是板 agent 本身**，而是板的 `data_owner`（人）：`CompositionCaps.mint_cap/4`（composition_caps.ex:140-178）`assert_target_owner` 后以 owner 权 issue；Mount moduledoc 明写「granter 永远 = target 的 data_owner（板主人授权，#154）」（mount.ex:6-8）。即「板→人发钥匙」在系统语义 = **板主人授权、经唯一 mint chokepoint 替板签发**——完全在机制内，现网 granted_by 行印证。
- **结论**：mount 机制**方向没错**。错的只是 receive 路线两处浅层选择：① grantee 选了目标会话的 assistant 而非点击者本人（share_receive.ex:79 `Mount.mount(..., assistant_uri, ...)` + :48 `@assistant_role`）；② MountRow 自然键含 session、没有 person-scoped 行位（mount_row.ex:9）。不是「机制不支持人类 grantee」——我们已经在给人发行了（Q1 现网证据），是 receive 没走这条路。修法 = xy-review ㊵ 任务单（person-scope 扩展 + 删 assistant 解析段），不需要动 Cap.issue。

## Q3 附件机制深查 + 接 kanban 权限的最小可行方案

**① 设计本体**：
- `Ezagent.Uploads.DownloadToken`（core download_token.ex）是**纯签名器**：payload 只有 `uri/issued_at/ttl`（:115-119），**没有 receiver 字段**——「kanban 传错 receiver」在机制上不成立；「mint 前必须由调用方授权」是模块契约（:34-37）；TTL 默认 300s（:61）、24h 硬顶（:64）。
- serve-time 复查在 `EzagentWeb.UploadsController.download/2`：uploads_controller.ex:93 `authorized?` → :110-116 = admin ∪ **chat-message 参与本位**（`caller_in_attaching_messages?` :133-157——按 Message 表 LIKE 找带该附件的消息行，caller 须是上传消息 sender 或该消息所路由 session 里发过言的参与者）。
- **为什么绑 chat 参与者**：codex P2-revision HIGH 防 auth-widening（moduledoc :42-54）——token 在渲染时就发给所有能 VIEW session 的人，泄漏 token 同 ws 内可重放；serve-time 独立复查把访问面钉回 pre-P2 契约。**不能删，只能等强替代**。
- **kanban 为什么恒 forbidden**：`attach_upload` 直接把 uploads URI 写进板 slice artifact（plugin_kanban world_actions.ex:330-349，`url = uploads URI`），**不产生任何 Message 行** ⟹ chat 复查恒 false，连上传者本人（非 admin）都被拒；再叠加渲染时预签（world_data.ex:386-412 `jsonable_artifact`→`mint!`）+ TTL 300s，停留 >5min 必 `:expired`（统一渲染成 forbidden，controller :98）。

**② 接 kanban 权限——可行，最小方案**（用户原则：有板钥匙就能看板上附件）：
- **不做 serve-time upload→board 反查**：附件 ref 存在板 `:kanban` slice 的 artifact.url 里，无反向索引，serve 时扫全部板不可行也不必要。
- **改「签名断言」路线**：mint 侧本就要求先授权——kanban 渲染/点击前已过 `read_ctx` cap 门（`visible?`/`holds_board_cap?`，world_data.ex:147-197 = 「caller 持指向该板的 cap」，正是用户原则的实现体）。把这个已验事实**签进 token**：`DownloadToken` payload 加可选 `grantee`（点击者 entity URI）+ `host_uri`（板 URI），MAC 签名不可伪造；**向后兼容**——旧 token 无新字段走旧 chat 复查分支。
- **serve 侧新分支**：token 带 `grantee` → 校 `caller == grantee` 即通过（person-bound，比 chat 复查**更强**的防泄漏：泄漏 token 换人无效，满足 codex HIGH 的替代标准）；`host_uri` 作为审计/二步的板钥匙复核位（serve 时校 caller 持指向 host 的 cap），最小闭环只需 grantee 分支。
- **kanban 侧配套**：渲染预签改**点击现签**——`kanban.download_artifact` dispatch 返回 fresh href（解 TTL 300s），mint 时带 `grantee=点击者`。
- **归属**：DownloadToken 加字段 + controller 授权分支 = **uploads 通用层（core+web），知会 Allen**（加可选字段向后兼容，非阻塞决策）；点击现签 + 传 grantee/host = **kanban 侧我们做**。与 ㊵ 人本位同向（都是「钥匙跟人走」）。
