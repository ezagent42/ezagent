## 1. ㊵ 正交模型（最大项）——复审四问

**Y**：气泡点击跳去别的会话（同会话点击也整屏重定向）；文案「按你的身份决定可编辑/可读」不准。
**X**：receive 整条链是「会话本位」设计，而用户钉死的模型是「人本位」。会话本位不止在落点解析一处，**在三层**：
1. **钥匙的 grantee**：`ShareReceive.receive_shared_board/3` 把只读钥匙发给**目标会话的 kanban-assistant**（share_receive.ex:79 `Mount.mount(session_uri, board_uri, assistant_uri, ...)`），不是点击者本人；落点解析挑「首个带 kanban-assistant 的 session」（:112-140）。
2. **Mount infra 本身**：`MountRow` 自然键 = `(session_uri, target_uri, grantee_uri, behavior)`（mount_row.ex:42-46，含 session），`Mount.mount/6` 第一参就是 session——**没有 person-scoped 挂载行的位置**。
3. **HTTP 落点**：气泡按钮是裸 `<a href>` 到 `/socialware/kanban/receive?token=`（unfurl.tsx:33-40），controller mount 后 302 到落点 session 页。

### ① person-scoped 板集合的读路存在吗（现读）

**半存在**。kanban tab 数据口径 `EzagentPluginKanban.WorldData.session_boards/2`（world_data.ex:111-128）：
- **过滤已是人本位**：`visible?/2` = admin ∪ 板 `data_owner`==caller ∪ **caller 持指向该板的 cap**（`holds_board_cap?` :184-197，查 `ctx.caller_caps` 里 cap.instance 命中板 URI）。`caller_caps` = LiveView mount 时 `load_caps(uri)` 快照（live_auth.ex:234 `:current_caps` → world_actions.ex:519 read_ctx）。
- **枚举仍是 ws 本位**：来源 = `RecipeResolver.list_by_recipe("kanban-manager", workspace_of(session_uri))`（:112-115）。⟹ **同 ws** 的持钥板：钥匙发给点击者后 tab 自动出现（读路现成）；**跨 ws** 的持钥板：永远枚举不到，即使持 cap。

## 2. ㊲ 附件 forbidden——归属定论：uploads 通用层，非 kanban 签发姿势

**Y**：节点「附件」产物点打开 → forbidden。
**X（两个独立根因，都不是「kanban receiver/ttl 传错」）**：
1. **serve-time 授权模型是 chat-message 参与本位**（主因）：`UploadsController.download/2` 在 token 验签**之外**跑第二道复查 `authorized?/2`（uploads_controller.ex:93,:110-116）= admin ∪「上传消息的 sender」∪「附件所路由 session 的参与者」——全部**查 Message 表**（`caller_in_attaching_messages?` :133-157 按 body LIKE 找带 attachment 的消息行）。kanban 的附件经 `attach_upload` 直接写进板 `:kanban` slice 的 artifact（world_actions.ex:330-343），**不产生任何 Message**⟹ 复查恒 false ⟹ 非 admin 连上传者本人都 forbidden。token 再新鲜也没用。
2. **TTL 300s + 渲染时预签**（次因）：`DownloadToken` 是 URI-bound 纯签名器，**没有 receiver 参数**（download_token.ex:115-119 payload 只有 uri/issued_at/ttl）——kanban「传错 receiver」在机制上不成立；`mint!(uri)` 在 `jsonable_artifact` **渲染时**签（world_data.ex:406），默认 TTL 300s（:61），tab 停留 >5min 再点必 `:expired`，controller 统一渲染成 forbidden（:98 uniform）。

**彻底修**（两半）：
- **uploads 通用层**：serve-time 复查加一条非-chat 消费面的授权分支——caller 对**附件宿主资源**持 cap（kanban 场景=对板持 Kanban cap，人本位、与 ㊵ 同向）。实现口需要 token 携带宿主 hint 或 person 绑定（给 `DownloadToken` 加可选 `grantee`/`host_uri` 字段，签进 payload；serve 时 person-bound token 校验 caller==grantee 即可替代 chat 复查——mint 侧本就要求「授权后才签」，world_data 渲染前已过 read_ctx cap 门）。莫德文档自陈复查是 codex HIGH 的防泄漏要求，**不能删只能替代**（person-bound 是更强的防泄漏：泄漏 token 换人无效）。
- **kanban 消费姿势**：点击时现签（`world:dispatch kanban.download_artifact` 返回 fresh href）替代渲染时预签，解 TTL；顺手把 grantee 绑点击者。

**任务单变化**：PR7 改判——不是「排查 receiver/ttl 传错」（无 receiver 可传），定域 = **uploads 通用层**（DownloadToken 加 person 绑定 + controller 授权分支，core+web）+ **kanban 侧点击现签**（我们）。DownloadToken 动的是 core 授权载体，建议知会 Allen（非阻塞：加字段向后兼容，旧 token 走旧复查）。

## 3. join 补发——现状核对 + 人本位下范围重算

**Allen 指的 caller-side helper 现状**（docs/futures/todo.md「#161 A2 deferrals」段，:68 附近）：
- helper **不存在**，是 deferral 里的 **Recommended**：「a shared caller-side confirmed grant helper invoked at the add sites」。背景：join 内 sync grant 会死锁（实证 5s timeout），deadline-free 的 CONFIRMED grant 只能 caller-side，散布「~8 add-site chokepoints」——**没有完整 8 处清单**，点名 4 个：World LV / orchestrator participants / anon admission / SessionCreator（另 approve_admission 同病）。
- 与 D1 的关系：D1（allen-decisions.md §D1）拍的是 join 补发 rule 家族/授权面；todo.md 这条是**同一件事的实现形态约束**（补发点必须 caller-side、必须共享 helper 否则又添 grant 真相源——正是 fix-plan X2 的病 + ShareReceive 撞过的 I12 paradigm-lock 铁闸，share_receive.ex:25-34 moduledoc 已记）。**实施建议**：D1 拍板后，join 补发就落在这个 shared helper 上，一个供给点做三件事（member-cap confirmed grant + member view caps + mount operate keys），add-site 清单作为实施第一步盘出来。

**人本位（㊵）下 kanban 消费面还需要吗——需要，且是主供给路，范围不缩反清**：
- **mount operate keys 补发（⑧ TODO）**：人本位 tab = 持钥板集合 ⟹ 新成员进会话若不补发 person keys，tab 上看不到本会话已挂的板（`reconcile_session_mounts` 只重发已记录 grantee，mount.ex:184）。「编辑权来自成员身份」（㊵ 文案钉死）在 CapBAC 里的物化形态**就是** join 时按 MountRow `:operate` 行给新成员铸 person keys。范围不缩小。
- **view render cap 补发（⑤ TODO）**：与 D3 耦合——D3（tab=plugin 级恒显）落地后，kanban_render 这张 cap 的 tab 门控意义消失，join 补发的 view-cap 半边**缩小到非-kanban views**（机制保留，kanban 不再依赖）。D3 若先落，D1 实施量减半边。
- **结论**：join 补发任务单（PR5，严格等 D1）**不变但加一行**：实施载体 = todo.md:68 的 shared caller-side helper（与 #161 A2 deferral 合流，勿另起 grant 点）；kanban 消费面 = mount `:operate` 行补发（主）+ view caps（D3 落地前）。
