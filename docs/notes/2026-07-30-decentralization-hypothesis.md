# Does the "centralized session" cause our complex bugs — and would full (Bluesky/git-style) decentralization avoid them?

*Research memo for Allen — grounded in the actual ezagent codebase (origin/main @ 81a90855c, 2026-07-30) and the actual bug corpus (#189, #1627, #201/#1570, #206, #207, #1576, #1577/#1578, read-plane, #192). Bilingual: this file (EN) + `decentralization-hypothesis.zh_cn.md`.*

---

## ① The hypothesis, restated testably

Allen's claim decomposes into four assertions:

1. **(Premise)** ezagent is already, in essence, a decentralized actor model.
2. **(Goal)** A mechanistically clear + simple authorization/caching model is achievable — business logic may stay verbose, but as *compositions of a simple mechanism*.
3. **(Causal claim)** The complex bugs we keep hitting are caused by having introduced a **centralized session** — a coordination point that *demands entity-state consistency*.
4. **(Counterfactual)** Under full decentralization à la Bluesky — every actor keeps its information fully local, no global-consistency guarantee, content is *copied to the viewer's node on view*, the viewer may modify its copy and *push back* to the origin (a git model) — this complex-bug class would not arise.

The test: map where the system actually demands consistency (②), classify each real bug's root cause (③) as
**[A]** caused by a global-consistency / centralized-chokepoint requirement,
**[B]** caused by state duplication *without an owner* (two copies / two writers, no reconciliation rule — i.e. too little single-ownership, not too much),
**[C]** orthogonal (ordering/liveness, crypto/key lifecycle, plain logic bug),
then evaluate the counterfactual honestly (④), and conclude (⑤⑥).

## ② The current-state map: what is actor-local, what demands agreement, and what invariant each point guards

**Deployment reality first:** v0 is a **single BEAM + single SQLite/PG** (`ARCHITECTURE.md` §1.1; federation is v0.x+). Every "global" datum is one node, one DB. So today's consistency demands cost *one DB read*, not a distributed consensus round. None of the bugs below is a CAP-theorem cost; they are bookkeeping costs between *multiple internal copies* of the same datum.

### Already actor-local / decentralization-shaped (the "Bluesky-like" parts that exist today)

| Mechanism | Evidence | What is local |
|---|---|---|
| **Caps are signed bearer artifacts; every target Kind is its own signing+verify authority** (per-Kind ed25519, born-signed, strict verify) | `apps/ezagent_core/lib/ezagent/cap/authority.ex`, GLOSSARY #164 (PR #1457) | Issuance and verification are per-entity; no central ACL engine |
| **Each entity holds its own caps** (holder-side store: `users.caps_json` / snapshot `:identity` slice / post-#189 unified `identity_caps` store keyed by URI) | `apps/ezagent_domain_identity/lib/ezagent/entity_caps.ex` + `entity_caps/store.ex` | The principal gate loads from the holder's own durable store, never from presented caps (F-1) |
| **Entity state = own GenServer slices + own snapshot row** | `kind_snapshots`, `{:snapshot, :on_change}` | Actor-local state, single writer (the actor) |

### Consistency-demanding points (what invariant, who must agree)

| Point | Invariant demanded | Who must agree | Nature |
|---|---|---|---|
| **KindRegistry `put_new`** (unique URI→pid, crash on duplicate) | *At most one live actor per URI* | Every spawner | **Constitutive of the actor model** — this is what makes actor-local state coherent at all (single writer per key). `kind_registry.ex` |
| **Authority generation plane** (`kind_cap_authorities`: one-active-per-URI, monotonic generation; `Authority.verify_against_current` = fresh read; `EntityCaps.verified/2` gen-gates) | *A cap is honored iff signed by the target's CURRENT generation* — i.e. **revocation takes effect immediately** | Every verifier + the holder's own stored license | **Security-driven.** Signing defends forgery/tamper/retarget; revocation *requires* this consistency point ([[cap-signing ≠ revoke-completeness]]) |
| **Principal gate** (`Cap.Authorize.principal_current?` → holder's durable store, gen-gated) | A gen-bumped principal loads empty ⇒ inert | Holder store ↔ generation row | The holder's local license is a **local replica of an authorization fact** that must track the generation counter — the one genuinely "replica-vs-global" seam in the system |
| **Dispatch step 5.5 cap chokepoint** + **read-plane chokepoints** (`SessionReads`, `InternalReads`, version-first atomic snapshot) | *No ungated path exists* (write or read); feed snapshot: *reported version ⇒ its messages are visible* | All dispatchers / all readers | **Security/product-driven**; enforced by anti-bypass CI gates |
| **Session** (`Ezagent.Entity.Session` — "routing context owner", IRC-channel shape) | (i) receivers of a message = *current* members, checked at delivery (revoke ⇒ immediate receive-deny, A2 §14.5); (ii) turn settlement happens exactly once, in order | (i) session roster ↔ member-held caps (two copies today → #192); (ii) only the session actor itself | (i) security-driven; (ii) **free** — the actor mailbox IS the serializer. Everything else the session does (history, surfaces, feeds) is already projection/EC |
| **Workspace roster + Loader** (workspace holds `{:member, URI}` children; Loader respawns at boot) | Boot brings the fleet up in dependency order | Boot sequence | Boot-coherence; source of the ~289 `no process: Workspace.Supervisor` cascade when poisoned |
| **Boot-time registries** (BehaviorRegistry, TemplateRegistry strict-on-duplicate, RoutingRegistry `put_new`, SchemeRegistry, `ManifestSeed.scan_all!` fail-loud) | The node's declaration set is coherent or the app doesn't boot | All plugins at boot | Deliberate fail-loud ("router not req/resp: silent = buggy", ARCH §1.2) — but blast radius is *whole-app* (#206) |
| **Flavor store** (`AgentFlavorAttributes`, global rows keyed by agent URI; plugins write their OWN agent's flavor inside `instantiate` **by design**, Allen 0727) | One committed flavor row per agent URI, readable *during* instantiate (#1578 contract) | Template pre-store hook + 4 plugin writers | Multi-writer on one row → needed CAS ownership (#201) |
| **Cross-actor cap delivery** (`absorb_cap` into the receiver's own store) | Grant reaches the holder's store exactly once, even if receiver is cold | Granter → receiver actor | A liveness problem **created by the actor-local design** (caps live in the holder's store); cured by `Cap.DeliveryOutbox` (durable retry, applied-only-after-commit) |

**Reading of the map:** the demands that exist are (a) *constitutive of the actor model* (single live actor per URI), (b) *security-driven* (revocation immediacy; no ungated read/write paths), (c) *boot coherence*. The session itself is **already a convergence point, not a strong-consistency demander**: history is an append log with derived replay; surfaces are monotonic EC projections; turn sequencing is single-actor mailbox order (free); the only strict thing it does is membership-as-authorization at delivery time — a security choice, not an architectural accident.

### Tally (being honest with the count)

- **[A] as the cause of the bug: ~0.5 of 9.** Only #206's *blast radius* (global fail-loud boot gate) is a real "centralization hurt us" finding — and it was the amplifier, not the defect. The two other [A]-classified items (read-plane) are cases where **missing** chokepoints caused the bugs and adding them was the fix.
- **[B] duplication-without-owner: ~5 of 9** (#201 multi-writer slot, #192 dual membership truth, #206's stale replica, #189's multi-home cap plane, #1577/#1578, plus #207's deep half — the in-flight cap needing a durable owner) — the dominant class. Every one is a violation of the design's own P3 ("single source of truth for any datum"), not a consequence of it.
- **[C] liveness/ordering/lifecycle: ~3.5 of 9** (#207's trigger, #1576, #1627, #189's resurrection/tombstone corners) — actor-model plumbing and key lifecycle; model-independent.
- **Cross-cutting:** a large share of the #189-family pain was **transition cost** — the choreography of migrating between two authorization planes (dual-write, cold-load reconcile, backfill, parity barrier, epoch fence). The board's own lesson (2026-07-30): the one-shot cutover rhythm (additive → write-plane → cutover) worked; the long-lived dual-plane window is what bled.
- **The session did not cause any of these.** No bug in the corpus is "the session demanded entity-state consistency and that demand broke". The session-adjacent bugs are roster-duplication (#192, class B) and view-assembly liveness (#1576, class C).

## ④ The Bluesky/git alternative, evaluated honestly

**What Bluesky (AT Protocol) actually is** — relevant because the hypothesis names it:

- Each user's data lives in a **signed, git-like repo** on their PDS (Merkle log). Relays crawl; **AppViews aggregate** — and in practice Bluesky Inc. runs the dominant relay, AppView, and most PDSes. The decentralized-write layer is real; the *read* layer everyone uses is a centralized materialized view — functionally the same role as ezagent's session/`SessionReads` plane.
- **All repo data is public.** Interactions (likes, replies) are records in the *author's own* repo referencing the target by AT-URI + CID. You **cannot modify someone else's record and push back** — no cross-repo merge exists in the protocol. The "viewer edits its copy and pushes back" model Allen describes is a *pull-request workflow*, which presupposes exactly (a) write authorization at the origin and (b) merge semantics — the two things the hypothesis hoped to avoid.
- **Private/permissioned data is an open problem in atproto** — per the spring-2026 protocol roadmap it's a major workstream *through summer 2026* (Blacksky/Northsky/Habitat sketches). The reference model achieves its simplicity by **not having** capabilities, private state, or human-in-the-loop gating — ezagent's entire product domain. (Sources: [AT Protocol Spring 2026 roadmap](https://atproto.com/blog/2026-spring-roadmap), [Bluesky federation architecture](https://docs.bsky.app/docs/advanced-guides/federation-architecture), [OAuth for AT Protocol](https://docs.bsky.app/blog/oauth-atproto).)

**Per bug class, what full local-first + copy-on-view + push-back would do:**

| Bug class | Would it disappear? |
|---|---|
| Revocation/generation family (#189 stale license, #1627 brick) | **No — it is the classic EC pain, made general.** A cap revoked at the owner while a viewer's replica still honors it is precisely what the gen-gate exists to prevent, and precisely what §14.5's "revoke ⇒ immediate receive-deny" acceptance test forbids. You either keep a consistency point for revocation (= today's design) or accept revocation lag (= a security regression Allen already rejected). Boot-brick → silent-resurrection is a trade between failure modes, not a bug-class elimination |
| Two-writers-one-row (#201) | **No — it becomes a merge conflict.** And the industry-standard resolution is what was already shipped: a single arbitration point at the origin decides the owner, and only the winner writes (git's shared ref advancing by reject-non-fast-forward is the same shape). Divergent-replica merge is the git *conflict* problem; the git model contains it, it doesn't dissolve it |
| Stale replica (#206) | **Worse by default.** Local-first without a reconciliation rule is exactly "skip-if-exists". The cure is hash-based reconcile + bounded blast radius — orthogonal to centralization |
| Cross-actor delivery (#207) | **Multiplies.** Every replica boundary needs outbox/at-least-once/idempotent-apply. The DeliveryOutbox is this machinery, built once |
| View assembly / liveness (#1576) | **Unchanged or multiplied** (cold replicas, out-of-order results are local-first's daily weather) |
| Torn reads (straddle) | **Tolerated rather than fixed** — Bluesky-style viewers accept stale/partial views. Ezagent's feed plane already took the EC route *with* a monotonic version so a poll can't latch a torn state. For turn-committed socialware surfaces, "page without its content" was judged a bug, not acceptable staleness — a product judgment, not an architecture accident |
| Membership dual-truth (#192) | **The local-first answer is already the plan** — caps (held, distributed) as truth, roster as projection |

**Where ezagent is already decentralization-shaped** — and where the pain actually sat: signed bearer caps verified against per-entity authority; entity-owned cap stores; append-log history with derived replay; monotonic-versioned EC projections; content-hash no-clobber reconciliation for definitions; push replicas with resubscribe/catchup (ExternalMirror). The pain concentrated at the **sync/reconcile seams** — overwhelmingly the *migration* seams between the old snapshot-plane and the new store-plane (dual-write, cold-load reconcile, adopt-clobber during spawn races, backfill/parity/epoch). That is **transition cost of re-homing a datum, not steady-state cost of having an owner**. The steady state on the other side of #1621 is *simpler and more mechanical* than before: one store, one status enum, one read facade, snapshot demoted to projection.

**The session, re-examined against what socialware actually needs from it:**

| Session function | What it requires | Strict or convergent? |
|---|---|---|
| Chat fan-out | current-member set at delivery time | **Strict at the gate** (security: revoke ⇒ immediate deny) — but the gate is one cap check at one chokepoint |
| Chat history / rejoin | append log + per-member cursor replay | Convergent (already) |
| Turn state machine (hold/settle/approve) | settlement exactly-once, ordered | **Serialization, not global consistency** — the session actor's mailbox provides it for free |
| Surfaces / feeds / SessionView | committed-state projections | Convergent (already; monotonic version) |
| Publisher / ExternalMirror | cursors, ring buffer, catchup | Convergent (already) |
| Socialware manifest / Definition | named lookup + divergence policy | Convergent with explicit no-clobber reconcile (already) |

The session is a **mailbox + projection surface** — a convergence point. Its only two strict behaviors are membership-at-delivery (a security decision) and single-actor sequencing (free). The premise "the session demands entity-state consistency" is, on the code as it stands, **mostly false**.

## ⑤ Verdict

**The causal claim (③ of the hypothesis) is not supported by the bug corpus; the counterfactual (④) would make the two hardest problems harder. Verdict: the hypothesis does not hold in its causal core — but two refined readings of it are right and actionable.**

The evidence:

1. **Count:** of 9 bug clusters, ~4.5 are duplication-without-owner ([B]), ~4 are liveness/ordering/key-lifecycle ([C]), and only #206's blast-radius aspect is a genuine "central chokepoint hurt us" ([A]). The two other [A] entries are inverted — *missing* chokepoints caused the bugs, and centralizing (SessionReads, atomic version-first snapshot) fixed them.
2. **The session is not the driver.** Nothing in the corpus is "the session demanded cross-entity consistency and broke". The session already is what the hypothesis wants it to become: an actor mailbox plus eventually-consistent projections, with exactly two strict points (membership-at-delivery, turn sequencing) that are respectively a security requirement and free.
3. **The [B] class is a violation of decentralization's own discipline, not of centralization.** Actor-model soundness = single writer per datum + async messaging. Every [B] bug is a datum with two homes or two writers — a P3 violation. The fixes all moved *toward* single ownership (one unified cap store; "only the spawn winner writes" flavor ownership; roster-as-projection-of-caps; a durable outbox owning the in-flight grant), which is equally the git model's actual mechanism (a serialized ref only the winner advances) — not away from it.
4. **The counterfactual imports the two classic EC pains** — revocation propagation and merge semantics — into the security core of a product whose acceptance tests (revoke ⇒ immediate receive-deny; human gating before external audiences) explicitly forbid the lag those pains create. And the named reference (Bluesky) has not solved decentralized private/authorized data; it side-steps it by being all-public and by centralizing its read model in practice.
5. **A large share of the observed complexity is transition cost, not steady-state cost** — the #189 dual-plane window (dual-write, cold-load reconcile, backfill, parity, epoch). The one-shot cutover (#1621) that ended it validated the "additive → write-plane → cutover" rhythm; the end state is mechanically simpler than the starting state.

**What the hypothesis gets right (the refined kernel):**
- Where a datum's *natural home* is the entity itself, holding it centrally as a second copy breeds drift — #192's roster is exactly that, and cap-as-truth (the "decentralized" copy as owner) is the right direction, already planned.
- Central *fail-loud* points must have **bounded blast radius** — #206's whole-app-down for one bad package is a real centralization cost worth engineering away (per-package quarantine).
- Cross-actor state transfer must be **EC by construction** (outbox + idempotent apply), never fire-and-forget — #207's fix generalizes.
- Allen's stated goal — *simple mechanism, verbose business logic as compositions of it* — is achievable, and the mechanism is the one the design already declares: **one owner per datum (P3) + signed bearer caps verified at one gate + mailboxes + derived projections**. The complex bugs came from drift *away* from that mechanism (two homes, two writers, missing outbox), plus one deliberate, now-mostly-paid migration.

## ⑥ Practical recommendations

**Worth moving further toward local-first / single-entity ownership (do these):**

1. **Finish #192 / #1620: roster = projection of member-held caps.** Caps in holder stores become the only membership truth; the session's `:members` is a derived view. This is the corpus's clearest "decentralize it" win — it deletes a [B] seam. Keep the delivery-time cap check strict.
2. **Make the DeliveryOutbox pattern the standard for *every* cross-actor state delivery** (grants, revokes; audit any other fire-and-forget cross-store writes). At-least-once + applied-after-commit + idempotent apply is the actor-native EC contract. The board's pending "pending absorb + 幂等 + fail-closed" review items are this exact discipline.
3. **Bound the boot blast radius: per-package quarantine in `ManifestSeed.scan_all!`** — fail the package loudly (telemetry + visible degradation), boot the rest. Same for any future global fail-loud registry scan. This is the legitimate #206 lesson.
4. **Give every file/home-dir replica a content-hash reconciliation rule** (the `DefinitionRegistry` no-clobber-with-loud-divergence policy, applied to package seeds and any `$EZAGENT_HOME` content): absent → seed; hash-equal → no-op; diverged → don't clobber, surface loudly, explicit apply. "Skip-if-exists" is banned as a policy.
5. **Keep cutovers one-shot.** The #189 lesson: the dual-plane window is where [B] bugs breed. Additive → write-plane → atomic cutover, with the shortest possible shadow period and an explicit epoch/fence. (Already the board's own conclusion; make it the standing rule for any future re-homing.)
6. **When federation (v0.x+) arrives**, the current cap plane is the right substrate — signed bearer artifacts + per-entity authority + generations are exactly what a multi-node deployment needs. Plan revocation there as *explicitly windowed* (generation checks against the issuer with bounded staleness), a conscious product decision rather than an accident.

**Do not touch (these are load-bearing, and the corpus proves it):**

7. **The generation gate / revocation immediacy** (`verify_against_current`, gen-gated holder reads, F-1 "presented caps never satisfy the principal gate"). This is the security core; every "relax it" direction re-opens resurrection/lag holes codex kept catching.
8. **KindRegistry single-live-actor-per-URI + `put_new`-only registration.** It is what makes actor-local state sound. Adopt semantics stay winner-writes-only, gated on the core spawn receipt `{:started, created?}`, with non-owner deletes forbidden and incarnation-scoped rollback (#1604 shape). Also standing: #1501's rework items (pending-absorb merge, idempotent grant, fail-closed absorb) complete the outbox contract — land them, don't relax them.
9. **Turn settlement as single-actor sequencing.** Human-in-the-loop gating needs an ordered, exactly-once settle point; the actor mailbox provides it at zero cost.
10. **The read-plane chokepoints and their anti-bypass gates** (SessionReads authorize-first; version-first atomic feed snapshot). They were the *fix*, and their EC-tolerant design (monotonic version + replay self-heal) is already the right local-first-compatible shape.
11. **The "flavor readable during instantiate" contract** (#1578) — a standing warning that some consumers legitimately demand read-your-write; enumerate such consumers before making any write more eventual (#1604's answer was to change the read's data source, not to make it tolerate eventual-ness).
