### Brainstorm record (historical — superseded by the spec)

We were in `superpowers:brainstorming` for the 3rd capability: **admin iterates
the AI**. Settled decisions:

**Strategic (the big one — locked in discussion):**
- Do NOT cargo-cult AutoService's soul-layer decomposition (L0/L1/L2/L3 + flow_directives
  + KB chunks + slot templates + CR + lint). That complexity was *earned* by
  AutoService's production scale (cinnox 80KB soul, multi-tenant, governance) — it is
  the end-state of iterating on real pain, not a starting requirement.
- **Approach = incremental + empirical A/B.** Build the smallest slice, then test
  with **cinnox** (NOT acme — acme's soul is too tiny to reveal any pain) using a
  small fixed case set + simple rubric (right facts / follows flow / no internal-leak /
  no drift), same model. Each *next* scope (KB? flow? layers?) is gated by a measured
  A/B (with vs without) on cinnox cases; **if it doesn't measurably improve answers,
  drop it.** AutoService's pieces = a catalog of proven solutions to specific pains;
  adopt each only when the pain shows + re-abstract onto ezagent primitives (fewer
  modules — conceptually just 3: compose / retrieve-selectively / edit-safely).
- **Sequencing decided:** (1) build scope #1 = editable soul (FUNCTIONAL only —
  "edit → new conversation uses it"; the quality A/B starts at scope #2). (2) THEN a
  separate cycle to build the cinnox A/B measurement harness. (3) Use the data to pick
  scope #2.

**Scope #1 (this brainstorm) — editable soul. DESIGN PRESENTED, AWAITING APPROVAL:**
1. **Scope**: admin edits a tenant's customer soul (whole markdown), save → new
   conversations auto-use it. No layers/KB/flow/CR/lint/versioning. Tenant-parameterized.

## Non-obvious learnings (do NOT re-derive)

- **Asset/CSS gotcha (bit us twice)**: under shared `MIX_DEPS_PATH`, esbuild's
  `NODE_PATH` points at repo-local `deps/` which doesn't exist → make a `deps` symlink
  to the shared cache, then `mix esbuild`/`mix tailwind`. AND Tailwind v4 `@source`
  globs in `apps/ezagent_web/assets/css/app.css` must list each plugin's lib path —
  the customer-chat plugin's path is now there; any NEW plugin with its own classes
  needs an `@source` line or its CSS gets purged (broke layout silently; compile+tests
  were green — only the live browser caught it).
- **Operator cap**: `Ezagent.Capability` field is `workspace_uri` (NOT `workspace`);
  wrong key returns nil → gate silently denies everyone. `:require_entity` on_mount
  sets `is_system_member?` (admin bypass works).
- **Soul-path hop count**: files at `apps/<app>/lib/<app>/x.ex` are 5 `..` from repo
  root (the old `customer_chat/` subdir was 6). Bootstrap uses 5.
- **Phoenix scope alias**: can't put a route for `EzagentPluginCustomerChat.X` inside
  `scope "/", EzagentPluginLiveview` — the scope prepends its alias. Use a scope with
  the right alias.
- **`deps` symlink + `.DS_Store`** are gitignored now (`/deps`, `.DS_Store`); don't
  re-track them.
- **cc first-send race**: the very first send right after a fresh `/chat` mount can
  occasionally land in the `:connecting` window and drop; retry works. Known, deferred.
- The customer LiveView's persistent connection structurally fixes the old C3 SSE
  120s-timeout tension (operator messages reach the customer live).
