# MFU 平台概念模型（living doc）

> 状态：持续迭代
> 建立：2026-07-28
> 最近更新：2026-07-31（依据多角色组织世界 v0.3）
> 适用范围：MFU（My First Unicorn）完整游戏、共享世界、订单、组织、资源、成长与多角色接入
> 规则：平台概念、概念边界或概念关系发生变化时，必须先修改本文。GDD 与 infographic 是版本快照，不回改。

## 0. 本文解决什么问题

MFU 过去用“成长树”和“解锁”两个词同时表达经验、技能、认证、会籍、角色与平台功能，导致以下概念被混在一起：

- 做过多少与做得多好；
- 学会了什么与平台允许做什么；
- 获得认证与加入一个组织；
- 达到候选门槛与被孵化器正式选中；
- 学生本人的能力、公司的能力和 Agent 的能力。

本文建立平台统一语言，并回答六个问题：

1. 平台正在帮助谁成长；
2. 什么事实可以证明成长；
3. 学校不同课程如何对应同一套能力标准；
4. 信誉、认证和角色资质分别代表什么；
5. 孵化器如何依据证据发现并验证潜在 OPC。
6. 一个订单如何经过拆解、匹配和交付，让独立猎人逐渐形成组织。

## A. 当前平台运行模型（v0.3）

本节描述当前完整可玩 Demo 已经采用的宏观模型。后文保留更详细的能力、认证和人才培养定义；Card Array、猎人教学和学生生命周期的历史设计已移至独立功能性 Demo，不再代表完整游戏的唯一主循环。

### A.1 所有玩家使用相似的页面架构

学校、孵化器、企业和学生进入平台后，都使用同一套核心结构：

```text
我的工作台
├─ 订单板
├─ 孵化中的组织
├─ 待处理
└─ 资源栏

世界
├─ 订单市场
├─ 世界动态
└─ 新闻与公告
```

不同玩家拥有的订单、组织、资源、权限和目标不同，但核心玩法一致：

```text
从世界发现或发布任务
→ 把已承接任务交给组织
→ 组织调用资源执行
→ 玩家处理异常、验收和结算
→ 组织与资源积累成长
```

### A.2 我的工作台

**我的工作台**是当前玩家管理自己已经承担的责任和持有资源的地方。

它不展示世界上所有机会，只展示与当前玩家直接相关的经营状态。

#### 订单板

订单板只保存当前玩家已经承接的订单：

```text
待确认 → 待分配 → 进行中 → 待结算 → 已完成
```

`待分配`表示当前玩家已经接下订单，但尚未交给内部 MVO。它不是市场上的公开订单。

#### 孵化中的组织

这里展示当前玩家拥有、管理或参与的 MVO：

- 正在执行什么；
- 组织图有哪些节点；
- 哪些节点已完成、正在运行、尚未开始或等待外部承接；
- 使用了哪些人才、Agent、工具/IP和算力；
- 交付、收入、成本、经验、等级和认证状态。

#### 待处理

待处理只保存需要玩家作出决定的事项，例如：

- 验收或打回；
- 风险处理；
- 收款确认；
- 资源冲突；
- 预算异常；
- 组织升级。

它不是永久档案。决定完成后，结果进入订单、组织、资源或财务记录。

#### 资源栏

当前资源分为五类：

- 人才；
- Agent；
- 工具/IP；
- 算力；
- 资金。

资源可以属于玩家，也可以加入 MVO。MVO 完成一个订单后，资源结束本单占用，但不会自动离开组织。

### A.3 世界

**世界**是不同玩家共同活动的公共空间。

#### 订单市场

市场订单尚未被当前玩家承接。玩家承接后，订单才从世界进入自己的订单板。

玩家也可以在世界发布订单。自己发布的订单留在市场等待其他玩家承接，不能被自己再次承接。

订单市场推荐按行业领域筛选，例如：

- 推荐；
- 全部；
- 教育与校园；
- 消费与零售；
- 内容与品牌；
- 软件与 AI；
- 社会创新；
- 节点外包；
- 我发布的。

平台不根据“学校用户”“企业用户”等身份给用户或订单作封闭分类。角色只影响推荐和当前拥有的内容。

#### 世界动态与公告

世界动态记录其他组织的公开事件，例如发布订单、完成节点、获得评价或升级。新闻与公告保存平台活动、竞赛和系统信息。

### A.4 MVO 与组织图

**MVO（Minimum Valuable Organisation，最小有效组织）**是能够调用一组资源、按照任务流持续产出有效结果的最小组织。

组织图同时定义：

- 任务节点；
- 节点之间的连接；
- 输入和输出；
- 执行顺序；
- 装入节点的人才、Agent、工具/IP与其他资源。

组织执行订单时，项目进度必须能回到具体节点，而不仅是一条总进度。

### A.5 节点外包

MVO 可以把尚未完成的单个节点发布为新的市场订单：

```text
原订单
→ 原 MVO
→ 某个执行节点
→ 发布节点外包订单
→ 外部组织承接并返回成果
→ 成果回到原节点
→ 原 MVO 继续执行
```

节点外包不是点击按钮后直接花钱增加进度。它必须形成一张真实订单，并保留来源订单、来源 MVO和来源节点。

### A.6 订单结算与组织成长

当前订单闭环是：

```text
承接
→ 分配给 MVO
→ 执行
→ 验收
→ 开票
→ 收款
→ 完成
```

验收通过不等于已经获得收入。只有确认收款后：

- 资金入账；
- 订单完成；
- 本单资源占用解除；
- MVO 获得履约记录、经验、等级或优化点。

### A.7 多角色与共享世界

当前确认的首批角色视角：

- 孵化器运营者；
- 学校创新创业课程负责人；
- 企业创新负责人；
- 学生创业者（正在成长为 OPC）。

四个角色使用相同游戏架构，拥有独立工作台，并共享同一个世界。

角色自己的订单板、组织、资源、资金、算力、待处理、办公室和履约记录互相独立。订单市场、世界动态、新闻公告以及公开的跨角色发布与承接记录属于共享世界。

Demo 顶部的角色切换器只用于向观众演示不同用户视角，正式产品依据登录身份进入对应工作台。世界订单首先提供“推荐”，并可按教育与校园、消费与零售、内容与品牌、软件与 AI、社会创新等行业领域筛选；不按“学校发布”“企业发布”等用户身份分类。

角色不是平台对用户的唯一分类。同一个真实用户未来可能同时拥有多种身份或加入多个组织。

### A.8 尚未确定的组织边界

以下问题尚未成为平台正式规则：

- 学校、企业、孵化器等长期组织与 MVO 的最终关系；
- 一个人同时加入多个组织的成员模型；
- 学校与孵化器如何共同安排同一个学生；
- 调度是否采用预授权额度；
- 跨组织信息可见性；
- 收入、作品、IP和成长的跨组织归属。

这些问题统一登记在：

[`../pending-decisions/组织、多重成员关系与跨组织调度.md`](../pending-decisions/组织、多重成员关系与跨组织调度.md)

在问题确认前，Demo 可以展示多角色共享世界和跨角色订单，但不能把具体调度权限写成正式机制。

## 1. 平台定位

MFU 起源于面向学校与孵化器的“大学生创新创业课”教具，目前完整平台同时支持学校、孵化器、企业和学生使用同一套组织经营机制。

学生不是通过填写一份静态测评来证明自己，而是在经营一家 AI-native 模拟公司（OPC）的过程中：

- 发现与理解需求；
- 编排本人、人类成员、Agent 与外部资源；
- 完成课程任务、模拟项目和真实命题；
- 接受教师、企业、协会和孵化器的评价；
- 积累可追溯的能力证据、经营履历与信用记录；
- 最终被真实孵化器发现，并通过额外验证后获得入驻邀请。

平台不替学校完成教学设计，也不替孵化器作最终录取决定。平台提供共同能力标准、实践环境、证据档案和筛选工具。

### 1.1 五方角色

| 角色 | 在平台中的主要责任 |
|---|---|
| 学生 | 学习、经营 OPC、完成任务、形成个人能力证据 |
| 学校 | 设计课程、提供教学资源、组织评价、观察教学效果 |
| 老师/教练 | 出题、辅导、评价、帮助学生根据能力缺口继续学习 |
| 孵化器 | 提供真实命题、发现候选人、发出验证任务、作出入驻决定 |
| 协会/评价机构 | 提供行业评价、信誉等级、专业认证或角色资质 |

### 1.2 Card Array 教学模型中的角色

> 本节描述独立 Card Array 教学 Demo 如何帮助新用户理解从局部任务到组织形成，不等于当前完整游戏只允许这些角色或只能采用平台自动匹配。

| 角色 | 定义 | 在校期间 | 真实社会 |
|---|---|---|---|
| 发单方 | 提出完整需求并最终验收结果 | 学校/课程团队 | 企业或其他真实客户 |
| 拆单方 | 把完整订单拆成有依赖关系的步骤，汇总步骤结果并初验 | 多个专业的老师 | 孵化器、协会或平台 |
| 平台 | 展示步骤拓扑、匹配猎人、记录状态与评价 | MFU | MFU |
| 猎人 | 独立完成一个步骤的人或 Agent | 学生或学生的 Agent | freelancer 或其 Agent |
| 组织 | 人类猎人连接上下游后建立的持续经营主体 | 学生组织 | OPC |

Agent 可以作为猎人执行步骤并出现在拓扑中，但 Agent 是人或公司的资产，不能主动联系上下游、发起邀请或成立组织。这些行为必须由其所属的人确认。

## 2. 订单如何促成组织形成

### 2.1 订单、步骤与拓扑

**订单**是发单方希望获得的完整结果。订单进入市场后，先由拆单方拆成 N 个步骤。

**步骤拓扑**不是普通待办列表，而是同时记录：

- 每个步骤要交付什么；
- 哪些步骤是上游或下游；
- 哪些步骤可以并行；
- 每个步骤当前的完成状态；
- 最终结果如何汇总。

猎人执行步骤时可以看到整单的大致拓扑、依赖关系、完成进度和同单协作者。自己的节点始终高亮；所有同单协作者可以进入订单聊天室，讨论接口、素材和交付状态。

### 2.2 从订单到猎人

```text
发单方提出订单
→ 拆单方拆成步骤拓扑
→ 平台把每个步骤匹配给一名猎人
→ 猎人只为自己的步骤负责
→ 拆单方汇总并初验
→ 发单方最终验收与评价
```

平台负责匹配，但 v0.15 暂不解释匹配算法，也不展示一个替发单方作决定的总分。

### 2.3 从猎人到组织

同单猎人在执行期间已经可以互相看到并交流。步骤完成后，人类猎人可以根据本次真实协作记录，向合适的上下游或其他同单伙伴发送长期合作邀请；对方接受后形成持续关系。

```text
完成一个步骤
→ 回看同单协作者与上下游关系
→ 邀请合适的人或 Agent 继续合作
→ 建立组织
→ 组织承接更多类似订单
```

组织形成后，市场可以把完整订单交给组织。组织再使用内部任务编排，把工作安排给成员和 Agent。由此形成两种互补的匹配：

- 组织形成前：平台把步骤匹配给猎人；
- 组织形成后：市场把完整订单匹配给组织，组织自行编排内部执行。

## 3. 成长主体与归属

### 3.1 人（主理人）

人拥有：

- 个人经验；
- 个人能力；
- 专业认证；
- 角色资质；
- 荣誉与背书；
- 跨公司保留的能力证据和生涯档案。

公司失败、清算或更换不清除个人档案。

### 3.2 公司（OPC/组织）

公司拥有：

- 订单与履约经验；
- 公司声望与信用；
- 组织能力；
- 公司资产；
- 公司获得的信誉等级、资质与会籍；
- 公司可使用的平台功能。

公司能力不是主理人个人能力与 Agent 能力的简单相加。只有当流程、资产和协作方式能够被公司稳定复用时，才形成组织能力。

### 3.3 Agent

Agent 是人或公司的资产，不是独立成长主体，不设置能力树。

Agent 使用以下方式表达成长：

- 能力分；
- 训练资产；
- 实战评价史；
- 里程碑徽章；
- 版本与归属记录。

购买一个强 Agent 不等于购买了主理人的个人能力。

### 3.4 0 号 Agent（小 H）

小 H 跟随个人档案，保存偏好、复盘和长期陪伴信息。它属于个人资产，但它的能力仍不计入个人能力。

## 4. 核心概念

### 4.1 行为记录

行为记录是“发生过什么”的事实，例如：

- 打工次数；
- 完成订单数；
- 作品数；
- 人脉数；
- 复盘数；
- 评审次数；
- 带队次数。

行为数量只能证明参与和活跃，不能单独证明能力水平。

### 4.2 经验

经验是行为记录形成的履历，回答：

> 这个人或组织在平台上做过多少事、接触过多少情境？

经验以计数、进度条、时间线和案例列表呈现。经验不直接使能力达标，但可以：

- 为能力评价提供样本；
- 形成履约记录；
- 影响声望和信用；
- 帮助客户判断响应速度与熟练程度。

### 4.3 能力证据

能力证据是经过评价、能够说明某项能力水平的材料，例如：

- 课程作业及评分；
- 情境测评结果；
- 独立项目及验收结果；
- 复杂命题及多轮修改记录；
- 竞赛评级；
- 专家作品评价；
- 平台外证书或奖项；
- 失败后的复盘与下一次改进结果。

作品数量属于经验；经过评价的具体作品才可能成为能力证据。

### 4.4 能力

能力回答：

> 这个人或组织已经被证明能够完成什么？

能力必须满足三个条件：

1. 离开 MFU 平台后仍然存在；
2. 可以通过任务、作品、考试或专业评价证明；
3. 表达可观察的结果，而不是学习进行中的状态。

“A/B 测试器”“联合竞标按钮”不是能力；背后的“实验验证”“协作与资源组合”才是能力。

### 4.5 声望与信用

| 概念 | 回答的问题 | 主要依据 |
|---|---|---|
| 声望 | 市场是否看见并认可这个人/组织 | 公开成绩、竞赛、评价、影响力 |
| 信用 | 是否值得相信其会履行承诺 | 履约、违约、响应、责任记录 |

声望与信用不是专业能力。大量交付可以带来高经验和高信誉，但不自动证明高水平专业能力。

### 4.6 信誉等级

青铜、白银、黄金属于信誉等级，表达平台市场中的活跃度、可靠性与公开认可。

信誉等级：

- 可以由协会或平台规则颁发；
- 可以作为会籍、订单或功能开通条件；
- 不作为专业能力节点；
- 不自动等于孵化器入驻。

### 4.7 专业认证

专业认证证明某项专业能力达到规定标准，例如：

- MFU 判断力认证；
- 学校课程认证；
- 专家作品集评级；
- 行业证书；
- 竞赛奖项所证明的专业水平。

判断力认证属于 MFU 课程认证：学生完成至少 5 次路由判断，系统根据结果基准评价，达标率达到 60% 后获得认证。次数保证最低样本，达标率证明能力。

专业认证是能力证据之一，不等于能力本身。同一能力可以由不同证据组合证明。

### 4.8 角色资质

角色资质证明个人或组织被允许承担高责任角色，例如：

- 评审员资质；
- 教练资质；
- 孵化平台资质；
- 平台运营授权。

角色资质通常同时要求专业能力、实践经验、信誉和人工审核。取得资质后可以申请或开通相应工作台，但资质本身不进入成长树。

### 4.9 荣誉与背书

荣誉与背书表达社会认可，例如：

- 孵化器背书；
- 比赛冠军；
- 优秀团队；
- 机构推荐。

荣誉默认只用于展示；只有规则明确规定时，才参与功能开放判断。

### 4.10 会籍

会籍是人与组织之间已经成立的关系，例如：

- 学校学籍；
- 孵化器预备营；
- 协会会员；
- 孵化器入驻会籍。

“有资格申请”“已经申请”“获准加入”是三个不同状态。

### 4.11 平台功能

平台功能是 MFU/ezagent 提供的具体操作，例如：

- 联合竞标；
- Agent 资产出租；
- 公开评审；
- A/B 测试模拟器；
- 教练工作台；
- 孵化器 Scouting、grant 与投后管理。

功能依赖平台实现，因此不作为能力节点。功能可以读取能力、信誉等级、专业认证、角色资质、会籍、风险状态和人工审批结果。

### 4.12 功能开放规则

功能开放规则回答：

> 谁在什么条件下可以做什么？

示例：

```text
联合竞标可用
= 公司达到白银信誉
+ 至少两个专业方向具备独立交付能力
+ 当前没有严重违约
```

```text
公开评审可用
= 对应领域能力已达标
+ 获得评审员角色资质
```

```text
孵化器工作台可用
= 组织取得孵化平台角色资质
+ 平台完成开通
```

## 5. 个人能力框架

### 5.1 OPC 核心能力

v0.15 demo 使用六项最小核心能力：

| 能力 | 可观察结果 |
|---|---|
| 机会判断 | 能识别值得解决的问题与可能的市场机会 |
| 客户理解 | 能澄清需求、识别约束并判断真实价值 |
| 方案设计 | 能把问题转化为可执行、可验收的方案 |
| 资源编排 | 能合理安排本人、成员、Agent 与外部资源 |
| 交付负责 | 能定义验收标准、控制质量并为结果负责 |
| 复盘迭代 | 能从结果中提取原因并改变下一轮行动 |

后续可以增加商业判断、协作沟通、风险与伦理等能力，但 v0.15 不扩张节点数量。

### 5.2 专业能力方向

专业能力允许并行与放射状发展，例如：

```text
内容与表达（领域，不是达标节点）
├─ 图文内容
├─ 视频内容
└─ 长文内容
```

其他候选领域包括创意与设计、市场与增长、产品与技术及行业专项能力。领域名称用于分类，只有可评价的成果才成为节点。

### 5.3 能力达标层次

成长树不显示“学习中”这类过程节点。v0.15 使用三类达标标准：

#### 基础应用达标

在要求明确、范围有限、允许获得指导的任务中，能够正确使用基础方法完成作品。

证据要求：

- 任务被标记为基础难度；
- 使用共同评价标准；
- 核心指标达到最低门槛；
- 有足够样本避免偶然通过。

#### 独立交付达标

面对相对真实的需求，在没有教师代替关键决策的情况下，能够独立完成并通过验收。

证据要求：

- 存在真实或模拟真实的验收标准；
- 学生承担关键判断；
- 成果由合格评价者确认；
- 最好在不同情境中重复达标。

#### 复杂项目达标

能够处理多重约束、不确定信息、需求变化或多方协作的任务。

复杂任务应符合若干共同特征：

- 需求需要主动澄清；
- 多个目标存在冲突；
- 涉及多个专业领域；
- 需要多轮修改；
- 需要与客户或队友协调；
- 没有唯一标准答案；
- 结果接受真实用户或市场检验。

任务发布者不能仅靠自行标注使任务变成“复杂任务”；任务必须符合平台复杂度标准，成果仍需通过评价。

### 5.4 高阶分支

“专业评审”“教学带教”“方法创新”“专业负责”不是所有能力共同的第四等级。它们是复杂项目达标后可能出现的不同分支，并使用各自评价方式。

## 6. 多学校课程如何对应统一能力

### 6.1 两层结构

#### 平台统一能力标准

平台统一定义：

- 能力领域；
- 可观察的能力成果；
- 任务难度；
- 评价标准；
- 可接受的证据；
- 达标要求。

#### 学校课程

学校自由定义：

- 课程名称；
- 教学内容；
- 教学顺序；
- 学分与学时；
- 作业、考试和项目；
- 本校评价安排。

学校课程不直接等于平台能力节点。

### 6.2 多对多对应

平台允许：

- 一门课程对应多个能力；
- 多门课程共同证明一项能力；
- 不同学校用不同课程组合达到同一能力；
- 平台外课程与证书对应平台能力。

示例：

```text
A 校：建筑设计基础 1 + 建筑设计基础 2
                         └──→ 建筑设计基础应用达标

B 校：建筑设计初级
                         └──→ 建筑设计基础应用达标
```

### 6.3 学分与学时

学分和学时说明学习投入与课程完成情况，不单独证明能力。

```text
课程覆盖范围
+ 学习投入
+ 作业/项目评价
+ 必要的综合测评
= 能力是否达标
```

v0.15 demo 只展示人工维护的“课程 → 平台能力 → 评价任务”对应表。审核、版本与跨校校准机制留待后续。

## 7. 证据归属：学生、Agent 与公司

每份成果至少标记一种贡献方式：

| 标记 | 含义 | 对个人能力的作用 |
|---|---|---|
| 学生主导 | 学生作出关键判断并完成主要工作 | 可以形成对应个人能力证据 |
| Agent 主导 | Agent 完成主要判断与执行，学生仅确认 | 主要进入公司履历和 Agent 评价 |
| 共同完成 | 学生与 Agent/成员分别承担关键部分 | 按记录的个人贡献形成部分能力证据 |

同一成果可以同时产生不同记录：

- 最终作品质量 → 公司交付记录；
- 学生的任务拆解与路由 → 资源编排证据；
- Agent 的执行结果 → Agent 实战评价；
- 学生最终验收与担责 → 交付负责证据。

采用多图结构，但每类图只表达一种成长。

### 8.1 个人成长树

### 8.2 公司成长树

角色资质本身不在图上。

## 9. OPC 候选档案

候选档案服务孵化器筛选，但不替孵化器作决定。

v0.15 最小档案包括：

- OPC 核心成长树；
- 专业方向；
- 经验与履约记录；
- 信誉等级；
- 专业认证与角色资质；
- 代表性证据及贡献归属；
- 尚未验证的能力缺口；
- 建议的下一道验证任务。

平台不生成一个统一“OPC 总分”。不同孵化器可以依据自己的方向使用同一份证据作不同判断。

黄金信誉或其他门槛只能使候选人“值得关注”，不能自动产生入驻邀请。正式入驻必须经过孵化器真人判断和验证任务。

## 10. 三个闭环

### 10.1 学习闭环

```text
学校课程
→ 学生完成任务
→ 获得评价与反馈
→ 积累能力证据
→ 能力达标
→ 推荐下一门课程或任务
```

### 10.2 经营闭环

```text
学生经营 OPC
→ 编排本人、成员、Agent 与外部资源
→ 完成模拟或真实任务
→ 分别形成个人证据、公司履历与 Agent 资产
→ 获得新的市场机会
```

### 10.3 筛选闭环

```text
能力档案 + 经验履历 + 信誉与认证
→ 孵化器发现候选人
→ 发出高难度验证任务
→ 真人评估
→ 发出入驻邀请
```

## 11. 统一用语

以后不再笼统使用“解锁”，应按实际事件使用：

| 用语 | 准确定义 |
|---|---|
| 达标 | 能力证据满足标准 |
| 获证 | 正式取得认证或资质 |
| 有资格申请 | 满足申请门槛，但关系尚未成立 |
| 加入 | 会籍关系成立 |
| 开通 | 平台功能已经可以使用 |
| 受邀 | 学校、孵化器或其他真人作出选择 |

“成长树”是平台正式产品名称；“技能树/科技树”只用于描述历史版本。成长树承载能力成长，但不承载经验、认证或平台功能。

## 13. 状态与后续治理

### 已确认

- 经验、能力、认证与平台功能分离；
- 能力采用宽领域与可评价成果，不把细碎工具作为节点；
- 成长树允许进阶、放射、汇合与交叉；
- 信誉等级、专业认证、角色资质、荣誉背书是不同概念；
- 平台功能由独立规则开通；
- 平台统一能力标准，学校自由设计课程并建立多对多对应；
- 学分与学时不直接证明能力；
- 学生、Agent 和共同完成必须区分；
- 候选档案不使用单一 OPC 总分；
- 孵化器作最终筛选决定。

### v0.15 demo 简化

- 使用六项 OPC 核心能力；
- 使用人工课程对应表示意；
- 使用三种贡献归属；
- 使用示例性功能开放规则；
- 不实现跨校审核、评价者校准和完整防刷机制。

### 后续治理

- 能力标准与课程对应关系的审核、版本和撤销；
- 评价者资格与跨校评分校准；
- 任务难度审核；
- 证据防刷、小样本和异常行为识别；
- 学生授权、隐私、申诉和档案携带；
- 专业认证与角色资质的有效期、暂停和撤销。
