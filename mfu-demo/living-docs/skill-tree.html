1. What —— 成长树是什么

成长树只展示已经被证据证明的稳定能力，不是经验条、徽章架或平台功能菜单。

节点必须同时满足：

  1. 表达“已经能够完成什么”，而不是“正在学习”；
  2. 离开 MFU 平台后仍然成立；
  3. 有明确的任务与评价方式；
  4. 粒度足够稳定，不把单一工具、按钮或作品形态误当成完整能力。

1.1 三类成长树

成长树 谁拥有 展示什么 不展示什么
个人成长树 主理人 OPC 核心能力与专业能力的达标结果 打工/作品计数、信誉等级、会籍、功能按钮
公司成长树 公司 可稳定复用的组织能力 主理人技能与 Agent 能力的简单并集
角色成长树 已取得角色资质的个人或组织 在教练、孵化、平台运营等角色中的实践能力 角色资质本身、工作台按钮

1.2 v0.15 个人成长树

OPC 核心能力采用六项最小集合：

  • 机会判断；
  • 客户理解；
  • 方案设计；
  • 资源编排；
  • 交付负责；
  • 复盘迭代。

专业领域允许放射状展开。例如“内容与表达”是分类，下面可以并列图文、视频、长文等方向；分类本身不是达标节点。

每个方向可以出现三类可评价成果：

  • 基础应用达标；
  • 独立交付达标；
  • 复杂项目达标。

专业评审、教学带教、方法创新和专业负责是复杂项目之后可能出现的不同分支，不是统一的第四级。

2. Why —— 为什么这样设计

2.1 解决什么问题

成长树模型延续 flywheel-audit 对 progression 的要求，但不再承担全部权限：

问题 成长树如何回应
Progression 有骨架无感知 树就是骨架：节点 = 里程碑，解锁 = 有仪式感的事件，分支 = 可选路径
白银→黄金中期真空 能力证据持续积累，学生每周都能看到距下一项达标还差什么
四种 Bartle 玩家类型出口单一 不同能力分支、专业方向、角色实践与真实挑战提供不同追求
其他角色界面要不要做 角色资质负责开通工作台，角色成长树负责表达开通后的成长
目标透明度 能力标准与本人证据公开透明；孵化器偏好和最终选择不由平台预设

2.2 核心模型与兑现链

课程 / 任务 / 项目
        ↓
经过评价且标明贡献归属的能力证据
        ↓
满足平台统一能力标准
        ↓
能力节点达标

能力达标可以成为平台功能开放的条件之一，但功能本身不进入成长树：

能力 + 信誉等级 + 专业认证/角色资质 + 会籍/人工审批
        ↓
独立的功能开放规则
        ↓
联合竞标、公开评审、工作台等平台功能

D41 外部认证录入 主理人/公司可录入平台外获得的认证资格（学历、行业证书、作品集奖项），经核验后解锁相应技能树节点——解决「高手新入驻」场景（B 案例：平台外水平高但无平台记录）。核验机制待定（协会认证 Agent 初审 + 人工抽查？）；录入的外部认证在徽章架上与平台内认证并列展示、标注来源 已定 2026-07-27（Allen 批准框架时确认的方向）
D42 成长树不等于功能菜单 联合竞标、资产出租、公开评审、A/B 测试器和各类工作台属于平台功能；能力、信誉、认证、资质等只作为功能开放条件 已定 2026-07-28
D43 节点必须是达标结果 节点统一表达可评价的完成状态，不使用“学习中”；过程通过未开始/证据积累中/已达标展示 已定 2026-07-28
D44 宽领域 + 分支能力 不再把 A/B 实验、模板等细碎方法各做节点。领域用于分类，能力成果可以进阶、并列、汇合和交叉 已定 2026-07-28
D45 多校课程映射 平台统一能力标准，学校自由设计课程；课程与能力是多对多关系。学分/学时是证据输入，不直接证明能力 已定 2026-07-28
D46 证据必须标明贡献归属 学生主导、Agent 主导、共同完成分别记录；只有学生承担关键判断的部分才进入个人能力证据 已定 2026-07-28
D47 三类成长树 保留个人、公司、角色三类成长树；角色资质先开通工作台，角色成长树描述履职后的成长，资质本身不作节点 已定 2026-07-28

2.4 其他设计原则

  • 统一起点（flywheel-audit §5.2）：做孵化器视图 = 做同一张面板 + 孵化器树解锁的额外模块，不是另做一套界面（D27）
  • 树公开：树结构与解锁状态对所有登录用户公开（D28）——野心机制 + 信任机制 + 竞争情报
  • 分支价值由市场决定（命题供给/会籍需求），系统不标「最优路径」
  • GDKeys 7 原则的逐条落地见 GDD v0.14 §5.10.4（若落地方式变更，改记到本文 §9）

3.2 节点的解锁时机与检查机制

  • 检查时机（当前实现，两处）：① tick() 周结算——新解锁记入日志（正式版应改为结算日事件推送）；② renderRadialTree() 渲染时静默刷新
  • 父节点检查自动派生：节点的 deps 声明结构依赖，nodeAvail(n) 统一做「所有 deps 已解锁 + 自身条件」判断——condFn 只写额外条件，不再手写父节点检查（P-01，2026-07-27 落地）
  • 解锁即永久：已解锁节点不回退，切换专精线已训 Agent 不降级（GDKeys 5：成本是时间，不是损失）
  • 三种状态：unlocked（已解锁）/ available（条件已满足待解锁）/ locked（条件未满足）

3.3 条件的合法来源（D32 + P-15 框架）

树 condFn 允许读取的字段 打工能否作为条件
主干树（公司树） 公司字段（S.credits、S.lines、S.rep、S.cred、S.rank、S.realN/Q、公司树节点状态） ❌ 永不（D32）
个人树 个人字段（S.profile.*——含 gigs、guildHist、certs、S.reviews） ❌（P-15 批准：打工只进经验条）⚠️ 现有 P-00 条件待框架落地时移除
资质树 同主干树（公司字段）+ 资质树自身节点状态 ❌

约束：个人树节点的 condFn 不允许读公司状态（S.guilds、S.rank、S.cash…）。认证要通过 D36 的个人认证记录进入个人树。

3.4 解锁后兑现什么（grants 机制）

每个节点声明 grants（它开启什么）。兑现链：

资质认证（如 N-13 解锁）→ 资质树诞生 → 根节点开启功能面板（如孵化器工作台）
                                    → 子节点开启或改变面板内的使用权限
  • 根节点 grants：panel:incubator（面板可见 + 基础只读）
  • 子节点 grants：feature:scouting（配置候选追踪）、feature:directed-order（定向命题）……
  • UI 层查询「当前组织已解锁的 grants 集合」决定面板可见性/可操作性
  • 主干树节点同理：N-04 设计提案 grants feature:reverse-pitch，N-05 品牌模板 grants feature:template-market……（当前全部未实现，见 §6 P-08）

3.5 树的消亡

事件 影响
公司破产/清算 公司主干树随公司消亡；个人树不受影响（跨公司保留）；公司已获得的认证在个人档案中的记录保留（D36）
公司消亡时的资质树 资质树（功能面板使用权）随公司消亡而关闭；个人档案中的认证记录保留，作为重建时的凭据（推论，若需调整在此修订）
个人树 永不消亡

3.6 成长归属：Agent 的成长算谁的（D39）

  • Agent 的成长不算个人成长。Agent 是公司资产（D19：可出售/转让/归档）——若 Agent 成长计入个人成长，卖掉一个训练好的 Agent 就等于卖掉个人成长，花钱买强 Agent 就等于花钱买个人技能（撞 D17「金钱买不到能力」）
  • Agent 没有成长树。平台上只有两种实体有树：公司（Org）和人。Agent 是资产，不是实体。Agent 的 progression 用能力分 + 训练资产清单 + 里程碑徽章（能力分 6/8/10 觉醒点，见 flywheel-audit C.5）表达，不设树
  • Agent 能力分 = f（训练资产， 实战评价史）——本就是质量信号驱动的成长，与技能/经验框架（P-15）的原则一致
  • 例外：0 号 Agent 小 H 属于人（D29，随档案永续、不可交易），其沉淀 = 个人偏好配置，算个人资产，但仍不是树节点
  • 对 GDD v0.14 开放问题 #12（D34）的回答：企业树 ≠ 成员/Agent 个人树的并集——倾向「否」，框架方向已获 Allen 认可

5.1 渲染架构

两棵树共享同一套渲染引擎（renderRadialTree(scope) + nodeAngle(n, scope)），通过 scope 字段区分。资质树的渲染复用同一引擎（新增 scope + 参数行，见 §7.1）。

5.2 连线逻辑

连线从父节点（deps[]）指向子节点，使用正交路径：

M parentX parentY  →  L parentX midY  →  L childX midY  →  L childX childY

midY = parentY + (childY - parentY) * 0.55（偏向父节点一端）。

CSS: stroke-width:3; stroke-linejoin:round; stroke-linecap:round。 状态 class：unlocked（子节点已解锁 → 实线 teal）、available（仅父节点解锁 → 虚线 gold）、默认（虚线 gray）。

5.3 节点状态机

每个节点在 S.treeNodes[id] 中存储 {unlocked: boolean}。

// 初始化（$('startBtn').onclick 中调用）
function initTreeNodes(){
  TREE_NODES.forEach(n => {S.treeNodes[n.id] = {unlocked: n.condFn()};});
}

// 可解锁判断（P-01）：父节点检查从 deps 自动派生，condFn 只写额外条件
function nodeAvail(n){
  return n.deps.every(d => {const ds = S.treeNodes[d]; return ds && ds.unlocked;}) && n.condFn();
}

// 解锁检查（tick() 周结算记日志；renderRadialTree() 内静默调用）
function checkTreeNodes(){
  let newly = [];
  TREE_NODES.forEach(n => {
    if (!S.treeNodes[n.id].unlocked && nodeAvail(n)) {
      S.treeNodes[n.id].unlocked = true;
      newly.push(n);
    }
  });
  return newly;
}

5.4 三种渲染状态

状态 CSS class 条件 视觉效果
unlocked .tnode.unlocked S.treeNodes[id].unlocked === true cream 填充 + teal 描边
available .tnode.available !unlocked && nodeAvail(n) 金色虚线描边 + 脉冲动画
locked .tnode.locked 以上皆否 灰色填充 + 灰色描边 · cursor:default

连线对应三种状态：.tline.unlocked（teal）、.tline.available（金色虚线）、默认（灰色虚线）。

7.1 技术 SOP —— 如何加节点 / tier / 树

新增一个主干树节点

在 TREE_NODES 数组中，N-14 之后、// ---- 个人成长树节点 ---- 注释之前插入：

{id:'N-15',tier:4,name:'新节点名称',verb:'动作',icon:'🆕',group:'newgroup',scope:'company',deps:['N-11'],
 cond:'条件描述',condFn:()=>/* 只写额外条件 */,level:{cur:0,max:1}},

检查清单：

  1. verb 在整棵树上只出现一次（D31 动词规则）
  2. 只写 deps + 额外条件——父节点检查由 nodeAvail 自动派生（P-01 已修复），不要在 condFn 里手写父节点检查
  3. 声明 grants（§3.4）；没有兑现的节点不允许合入
  4. 在本文 §4 补节点定义表
  5. §9 变更记录 +1

新增一个个人树节点

在 P-06 之后、]; 之前插入（格式同上，scope:'personal'，deps 引用 P-xx 节点）。 额外约束：condFn 只读个人字段（§3.3）；P-15 批准后：计数类条件一律进经验条，不做树节点。

新增一棵资质树（如孵化器树）

  1. 主干树上的认证节点（根）已存在（如 N-13）；其 condFn 通常为外部授予
  2. 子节点用新 scope（如 'incubator'）加入节点数组，deps 引用根节点 id；渲染时根节点同时出现在主干树（scope:'company'）和资质树（scope:'incubator'）的过滤器中（同节点兼作树根，D35）
  3. renderRadialTree 参数表加一行（viewBox/中心/半径），背景环数组按 tier 调整
  4. 资质树的访问路径 = 对应功能面板内嵌（不是 ERP tab）
  5. 声明每个子节点的 grants 并接到 UI 权限查询

新增 tier

  1. 在 renderRadialTree 中扩展 radii 映射（每个 scope 都需要对应半径）
  2. 在背景环渲染的数组中添加新 tier
  3. 确保新 tier 的半径不超过 viewBox 范围

7.2 运营 SOP —— 谁能开新树 / 新分支

基础决策：D38 —— 树内容由平台统一定义（2026-07-27）。

原则：树的内容是平台级公共品，定义权集中在平台；角色组织获得的是解锁状态，不是定义权。

角色 能做什么 不能做什么
平台运营（ezagent，N-14）= 现实中的游戏策划 新增/修改任何树的节点、分支、tier；调整解锁数值；定义新资质树 —
协会 提案认证门（gate）节点的门槛数值（认证标准本就是协会资产）；提案新认证节点 直接上线——仍需平台运营合入
孵化器/其他角色组织 解锁资质树后获得面板使用权；可提案自己业务需要的功能子节点 自定义树结构
普通组织（OPC） 解锁节点；看到全树 提案需经协会或平台渠道

新节点上线流程：

  1. 提案：写明 verb、解锁条件、功能兑现（grants）、数值依据
  2. 评审：动词唯一性检查 + 数值 playtest
  3. 合入：按 §7.1 技术 SOP 实施
  4. 公开：树结构变更对所有用户可见（D28），在结算日事件中公告
  5. 记录：本文 §6（如有问题修订）+ §9 变更记录

开「新资质树」的判定：默认作为现有主干树认证节点的展开（D35）。只有当面板/视角/字段完全不同于现有类型时，才考虑全新树型，且需本文档重大版本记录。

待决策：

  • 组织自定义「目标节点」（GDD 开放问题 #9 的世界杯模式）是否开放？当前建议：demo 阶段不开放，待目标树讨论有结论
  • 数值门槛的最终拍板权：平台运营单方决定，还是需要协会联署？（认证通胀风险，gap-analysis #17）
  • 外部认证录入（D41）的核验机制：协会认证 Agent 初审 + 人工抽查？核验失败的惩罚？
