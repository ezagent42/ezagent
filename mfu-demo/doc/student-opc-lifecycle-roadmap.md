## 0. 本文解决什么问题

当前 MFU 已经分别记录了平台概念、成长体系、五方体验、订单全生命周期、核心卡牌阵列玩法和首个教学订单，但还缺少一张把它们串起来的完整地图。

本文同时回答两个问题：

1. **一个学生进入 MFU 后，会怎样从完成一小步，成长为能够经营 OPC、连接他人并承接完整订单的人？**
2. **为了支持这段生命周期，Demo 和正式平台应当按什么顺序增加能力？**

这两条线高度重合，但不能混为一谈：

- **用户生命周期**描述一个学生 / OPC 经历了什么、做成了什么；
- **产品演进路线**描述平台需要提供什么体验和工具；
- 用户不必按固定时间升级，也可以在某个阶段反复练习、暂时离开或回到前一阶段；
- 产品路线不是固定日期承诺。每一阶段是否继续，应由上一阶段的试玩和真实使用结果决定。

## 1. 一句话总路线

> 学生先在一个大项目中完成自己的一小步，再学会编排本人和 Agent，随后主动连接上下游形成组织，逐渐承接完整订单、积累可信证据，并最终被真实市场和孵化器发现。

```text
完成一小步
→ 学会人机编排
→ 独立重复交付
→ 用证据证明成长
→ 主动连接上下游
→ 形成稳定组织
→ 进入真实市场
→ 获得认证、合作与孵化机会
```

这条路线的核心不是“刷数值升级”，而是玩家能够承担的价值范围不断扩大：

```text
大项目中的一个位置
→ 一项可独立负责的任务
→ 一份完整交付
→ 一套可重复的组织能力
→ 更大的订单与真实机会
```

## 2. 全景图：用户生命周期与产品演进

| 阶段 | 学生 / OPC 此时是谁 | 核心行动 | 阶段成果 | 平台需要提供的主要能力 | 产品状态 |
|---|---|---|---|---|---|
| 1. 首次教学订单 | 第一次进入平台的新猎人 | 在工作台编排本人和 Agent，检查错误成果，调教并重新交付 | 看懂“编排—执行—检查—调教—重试—结算” | 昵称、角色 Tour、ghost 拖拽、教练提示、四种调教方式与整单结算 | **v0.3.2 试玩中** |
| 2. 自由订单起步 | 能独立完成小步骤的猎人 | 选择订单、面对真实截止时间、重复交付、查看上下游 | 形成稳定使用平台的基础循环 | 学生工作台、订单列表、真实倒计时、通知、作品与近期反馈 | **下一步** |
| 3. 人与 Agent 共同成长 | 初步经营个人 OPC 的主理人 | 复盘失败、训练 Agent、调整阵列、积累能力证据 | 本人和 Agent 各自变得更可靠 | Agent 训练资产、个人经验、成长树、贡献归属、证据档案 | **已有概念设计，待收敛体验** |
| 4. 保存可信伙伴卡牌 | 能完成局部任务的可靠协作者 | 查看同单表现、保存伙伴卡牌、再次联系 | 形成可联系的能力网络 | 同单协作者、订单聊天室、伙伴档案与保存卡牌 | **已有概念，待设计** |
| 角色分支：组织者 / 拆单方 | 已取得组织资质的人，或已认证组织 | 邀请成员、成立组织、拆解并分配完整订单 | 从能力网络形成有责任关系的组织 | 组织资质、独立教学、成员关系与拆单工具 | **已有角色页面原型，待独立关卡** |
| 5. 组织承接完整订单 | 能组织一组卡牌的 OPC 主理人 | 接完整订单、内部拆解、安排成员与 Agent、汇总交付 | 形成可重复的组织交付能力 | 组织工作台、多层阵列、内部任务编排、资产与公司记忆 | **已有订单流程与角色页面原型** |
| 6. 真实市场与可信评价 | 有履约记录的 OPC / 组织 | 接真单、接受评价、建立声望与信用、获得认证 | 被客户和合作方可信地选择 | 匹配、评价、信誉、认证、功能开放、作品与履约档案 | **已有概念和信息图，规则需继续验证** |
| 7. 孵化与更大机会 | 已被市场验证的 OPC 候选人 | 接受验证任务、申请或接受会籍、使用支持资源 | 被学校、协会和孵化器发现并进一步验证 | 候选档案、Scouting、定向命题、grant、入驻邀请与投后 | **已有 Happy Path 和路线草案** |
| 8. 高级市场协作 | 稳定组织或行业参与者 | 联合竞标、公开评审、出租能力、组织更大协作网络 | 从交付组织成长为市场节点 | 阵列对阵阵列、联合竞标、公开评审、资产 / 服务出租 | **远期玩法方向** |

阶段之间不是一次性的等级跳转。真实用户可能同时处于多个状态：例如个人能力已经成熟，但刚组建的新公司仍处于组织磨合阶段。

## 3. 阶段 1：首次教学订单

### 3.1 用户故事

学生第一次进入平台，不需要先读懂经验、成长树、认证、市场和孵化器。他先收到一份有明确背景的教学订单，并被匹配到完整项目中的一个步骤。

玩家需要：

1. 输入自己的昵称；
2. 看懂自己负责的任务位置；
3. 在编排工作台内认识本人卡牌和自己的第一个 Agent“小角”；
4. 通过 ghost 动画理解把角色卡牌安排到任务环节；
5. 自由编排本人和 Agent，并查看创业教练提示；
6. 检查 Agent 第一次产生的错误成果；
7. 认识喂范例、写守则、复盘和安装工具四种调教方式；
8. 花钱安装 Form、花本人时间写守则；
9. 回答 Form 并让 Agent 重新执行；
10. 交付自己的步骤；
11. 等待完整订单完成后统一结算。

### 3.2 通过这一阶段的标志

玩家能够用自己的话复述：

- 我不必一开始就完成整个大项目，可以先负责其中一步；
- 我需要决定本人和 AI 分别做什么；
- Agent 可以执行，但人需要检查成果并承担最终责任；
- 错误执行会浪费算力，调教 Agent 也需要投入时间和现金；
- 我可以通过安装工具、写守则和再次验证训练 Agent；
- 我的步骤完成不等于完整订单已经完成。
- 卡牌没有唯一正确位置；我可以自由安排，并参考创业教练的风险提示；
- Agent 可以通过范例、守则、复盘和工具四种方式被调教。

### 3.3 对应产品交付

- 当前可玩原型：[`../MFU-协作阵列-v0.1-可玩原型.html`](../MFU-协作阵列-v0.1-可玩原型.html)
- 核心玩法与 v0.3 / v0.3.2 教学设计：[`core-gameplay-card-array.md`](core-gameplay-card-array.md) §12–§23
- v0.1 实施记录：[`../../docs/superpowers/plans/2026-07-29-mfu-card-array-v01.md`](../../docs/superpowers/plans/2026-07-29-mfu-card-array-v01.md)
- v0.2 实施记录：[`../../docs/superpowers/plans/2026-07-29-mfu-first-tutorial-v02.md`](../../docs/superpowers/plans/2026-07-29-mfu-first-tutorial-v02.md)

### 3.4 进入下一阶段前要验证

- 完全不了解 MFU 的人能否在一分钟内明白第一步；
- 玩家是否觉得编排卡牌真的需要选择，而不是照提示点击；
- 玩家是否能从错误成果中理解返工、调教和资源成本；
- 玩家是否理解自己的步骤与完整订单是两个完成状态；
- 玩家是否愿意领取第二份订单，而不只把它当成一次性演示。

## 4. 阶段 2：自由订单起步

### 4.1 用户故事

完成教学后，玩家回到自己的日常工作台。平台不再替他固定唯一任务，而是让他看到：

- 正在执行、等待本人判断和等待协作者的任务；
- 可以领取的新步骤或小订单；
- 即将到期的时间、剩余本人时间和 Agent 算力；
- 最近的交付物、客户反馈和复盘入口；
- 自己在完整订单中的位置与同单协作者。

这里形成平台最重要的可重复循环：

```text
选择任务
→ 组成阵列
→ 暂存或确认执行
→ 离开平台
→ 回来处理判断
→ 完成交付
→ 查看反馈
→ 再接一单
```

第一份自由订单首次教授正式时间规则：

- 正式订单与现实世界时间同步；
- 页面关闭后倒计时继续；
- Agent 可以离线执行；
- 等待本人判断会消耗真实时间；
- 截止临近时平台发出提醒。

### 4.2 通过这一阶段的标志

- 玩家不依赖教学提示，也能完成不同的小步骤；
- 玩家会因任务要求不同而改变本人 / Agent 的安排；
- 玩家理解自己的一小步如何影响上下游和最终交付；
- 玩家开始形成作品、履约记录和协作记录。

### 4.3 对应产品演进

下一版不应立刻把旧 Demo 的全部系统搬回来，而应围绕自由订单补一个最小学生工作台：

1. 我的任务；
2. 等我判断；
3. 可领取订单；
4. 我的卡牌；
5. 最近交付与反馈。

### 4.4 已有材料

- 订单、步骤、拓扑、猎人与组织：[`platform-concept-model.md`](platform-concept-model.md) §1.2–§2
- 学生从首次接单到重复实践的早期设想：[`v0.13/happy-paths-v0.13.md`](v0.13/happy-paths-v0.13.md) §1 Phase 1–2
- 一个订单的完整流程与角色页面原型：[`role-pages/`](../role-pages/)
- 宏观机制和订单泳道图：[`v0.15/infographics/MFU-v0.15-机制信息图.html`](v0.15/infographics/MFU-v0.15-机制信息图.html)

### 4.5 进入下一阶段前要验证

- 哪些任务差异真正会改变阵列，而不只是换文案；
- 玩家最常因什么原因回来：截止时间、Agent 提醒、协作者消息还是客户变化；
- 一次交付后，玩家最想改的是连接、卡牌组合还是单张卡的能力。

## 5. 阶段 3：人与 Agent 共同成长

### 5.1 用户故事

玩家完成多次交付后，平台开始把结果沉淀为清晰证据，但不把所有内容压成一个“总战力”。

每一次行动可能改变四类数据：

1. **经验**：做过多少、遇到过哪些情境；
2. **成长树**：本人或组织已经被证明能够完成什么；
3. **声望与信用**：市场是否看见、是否相信其会履约；
4. **认证与资质**：特定能力或高责任角色是否经过认可。

同时，人与 Agent 必须分开归属：

- 学生的理解、判断、沟通和最终责任形成个人能力证据；
- Agent 的执行结果、训练资料、守则、版本和评价形成公司资产；
- 人与 Agent 共同完成作品时，记录各自贡献；
- 买到或租到强 Agent，不等于学生本人获得相同能力。

### 5.2 通过这一阶段的标志

- 玩家能从反馈中找到可改进的具体卡牌或连接；
- 玩家能够把一次失败转化为 Agent 守则、流程或检查点；
- 同一种能力能够由不同学校课程、平台任务或外部认证证明；
- 成长数据能帮助下一次选择，但不会自动替玩家组出“最优阵列”。

### 5.3 对应产品演进

- 个人与公司经验条；
- 个人、公司和角色成长树；
- Agent 训练资产、版本和实战评价；
- 作品与能力证据档案；
- 专业认证和角色资质徽章架；
- 学校课程与平台统一能力标准的对应工具。

### 5.4 已有材料

- 全部概念、归属和关系：[`platform-concept-model.md`](platform-concept-model.md) §3–§8
- 成长树规则与历史迁移：[`skill-tree.md`](skill-tree.md)
- v0.15 能力、课程映射、证据归属和功能开放：[`v0.15/MFU-策划案-GDD-v0.15.md`](v0.15/MFU-策划案-GDD-v0.15.md) §5.10–§5.14
- 四种成长的视觉解释：[`v0.15/infographics/MFU-v0.15-机制信息图.html`](v0.15/infographics/MFU-v0.15-机制信息图.html)
- 当前概念 Demo：[`../MFU-v0.15-可试玩原型.html`](../MFU-v0.15-可试玩原型.html)

### 5.5 进入下一阶段前要验证

- 哪些成长反馈会真正改变玩家下一次编排；
- 玩家能否区分“做得多”“已经达标”“别人信任我”和“获得认证”；
- 学校能否把不同课程映射到统一能力，而不被迫修改自身课程名称和结构。

## 6. 阶段 4：保存可信伙伴卡牌

### 6.1 用户故事

玩家在多个订单中反复遇到上下游伙伴。完整订单结算后，他可以根据对方的真实交付与协作记录，保存可信协作者的卡牌，逐渐形成一张可联系的能力网络。

这一阶段遵循：

```text
在同一订单中合作
→ 看见彼此的真实交付与协作记录
→ 保存可信协作者卡牌
→ 在未来任务中再次联系
→ 形成可联系的能力网络
```

同单协作者可以进入订单聊天室，讨论素材、接口和状态。保存卡牌不等于对方已经加入组织，也不代表玩家可以直接调用对方；真人、OPC 或对方拥有的 Agent 均受其所有者意愿、档期和授权约束。

### 6.2 通过这一阶段的标志

- 玩家会根据真实合作记录选择伙伴，而不是只看抽象分数；
- 玩家能区分“保存卡牌”“联系对方”和“对方接受任务”；
- 一次性的任务关系能够沉淀为可再次联系的能力网络；
- 玩家不会把真人卡误解为自己拥有的资产。

### 6.3 对应产品演进

- 同单协作者与上下游可见；
- 订单聊天室；
- 保存与移除可信伙伴卡牌；
- 再次联系、邀请参与任务和对方接受 / 拒绝；
- 伙伴的档期、能力证据、作品和履约记录；
- 个人的能力网络。

### 6.4 已有材料

- 被动连接与主动连接规则：[`core-gameplay-card-array.md`](core-gameplay-card-array.md) §5
- 猎人如何形成组织：[`platform-concept-model.md`](platform-concept-model.md) §2.3
- 保存伙伴卡牌与组织教学的后续边界：[`core-gameplay-card-array.md`](core-gameplay-card-array.md) §21.8
- 猎人工作台、聊天室和组建组织页面：[`role-pages/`](../role-pages/)

### 6.5 进入下一阶段前要验证

- 什么情况下玩家愿意保存并再次联系一个协作者；
- 保存的卡牌怎样保持档期与能力证据的新鲜度；
- 玩家是否能理解真人卡是合作关系，而不是自己的资产。

## 7. 角色分支：成为组织者 / 拆单方

### 7.1 谁会进入这一分支

普通学生 / OPC 在积累可靠交付、协作记录并获得成立组织的资质后，解锁独立的“组织与拆单教学关卡”。

孵化器、协会等已经得到平台认证的组织，可以直接解锁该教学关卡，不需要重复学生的前置成长过程。

### 7.2 教学关卡教授什么

```text
从能力网络选择伙伴
→ 发出组织邀请并获得真人接受
→ 给组织命名
→ 接收一个完整订单
→ 把订单拆成有连接关系的步骤
→ 分配给组织成员和 Agent
→ 汇总并完成整单交付
```

保存他人的卡牌不等于对方加入组织。只有明确邀请并由对方真人接受后，组织关系才成立。

### 7.3 通过这一分支的标志

- 玩家能建立一个有名字和明确成员关系的组织；
- 玩家能移动步骤并修改步骤之间的连接；
- 玩家能把步骤分配给组织内部的人与 Agent；
- 玩家理解组织对完整订单负责，成员分别对自己的步骤负责。

### 7.4 对应产品演进

- 成立组织的资质与教学解锁；
- 组织邀请、接受、拒绝和退出；
- 组织命名、成员与角色；
- 可编辑步骤与连接关系的拆单工具；
- 组织内部聊天室和任务分配；
- 完整订单的汇总与验收。

## 8. 阶段 5：组织承接完整订单

### 8.1 用户故事

形成组织后，玩家不再只等待平台分配一个步骤，而可以让组织承接完整订单。OPC 主理人需要：

1. 理解完整需求与验收标准；
2. 把订单拆成有先后、并行、检查和汇总关系的位置；
3. 安排本人、Agent、成员和外部伙伴；
4. 处理执行中的变化与冲突；
5. 汇总局部成果并对最终结果负责；
6. 把有效流程、作品和复盘沉淀为公司记忆。

平台各角色仍使用同一种核心语言：

- 拆单方用 OPC 卡牌组成大订单阵列；
- OPC 用本人、Agent 和伙伴卡牌组成内部阵列；
- 独立猎人用本人和 Agent 完成自己的步骤。

### 8.2 通过这一阶段的标志

- 组织能够稳定完成不止一类完整订单；
- 更换某个成员后，关键流程和质量标准仍能被复用；
- 组织能力不是成员能力的简单相加，而是经过交付验证的协作方式；
- 主理人能够解释某次交付为何成功或失败。

### 8.3 对应产品演进

- 完整订单工作台；
- 可编辑步骤与连接关系的拆单工具；
- OPC 阵列与内部人 / Agent 阵列的逐层展开；
- 执行状态、变更、检查和汇总；
- 组织资产、阵列模板、流程和公司记忆；
- 对外包子步骤形成新的“拆单—匹配—完成”小循环。

### 8.4 已有材料

- 所有角色共用的卡牌阵列语言：[`core-gameplay-card-array.md`](core-gameplay-card-array.md) §2–§8
- 组织能力与公司资产边界：[`platform-concept-model.md`](platform-concept-model.md) §3.2、§7
- 订单全生命周期角色页面：[`role-pages/`](../role-pages/)
- 旧版完整经营循环参考：[`../MFU-v0.14-可试玩原型.html`](../MFU-v0.14-可试玩原型.html)

### 8.5 进入下一阶段前要验证

- 多层阵列怎样展开才不会让人看不懂；
- 哪些公司记忆会真实提高下一单质量；
- 组织接整单与个人接步骤之间，责任、信用和收益如何分配。

## 9. 阶段 6：真实市场与可信评价

### 9.1 用户故事

当组织能够稳定交付后，平台开始把任务、能力和信誉连接成市场闭环：

```text
订单进入市场
→ 被拆成步骤或直接匹配给组织
→ 人与 Agent 完成交付
→ 客户、老师、专家或大众评价
→ 形成作品、能力证据、声望与信用
→ 更合适的任务和伙伴愿意再次连接
```

有些平台功能由信誉、能力、认证、资质和风险状态共同决定，但功能本身不进入成长树。例如联合竞标、资产出租、公开评审都是平台功能，不是个人或公司的能力节点。

### 9.2 通过这一阶段的标志

- 客户可以依据相关证据选择组织，而不是依赖一个总分；
- 评价能够区分交付质量、履约可靠性和专业能力；
- 好作品和坏结果都能产生可追溯反馈；
- 功能开放规则清楚说明“为什么现在可以使用”；
- 认证不会代替真实任务表现，真实任务也不会自动等同专业能力。

### 9.3 对应产品演进

- 任务与组织匹配；
- 真实验收和多来源评价；
- 作品、履约、声望与信用档案；
- 专业认证、信誉等级、角色资质和会籍；
- 联合竞标、资产 / 服务出租、公开评审等功能开放规则；
- 争议处理、风险状态和人工审核。

### 9.4 已有材料

- 经验、能力、信誉、认证、资质与功能的边界：[`platform-concept-model.md`](platform-concept-model.md) §4
- 功能开放规则：[`platform-concept-model.md`](platform-concept-model.md) §4.11–§4.12
- 平台功能与成长树分离：[`skill-tree.md`](skill-tree.md) §3–§4、§8.1
- 五方市场行为：[`v0.13/happy-paths-v0.13.md`](v0.13/happy-paths-v0.13.md)
- 市场闭环信息图：[`v0.15/infographics/MFU-v0.15-机制信息图.html`](v0.15/infographics/MFU-v0.15-机制信息图.html)

### 9.5 进入下一阶段前要验证

- 匹配需要哪些最低信息，哪些部分可以暂时保持黑箱；
- 谁可以评价什么，评价者本身如何建立可信度；
- 信誉等级分别应该开放哪些机会，而不造成概念混乱；
- 学校练习、模拟订单和真实订单的证据权重如何区分。

## 10. 阶段 7：孵化与更大机会

### 10.1 用户故事

孵化器不是依据平台总分自动录取学生。它先通过候选档案发现值得关注的 OPC，再用更高难度任务、交流和小额支持继续验证，最后由真人作出入驻或投资判断。

```text
持续交付形成候选档案
→ 孵化器发现并关注
→ 发出定向验证任务
→ 观察高难度交付和资金使用
→ 真人作出判断
→ 发出预备营、会籍或入驻邀请
→ 持续投后支持
```

学生可以接受邀请，也可以拒绝并继续独立经营。个人档案、Agent 资产、公司作品和协作记录继续保留。

### 10.2 通过这一阶段的标志

- 孵化器能看见证据与缺口，而不是只有排名；
- 学生知道自己为何被关注、还需证明什么；
- 验证任务与支持资源形成可追溯记录；
- 入驻决定明确属于孵化器真人，而非平台自动触发。

### 10.3 对应产品演进

- OPC 候选档案；
- 孵化器 Scouting 与关注列表；
- 定向验证任务；
- grant、桥贷或其他支持记录；
- 预备营、会籍和入驻邀请；
- 投后工作台与持续成果记录。

### 10.4 已有材料

- 候选档案与孵化筛选：[`platform-concept-model.md`](platform-concept-model.md) §9
- 孵化器完整 Happy Path：[`v0.13/happy-paths-v0.13.md`](v0.13/happy-paths-v0.13.md) §4
- 孵化器角色成长树与工作台方向：[`skill-tree.md`](skill-tree.md) §8.2
- GDD v0.15 候选档案：[`v0.15/MFU-策划案-GDD-v0.15.md`](v0.15/MFU-策划案-GDD-v0.15.md) §5.14

### 10.5 继续演进前要验证

- 哪些证据最能预测真实创业潜力；
- 孵化器需要哪些平台内验证，哪些必须在线下完成；
- grant、会籍、认证和入驻邀请如何保持概念独立；
- 学生失败、公司清算或更换组织后，哪些档案继续保留。

## 11. 阶段 8：高级市场协作

### 11.1 用户故事

当基本的订单—阵列—交付—评价循环稳定后，可以发展“阵列对阵阵列”的竞标玩法：

1. 两个协会或组织面对同一个订单；
2. 双方分别提交 OPC 卡牌组合阵列；
3. 每个 OPC 使用自己的内部人 / Agent 阵列；
4. 双方产生真实或模拟交付物；
5. 企业、专家或大众按公开标准评审；
6. 中标结果与反馈回流到卡牌、阵列和组织档案。

这不是角色互相攻击，而是对同一个真实问题给出不同组织方案。

### 11.2 对应产品演进

- 联合竞标与竞标房间；
- 阵列方案提交和必要的信息保护；
- 多层阵列的结果摘要；
- 公开标准、专家评审与大众评审；
- 中标、落选、申诉与评价回流；
- Agent、阵列模板或专业服务的授权 / 出租。

### 11.3 已有材料

- 竞标对战方向：[`core-gameplay-card-array.md`](core-gameplay-card-array.md) §9
- 联合竞标、资产出租、公开评审的概念边界：[`platform-concept-model.md`](platform-concept-model.md) §4.11–§4.12
- 旧成长树中的历史节点与迁移台账：[`skill-tree.md`](skill-tree.md) §3.0、§4.1

### 11.4 开始这一阶段的前提

高级玩法不应早于以下三件事：

1. 单个玩家的小阵列已经好玩；
2. 组织能用阵列稳定产出完整交付；
3. 评价体系能够解释不同阵列为何产生不同结果。

## 12. 产品演进的建议顺序

### Now：证明首个教学订单

目标不是增加更多系统，而是确认：

> 玩家是否愿意通过编排本人和 Agent 完成自己的步骤，并能从真实成果中理解检查、调教和重试的价值。

当前工作：

- 团队试玩首个教学订单；
- 记录首次理解时间、卡住位置和是否愿意继续；
- 优化昵称、拖拽教学、错误成果、资源成本和第一次 Agent 调教；
- 暂不把旧 Demo 的全部经营与成长系统搬入新原型。

### Next：建立可重复的学生 / OPC 日常循环

优先补齐：

1. 最小学生工作台；
2. 多个可重复的小订单；
3. 等待判断、协作者消息和截止提醒；
4. 交付、作品和复盘；
5. Agent 训练资产。

完成后再接入最小成长反馈，验证哪些数据真的帮助下一次组阵。

### Later：连接、组织与市场闭环

按依赖关系逐步建设：

```text
保存可信伙伴卡牌
→ 取得组织资质
→ 组织与拆单教学
→ 真实邀请、成员关系与阵列模板
→ 完整订单和多层编排
→ 真实评价与信誉
→ 认证和功能开放
→ 孵化器筛选与支持
→ 联合竞标等高级市场玩法
```

Later 中的具体顺序可以根据学校、企业或孵化器试点调整，但不能绕过基本依赖。例如，没有真实交付和评价，不应先做复杂认证；单人阵列尚未成立，也不应先做多层竞标。

---

## 13. 不应在第一阶段提前加入的内容

以下内容有价值，但过早出现会稀释核心玩法：

- 完整现金流与公司生存模拟；
- 全部经验条、成长树、认证和徽章同时弹出；
- 协会、OPC、成员和 Agent 多层阵列同时展开；
- 自由无限画布和复杂连线编辑；
- 孵化器完整后台；
- 联合竞标与大众评审；
- 用一个总分决定匹配、胜负或成长。

原则是：

> 新概念只在玩家第一次需要它时出现；新页面只服务当前生命周期阶段的核心行动。

## 15. 当前结论

当前的协作阵列 Demo 不是一条会被丢弃的旁支，而是学生 / OPC 正式进入平台后的首个教学订单，也是未来学生 / OPC 产品的最小核心。

后续会围绕它逐步长出工作台、自由订单、成长证据、真人连接、组织经营、真实市场和孵化机会；但在核心玩法获得验证后，正式产品应拆分为清晰模块，而不是无限扩大一个单文件 HTML。

因此，下一步仍然是：

> 先把第一关做到让同事和新用户真正想继续玩，再增加第一关结束后必需的最小工作台与自由订单循环。
