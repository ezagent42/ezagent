# 组织、多重成员关系与跨组织调度（待决策）

更新日期：2026-07-31

状态：讨论中，以下内容均未批准实施。

## 为什么需要重新定义“组织”

当前 Demo 中的“MVO”主要表示为完成任务而形成的最小有效组织。多角色设计又引入学校、孵化器、企业、协会和学生社团等长期存在的组织。

如果继续用同一个“组织”概念承载两者，会出现以下混淆：

- 学校把学生加入学校，与把学生放入某个执行任务的 MVO，是否是同一种关系；
- 学生同时属于学校、孵化器、社团和多个 MVO 时，谁能安排学生；
- 学校、孵化器和企业能否共同提供资源组成一个 MVO；
- 学生从组织成员成长为自己组织的主理人时，发生了什么变化；
- MVO 完成任务后是解散、保留，还是升级为认证 Organization。

## 当前讨论方向

可能需要区分两类组织。

### 长期组织

候选示例：

- 学校；
- 孵化器；
- 企业；
- 协会；
- 学生社团。

候选职责：

- 管理成员与身份；
- 提供内部动态；
- 提供任务、教师、教练、Agent、工具、数据、资金和算力；
- 设置成员可见范围与调度权限；
- 保存长期关系和治理规则。

### 执行组织 MVO

候选定义：

- 为完成某类任务形成的最小有效组织；
- 可以组合来自多个长期组织以及个人持有的资源；
- 通过持续执行任务积累经验、能力和认证；
- 可能升级为长期存在的认证 Organization。

目前尚未确定两者是否在产品中使用不同名称、不同页面或统一的组织模型。

## 多重成员关系

当前倾向支持一个人同时加入多个相互交错的组织，例如：

```text
一个学生
├─ 所属学校
├─ 参与的孵化器
├─ 专业协会或学生社团
├─ 学校实践 MVO
├─ 孵化项目 MVO
└─ 自己主理的 MVO
```

支持多重组织关系的原因：

- 学生现实中本来就同时参与学校、社团、项目和课余工作；
- 跨专业、跨学校和跨机构协作需要成员关系可以交错；
- 学生需要从“参与别人的组织”逐渐成长为“主理自己的组织”；
- 平台希望让长期组织共同孵化新的有效组织，而不是争夺学生的唯一归属。

这一方向尚未形成正式规则。

## 尚未确定的问题

### 1. 组织类型与命名

- 长期组织和 MVO 是否都叫“组织”；
- 是否需要“机构”“社区”“空间”等新概念；
- MVO 获得认证后是否自动成为长期 Organization；
- 学生社团属于长期组织还是 MVO。

### 2. 成员身份

- 同一个人在不同组织中可以拥有哪些角色；
- 成员、管理员、主理人、导师和外部协作者如何区分；
- 学校视角中的“学生资源”和学生自己的账号如何关联；
- 一个人同时参与多少个 MVO，是否需要上限。

### 3. 调度与本人同意

- 学校或孵化器能否直接安排学生进入任务；
- 是否每次安排都需要学生确认；
- 是否采用“预授权时间额度内可安排，超出范围需本人确认”；
- 学生如何撤回授权或退出任务；
- 未成年人、课程任务和雇佣关系是否需要不同规则。

### 4. 时间和资源冲突

- 多个组织同时安排同一个学生时如何发现冲突；
- 冲突由学生决定、组织协商，还是平台自动排序；
- 时间、算力、Agent 和工具的占用是否使用同一套容量模型；
- 冲突应出现在谁的“待处理”中。

### 5. 权限与可见性

- 学校能看到学生在校外组织中的哪些信息；
- 孵化器能否看到学生的课程任务；
- 学生是否可以隐藏部分个人项目；
- 长期组织内部动态与世界动态如何分层；
- 跨组织 MVO 的档案由谁管理。

### 6. 成果与成长归属

- 跨组织 MVO 的收入、作品、IP 和评价归谁；
- 学生、Agent、MVO 和长期组织分别积累什么；
- 同一成果是否可以同时成为学校的学习证据和企业的交付记录；
- 组织解散后，成员是否保留履约证据和关系。

### 7. Demo 首版边界

- 多角色 Demo 是否只展示成员可以加入多个组织，而暂不实现完整权限；
- 是否需要演示学校与孵化器共同安排同一个学生；
- 是否需要演示学生拒绝或调整任务；
- 角色切换时如何表现同一个学生在不同组织中的视角。

## 下一次决策建议

后续讨论建议按以下顺序进行：

1. 确定组织的类型和统一语言；
2. 确定多重成员关系；
3. 确定调度授权和冲突处理；
4. 确定信息可见范围；
5. 确定成果、收入和成长归属；
6. 再决定哪些机制进入多角色 Demo。
